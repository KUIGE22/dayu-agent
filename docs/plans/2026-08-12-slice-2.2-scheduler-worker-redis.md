## 1. 动机、交付效果与非目标

Slice 2.1 已交付 tenant-scoped PostgreSQL durable job、attempt、lease、receipt、event 与 Agent correlation，但没有任何进程持续领取任务，也没有可重启的调度真源。当前 research-template 的 `monitoring-scheduler.json` 明确固定 `enabled=false`、`binding_status=unbound`、`automated_provider_execution_allowed=false`，只能作为安全预览资产，不能被偷偷升级为生产 scheduler 真源。

本 slice 完成后应得到：

1. 一个一次只服务一个显式 tenant 的 `dayu-cli platform scheduler` 进程；调度定义、cursor 与 occurrence outbox 全部落 PostgreSQL，重启、并发 scheduler、DST 与 misfire 都不会丢 fire 或重复生成不同 job。
2. 一个一次只服务一个显式 tenant 的 `dayu-cli platform worker` 进程；Redis hint 到达或 PG poll 超时后都只从 PostgreSQL claim，handler 只能经 Service-owned typed registry 调用，Worker 统一 heartbeat、取消观察、complete/fail 与 graceful drain。
3. production 启动必须先完成 Redis package/config/connectivity admission；运行中连续失败达到严格settings阈值（默认3）才降级为纯 PG polling，按settings健康间隔（默认30秒）探活成功后回到 event-assisted。Redis 丢消息、重复、乱序、重启均不得改变 queue、lease、fence、cancel、dedupe、schedule cursor 或 receipt。
4. Agent correlation 的重启治理使用 PostgreSQL join projection 提供的 deadline/cancel truth；需要取消 active Host run 时只调用 `Host.cancel_run()` 写入协作式 cancel intent，绝不调用 CLI signal 专用的 `cancel_run_and_settle()`，绝不因 worker 重启进入模型第二次。
5. 真实 PostgreSQL 16、真实固定 digest Redis 与真实 subprocess `SIGTERM` 都进入 integration gate；fake 只能补充 unit fault injection，不能替代真实 lane。

非目标：不实现 source connector/source health、业务 payload parser、research/Agent handler、API/UI、通知、Broker、生产 Compose、全局跨 tenant claim、动态 tenant enumeration、handler 热加载、任意 Python import path、APScheduler、Redis durable queue、Redis Streams 或修改 Slice 2.1 的 deterministic PG retry/backoff。poll/reconnect jitter 只属于本地等待，不得写入 `next_available_at`。

## 2. Controller blocking-contract 裁决

### S22-CTRL-001：scheduler 使用 PostgreSQL schedule + occurrence outbox

主计划五行 allowlist 不足以实现 restart/DST/misfire/disabled。本文正式扩大到 pure schedule domain、storage protocol、PostgreSQL store、`0004_durable_schedules` migration 与 ScheduleService。

`job_schedules` 是 immutable schedule definition/current cursor 真源；`job_schedule_occurrences` 是 cursor 与 job enqueue 之间的 durable outbox。固定顺序为：

```text
PG clock 读取 due schedule
-> transaction: INSERT pending occurrence（冻结完整 JobEnqueueRequest snapshot）+ CAS 推进 schedule cursor
-> commit
-> transaction: pending -> materializing（与 disable 的唯一线性化点）
-> commit
-> JobService.enqueue_committed_schedule_occurrence(冻结snapshot与确定性idempotency key)
-> best-effort Redis publish
-> transaction: materializing -> enqueued + 绑定同一 JobEnqueueReceipt.job_id
-> commit
```

这不是危险的 “advance cursor then hope enqueue succeeds”：cursor 推进和 pending occurrence 在同一事务；任何 enqueue 前崩溃都留下可重放的 pending/materializing occurrence，任何 enqueue 后/mark 前崩溃都用同一 immutable snapshot/idempotency key 复用同一 PG job。disable 只把仍为 pending 的 occurrence 变为 skipped；已经 materializing 的 occurrence 已越过线性化点，必须继续收敛为 enqueued。禁止删除 occurrence、使用 replay 当前时钟或把 materializing 回退为 skipped。

materializing 是 durable commitment，不是进程锁。多个 scheduler 可并发重放同一 materializing occurrence，但 `PostgresJobStore.enqueue` 必须以数据库原子 `INSERT ... ON CONFLICT DO NOTHING` + conflict re-read 收敛：相同 fingerprint 返回同一 job/receipt，不同 fingerprint 才返回 closed idempotency conflict，绝不泄漏裸 `IntegrityError`。因此不新增易过期的 materializer lease/fence；正确性由 immutable snapshot、数据库幂等与 mark 同 job 重放共同闭合。

### S22-CTRL-002：一进程一 tenant，tenant 必须显式

`platform worker` 与 `platform scheduler` 都要求 `--tenant-id <canonical UUID>`；没有默认值，不从 ticker、workspace、job payload、Redis channel 或全局变量推断。CLI 在任何 Redis/PG/Host/workspace 副作用前以 `TenantId` 构造固定 system `Principal(user_id="platform-worker" | "platform-scheduler")`，再只经 `Principal.to_scope()` 得到 `TenantScope`。

这里交付的是 explicit tenant selector 与 no-global-claim，不是认证 capability。`Principal` 仍是公开构造器，`TenantScope` 仍只是 misuse guard；外部已授权 operator/process manager 对该 tenant 的权限、数据库 credential 分发与进程隔离是启动前置条件，Slice 2.2 不实现也不伪测。部署方不能证明这一前置条件时必须 STOP 且不得启动 daemon；service-account/tenant roster/authentication 仍归 Slice 7.1/8.2。

本 slice 不读取 organizations 全表、不使用 BYPASSRLS、不新增 global claim。多 tenant 部署由进程管理器为每个已授权 tenant 启动独立 daemon；tenant roster、service-account authentication 与跨 tenant fairness 仍由 Slice 7.1/8.2 承担。

### S22-CTRL-003：descriptor registry 保持不变，新增 Service-owned execution registry

Slice 2.1 的 `JobHandlerRegistry` 仍只负责 immutable descriptor 的 register/get，不增加 invoke、payload parser 或业务 callback。`dayu.services.job_service` 新增独立 `JobExecutionRegistry` 与 async `JobExecutionHandlerProtocol`；`JobService.execute_claim(...)` 是 Worker 唯一 invocation gateway。

Worker 不 import source/research/Agent 业务类型，也不读取 registry mapping。未注册 handler 返回固定 non-retryable `JobFailure(SafeJobErrorCode.HANDLER_REJECTED, retryable=False)`，不得调用 Host、模型、provider 或业务 Service。Slice 2.2 production registry 精确为空；测试 handler 只存在于 tests，Slice 2.3 才能在 production composition 注册首个 source handler。

### S22-CTRL-004：Agent active-wait governance 由 PostgreSQL deadline 驱动

新增 tenant-scoped `list_governable_agent_runs` PG join projection，覆盖 lease 尚有效以及 lease 已过期的所有未终结 correlation，绑定 correlation、job、attempt、lease、persisted `deadline_at`、`job_cancel_requested_at` 与同一事务 PG clock 计算的 `deadline_reached`。不得用 worker wall clock、`correlation.updated_at`、Redis timestamp 或进程启动时间推导 deadline。

`JobService` 在本模块定义并注入 `@runtime_checkable HostRunCancellationProtocol.cancel_run(run_id) -> RunRecord`；既有 `Host` 以结构类型同时满足 reader/canceller，startup 传入同一实例，不 import concrete Host 到 storage。active Host run 遇 PG cancel/deadline 时：若 Host `RunRecord.cancel_requested_at is None`，幂等调用 `cancel_run`；已有 Host cancel intent 时只 reobserve。发送失败不改 PG job、不创建 attempt、不换 reserved ID，下个 governance interval重试。正常 Worker 永远不能调用 `cancel_run_and_settle`。

既有 generic heartbeat 对 deadline 会直接写 PG failed；本 slice 必须增加 correlated 分支：同一事务发现未终结 correlation 时，deadline/cancel 不走 generic terminalization，而是续当前 lease并返回 governance-required；Worker 在每次 heartbeat 前后运行同一 governance/reobserve，先投射 Host cancel，再只按 Host terminal receipt reconcile。generic 无 correlation job 继续保持 Slice 2.1 原 deadline 语义。`job_cancel_requested_at` 与 Host `cancel_requested_at` 是两个不同字段，不得混用。

### S22-CTRL-005：production event-assisted，integration 可显式 PG-only

新增 `PlatformDeploymentProfile.INTEGRATION`，只供测试/本地 durable integration：平台启用、`use_in_memory_adapters=False`、必须且只允许 PostgreSQL DSN 环境变量；object storage、Redis、auth 任一非空都 fail-fast，绝不静默忽略。`load_platform_settings` 接受并严格验证该 profile；普通 `prepare_host_runtime_dependencies` 在任何路径/Redis/PG/S3/Host副作用前拒绝，只有 `platform worker|scheduler` 专用 preparation 可接收。现有 `DEVELOPMENT` 的 “显式 in-memory 且禁止production infra” 契约不放宽；`PRODUCTION` 继续要求四个infra env。

`PlatformQueueMode` 由 profile 唯一派生：production=`event_assisted`，integration=`postgres_polling`，development 仅允许依赖注入 unit tests而不构造 durable CLI。production 缺 Redis package、URL 或首次 ping 失败必须在 PG engine、Host、Fins、workspace 创建前 fail-fast；通过 admission 后的运行期故障只有达到`settings.redis_failure_threshold`才允许降级。

### S22-CTRL-006：同步adapter/持久层 + async process loop

Worker/Scheduler loop 使用 `asyncio`；`JobExecutionHandlerProtocol.execute` 为 async。现有同步 `JobService`/repository 与同步 redis-py adapter 调用只经 `asyncio.to_thread` 从 loop 调用，不能在事件循环直接阻塞。Redis adapter 统一使用同步 `redis.Redis`/`PubSub`，固定 RESP2、bytes response，不启用 hiredis；JobService 因而能在同步 `enqueue` 的PG commit之后做一次有界同步publish，Worker则在thread中等待PubSub。

一个 worker process 同时最多处理一个 attempt；吞吐通过多 worker process 扩展。Worker 在 handler task 并行运行 heartbeat task；signal 只进入 DRAINING，不把进程停机伪装成业务 cancel/fail。`asyncio.to_thread` 外层取消不等于内层线程取消：每个handler、heartbeat、PG与Redis调用必须有唯一future owner，同类至多一个in-flight，resource close前必须await/reap真实inner work；不得把 `Task.cancel()` 当作线程终止。

`shutdown_grace_seconds` 是停止 intake 后的 cooperative soft grace，不承诺能强杀非协作 in-process handler。grace 到期先请求 handler cancellation，但只要 handler/inner future 仍活跃就继续 heartbeat且不关闭共享资源；协作收敛后才关闭。第二个signal是operator hard-stop边界：进程可直接非零终止且不写任何PG/Host terminal，OS停止线程后由lease expiry/recovery接管。计划不同时承诺“首个signal固定时限退出”和“非协作handler零late side effect”。

### S22-CTRL-007：startup/recovery 顺序与 Redis 生命周期

唯一 startup 结构是两个 public wrapper 共用一个 private composition root：

```text
prepare_host_runtime_dependencies
  -> load/validate settings（INTEGRATION立即拒绝）
  -> disabled/development: typed NOT_REQUIRED admission，queue_settings=None
     production: load queue settings -> _prepare_queue_admission（Redis import/client/ping）
  -> _prepare_host_runtime_after_queue_admission

prepare_platform_queue_runtime_dependencies
  -> load/validate settings（只收PRODUCTION/INTEGRATION）
  -> load queue settings
  -> production同一_prepare_queue_admission；integration typed POSTGRES_ONLY admission
  -> 同一_prepare_host_runtime_after_queue_admission
  -> typed PreparedPlatformQueueRuntime(JobService, ScheduleService, Redis refs, existing runtime)
```

`_prepare_host_runtime_after_queue_admission` 不得重读settings/重复ping，并且是唯一S3/PG/Host/workspace/composition builder；禁止callback、布尔bypass或special wrapper再调用ordinary wrapper造成二次admission。production queue admission必须早于路径解析、`_read_postgres_dsn`、engine、S3、Host与workspace写。NOT_REQUIRED只保持既有disabled/development ordinary路径（其中development可显式注入provider）的语义，不构造Redis或要求durable services；production即使显式注入provider也必须先取得REDIS admission，显式provider只替换composition内容、绝不能成为Redis绕过路径；POSTGRES_ONLY只允许special integration wrapper。

admission由prepared runtime单一持有；构造任一步失败按逆序、exact-once关闭。正常结束固定为 stop intake/subscription -> drain/reap all inner futures -> close PubSub/Redis -> close existing prepared runtime。scheduler 为复用同一 JobService/descriptor/publisher contract，允许构造既有 prepared Host runtime，但不得调用 Agent、模型或 provider handler；测试以 trap 证明。

### S22-CTRL-008：实现期 activation 与 availability 合同勘误

实现期直接证实原合同不可生成：`ScheduleActivationRequest`没有`next_fire_at`，Store exact API既不向Service提供disabled draft的PostgreSQL clock observation，也不能提交Service算出的cursor；而`reserve_occurrences`只接受active/current-cursor且batch必须包含1至3条occurrence。croniter又只允许由ScheduleService import，因此不得让Store猜时钟、计算cron、用空batch激活或直接拒绝全部`ACTIVE`请求。同一审计还确认PENDING occurrence只有ID时没有point-read，ScheduleService无法在`begin_materialization`提交状态前证明descriptor/execution handler availability。

本勘误固定为“两阶段PG-clock observation + optimistic CAS commit”，不使用callback、不跨层持有SQL事务：

1. `ScheduleStoreProtocol.get(...)`返回`ScheduleObservation(definition, database_now)`；`database_now`必须与definition在同一tenant-scoped事务读取。ScheduleService以该PG时钟和唯一cron helper计算严格首个future candidate。
2. Store `set_state(..., activation_next_fire_at=...)`重新锁schedule并校验同一tenant/id/version/state。ACTIVE成功的唯一线性化点是在持有row lock后执行的一条条件DML statement：用同一one-row materialized CTE取得`clock_timestamp()`，同一值同时进入`:candidate > database_now`谓词与返回的`ScheduleObservation.database_now`；CAS谓词同时含tenant/id/expected version/source state。禁止`transaction_timestamp()`、锁前时钟、Python precheck或“先判断再无时间谓词UPDATE”。时间谓词零行时在仍持锁事务内重读row与fresh `clock_timestamp()`，返回`clock_stale`且零mutation；candidate仍future时该同一statement写`active + next_fire_at + version+1`。每次public activate/re-enable总计最多三次`set_state` CAS尝试，**包含首次**；三次均stale就返回第三次closed result，原`expected_version`不变且不自动rebase。
3. `get_occurrence(...)`提供tenant-scoped immutable point-read。PENDING调用方必须先用其中冻结的descriptor直接查询JobService availability，再把closed `ScheduleMaterializationAdmission`传给`begin_materialization`。Store始终按实际持久state裁决：PENDING+available转MATERIALIZING；PENDING+unavailable返回typed `unavailable`且对schedule/occurrence零mutation，Scheduler继续当前bounded page并由process-local keyset cursor跨tick轮转，不得busy-loop或skip fire；PENDING+committed_replay是invariant。如果并发赢家已把行转为MATERIALIZING，则任何stale admission都不得撤销durable commitment，直接返回enqueue。初始读到MATERIALIZING必须用`committed_replay`且不得调用availability。
4. descriptor registry与execution registry只允许append、同identity exact-idempotent、冲突拒绝，禁止remove/replace；因此positive availability在单进程生命周期内单调。negative availability只是该进程的瞬时能力判断，绝不能成为跨进程全局disable/skip真源：activation保持disabled并抛closed `ScheduleExecutionUnavailableError`，PENDING只返回上述`unavailable`。availability不写PG、不进Redis、不做process cache；mixed-version或capability-skew scheduler最多延后处理，不能丢fire。
5. disabled draft允许`next_fire_at=NULL`；active必须非NULL；曾激活后被manual或scan-limit disable的schedule保留原cursor供审计。re-enable忽略该旧cursor并覆盖为fresh PG-clock candidate；显式disable只把PENDING改为`schedule_disabled`，保留其snapshot与exact nonnegative `coalesced_count`，绝不改MATERIALIZING/ENQUEUED/SKIPPED。

当前WIP中`set_state(ACTIVE)`无条件抛invariant、production `if False`占位、disabled强制清空cursor以及active/NULL DDL组合都只是暴露缺口的未接受中间态；恢复实施后的第一件事必须按本节删除/修正并先跑focused/static/真实PG门禁。

### S22-CTRL-009：实现期 runtime identity、cron exhaustion 与安全导入勘误

第二轮实现期审计证明四处原合同无法由既有allowlist唯一编码，因此再次冻结实现并以本节覆盖所有冲突旧文字；不新增production路径、不改0004主键、不让Redis成为真源：

1. **lookback/scan-limit audit identity**：第2步的lookback audit在batch提交前只是provisional。Service局部scan origin只有`persisted_cursor`与`distinct_relocated_cursor`两态：进入扫描固定为前者，scan-limit anchor为persisted cursor；只有首次得到`candidate_utc >= L`且该值与persisted cursor不同后才切到后者并把anchor改为该candidate，不因invalid/nonexistent raw candidate变化。若仍为`persisted_cursor`时耗尽raw candidate limit，则lookback audit与scan-limit audit会命中0004唯一键`(tenant_id, schedule_id, schedule_version, scheduled_for)`；该唯一分支固定由`candidate_scan_limit_exceeded`取得优先级，只构造一条以persisted cursor为`scheduled_for`的scan-limit audit，不构造同identity的lookback row。若已进入`distinct_relocated_cursor`，两个audit才可同batch存在且必须拥有不同`scheduled_for`。`ScheduleReservationBatch.__post_init__`构造期必须拒绝任意重复`reservation.scheduled_for`并抛固定`ScheduleInvariantError("schedule_batch_duplicate_scheduled_for")`，使错误在pure boundary closed，而不是泄漏数据库unique error。禁止伪造微秒、改唯一键、吞掉scan-limit或让INSERT error决定业务语义。

`ScheduleStateTransitionResult` action矩阵是hard invariant：

- `applied`：request expected version等于previous version；observation definition只允许state/cursor/version/updated_at变化，version恰好`+1`且state等于target。ACTIVE要求previous disabled、candidate aware UTC、`candidate > observation.database_now`且after cursor等于candidate；DISABLED要求candidate=None并保留previous cursor。
- `unchanged`：previous与observation definition逐字段相等、version不变、state已等于target、candidate=None。
- `clock_stale`：request target为ACTIVE、previous为disabled、candidate非None且`candidate <= observation.database_now`；previous与observation definition逐字段相等、version/cursor/state均不变。

每个pending snapshot固定：`available_at = occurrence.scheduled_for`，`deadline_at = occurrence.scheduled_for + schedule.job_deadline_seconds`；descriptor、payload与idempotency key来自reserve事务锁定的immutable schedule revision。`domain.jobs.job_enqueue_request_fingerprint(request)`是唯一算法真源，ScheduleService与PostgresJobStore共同调用，旧storage私有实现删除而非复制。crash replay必须重建byte-identical `JobEnqueueRequest`，不得重新读取current time或可变schedule内容。

### 5.2 DST/misfire算法

实施前先在pinned croniter上运行pure empirical gate，固定 `America/New_York` spring-gap 02:30、fall-fold 01:30与`Asia/Shanghai`无DST样本；croniter只接收/返回naive local datetime，ZoneInfo round-trip是唯一DST classifier。若croniter会在调用内部平移/吞掉候选而无法实现下述逐字语义，立即STOP/plan-fix，不得猜测或改期望。

Service从persisted UTC `next_fire_at` 与IANA timezone、PG `database_now`计算batch：

1. activate/re-enable在同一PG clock下寻找严格晚于database_now的首个有效candidate并写`next_fire_at`；旧skipped/materializing/enqueued occurrence不复活。nonexistent local time跳过，不得平移到gap后；ambiguous local time固定`fold=0`且只生成一个UTC fire。
2. `database_now < next_fire_at` 时无due。令`L = database_now - schedule_max_lookback_seconds`。`next_fire_at < L` 时先构造一条**provisional** `lookback_exceeded` skipped audit：`scheduled_for`固定为进入事务时的persisted cursor、`coalesced_count=None`；它只有在第3步确定不会与scan-limit audit命中同一自然键后才进入batch。working cursor必须重定位为最早有效UTC candidate `C` 且`C >= L`，不能逐条展开边界外fire，也不能用严格`get_next(L)`跳过`C == L`。唯一实现规则是以`L - 1 minute`转换出的naive local minute作为croniter seed，逐个做ZoneInfo round-trip/DST分类并丢弃`candidate_utc < L`，首个`>= L`者进入第4/5步；这些重定位候选同样计入candidate scan limit。`C == L`必须按grace进入expired或eligible，绝不能被lookback audit吞掉。
3. 从working cursor枚举至首个严格晚于database_now的candidate；process-local scan origin初始为`persisted_cursor`，只有relocation取得与persisted cursor不同的首个有效`candidate_utc >= L`才切为`distinct_relocated_cursor`。每次croniter产出raw naive-local candidate时先把scan count加1，再做ZoneInfo round-trip、nonexistent/ambiguous分类，因此invalid candidate同样消耗limit；只有分类后的有效UTC cursor要求严格增加。raw count不得超过`schedule_candidate_scan_limit`。达到上限仍无future candidate时，丢弃尚未提交的expired/eligible provisional groups，构造显式`resulting_state=disabled`、`resulting_next_fire_at=expected_next_fire_at`的batch，并构造一条`candidate_scan_limit_exceeded` skipped audit：`scheduled_for=进入本轮scan前的working cursor`、`coalesced_count=None`。scan origin仍为`persisted_cursor`时按S22-CTRL-009只保留scan-limit row；已为`distinct_relocated_cursor`时两条audit才同batch存在且必须pairwise distinct。Store同一事务插入最终1至2条audit、disable schedule、保留原persisted cursor并把既有PENDING按`schedule_disabled`收敛；不得从skip reason隐式推断disable，不得把已扫描的partial eligible group入队。re-enable按第1步从新PG clock重新计算。`CroniterBadDateError`不是raw candidate也不是scan-limit：register deterministic probe时映射为`ScheduleInputError("schedule_cron_has_no_candidate")`；runtime遇到时固定`ScheduleInvariantError("schedule_cron_iteration_exhausted")`并零mutation停止。因为registration会挡住该表达式，runtime exhaustion回归必须通过真实Store测试准备直接持久化immutable legacy/invalid schedule definition再调用Service路径，不得mock croniter、放宽registration gate或绕过真实Store read。
4. due candidate满足`database_now - candidate <= misfire_grace_seconds`（等号包含）才eligible；更老但仍在lookback内的candidate归`misfire_expired`。expired组写一条skipped occurrence，`scheduled_for=该组最新candidate`、`coalesced_count=组大小-1`。
5. eligible组按`coalesce_one`只写一条pending occurrence，`scheduled_for=该组最新candidate`、`coalesced_count=组大小-1`，并冻结完整enqueue snapshot。若无eligible，则batch只有skipped audit；若同时有lookback/expired/eligible，batch最多三项。
6. batch插入与cursor/state/version CAS是同一事务。normal batch显式`resulting_state=active`且cursor为枚举所得首个future candidate；scan-limit batch显式`resulting_state=disabled`且cursor等于锁内重验的expected persisted cursor。失败全回滚；重启以相同PG time边界和persisted cursor得到同一audit identity，不无审计跳fire。

`0004_durable_schedules` 新增且仅新增：

DDL exact CHECK：pending/materializing必须`job_run_id IS NULL AND skip_reason IS NULL`且snapshot完整；enqueued必须`job_run_id IS NOT NULL AND skip_reason IS NULL`且snapshot完整；skipped必须`job_run_id IS NULL AND skip_reason IS NOT NULL`，其中`schedule_disabled`必须保留完整snapshot与exact nonnegative `coalesced_count`，其它skip reason必须snapshot全NULL。lookback/scan-limit仅允许`coalesced_count IS NULL`，其它状态/reason要求exact nonnegative count。cross-tenant FK、active+NULL cursor、非法nullable/state组合与immutable-column UPDATE必须由真实PG16直接拒绝；disabled+历史cursor是合法审计状态。

其余三项保持计划既有参数/返回。`get_occurrence`是availability前唯一合法point-read；禁止list scan、process cache、先begin后查、把SQLAlchemy session/row泄漏给Service或新增callback。

- ACTIVE request在locked source已ACTIVE时要求`activation_next_fire_at=None`并返回unchanged；locked source为DISABLED时要求aware UTC candidate。成功激活必须在取得schedule row lock后使用**一条**conditional DML statement：one-row materialized CTE读取一次`clock_timestamp()`，同一值用于`:candidate > database_now`谓词和RETURNING observation，tenant/id/version/source-state CAS同在该statement。条件零行时仍持锁重读row与fresh clock并返回clock_stale；禁止锁前clock、`transaction_timestamp()`、Python时间比较后无guard UPDATE。version/state冲突抛既有closed `ScheduleVersionConflictError`且Service不得自动采用新version。DISABLED request要求candidate=None；ACTIVE->DISABLED保留既有cursor、只skip PENDING并递增version，already DISABLED返回unchanged且零mutation。
- ScheduleService对clock_stale保持原`expected_version`，使用result observation的fresh PG clock重算；每次public activate/re-enable**总计三次set_state CAS尝试，包含首次**。第三次仍stale就直接返回第三个clock_stale result，调用方可稍后显式重试。不得用本机clock、sleep、放宽future条件或无限循环。
- ACTIVE source为DISABLED时，ScheduleService必须先检查execution availability；失败抛`ScheduleExecutionUnavailableError`并保持row原字节，不调用`set_state`。availability成功才计算cursor并尝试ACTIVE；已ACTIVE的exact-version ACTIVE request直接走Store unchanged，不以任一进程本地negative proof反向disable全局schedule。

- `list_due`只列`state=active AND next_fire_at <= database_now`，用`(next_fire_at, schedule_id)`、keyword-only limit与无重复wrap构造`ScheduleDuePage`；同一page的observation共享一次PG `clock_timestamp()`，cursor不持久化、不含availability。输入cursor过期/对应row已变化仍按纯keyset继续，确认无due row才返回空page/None cursor。
- `reserve_occurrences`按schedule->occurrence固定锁顺序，验证active/version/`expected_next_fire_at`。normal batch插入reservations并CAS到显式active/resulting cursor；scan-limit batch插入closed audit、显式CAS到disabled/原cursor并skip既有PENDING。state/version/cursor已变化返回`ScheduleReservationResult(lost_race, ())`且零mutation，不抛裸`IntegrityError`，不得靠reservation skip reason猜target state。
- `set_state(disabled)`同锁顺序把schedule置disabled、保留当前cursor，并仅将PENDING occurrence改为SKIPPED(schedule_disabled)；MATERIALIZING/ENQUEUED/SKIPPED不变。与`begin_materialization`的先后由同一row lock线性化。
- `begin_materialization`先用无锁locator取得schedule identity，再固定锁schedule->occurrence并逐字段重读。实际持久state优先于stale admission：PENDING+pending_available转MATERIALIZING；PENDING+pending_unavailable返回unavailable且schedule/occurrence零mutation；PENDING+committed_replay抛closed invariant；MATERIALIZING对任一admission都返回enqueue；ENQUEUED/SKIPPED返回既有closed no-work。
- `list_replayable`只列PENDING/MATERIALIZING：每次调用无条件优先最老MATERIALIZING，再用剩余slot按`(scheduled_for, occurrence_id)`轮转PENDING；总数受keyword-only limit约束，页内不得重复。PENDING到keyset尾部可无重复wrap到队头填充剩余slot，使任一unavailable row不能永久挡住later PENDING；MATERIALIZING不受pending cursor影响。ScheduleService的`materialize_occurrence`高层入口必须先调用store `begin_materialization`；PENDING原子转MATERIALIZING，MATERIALIZING可重放，ENQUEUED/SKIPPED返回closed no-work。Host Scheduler绝不直接调用该store方法。
- `materialize_occurrence`收到`begin_materialization(already_enqueued)`必须直接返回`ScheduleMaterializationResult(already_enqueued, occurrence, None)`；这是并发terminal race的正常closed结果，不得再次enqueue/publish/mark，也不得新增按job_id查询或伪造`JobEnqueueReceipt`。
- `materialize_occurrence`收到`begin_materialization(unavailable)`必须直接返回同名result并继续page内下一项；不得enqueue/publish/mark、skip/disable、在同tick再次读取同一occurrence或把本地negative availability写成全局事实。
- `mark_enqueued`只接受MATERIALIZING->ENQUEUED，即使parent schedule已在begin之后disabled也必须完成；ENQUEUED+同job为idempotent replay，不同job抛invariant；SKIPPED返回`skipped_conflict`且scheduler必须以runtime invariant停止，不能静默继续；PENDING直接invariant。

同时修正`PostgresJobStore.enqueue`的同key并发：job insert使用数据库原子conflict-do-nothing/returning，冲突后在同事务重读并比较完整fingerprint；相同请求返回同一`JobEnqueueReceipt(idempotency_reused=True)`且只产生一条created event，不同请求抛closed `JobIdempotencyConflictError`，永不泄漏unique violation。

`JobCancellationSignalProtocol`唯一owner是pure `domain.jobs`；`JobExecutionHandlerProtocol`
与execution registry在`job_service.py`，`WorkerJobGatewayProtocol`只在
`dayu.host.worker`声明，`SchedulerGatewayProtocol`只在`dayu.host.scheduler`声明。
除`execute_claim`为async外，上述gateway方法全部是sync，Host loop必须只经
`asyncio.to_thread`调用；返回值和异常只允许pure jobs/schedules closed types，绝不透出
Store、SQLAlchemy row、Host `RunRecord`、Redis exception或Service concrete type。
`JobService`/`ScheduleService`不继承、不import Host protocol，但必须由pyright structural
assignment证明精确满足；startup只做结构化注入。

Scheduler port特意是三条Service-owned高层入口而不是Store facade：
`list_replayable_occurrences`读取MATERIALIZING优先且PENDING keyset轮转的bounded page；
`reserve_due_occurrences`在Service内完成bounded due keyset轮转、availability skip、DST/misfire计算与单个reservation batch
事务，但绝不materialize；`materialize_occurrence`在Service内完成availability/begin、
committed enqueue与mark的一个不可分割process work unit。Host不得看见
`ScheduleStoreProtocol`、`begin_materialization`或`mark_enqueued`。

`ScheduleJobGatewayProtocol`唯一owner是`dayu.services.schedule_service`；`JobService`不import该Protocol但必须由pyright structural assignment满足。`is_execution_available`每次逐字段检查descriptor registry与execution registry，不返回registry对象、不缓存proof、不持久化availability。两个registry都没有remove/replace API：同identity注册exact-idempotent，不同descriptor/handler冲突fail closed；因此positive proof不能在本进程内从true漂移为false。negative proof只表示当前进程此刻不能执行：activation抛closed unavailable且保持disabled，PENDING materialization返回typed unavailable且零mutation；它绝不能disable active schedule或skip occurrence。

新增 frozen `JobExecutionRequest`，字段精确为 `tenant_id`, `definition_id`,
`job_id`, `attempt_id`, `attempt_number`, `descriptor`, `payload`, `deadline_at`；
它不含 `JobLeaseHandle`、fence、raw token或worker id。`JobExecutionRegistry` 只允许
handler.job_type、descriptor.job_type 与已注册 descriptor逐字段一致；同一handler identity
幂等，不同实例/descriptor冲突fail closed。`JobService.execute_claim` 再次核对 claim descriptor
与两个registries，把claim收窄为上述request后才调用；handler不得得到JobStore、lease/fence/token
或额外repository入口，Worker不得调用handler方法绕开Service。

worker identity只属于PG attempt审计、process日志与metrics；禁止业务handler按短生命周期worker身份分支side effect或构造幂等键，因此不进入execution request。测试必须反射/typed fake双重证明lease/fence/raw token/worker_id均不可见。

handler返回 `JobCompletion` 或 `JobFailure`；返回其它类型、抛未分类异常、业务cancel后伪造成功都由gateway映射为固定non-retryable handler_rejected，不持久化原始异常。唯一例外是Worker已在线性化的drain-abandon边界后发出task cancellation：此后任何handler return/error都完全忽略，不调用gateway complete/fail。未来业务handler必须自行把已知provider transient映射为closed retryable JobFailure。

ScheduleService可注册disabled draft。activate先通过Store `get`取得PG-clock observation；只有disabled->active才经JobService窄availability方法证明，缺失时抛closed error且row零mutation。PENDING occurrence先通过`get_occurrence`取得冻结descriptor，再证明availability并传closed admission；缺失时返回unavailable并保留PENDING。Store以schedule->occurrence锁和实际持久state作为唯一线性化真源；证明成功后registry不可remove/replace，MATERIALIZING durable commitment更不得被后续任何availability结果撤销。跨进程capability skew只能让本进程延后，不能终结另一进程可处理的fire。

MATERIALIZING replay不再重复执行可否决的handler availability gate，而是由ScheduleService把store刚返回的typed persisted `ScheduleMaterializationDecision`传给JobService窄`enqueue_committed_schedule_occurrence(scope, decision)`入口。该入口不持有或反向注入ScheduleStore；它只接受`action=enqueue`、`occurrence.state=materializing`、非空snapshot，并重算snapshot→`JobEnqueueRequest`与request fingerprint逐字段闭合后调用同一Postgres enqueue/idempotency真源。decision是ScheduleService内部trusted boundary，不是“跨事务仍持有数据库锁”的假承诺；真实state/identity由随后`mark_enqueued(scope, occurrence_id, expected_snapshot_fingerprint, job_id)`再次在ScheduleStore锁内重验。它不调用handler，也不把registry漂移当成撤销理由。若执行registry在job被claim时仍缺失，既有unknown-handler路径将该job安全失败一次；不得把occurrence永久卡在MATERIALIZING或伪造SKIPPED。因为Slice2.2 production descriptor/execution registries均为空，所以production不能激活新业务schedule；tests只能注入test descriptor/handler，Slice2.3才可注册source owner。

### 6.2 Governance projection

新增`JobHeartbeatAction={renewed, governance_required}`、frozen `JobHeartbeatResult(action, claim)`与closed `JobGovernanceRequiredError`。`JobStoreProtocol.heartbeat`和`JobService.heartbeat`精确升级为返回`JobHeartbeatResult`；generic job返回renewed并保持Slice2.1的cancel/deadline异常，未终结correlation则走下述特殊分支。

新增 `AgentRunGovernanceProjection`：`correlation`, `job_state`, `attempt_state`, `deadline_at`, `job_cancel_requested_at`, `deadline_reached`, `lease_expires_at`, `database_now`；所有identity必须与correlation逐字段闭合。新增`AgentRunGovernanceCursor(deadline_at, correlation_id)`；storage返回`AgentRunGovernanceProjectionPage(projections, next_cursor)`，JobService完成Host observe/cancel/reconcile后返回`AgentRunGovernancePage(results, next_cursor)`，两层page不得混用。新增closed `AgentRunGovernanceAction` 与 `AgentRunGovernanceResult(correlation_id, job_id, attempt_id, action, safe_error_code)`；三个UUID identity必须逐项来自同一projection并保持page顺序，action只报告 `ACTIVE_WAIT`, `MISSING_HOST_WAIT`, `CANCEL_REQUESTED`, `CANCEL_ALREADY_REQUESTED`, `TERMINAL_RECONCILED`, `NO_HOST_RECOVERED`, `SEND_RETRY`, `STALE`, `INVARIANT_FAILURE` 及其既有safe-code矩阵。JobService只用一个集中pure helper由原projection构造结果；组page前逐项验证result/projection cardinality、identity、顺序完全相等，且同页correlation/attempt identity不得重复。缺identity、跨projection拼接或仅靠page位置关联current claim均为构造期/Service invariant failure。

Worker调用`govern_agent_runs`只把closed `JobRepositoryFailureError`视为可重试基础设施失败：记录不含正文的safe event，不改变current attempt治理状态、不写terminal，并由同一Worker process-local consecutive counter计数；下一次重试只发生在原本的poll/heartbeat governance cadence，不新增时钟或单独interval。任一成功取得并验证的`AgentRunGovernancePage`立即把counter重置为0；失败数小于`settings.governance_failure_threshold`时已有current lease的独立heartbeat owner继续按原周期尝试续租，达到该精确阈值时必须保留PG/Host现场、停止新claim/handler并让runtime返回1，不再重试。重启后counter从0开始但PG/Host truth不变。任何其它未分类异常是程序/合同错误，必须立即保留现场并让runtime非零退出，绝不能被宽捕获成`SEND_RETRY`、连接降级或业务failure。`INVARIANT_FAILURE`是成功返回page中的closed truth failure，始终全局非零退出；它与调用抛异常是两条不同路径。

store只查询PG、计算deadline，不读Host。`list_governable_agent_runs(scope, cursor, limit)`必须覆盖lease有效/过期的全部未终结correlation，并以PG clock/tenant join收窄；固定`ORDER BY deadline_at ASC, correlation_id ASC`与同tuple keyset，limit精确来自settings page size。Worker每poll处理一页并保存process-local cursor，到尾部`next_cursor=None`后从头开始；长期ACTIVE_WAIT不能把后续deadline/terminal饿死，重启从头只是重复观察而不改变PG。不得只复用expired-correlation查询或永远读取first N。

JobService固定顺序：projection -> Host get_run -> strict observation；terminal走既有reconcile；Host missing且`lease_expires_at <= database_now`才允许既有NO_HOST targeted recover。Host missing但lease仍有效返回`MISSING_HOST_WAIT`：零recover、零新attempt，Worker按reobserve interval继续读取同一reserved id，但从第一次missing observation起**停止该attempt后续heartbeat/续租**并保留PG中已提交的`lease_expires_at`作为唯一等待上界；Host若在expiry前出现则转`ACTIVE_WAIT`并恢复同一lease heartbeat，若到expiry仍missing则先重新读取PG+Host、再走targeted recover。本地已知cancel只可投射cancellation signal，不能改变此边界。active+cancel/deadline才走Host cancel intent并立即reobserve；active无治理条件返回wait。`cancel_run`返回terminal、调用时KeyError或observe/cancel竞争均重新读取同一reserved run后按真实终态收敛。任何active/cancel-pending或valid-lease missing-Host correlation都不能进入generic/targeted recover或新attempt；missing Host也绝不能被当前owner无限续租。

Worker只维护一个process-local governance cursor；每个poll周期在claim前、每个correlated heartbeat前后都以精确同步gateway调用`await asyncio.to_thread(gateway.govern_agent_runs, scope, cursor, limit=settings.governance_page_size)`取得`AgentRunGovernancePage`，随后立即把同一cursor更新为`page.next_cursor`；为None时下一次调用从头开始。所有调用都必须显式传keyword-only limit，不得加默认值、分别维护poll/heartbeat cursor、丢弃next_cursor或复用storage projection page。Worker逐result用`job_id+attempt_id`匹配current claim：不匹配者只完成自身治理，禁止改变当前heartbeat/finalize；匹配者才按S22-CTRL-009更新当前attempt状态，`correlation_id`用于同一结果的安全审计/去重而不是推导attempt。generic job的deadline继续由heartbeat写failed。store同事务发现未终结correlation时，heartbeat不再用`min(now+lease_duration, deadline)`：固定`new_expiry=database_clock_now+lease_duration_seconds`，cancel/deadline未到返回renewed，已到返回governance_required；两者都只续同一lease/fence。随后Worker发Host cancel/reobserve，最终只由correlation reconcile写回。

`complete`与`fail`同样先检查未终结correlation；存在时零mutation抛`JobGovernanceRequiredError`，Worker丢弃handler result并进入`WAITING_FOR_CORRELATION`：禁止新claim并持续govern/reobserve。Host active/cancel-pending时继续同一lease heartbeat直到terminal reconcile或lease lost；Host missing时进入`MISSING_HOST_WAIT`子态并按上段停止续租、等待persisted expiry/targeted recovery。不能沿既有cancel/deadline/success/failure generic优先级写receipt。不存在correlation时完整保留Slice2.1行为。若本地handler另有业务cancellation signal，它只能帮助协作退出，不能替代Host cancel或自行写第二terminal。

所有会读取或修改同一Agent correlation的PG入口统一使用且只使用以下锁序：`job_runs -> job_attempts -> job_leases（存在时） -> agent_run_correlations`。精确覆盖`reserve_agent_run_correlation`、`authorize_agent_run_start`、`heartbeat`、`complete`、`fail`、generic `recover(scope)`、`recover_agent_run_after_no_host`与`reconcile_agent_run_terminal`；禁止任何入口先`FOR UPDATE` correlation再回锁job/attempt。reconcile/targeted recover允许先做一次不加锁的correlation locator读取以取得job/attempt identity，但该读取不是授权真源；随后必须按统一顺序加锁全部父行，最后锁定并逐字段重读correlation，若缺失/漂移则返回closed invariant且零mutation。heartbeat/complete/fail必须在锁定job/attempt/lease后再做同事务late correlation re-read，不能用锁前“未发现”缓存；reserve同样在父行锁内重验attempt/lease/job状态后才插入。generic recover即使候选SQL含`NOT EXISTS correlation`也只能把它当无锁候选过滤：必须在同一READ COMMITTED事务中先用第一条statement取得父行锁，再用**第二条独立statement**取得刷新后的statement snapshot并late lock/re-read correlation，不能把候选、锁父行、NOT EXISTS复核和terminal UPDATE压成一个旧snapshot statement；有任一已提交correlation即跳过且零mutation。这样reserve与generic finalize/recover竞争时只有一个线性化结果：reservation先赢则finalize/recover转governance-required/skip，generic finalize/recover先赢则reservation closed-reject，绝不产生第二terminal、漏治理或反向锁死。

## 7. Redis wake-up 与 Worker/Scheduler 状态机

### 7.1 Redis安全消息

channel固定 `dayu:platform:v1:wakeup:{tenant_uuid}`。message为canonical UTF-8 JSON bytes，字段只含 `schema_version=1`, `tenant_id`, `job_id`, `reason="enqueued"`；unknown/missing/duplicate/noncanonical/跨tenant/超固定byte上限、孤立Unicode surrogate或canonical re-encode失败消息一律返回Worker-owned `INVALID_MESSAGE`并计safe metric，不影响PG poll。绝不含payload、schema bytes/hash、attempt、fence、token、DSN、URL、Host run或错误正文。

`JobService.enqueue` 必须先完成PG commit取得receipt，再调用可选 `JobWakeupPublisherProtocol.publish_hint(scope, job_id) -> bool`。False/RedisError只记录safe event并照常返回receipt；不得回滚job或改idempotency。Redis adapter是唯一redis-py异常收窄owner，但pure read action/hint/subscriber/client protocols与`RedisRuntimeState`由`worker.py`拥有；Worker只依赖这些pure types，绝不import concrete adapter或间接加载redis-py。

### 7.2 Redis mode

```text
REDIS admission -> RedisRuntimeState.EVENT_ASSISTED
EVENT_ASSISTED
  -- consecutive_failures >= settings.redis_failure_threshold -->
POLLING_DEGRADED
  -- settings.redis_health_interval_seconds 到期，ping+resubscribe成功 -->
EVENT_ASSISTED

POSTGRES_ONLY admission -> redis_runtime_state=None -> pure PG polling
```

`PlatformQueueMode`仍是profile-derived deployment配置；`RedisRuntimeState={event_assisted,polling_degraded}`只由Worker持有且只在REDIS admission构造。POSTGRES_ONLY runtime的state、publisher、subscriber与client全部为None，永不construct/ping/subscribe/resubscribe/health-recover Redis，只按`poll_interval_seconds`调用同一PG claim。no-message是成功操作并重置连续失败计数；任何成功Redis操作也重置。invalid hint是协议拒绝，不计连接failure。进入/退出runtime state各记录一次固定structured event和counter，不存Redis URL。默认threshold/health interval是3/30秒，但运行逻辑必须读取settings而非硬编码；非默认合法值必须真实改变转换时机。REDIS两态与POSTGRES_ONLY都执行同一个 `JobService.claim(scope, worker_id)`；hint只让等待提前结束。

### 7.3 Worker attempt

```text
RUNNING -> govern -> PG claim -> HANDLING + HEARTBEATING
HANDLING -> JobService.execute_claim -> completion | safe failure
completion -> JobService.complete
safe failure -> JobService.fail
PG cancel/deadline heartbeat signal -> cancellation token -> handler收敛
complete/fail governance-required -> WAITING_FOR_CORRELATION + govern/reobserve
Host active/cancel-pending -> continue heartbeat
Host missing -> MISSING_HOST_WAIT + stop renewal until persisted expiry/recovery
lease lost -> 停止本地finalize，绝不换token/fence重试写
```

heartbeat interval固定 `min(poll_interval_seconds, lease_duration_seconds / 3)` 且必须正；不加jitter是为了保持lease安全上界可证明，不修改Slice2.1持久retry。每worker一次只持一个attempt，process manager应错开多worker启动；多进程同相heartbeat造成PG瞬时峰值作为明确residual，不以随机延迟牺牲fence时限。unexpected handler error不记录异常文本。generic job的complete/fail遇cancel/deadline/lease-lost按既有store真实结果收敛；correlated job严格走§6.2 governance-required，不得再写第二receipt。

每个sync store/Redis调用由唯一async owner保存inner future，同类最多一个in-flight；outer task取消后仍await真实inner完成。PubSub使用有界`get_message(timeout=min(poll_interval_seconds, 1.0))`，Redis connect/socket timeout也不得大于该值；close绝不与活跃Redis future并发。PG inner call没有被Python取消的假承诺：若未返回，first-signal drain保持runtime/heartbeat并等待，second-signal hard-stop后才由OS终止。

### 7.4 Scheduler occurrence

Scheduler维护两个且仅两个process-local cursor：`ScheduleReplayCursor | None`只轮转PENDING replay，`ScheduleDueCursor | None`只轮转active due；不混用、不持久化。每tick固定：gate open -> `list_replayable_occurrences(scope, replay_cursor, limit=settings.schedule_tick_batch_size)`；**page一返回、任何gate/epoch/materialize await之前**先把replay cursor赋为`page.next_pending_cursor`。page必须把MATERIALIZING排在全部PENDING前，Host随后逐项gate/epoch复核并调用`materialize_occurrence`，unavailable也消耗一个scan slot但继续页内下一项，不得结束tick。处理完该bounded page后，在gate open时**至多一次**调用`reserve_due_occurrences(scope, due_cursor, limit=settings.schedule_tick_batch_size)`；result一返回、读取reservation或执行其它await之前先把due cursor赋为`result.next_due_cursor`。因此每tick最多处理`batch_size`个replay selection，另加一个最多检查`batch_size`个due entry且最多reserve一次的Service call。随后wait，不在同tick重新扫描同一page；中途drain留下的未处理page item只会在cursor无重复wrap后再次出现，不会丢失PG work。

`reserve_due_occurrences`内部按Store due page逐entry检查；本进程execution unavailable的schedule只在本次调用中跳过且零mutation，继续检查later due。若整页unavailable，返回该页最后cursor，下一tick从边界后继续；到尾后Store无重复wrap，因此任意长度unavailable前缀都不能永久挡住later available schedule，也不会创建更多本进程无法处理的PENDING。找到首个available schedule才计算并reserve一个batch，result cursor固定为该entry cursor；新pending由下一tick replay page读取。Host不得调用store方法，不得从读取/reservation结果直接enqueue。若replay page与due page均无work则正常wait。

每次`materialize_occurrence`必须先point-read occurrence：PENDING才调用`is_execution_available`并映射为pending_available/unavailable；MATERIALIZING直接使用committed_replay并以trap证明availability调用数为0；ENQUEUED/SKIPPED用committed_replay进入Store closed no-work且也不查availability。该point-read不是授权真源，Store随后按schedule->occurrence锁重读state并以上述§5.3矩阵线性化。状态机：

```text
PENDING -- begin(pending_available) --> MATERIALIZING -- enqueue+mark --> ENQUEUED
PENDING -- begin(pending_unavailable) --> PENDING（typed unavailable，继续page内下一项）
PENDING -- explicit disable/misfire/lookback/scan-limit --> SKIPPED
MATERIALIZING -- crash/restart --> MATERIALIZING（同snapshot重放）
ENQUEUED / SKIPPED terminal
```

disable与begin都按schedule->occurrence锁序；disable先赢则pending->skipped且零job，begin先赢则materializing成为不可撤销的入队承诺，disable不得再改它。多个scheduler同时重放materializing只会经原子job idempotency得到同一job；Redis hint可重复但PG claim/fence不变。`skipped_conflict`表示实现/数据库不变量已破坏，scheduler固定nonzero停止并保留现场，不能用“closed conflict后继续”掩盖orphan job。

### 7.5 Signal/drain

`dayu.host.process_intake`新增event-loop-owned `ProcessIntakeGate`与frozen `IntakeEpoch(value)`，closed public surface精确为`capture() -> IntakeEpoch`、`request_stop() -> None`、`is_current(epoch: IntakeEpoch) -> bool`与`is_open: bool`。CLI signal callback只经event loop调用`request_stop`；第一次调用把RUNNING epoch递增一次并永久关闭gate，重复soft signal不重新开放。每个可能返回新work的`asyncio.to_thread`/await在派发前capture，返回后且在启动handler、heartbeat、下一次claim、begin/materialization、tick或subscribe前必须同时验证`is_open`与`is_current(captured)`。

首个SIGINT/SIGTERM的唯一线性化点是gate关闭：RUNNING→DRAINING，立即停止新claim/tick/subscribe。gate前已发出但gate后才返回的PG claim不得启动handler或heartbeat、不得写complete/fail/假terminal，已取得的lease只由persisted expiry/recovery收敛；gate后才返回的replay/list/reservation不得启动`materialize_occurrence`，已提交pending/cursor留给重启。只有gate关闭前已经派发的一个Service-owned`materialize_occurrence`算“当前 occurrence”，它即使在gate后返回也必须完成整个begin/enqueue/mark收口，返回后不得开始下一项。已有handler/heartbeat/当前occurrence与全部inner future在`shutdown_grace_seconds`内协作收敛；grace内完成则exit0。

grace到期先原子设置process-local `drain_abandon_requested=True`，再请求handler task cancellation；该线性化点之后任何handler return/error都忽略，绝不complete/fail或映射handler_rejected。若task/future仍活跃则进入`WAITING_FOR_INNER_WORK`，继续同一lease heartbeat、禁止close或新work；真实结束后停止heartbeat、关闭runtime、返回exit 1并让未终结lease到期恢复。第二SIGINT/SIGTERM是明确hard-stop primitive `os._exit(1)`：不调用fail/complete/cancel_run/mark/finally close、不写PG/Host terminal；OS停止全部线程后lease expiry/recovery接管。真实subprocess测试必须分别覆盖cooperative first signal与noncooperative second signal，不能只测空闲loop。

## 13. Residual risks、后续owner与完成定义

- Redis hint天然可丢、重复、乱序；PG poll将额外延迟限制在`poll_interval_seconds`，不承诺即时唤醒。
- Host cancel取决于provider/Agent cooperative boundary；pending期间只heartbeat/reobserve，不伪造terminal。
- START_REQUIRED→Host reserved ensure的跨库TOCTOU继续由Slice2.1 correlation/reserved identity防重；没有跨库事务。
- cooperative grace后仍运行的非协作handler会让首信号drain延长；第二信号是进程级hard stop，随后lease recovery仍无法消除任意外部非幂等副作用。未来handler必须使用provider idempotency/query-before-retry contract。
