## 4. 严格候选 schema 和 parser

- 新模块 `dayu/investment/domain/candidate_parsing.py` 提供 `parse_fact_candidate(raw: bytes) -> FactCandidatePayload`，只依赖纯域/标准库。`FactCandidatePayload` 定义在 `evidence.py`，复用该模块的 Fact label、UTC/date、FactValue 和 locator 校验，避免再造一套 Fact 规则；它没有任何持久化 ID、核验 witness 或 PIT 来源时间。
- 一个输出只能有一个 Fact proposal，根精确九键：`schema_version`、`candidate_type`、`fact_key`、`metric`、`value`、`period_start`、`period_end`、`effective_at`、`locator`。`schema_version='fact_candidate.v1'`、`candidate_type='fact'`。Claim proposal 由 `candidate_type='claim'` 明确拒为 `unsupported_material_claim`；未知 kind 为 `candidate_schema_invalid`。不得默默抽取自由文本中的事实。
- `fact_key`、`metric` 复用 Fact 的 bounded-code 校验。period 两字段必须同时 null 或同时为严格 `YYYY-MM-DD`；不能倒置。effective_at 为严格 UTC RFC3339 文本，以 `Z` 结尾、可有 1–6 位小数；拒绝 offset、naive、空格及宽松日期解析。它只是未经批准的 candidate proposal 时间。
- `value` 精确 tagged union：decimal arm 四键 `{kind,value,unit_code,currency}`；text/date/boolean arm 仅 `{kind,value}`。decimal 的 value 必须是字符串，语法 `-?(0|[1-9][0-9]*)(\.[0-9]+)?`；禁止指数/正号/空格/float/NaN/Infinity，随后按现有 FactValue finite/38 总位/12 scale/unit/currency 契约校验。canonical serializer 对 Decimal 使用 `format(value,'f')` 恢复原始定点文本及 scale，不能使用可能产生指数的 `str(Decimal)`；负零与尾随零不消除。text 非空、无首尾空白；date 严格日期；boolean 必须真实 bool。无无关 arm 字段和隐式转换。
- locator 精确复用 `EvidenceLocatorSnapshot.from_dict` 十一字段和五种 payload arm；不复制 Fins 私有 parser，不使用 path、hash-only locator、document_id-only fallback。locator 缺失或 null 返回 `evidence_missing`。
- raw 必须是 bytes；类型错误属于调用者错误，返回固定 input error，不写候选。≤1,048,576 bytes；拒绝 UTF-8 BOM、非法 UTF-8、重复键（包括 nested）、尾随数据、非对象、JSON float 与非标准常量、unknown/missing keys。以固定 input byte 上限和 JSON recursion 失败处理收束过深对象；`RecursionError` 映射 `candidate_json_invalid`，不能泄露原始异常/片段。解码出的字符串不得含孤立 surrogate 或 NUL，防止 PostgreSQL JSONB 写入时将业务拒绝误变成 infrastructure failure。
- canonical 输出仍 ≤1 MiB，使用 S31 `canonical_json_bytes`；合法日期/decimal 原始值不被舍入或补默认。canonical 扩张超限返回 `candidate_payload_too_large`。
- parser 使用 `CandidateParseError` + 闭合 `CandidateIntakeRejectionCode`，异常只含固定码，不含 raw 数据。错误优先级按遇到的验证阶段：raw byte 上限 → JSON 编码/结构 → root kind/schema → evidence 缺失 → 其余字段/值/locator；同阶段先按本节的固定字段顺序检查。parser 不决定 source freshness 或 promotion。

## 5. Service 调用链、Fins 观察与错误分类

1. 校验 scope/context/raw type，查询明确 company/security，实算 raw SHA-256/byte count；计算下节的 request fingerprint。
2. `find_intake_receipt(scope, operation_id, fingerprint)`。存在且相等则立即返回 immutable receipt；不同则 conflict。此 lookup 不重新 Fins 验证历史操作；它不表示该 source 当前有效。
3. parser 产生 typed payload，或固定拒绝码。parser reject 不调用 Fins。
4. 比较 payload.locator.ticker 与明确 security.ticker；不相等为 `evidence_cross_ticker`。
5. Service 用 Fins 的 public `parse_evidence_locator_projection(payload.locator.to_dict())` 转换结构；调用 `validate_evidence_locator`，再 `read_citation_projection`。比较回读 locator 的完整 canonical 十一字段 bytes，实算 SHA256(content_bytes) 并与输入 locator_content_sha256 比较；差异为 `evidence_readback_mismatch`。不能仅比较 document_id 或已有 digest。
6. 两次 Fins 调用全部成功后取 clock 的 UTC `checked_at`，产生 `CandidateFinsValidationWitness`：locator canonical SHA、citation SHA、checked_at。它是一次观察，不是 DB authorization witness；与 DB created_at 不设跨时钟先后 CHECK。
7. 调用新 repository 的 `record_intake(scope, request)`，在一个事务写 candidate+receipt。业务失败使用下节的安全 rejection envelope，state=rejected；成功 state=proposed。两种结果都没有写 Fact/Claim、verified witness 或晋升状态。

Fins source 业务拒绝固定映射：`source_identity_not_found`/`source_deleted`/`source_not_ingested`/`processed_not_found`/`processed_deleted`/`processed_reprocess_required` → `evidence_unavailable`；`ambiguous_source_identity` → `evidence_ambiguous_owner`；`document_version_mismatch`/`source_fingerprint_mismatch`/`processed_source_kind_mismatch`/`processed_version_mismatch`/`processed_fingerprint_mismatch`/`source_identity_changed`/`primary_content_changed`/`primary_sha_mismatch`/`primary_content_sha256_mismatch`/`locator_content_sha256_mismatch` → `evidence_stale`。这些固定 codes 来自当前 Fins `service_runtime.py` 的实际分支，message 不保存/不拼接。

当前 Fins fragment codes 的闭合分类如下，不能按异常 message/匹配数/私有 owner 数据猜原因，不能在 A 修改 Fins owner：

| Fins code | Service 结果 | 理由与固定行为 |
| --- | --- | --- |
| `table_row_out_of_range`、`table_column_missing` | `evidence_fragment_unresolved`，rejected+receipt | 正常records数据上的行/列不存在是已实证场景；当前Fins码也可能含owner形状问题，本结果只表示无法定位请求片段，不断言错误由Agent或owner造成 |
| `page_not_supported` | 同上 | 当前owner不能提供该page片段，合法payload不能当作有效证据 |
| `xbrl_fact_not_unique` | 同上 | 0或多条匹配都不能精确唯一定位；同一固定码采用同一闭合拒绝，不从message拆成“缺失/重复” |
| `table_not_records`、`xbrl_facts_unavailable` | `research_dependency_unavailable`，零candidate/receipt | 当前public结果不足以构建所需records/facts结构，保留owner数据/能力不可用，不归为Agent schema问题 |
| `invalid_locator_payload`、`artifact_kind_not_supported` | 同上 | 合法typed mirror与public parser转换后不应出现；视为owner契约/版本不一致，不用fallback补齐 |

`primary_read_failed`/`evidence_read_failed`、unknown Fins code、OSError/timeout、无效 Fins return/clock、identity storage/PG failure 均返回固定 `research_dependency_unavailable`（或底层已闭合的 storage error），不落 rejected candidate、允许重试。Fins meta 非法 `invalid_document_version`/`invalid_source_fingerprint` 属 owner 数据错误，按 dependency unavailable；不能当作 Agent schema invalid。已有business code只承诺本次片段不可用，不承诺未来永远无法恢复；已提交拒绝重试仍返回原receipt，修正/重建source后由新的operation重新入场。事务内任何失败都回滚 candidate+receipt。取消/KeyboardInterrupt/SystemExit 不捕获为业务拒绝。

候选观察之后 source 可改变：A 不持有跨 Fins/PG 的全局锁，也不承诺 PG commit 瞬间的 source freshness。未来晋升与消费必须重新 validate+readback，不能复用 intake witness 当永久缓存。

## 6. 原子写入、receipt 与 operation 幂等

- 新域模块 `candidate_intake.py` 持有 Context、RejectionCode、Witness、RecordRequest、Receipt 纯 DTO；它依赖 evidence 的公共 immutable 类型，不导入 services/Fins/SQLAlchemy。RecordRequest 是成功 payload+非空 witness 或拒绝码+空 witness 的严格二选一，不能由宽泛 dict 绕过验证。
- `CandidateIntakeRepositoryProtocol` owner 为新 `storage/candidate_intake_protocols.py`，仅 `find_intake_receipt(scope, operation_id, request_fingerprint) -> CandidateIntakeReceipt | None` 与 `record_intake(scope, request) -> CandidateIntakeReceipt`；使用既有 `EvidenceInputError/ConflictError/RepositoryError` 闭合错误。具体 `PostgresCandidateIntakeRepository` owner 为新 `postgres_candidate_intake.py`，不扩充已有 EvidenceRepository 的控制流。
- fingerprint 是固定域 `candidate_intake.v1` + tenant_id + 全部 context 字段 + explicit security ticker + raw_sha256 + raw byte count 的 canonical SHA256。**排除**动态 Fins 结果、checked_at、DB time、rejection outcome；同一 operation 的首次提交结果拥有裁决权。结果本身另以 payload_sha256 和 witness 完整保存，不混淆请求指纹与结果指纹。
- 合法 proposed payload 是 parser 的 canonical nine-key JSON。rejected payload 一律安全 envelope 精确四键 `{schema_version:'rejected_intake.v1',raw_sha256,raw_bytes,rejection_code}`，不保存 raw bytes、自由文本、异常 message、路径或 credential。receipt 有 payload_sha256 指向这个实际候选 payload。Fins 拒绝也采用相同安全 envelope，原始输入以 raw SHA 供可信调用者核验，raw 不落库。
- 每次 record 开启已有 RLS 模式的 READ COMMITTED 事务，设置 tenant context；先查 `(tenant_id,operation_id)` receipt。存在则核请求 fingerprint 和完整不可变请求字段；一致返回 receipt，异值 conflict。
- 不存在则在一个 SAVEPOINT 内插入 candidate(version=1, proposed/rejected) 与 receipt、flush、readback 校验；提交前确认 candidate canonical bytes/SHA、company/id/operation 与 receipt 完全闭合。23505只识别下面五个精确命名键，不根据SQL message/列猜键；其它唯一键为固定conflict，其它DB错误固定storage failure。
- 允许进入幂等核验的23505键：`pk_research_candidates`、`uq_research_candidates_tenant_company_id`、`uq_research_candidates_operation`、`pk_candidate_intake_receipts`、`uq_candidate_intake_receipts_tenant_candidate`。后两者是新0008显式名字；同请求并发可能先碰candidate ID的任意键，不能只认operation键。
- 命中允许键先回滚整个 candidate+receipt SAVEPOINT，再用新的 READ COMMITTED SELECT 按 **tenant_id+本次request.operation_id** 读完整已提交receipt。fingerprint及tenant/company/security/ticker/candidate ID/origin/extractor version/raw SHA/byte count全部相等、历史receipt自身闭合才返回；不存在或合法请求不同为stable `EvidenceConflictError`，已读取历史不闭合为storage failure。不能在aborted transaction继续查询，不能按命中的candidate ID跨tenant/operation找“可复用”结果。相同candidate ID但不同op/跨tenant全球PK碰撞时requested receipt不存在，必须conflict；同op异candidateID必须conflict。外层失败不留半个candidate/receipt。
- receipt 对外是 immutable intake 结果，包含 outcome、candidate_version=1、candidate ID、payload SHA、request fingerprint、context/raw identity、Fins witness（或拒绝码）、DB created_at。retry 永远返回原 receipt，即使将来 candidate 已被 CAS 推进；不把 mutable Candidate 当前状态写成原始 intake outcome。
- 既有 `create_proposed_candidate` 保留为可信底层 staging 入口，不被新 Service 调用；无 intake receipt 的旧 staging 行不能被本计划写成已经经过 Fins 检查，future S32-B 必须显式验证 receipt 或重新入场。A 不通过全仓 rename 删除已接受的 S31 接口。

## 10. 残余风险、S32-B 入口与收束

- A已经固定边界：source在观察之后漂移、app-role可信进程、既有低层staging无receipt、原始输出不落库。分别由future promotion/消费每次Fins复核、Phase7.1 credential/API、S32-B receipt准入、可信caller保存原raw负责；不能写成已解决的永久source freshness。
