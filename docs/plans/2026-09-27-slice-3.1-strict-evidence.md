## 3. 领域数据契约（唯一实现决策）

### 3.1 标识、值、时间与 locator

- 六类 DTO 使用 frozen slots、显式类型；UUID canonical 小写非 nil，ID 由 caller 提供，`TenantScope` 不充当认证。unknown enum、bool-as-int、float、NaN/Infinity、非 UTC aware datetime、无效/倒置 date、available_at 早于 ingested_at 全拒绝。`FactValue` tagged union 为 decimal/text/date/boolean，必须恰一个 payload。**decimal 的 ORM/PG 列精确 `value_decimal NUMERIC`，不声明 `(p,s)` typmod**；DTO 和 DB 在未舍入值上使用同一规则：finite，`scale∈[0,12]`，`max(1,integer_digits+scale)≤38`，其中 `integer_digits=0` 当 `abs(v)<1`，否则为整数部分的十进制位数；负数允许，合法输入原值往返不得隐式舍入。`1.0000000000001`、任意 39 位整数、NaN/±Infinity 拒绝。SQL CHECK/immutable pure SQL function 仅在 value_kind=decimal 分支检查非空数值、`value_decimal::text NOT IN ('NaN','Infinity','-Infinity')`、`scale(value_decimal)≤12` 与上述位数公式；非 decimal 分支须 value_decimal IS NULL。不能用 `NUMERIC(38,12)` 再 CHECK，因为 PG 会先按列 scale 舍入。text 非空、date 为真实日期、boolean 真 bool；numeric 必须有非空 unit_code，非 numeric 禁 unit/currency，`unit_code='currency'` 才且必须有三位大写 currency。metric/unit 开放受限字符串，不伪称 closed enum；value kind、verification/claim/confidence/horizon/evidence/conflict/candidate status 为 closed enum。PG16 依据：[Numeric Types](https://www.postgresql.org/docs/16/datatype-numeric.html)、[scale(numeric)](https://www.postgresql.org/docs/16/functions-math.html)。
- `EvidenceLocatorSnapshot` 是纯投资域的**结构镜像**，只接受 Fins v1 projection `to_dict()` 的 11 键：`repository_id,ticker,document_id,source_kind,artifact_kind,document_version,source_fingerprint,primary_content_sha256,locator_kind,locator_payload,locator_content_sha256`。固定 repository=`dayu.fins.public.v1`，source=`filing|material`，artifact=`source|processed`，kind=`document|page|section|table_cell|xbrl_fact`；payload 依 Fins §6.3.2 exact keys，source 只能 document，processed 可五类。严格 canonical ticker/document-id、非空 version、lower-64-hex hashes、无 path/URI/bucket/key/handle/secret 额外键。JSON canonical bytes 是 UTF-8/sorted keys/compact separators/`allow_nan=False`；拒绝重复键/BOM/trailing data、未知字段及未知 schema，存入 JSONB 后读回重建 canonical bytes 并再校验。3.1 的结构镜像不可声称 Fins 当前片段仍存在；3.2 必须 `validate_evidence_locator`/`read_citation_projection` 后才 promote。
- Fact 的 `security_id/locator_ticker/locator_json` 是显式列且各 `NOT NULL`；在 DB 中以 `((jsonb_typeof(locator_json->'ticker') = 'string') AND (locator_ticker = locator_json->>'ticker')) IS TRUE` 强制 ticker 来自已通过结构 CHECK 的同一 locator JSONB，再由公共 `(company_id,security_id,locator_ticker)` FK 绑定公共 security。Direct EvidenceLink 仅在 direct arm 有上述 security/ticker/JSON 值，DB ticker 等值及三列 FK 同样闭合；Fact arm 四个 direct-only 列全 NULL。Fins locator 的 `document_id` 和 source identity 原样保存于同一 JSONB，不用 workspace path 或 guessed URL；Fins locator 不加 tenant。A/B 可各自在私有行保存相同 locator JSON。ticker 无法唯一辨认公司，caller 必须给明确 `security_id`；它与 company/ticker 任一不符即拒绝，禁止按 ticker 猜 company 或自动改大小写。完整 locator 外部 owner readback 留到 3.2。显式 ticker+CHECK 是本片最小可行方案：沿用 V8 ORM/INSERT/FK/index 字段，生成列会改变写入/映射契约且在此不带来额外闭合；CHECK 使用 `IS TRUE`，不能只写 nullable 等式。
- Fact 为 immutable observation：每行有 `fact_series_id`、`revision_no>=1`、`prior_fact_id`（首版 null）、`fact_key`、原始 locator、value/unit/currency、`period_start/end`、**`effective_at`**、`published_at/ingested_at/available_at`、`extractor_version`、verification snapshot（`unverified|verified|invalidated`）、`operation_id`、`operation_fingerprint`、`created_at`。`effective_at TIMESTAMPTZ NOT NULL` 是 caller 明确提供的经济事实时点，不能从 period end 或 published_at 推导；forward guidance 不施加普遍 `effective_at<=published_at`。§6.5 PIT 映射固定为 `revision_id=facts.id`、`prior_revision_id=prior_fact_id`，四个时间字段原样输出；后续 backtest/optimizer 仍须独立验证 `available_at<=decision_at` 和 revision set，3.1 Fact 不自带最终 PIT 使用许可。同 series 修订新增行，不能覆盖原行；prior Fact 必须同 tenant/company/series 且版号恰为 n-1，repository 锁内校验、unique `(tenant_id,company_id,fact_series_id,revision_no)` 抗 race。`available_at>=ingested_at>=published_at`，未知时刻拒绝；verification 改变也追加 revision 并记录 verifier ID/time，confidence 不触发。

### 3.2 Claim、Evidence、Conflict 与 Candidate

- `claims` 是 tenant/company 内的 mutable shell：`id,tenant_id,company_id,created_at,updated_at,version`；version 是最新 ClaimVersion 的 CAS token。immutable `claim_versions` 含独立 id/claim_id/tenant/company、version_no、`transition_kind`（`claim_create|content_revision|submit_review|begin_revision|review_decision|expiry|conflict_resolution`）、**`evidence_mode='replace_all|copy_previous'` 与 nullable `copy_source_version_id`**、operation_id/fingerprint、statement/confidence/probability/horizon/valid_until/status/invalidation_rule、author_user_id、created_at。copy_source_version_id 在 copy_previous 模式必填，精确指向首次请求 expected_version 的同 tenant/company/claim immutable ClaimVersion；replace_all 必为 null，V1 只能 replace_all。review_decision/conflict_resolution 版另有完整不可变 review actor/token/grant/key/time/policy/reason witness；begin_revision 版另有 author_auth_token_id/checked_at/policy，author_user_id 来自 token.user_id、reviewer 字段全空；普通内容版的 author_user_id 不冒称认证。六表无 raw bearer/token hash/secret。`UNIQUE(tenant_id,claim_id,version_no)`；claim+V1 draft 同事务创建。后续 expected_version CAS 插入 V(n+1) 与该版完整 EvidenceLink 集合，更新 shell.version；失败全回滚。链接只在版本创建事务内插入；current 仅取 shell.version 对应版，缺失/漂移 fail closed。
- **状态矩阵按版本迁移而非终结 Claim lineage。** `create_claim` 建 V1 draft；通用 `append_claim_version` 仅做 `draft→draft`、`in_review→in_review`、`review_required→review_required` 的实质内容/证据修订（忽略新 link ID 后 statement/规则/target-identity 等至少一项变化，完整 links 新行），以及 `draft→in_review` 提交审核（`transition_kind=submit_review`，可复制原 links，无内容变更要求）。它不得从 rejected/invalidated/superseded 来源，也不得进入 approved/rejected/invalidated/superseded 或从其它状态进入 review_required。`record_claim_review` 仅做 `in_review→approved|rejected`、`approved→invalidated|review_required`（人工）、`review_required→superseded`，必须 reviewer grant；approved 至少一 supports、valid_until > PG statement clock。系统 expiry 唯一做 `approved→review_required`，无 actor。**`begin_claim_revision(scope_hint,raw_token,request)` 唯一做 `rejected|invalidated|superseded|review_required→draft`**，同一 claim_id/lineage，要求 active token/user/org、无需 reviewer grant，author 从 token 推导、非空 revision reason、expected_version CAS 与新版本完整 links；旧终态版本仍不可变。物理 approved 已过期须先由受控 current 访问物化 review_required，再以新 head/version begin；旧 expected_version 只能 optimistic conflict。`resolve_conflict_with_review` 可在 draft/in_review/review_required 产生同状态 successor，或 approved→review_required，仍须 reviewer grant。confidence/probability 不自动批准；Agent 无审查入口。
- `valid_until <=` 当前受控查询的 PG `statement_timestamp()` 且持久 head 为 approved 时，**effective status 立即 review_required**，任何局部就绪或后续消费者必须按时间拒绝。首次 current/eligibility 受控访问在同一事务以 claim CAS 恰好追加一次系统 review_required version 与完整 links；并发访问只一物化，其余重读新 head。未经访问的物理 head 仍可能 approved，3.1 无 scheduler，不宣称全库无人访问时已持久转态。as-of 历史查询不按未来时钟回写；未来无人访问 sweep 由后续独立 operation/scheduler work unit 设计并复用 CAS。
- `evidence_links` immutable，关系 `supports|contradicts|context`，指向一个 immutable ClaimVersion；target 恰好一个：same-tenant/company Fact，或 **`(security_id,完整 Fins locator JSONB)`** direct target。Fact arm 的 `security_id/locator_ticker/locator_json/locator_index_digest` 必须全 NULL；direct arm 的 `fact_id` 必须 NULL，`security_id/locator_ticker/locator_json/locator_index_digest` 必须全非 NULL、ticker 与 JSONB ticker 在 DB 级等值。每个新版本复制/替换自己的完整 Link rows，旧版不可补；supports 与 contradicts 可并存，confidence 不删反证。direct `(company_id,security_id,ticker)` 公共 FK 闭合；同 company/ticker 的不同 MIC/security_id 是不同 target，允许同 ClaimVersion/同 relation/同 locator 各有一条。Fact target partial unique 仍为 `(tenant_id,claim_version_id,relation,fact_id) WHERE fact_id IS NOT NULL`。direct link 保存完整 `locator_json JSONB` 与 DB 生成的 `locator_index_digest BYTEA` 32 bytes；partial unique **精确 `(tenant_id,claim_version_id,relation,security_id,locator_index_digest) WHERE fact_id IS NULL`**，无 full JSONB/expression B-tree key，也不新增 Fins locator 长度上限。DB trigger 对已归一化 JSONB 算 digest；同 JSONB 在 PG16 此契约下同 digest，但 digest 相同不证明完整 JSONB 相等。同 security_id/digest 冲突时必须比完整 JSONB：相同=duplicate，异值=digest_collision fail closed；不同 security_id 不冲突。digest 仅查重键，不是 locator 身份、Fins hash/source freshness 或跨证券证据等价。
- `claim_conflicts` 绑定同 tenant/company 两个不同 immutable ClaimVersion endpoint，material、open|resolved、reason、created_at、version 与 resolution reviewer witness/time/reason/new version/new link。端点 UUID 排序且唯一无向 pair；任一 endpoint 所属 claim lineage 的 open material conflict 阻止局部就绪及后续 forecast/decision。`resolve_conflict_with_review` 同事务用 reviewer grant/token-derived actor，按 claim→conflict 锁序双 expected_version 校验，新增选定 lineage 的 successor ClaimVersion 与完整 links；至少一条 target identity 是冲突后新纳入且不在原两端 link target 集合中，CAS 更新 head/resolution，旧 endpoint/link 不改。approved 源→review_required，draft/in_review/review_required 源→同状态；**rejected/invalidated/superseded 源须先独立 `begin_claim_revision` 成同 lineage draft，再用新的 expected_version resolve**，不得在 resolve 内隐式重开。resolution/successor 同一 reviewer witness 与 operation ID，resolve 不 reapprove，新 draft/in_review/review_required 仍须独立批准；新矛盾建新 conflict。
- `research_candidates` 为 tenant/company 私有 staging：`id,tenant_id,company_id,origin,canonical_payload_json,sha256,operation_id,operation_fingerprint,state,created_at,updated_at,version,rejection_code`；origin closed `agent|human`，状态 closed `proposed|validated|accepted|rejected`。3.1 repository 仅允许 `create_proposed_candidate` 与 scoped read；输入是 bounded、finite、strict JSON，保存 canonical hash，payload 永不修改。3.2 strict parser/owner freshness/human-or-Service promotion 再取得 validated/accepted/rejected transition owner；3.1 不提供通向 authoritative Fact 的 candidate 快捷函数，也不把 candidate accepted 当 Claim approved。

### 3.3 S31-Auth：审查凭证与授权时点

- 本 slice 的 reviewer permission key 是 `investment.claim.review`；0007 不自动向租户/角色授予，缺 grant 则 reviewer 路径 fail closed，但**无 grant 的 active bearer actor 可调用 `begin_claim_revision`**。高熵 bearer 由 Phase 7.1 未来 issuer 用至少 256 bit 随机种子签发；3.1 只验证已有 token。输入为 43 字符 canonical unpadded base64url、解码恰 32 bytes；形态不证明熵。`token_hash=SHA256(raw ASCII bearer bytes).hexdigest()`，raw 只在内存，SQL 仅传 hash；raw/hash 不得进日志、异常、repr、argv、文件或六表。PG 测试用 `secrets.token_urlsafe(32)` 合成 fixture，不读真实凭据。
- `scope_hint.tenant_id` 对 begin/review/resolve 都只是**不可信 lookup hint**。READ COMMITTED 同一事务先 `SET LOCAL app.tenant_id` + readback；随后按动作选一条**普通 SELECT**（无 FOR UPDATE/SHARE）。**active actor 查询**只 join `api_tokens t/users u/organizations o`，所有关联显式 tenant 相等，WHERE `t.tenant_id=:hint`、hash 匹配、t/u/o active、`t.expires_at IS NOT NULL AND t.expires_at>statement_timestamp()`，返回 token-derived tenant/user/token ID 和同语句 DB time；不要求 permission/grant。**reviewer 查询**在同一 token/user/org 骨架上 join `user_roles ur/roles r/role_permissions rp/permissions p`，每个私有 join tenant 等于 t.tenant_id，且 `p.permission_key='investment.claim.review'`；多 grant 按 IDs 固定排序取一，返回 grant/permission IDs、key、同语句 time。每动作仅一次授权 SELECT，绝不先 core auth 再另查 grant。无匹配统一 unauthorized，不透露 token/tenant/grant 存在性；命中后只信 token-derived tenant/actor，Claim/Conflict tenant/company 谓词与 RLS 使用它，绝不借 audit BYPASSRLS。
- **两种动作的授权线性化点各为自身 SELECT 的 READ COMMITTED 语句快照**，witness 的 checked_at 取同语句 `statement_timestamp()`。token/user/org（reviewer 另含 grant）撤销在快照前提交则拒绝；快照后与事务重叠的撤销不追溯已通过的历史操作，即使先于该事务 commit；不能声称 commit 瞬间仍有效。active actor 的 grant 撤销本来不影响 begin。无需跨租户全表锁；0001 ur/rp 无 UPDATE，不能假定锁定 SELECT 可用。若业务以后要求 commit-time guarantee，另审锁/ACL/成本方案。PG16 依据：[READ COMMITTED](https://www.postgresql.org/docs/16/transaction-iso.html)、[statement_timestamp](https://www.postgresql.org/docs/16/functions-datetime.html)、[SELECT locking privileges](https://www.postgresql.org/docs/16/sql-select.html)。
- `dayu_platform_app` DB 连接是可信进程边界，沿用 0001–0006，不新增 SECURITY DEFINER reviewer function 或 status-specific RLS policy。对任意持 app-role DB 凭据的恶意 SQL 不承诺隔离，Phase 7.1 API/credential owner 完成前不得外露凭据。对外可调用的 repository 路径中，review/resolve 要 bearer+grant，begin 要 bearer+active actor，通用 append 禁 reviewer status entry 与 terminal-source bypass。

## 4. 数据库约束与权限（0007 精确交付）

- 六表：`facts`、`claims`、`claim_versions`、`evidence_links`、`claim_conflicts`、`research_candidates`，均 tenant/company NOT NULL FK RESTRICT、caller UUID PK、closed status/CHECK；Fact `effective_at` 非空且 `security_id/locator_ticker/locator_json` NOT NULL、ticker-JSONB 等值 DB CHECK，**`value_decimal NUMERIC` 无 typmod**（ORM `Numeric(asdecimal=True)` 不带 precision/scale，PG catalog `atttypmod=-1`）。0007 以 DB CHECK/纯 SQL function 对原值验证 finite、scale≤12、总位数≤38，value_kind 与 payload/unit/currency 同时闭合；`NUMERIC(38,12)` 禁用。ClaimVersion `transition_kind`、begin author token witness 与 reviewer witness 按动作 CHECK；Conflict resolution witness 完整。ORM mapped 18→24、PG physical 27→33、public 3/private 24→30；禁止 public locator table 或 locator.tenant_id。
- 公共 `securities` 新增 `uq_securities_company_id_id_ticker`；Fact/direct link `(company_id,security_id,locator_ticker)` composite FK 指向它，Fact 与 direct 各有 DB `IS TRUE` ticker-JSONB 等值 CHECK；Fact 三列全非 NULL，direct 仅在 direct arm 三列全非 NULL，故默认 MATCH SIMPLE 无空值逃逸。Fact `UNIQUE(tenant_id,company_id,id)` 与 series/revision unique；Claim/Version/Link `UNIQUE(tenant_id,company_id,id)`，各私有 FK tenant/company 闭合。ClaimVersion 另有 `UNIQUE(tenant_id,company_id,claim_id,id)`，nullable `copy_source_version_id` 以 `(tenant_id,company_id,claim_id,copy_source_version_id)` self-FK 到 immutable source；repository 核 source.version_no=expected_version 与完整 links。EvidenceLink 再有 `UNIQUE(tenant_id,company_id,claim_version_id,id)`；Conflict 端点 same-tenant/company FK、UUID 排序 CHECK 与无向 pair unique，resolution `(tenant_id,company_id,resolution_new_version_id,resolution_new_link_id)` FK 到 successor link。prior Fact 自引用 tenant/company，series/version 相邻由 repository 锁内核。Fact、ClaimVersion、Conflict-open、Candidate 各 `UNIQUE(tenant_id,operation_id)`；Conflict resolution 另有非空时 `(tenant_id,resolution_operation_id)` partial unique，同 row 存 fingerprint/new version/new link。所有 FK RESTRICT；不靠应用谓词代替。

ELSE NEW.locator_index_digest := NULL; END IF`，覆盖 caller digest；raw 缺 locator 时所得 NULL 仍被 arm CHECK 拒绝，PG16 内建 `sha256(bytea)` 返回 BYTEA，无 pgcrypto。digest 只算已存 JSONB，不混入 security_id；security_id 独立参与 direct unique 与完整目标身份。每条新版本复制 direct link 要重建/核对显式 ticker=完整 JSONB ticker，DB 重算 digest，绝不信旧行/caller；复制 Fact link 的四 direct-only 列仍全 NULL。完整 JSONB 留 heap/DTO 比较，source_fingerprint/locator_content_sha256 不作 Fins freshness；不建立 full JSONB B-tree unique。PG16 依据：[CHECK NULL/TRUE](https://www.postgresql.org/docs/16/ddl-constraints.html)、[FK MATCH SIMPLE](https://www.postgresql.org/docs/16/sql-createtable.html)、[binary sha256/convert_to](https://www.postgresql.org/docs/16/functions-binarystring.html)、[B-tree item limit](https://www.postgresql.org/docs/16/btree-intro.html)。

- Upgrade admission：确认 exact 0006 head、public securities 既有列与角色/RLS baseline、目标六表/约束/function/trigger 无命名碰撞；在持有必要锁后建立新增约束和六表/权限；不修改 0001–0006 文件或旧数据。所有 DDL 在 Alembic 单事务；失败零 partial schema。Downgrade 先以 NOWAIT 锁住六表和新增 securities 约束关联对象，确认六表无业务行、无外部 FK/view/function/role dependency，再按 conflict→link→version→claim/fact/candidate 的依赖逆序移除 policy/trigger/function/table/unique，禁止 CASCADE；拒绝时 0007 对象和 Alembic revision 均不变。独立随机库真实 `upgrade head→downgrade -1→upgrade head` 证明 baseline 0006 回放与 0007 恢复；不得假设有数据可破坏性回滚。

- 0001 auth 表 ACL/RLS 原样复用；ur/rp 对 app 仅 SELECT/INSERT/DELETE，actor/reviewer 两种授权 SELECT 都不带锁定子句。受控 repository 与私有 app-role 凭据是真实 witness 的可信边界；0007 CHECK 仅验证形状。Raw parameterized SQL 以 `CAST(:v AS NUMERIC)` 送入 unconstrained column、绕开 DTO/ORM 映射作 PG 反例，不能以 Python 拒绝代替 DB 拒绝。

协议方法如下；普通 `scope` 是可信进程内隔离上下文，review 方法 `scope_hint` 仅不可信 lookup hint，request/projection 在 domain/evidence.py，不暴露 ORM/Session/Fins handle：

- 状态入口以 §3.2 矩阵为唯一权威。`append_claim_version` 只做 draft/in_review/review_required 同状态实质修订及 draft→in_review 提交；拒绝 terminal 来源、begin_revision、reviewer status entry。`begin_claim_revision` 是同 claim lineage 从 rejected/invalidated/superseded/review_required 到新 draft 的唯一入口，先在同事务做 §3.3 active actor SELECT，author_id=token.user_id，revision reason、expected_version、新 version ID、完整 links 与 CAS 必填；无 reviewer grant 时仍可成功。`record_claim_review` 唯一 approve/reject/invalidate/supersede/manual-review-required；`resolve_conflict_with_review` 唯一 conflict resolution；这两者先用 reviewer SELECT，request 无自由 reviewer ID/time/permission ID。错误 hint、token、状态边、旧版本、跨租户都脱敏 fail closed/rollback；旧 terminal row/link 不变。
- EvidenceLink 无独立插入方法。`create_claim` V1 携完整替换 links；`append`/`begin`/`review`/`resolve` 的新版本只能显式 replace_all 完整 links 或 `copy_previous_links=true`，互斥。首次 copy 先锁 Claim、核 persisted current.version_no=expected_version，读 immutable source Version 与完整 Links；按 `(relation,target kind,Fact ID 或 security_id+完整 direct locator JSONB,old_link_id)` 排序，生成新 link ID `uuid5(NAMESPACE_URL,"dayu:evidence-link-copy:v1:"+new_version_id+":"+old_link_id)`，同事务插入全量新 Links 并存 mode/copy_source_version_id。显式 replace 存 mode=replace_all/source null。source/link 缺失、跨 claim/tenant/company、target closure 漂移均 fail closed；copy 的 Fact links 四个 direct-only 列必须全 NULL，direct links 必重建/核 `locator_ticker=locator_json->>'ticker'` 且 security/ticker/JSON 全非 NULL，交 DB CHECK/FK 再验证；begin 不建新 Claim/改 claim_id，conflict endpoint lineage 保持。不同 security_id+同 locator 的两个 source links 必分别复制并保留，新 digest 由 DB 对 JSONB 各自重算；fingerprint 用完整 `(security_id,locator_json)`，不以 digest 代替 target identity。所有写入显式 tenant/company predicate、RLS+composite FK；认证路径 CAS 用 token-derived tenant。
- 每方法独占 Session/READ COMMITTED transaction，SET LOCAL/readback；Fact series/previous 锁+unique 决定 revision race，Claim 锁 shell 后读 current/links、核状态/冲突/到期、插入 Version+links、expected_version CAS；Conflict 固定 claim→conflict 锁顺序、双 expected versions。若 `begin` 看到未访问的 expired approved，**本次不写并返回稳定 `review_required_materialization_needed`**；调用方先经受控 `get_claim` 的独立事务物化 review_required，取新 version 后重试 begin，不能在失败事务中物化又回滚、也不能无声跨两个版本。其它失败整体回滚，无 partial row。auth helper 不独立提交或更新 last_used_at。
- `local_claim_eligibility` closed reason 精确 `expired|material_conflict|not_approved|missing_support|locally_ready_requires_fins_validation`，顺序为 PG 时间到期→open material conflict→非 explicit approved→无 supports→局部就绪但待 Fins。没有 `usable/forecast_ready/decision_ready`。结构合法、实际不存在/已删除/hash drift 的 Fins locator 在 3.1 也只可能到局部结果；3.2 validate/readback/freshness 后才给最终 readiness。current 读/eligibility 执行 expiry gate；as-of 不物化。未来消费者必须先过 3.2 与 PG 时间/conflict gate。
- 所有写 request 含 canonical operation_id 与 SHA256 canonical JSON fingerprint，覆盖 kind、tenant/company、业务 ID、新 version/link IDs、expected version、目标状态/reason、locator/value/time。replace_all frame 固定 mode=replace_all、排序完整显式 link IDs/relations/Fact ID 或 **`security_id+完整 direct locator JSONB`**。copy_previous frame 在首次尝试按 expected_version immutable source 展开，固定 mode=copy_previous、source Version ID/version_no、排序完整 source link target identities（relation、Fact ID 或 `security_id+完整 direct locator JSONB`、old_link_id）及所有生成后的 new link IDs；首次存入 operation_fingerprint，不从提交后 current head 展开。begin frame 加 token-derived actor/action kind，review/resolve 加 actor/permission key；均不含 raw/hash、token/grant IDs、checked_at 或 digest 作为身份。重试时 begin/review/resolve 先重新认证，普通可信 scope 路径先设 RLS；随即按 tenant+operation_id 查原已提交对象，在 current CAS/复制展开之前处理。命中 copy operation 时从存储 copy_source_version_id 与 request expected_version 读原 immutable source+links，按原 new version ID 重算 frame/fingerprint、核已提交 links/IDs；相同返回原投影零新行，异 actor/payload/mode/source stable conflict，source/link 缺失漂移 fail closed。无命中才按 current expected_version 首次构造；旧 expected_version+新 operation ID optimistic conflict。旧 token revoked 的认证入口即使 op 已提交也 unauthorized，历史不回滚；同 actor 新有效 token 可同指纹重试（begin 无 grant、review/resolve 需 grant）。Conflict retry 另核 successor Version 与 resolution operation/link 双向一致；系统 expiry 独立 deterministic UUID5，不冒充 actor。
