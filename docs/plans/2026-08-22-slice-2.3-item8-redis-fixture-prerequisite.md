## 4. 已收敛的实现合同

### 4.1 Imports 与常量

在唯一测试文件内把现有 `from sqlalchemy import Engine` 收窄扩展为 `from sqlalchemy import Engine, text`。新增：

```python
_SCHEMA = "dayu_platform"

_MIGRATED_DATABASE_CLEANUP_TABLES = (
    "source_health_alert_outbox",
    "source_health_states",
    "source_sync_operations",
    "source_health_snapshots",
    "source_sync_runs",
    "job_schedule_occurrences",
    "agent_run_correlations",
    "job_events",
    "job_attempt_receipts",
    "job_leases",
    "job_attempts",
    "job_runs",
)
```

tuple 顺序是合同，不得 alphabetize。它只列删除 Redis-owned `job_runs` 所需的真实 FK descendants：先删 source durable children，再删可能绑定 job 的 `job_schedule_occurrences` 与其余 job descendants，最后删 job parent。必须保留 `job_schedule_occurrences`，因为它可通过 `job_run_id` 引用 Redis-owned job；必须排除不引用 job 的 parent `job_schedules`。未删除的 `job_schedules` 由 `0004` 现有 `job_schedules + job_schedule_occurrences` fail-closed count 作为跨域污染的权威 readback，不新增 helper-side count，也不使用 `CASCADE`。

### 4.2 私有 cleanup helper

新增模块级私有函数，精确签名：

```python
def _clear_migrated_jobs_database(bootstrap_dsn: str) -> None:
```

实现要求：

1. 只用 `create_platform_engine(bootstrap_dsn)` 创建一个 bootstrap cleanup engine；不得复用已 dispose 的 app engine，不得用临时 app LOGIN/RLS path。
2. `with engine.begin() as connection:` 建立唯一事务。
3. 按 `_MIGRATED_DATABASE_CLEANUP_TABLES` 顺序逐表执行 schema-qualified `DELETE FROM dayu_platform.<table>`；table name 只能来自 frozen tuple，禁止外部输入、动态发现、反射或 `CASCADE`。
4. 所有 DELETE 在同一事务内成功才 commit；任一失败由 SQLAlchemy 原异常向外传播并回滚，不继续 downgrade。
5. `engine.dispose()` 必须在 `finally` 中恰好一次执行；不得用第二 engine、nested helper 或兼容 fallback。
6. helper 的中文 docstring 必须包含：`bootstrap_dsn` 参数、无返回值、SQLAlchemy/数据库异常传播；不得声称 cleanup error 可忽略。

不额外做 count assertion：紧接其后的 migration admission、catalog self-check 与完整 downgrade 才是权威 readback。重复扫描会制造第二真源而不增加保护。

### 4.3 Fixture teardown 调用点

把 `migrated_jobs_database` 的 `finally` 固定为：

```python
finally:
    _clear_migrated_jobs_database(bootstrap_dsn)
    run_alembic_downgrade(bootstrap_dsn)
```

不得把 cleanup 放在 test body、`job_runtime`、Redis fixture 或 `lifecycle_database`。原因：业务行属于 migrated database lifecycle；只有该 fixture 同时拥有 exact database identity、bootstrap DSN 与 downgrade 责任。

### 4.4 全 teardown 顺序

每个使用 `job_runtime` 的测试必须保持以下顺序：

1. 测试 body 中创建的 subscriber/adapter 由各自 `finally` 关闭。
2. `job_runtime` finalizer：关闭 publisher adapter；dispose app engine；删除 temporary LOGIN 及其 `dayu_platform_app` membership。
3. `migrated_jobs_database` finalizer：创建 bootstrap cleanup engine；一个 transaction 内按 §4.1 exact order DELETE；commit；finally dispose bootstrap engine；运行 `downgrade base`。`0006` 此时看到 empty `job_runs`；`0004` 必须以自身 two-table count 看到 cleanup 后的 empty `job_schedule_occurrences` 与未被 Redis fixture 删除的 `job_schedules`：正常路径 parent 为空，任一跨域 parent row 则由 migration fail closed。各 migration admission 全部通过后，最终 `0001` 删除 cluster-global group roles。
4. `lifecycle_database` finalizer：FORCE drop 已回到 base 的独立 database。
5. `redis_cluster` finalizer：复核 exact owner label，删除 Redis container，再删除 Redis network。实现不得依赖它和 PostgreSQL sibling finalizer 的相对先后；`job_runtime` 关闭后两者之间不得再有调用。
6. 文件级 pytest process 结束时，session-scoped `platform_cluster` 收集 bounded/redacted diagnostics，并按 owner label删除 PG container，再删除 PG network。

fixture cleanup 异常必须保留原失败，不能为了让后续 test setup 看似成功而手工 drop group role、吞异常或直接跳过 migration chain。

## 5. 为什么选择清理业务行

### 5.1 这是唯一符合数据所有权的最小方案

每个 Redis job 测试使用 `lifecycle_database()` 创建的随机独占数据库，测试完成后本就要丢弃；其 job rows 及真实 FK descendants 是 test-owned transient evidence，没有跨测试保存价值。由 owning fixture 在 teardown 中显式删除，正好匹配数据生命周期。`job_schedules` 不属于该 ownership closure，必须留给 `0004` 的现有双表 admission 检出任何跨域污染。

### 5.2 不弱化 migration

`0006` 拒绝带 `job_runs` 的 downgrade，防止真实 workspace 在 destructive rollback 中静默丢失 request identity。把条件删除、改成 warning、自动清业务表或加 test bypass 会破坏生产安全合同，并让 migration 负责不属于它的数据生命周期。

### 5.3 不吞异常

吞掉 downgrade error 会让独立 database 被 FORCE drop，却保留 cluster-global roles；下一测试才以 unrelated role-conflict 失败，掩盖真正 teardown failure。fixture 必须在第一处错误 fail closed，完整文件 gate 才能证明三个 tests 之间无 contamination。

### 5.4 不抽共享 helper

现有 schedules/sources/jobs fixtures已有各自 slice-owned cleanup，表集与 lifecycle 不完全相同。本 prerequisite 只有一个 caller；把它提升到 `conftest.py` 会扩大 ownership、耦合 future migration tables，并要求第二文件 scope。一个有 typed constant 与中文 docstring 的本地 helper 更小、更可 review。

## 9. Failure / STOP 条件

任一命中立即STOP并报告，不得自行改方案：

1. branch/HEAD/index/untracked、§2.1 exact-four、Redis baseline或reviewed candidate漂移。
2. 唯一测试文件不足以闭合修复，需要conftest、migration、production、workflow、README或第二测试文件。
3. 真实FK要求的table不在§4.1，或§4.1顺序在exact schema下失败。
4. cleanup/downgrade仍失败、第三测试仍见role conflict、测试少于/多于3、出现skip/xfail。
5. Pyright、Ruff、architecture、UTF8/LF/diff/allowlist、owner-label cleanup任一非零。
6. Docker daemon或exact PG16/Redis digest缺失；禁止网络pull或替代。
7. 需要吞异常、放宽0006、`CASCADE`、direct role drop、test-only migration bypass或重跑成功掩盖首次失败。
8. staging无法与Item 8 preserved WIP精确分离，或出现不明tracked/untracked path。
