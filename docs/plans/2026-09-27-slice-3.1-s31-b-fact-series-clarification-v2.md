## C01：Fact series 的公司维度

V9 §3.1/§4 和现有 0007 明确允许同一租户下不同公司复用 `fact_series_id`：修订版号唯一键为 `(tenant_id, company_id, fact_series_id, revision_no)`；`create_fact` 对前版的检查和事务 advisory lock 也绑定公司。现有 `list_fact_revisions(scope, fact_series_id)` 却以 tenant+series 读取，把两个合法的 revision 1 混为一条链并抛 `EvidenceRepositoryError`。`TenantScope` 没有公司身份，调用者不能从它推断公司。

采用 **`(tenant_id, company_id, fact_series_id)` 作为一条 Fact series 的完整身份**。协议和实现的唯一签名改为：

```python
list_fact_revisions(
    scope: TenantScope, company_id: UUID, fact_series_id: UUID
) -> tuple[Fact, ...]
```

`company_id` 是必填且须为非 nil UUID；方法在同一 `SET LOCAL`/READ COMMITTED 事务中明确使用 tenant、company、series 三个等值谓词，按 `revision_no` 升序读取并核版号从 1 连续、每版 `prior_fact_id` 正好指向本链前版、各行 tenant/company/series 一致。该公司没有此 series 时返回空 tuple；其它租户的相同公司/series 也返回空，不合并数据或猜公司。持久链漂移仍固定脱敏失败。

`create_fact` 的公司作用域、advisory key、prior 检查及 0007/ORM 的既有 unique/FK 保持原义；本澄清不加迁移、不禁止两个公司共用同一 UUID。旧二参数入口移除，不留可选 `company_id` 或兼容 wrapper。当前 S31-B 未发布，调用方和协议静态测试同步改为三参数。

## C02：原 V9 测试门的精确补证

在真实 app-role PostgreSQL 16 的 repository 用例中：

1. 同一租户的公司 A/B 使用同一 `fact_series_id`，各自建立 revision 1、2；分别调用三参数列表只得到本公司有序链。不存在的公司/series 与跨租户 scope 返回空；跨公司 prior 不能串链。两公司读写可交错，操作指纹与既有 unique 不漂移。
2. `append_claim_version` 的 `copy_previous` 操作成功后，让该 Claim head 再前进；用原 operation ID、原 expected version 和原 payload 重试，应返回原 immutable 版本与原完整 links，不新增 Version/Link。不同 operation ID 携旧 expected version 应 CAS 失败；不同 payload/mode 不得被当成原操作。
3. 经 reviewer grant 在真实 repository 中验证 `approved→invalidated`、`review_required→superseded`，再分别由 active bearer 以同 lineage `begin_claim_revision` 重开 draft；ordinary append 从 `rejected|invalidated|superseded` 来源须拒绝，且构造合法 DTO 的 `draft→review_required` 也须由仓储状态门拒绝。失败前后 head/version/link 行数及旧 immutable 行相同。其它 reviewer-only 目标若在 DTO 构造时已拒绝，只记 domain 测试，不冒充 repository PG 负例。覆盖 approved 到期需先物化的边界，不用 domain validator 的单元结果替代数据库入口证据。

上述第 2、3 项是原 V9 §3.2/§7/§119 已存在的要求，审查 M2 指出的是验收证据缺口，不改变状态矩阵或授权规则。测试使用随机库、合成 bearer 和参数化 SQL，失败整体回滚；保持 Fins 只给结构镜像和局部就绪，不宣称实时 source 有效。
