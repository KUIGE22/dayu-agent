## 1. 动机、成功标准与非目标

当前平台缺少 PostgreSQL durable queue，无法把长运行投资任务的入队、领取、lease、重试、取消和崩溃恢复做成可审计真源。本 slice 建立通用、tenant-scoped 的 job contract；它只提供可被后续 scheduler/worker/业务 Service 使用的持久化状态机。

成功标准：两个 PG16 worker 同时 claim 时只有一方得到同一 job；所有写入由 lease token、fence 和 expiry 拒绝陈旧调用；相同 idempotency key 只生成一个语义相同的 job；取消、deadline、retry、crash 和 Host reconciliation 均有闭合状态和不可变 receipt/event；对同一 Agent correlation，Host 最多一次进入本地模型执行。

非目标：不启动 scheduler、worker、Redis、CLI queue 命令、API、UI、业务 handler、Agent handler、source connector 或任何 Broker；不注册 production handler；不实现外部 provider exactly-once；不改变现有随机 `register_run()` 路径；不把 payload/result 作为业务 schema 或让 LLM 写 authoritative business record。

### 3.1 Reserved Host run

在现有唯一 Host protocol owner `dayu.host.protocols.RunRegistryProtocol`（当前源码
`dayu/host/protocols.py:557`）新增下列 `ReservedRunEnsureResult`、
`ReservedRunIdentityConflictError`、`ReservedAgentRunExistsError` 与 `ensure_reserved_run` method；该文件在本 slice 的改动严格限于
这四个 reserved identity contract，不能成为 PG job DTO、repository Protocol 或 application
Service 的 owner：

```python
@dataclass(frozen=True, slots=True)
class ReservedRunEnsureResult:
    record: RunRecord
    created: bool

class ReservedRunIdentityConflictError(RuntimeError):
    """reserved run 与既存不可变身份不一致时抛出。

    ``record`` 是已持久化的安全 Host record，仅供调用方查询/恢复；异常
    文本不序列化该 record。
    """

    record: RunRecord

    def __init__(self, record: RunRecord) -> None:
        """保存既存 record 并初始化固定 safe message。

        Args:
            record: 与请求 reserved identity 冲突的既存 Host record。

        Returns:
            无。

        Raises:
            无。
        """
        self.record = record
        super().__init__("reserved_run_identity_conflict")

class ReservedAgentRunExistsError(RuntimeError):
    """reserved run 已存在、不得再次构造 Agent 时抛出。

    ``record`` 是已持久化的安全 Host record，仅供调用方查询/恢复；异常
    文本不序列化该 record。
    """

    record: RunRecord

    def __init__(self, record: RunRecord) -> None:
        """保存既存 record 并初始化固定 safe message。

        Args:
            record: 已存在的 reserved Host record。

        Returns:
            无。

        Raises:
            无。
        """
        self.record = record
        super().__init__("reserved_agent_run_exists")

class RunRegistryProtocol(Protocol):
    def ensure_reserved_run(
        self, *, reserved_run_id: str, session_id: str | None,
        service_type: str, scene_name: str | None,
        metadata: ExecutionDeliveryContext | None,
    ) -> ReservedRunEnsureResult: ...
```

`reserved_run_id` 只接受 `run_` 加 32 位小写 hex 的确定性 Host ID；JobService 以 attempt UUID 生成 `run_{attempt_id.hex}`。32 hex reserved 格式与既有 `register_run()` 的 `run_` + 12 位随机 hex **永久共存**：SQLite `runs` schema 不增加固定长度 CHECK，`get_run`/`list_runs` 和下游不得按长度推断来源或类型，旧路径生成的 ID、bytes 与行为逐字不变。

`ReservedRunIdentityConflictError(record)` 与 `ReservedAgentRunExistsError(record)` 均必须把传入的同一 `RunRecord` 赋给公开只读 `.record`；`RuntimeError.args` 只精确为相应固定 safe code（`"reserved_run_identity_conflict"` 或 `"reserved_agent_run_exists"`），不得插入 record、metadata、token、payload 或其他敏感 identity detail。`RunRegistry.ensure_reserved_run` 是 Host 侧 reserved ID 格式校验的唯一 owner：必须在开启 `write_transaction()` / SQLite `BEGIN IMMEDIATE` 或任何 SQLite 写入前，以 `run_` + 32 位小写 hex 严格校验；不合法即抛 `ValueError("invalid_reserved_run_id")`，零 SQLite/Host side effect。executor 与 Host 只委托、不得复制第二 validator；PG DTO/DDL 仍独立执行同一格式不变量。通过校验后，`ensure_reserved_run` 必须在唯一一个 `write_transaction()` 中完成 `INSERT OR IGNORE`（或等价唯一冲突仲裁）→ `SELECT` → `run_id/session_id/service_type/scene_name/normalized metadata` immutable compare：插入胜出且读回 `CREATED` 返回 `created=True`；精确既有记录返回 `created=False`；任一 identity 差异抛上述稳定 `ReservedRunIdentityConflictError(existing_record)`。严禁事务外 `SELECT` 后再 INSERT 的 check-then-insert 路径，且不得把唯一冲突泄漏给调用方。

只给 `dayu/host/host_execution.py` 所有者定义的 `HostExecutorProtocol.run_agent_stream`、`run_prepared_turn_stream`、`run_agent_and_wait`、`run_agent_and_wait_replayable`，以及 `Host` 同名委托入口增加 keyword-only `reserved_run_id: str | None = None`。`replay_agent_and_wait` 与 generic operation 不扩展。reserved 值非空时 executor 必须先 ensure；只有 `created=True` 才能 `_start_run`、构造 Agent 或调用模型。`created=False` 时绝不调用模型，立即抛 `ReservedAgentRunExistsError(record)`；调用方根据携带的 record 查询/恢复。无 reserved 值时保留现有调用、异常和随机 run 行为逐字不变。直接证据是实际 `DefaultHostExecutor.run_agent_stream` 为 async Agent entry，而 `run_agent_and_wait*` 亦为 async；同步 JobService 不得也不能凭空构造 `ExecutionContract` 或调用其中任一 entry。

| `JobLeaseHandle` | `tenant_id: TenantId`; `job_id: UUID`; `attempt_id: UUID`; `fence: int`; `raw_token: str`; `acquired_at: datetime`; `expires_at: datetime` | fence 正；token 是 256-bit 随机值的小写 64-hex，仅在 claim 返回一次且绝不持久化明文；`expires_at > acquired_at`。 |
| `JobClaim` | `tenant_id: TenantId`; `definition_id: UUID`; `job_id: UUID`; `attempt_id: UUID`; `attempt_number: int`; `worker_id: str`; `descriptor: JobHandlerDescriptor`; `payload: CanonicalJobDocument`; `lease: JobLeaseHandle`; `deadline_at: datetime` | attempt 正；worker_id 非空无首尾空白；嵌入 lease 的 tenant/job/attempt 必须逐字段等于外层，lease fence 为此 attempt 当前 fence；deadline 晚于 lease acquired 时间。 |
| `JobCompletion` | `result: CanonicalJobDocument` | 仅可由有效 lease 的正常业务完成调用；不得以空/原始异常代替 result。 |
| `JobFailure` | `safe_error_code: SafeJobErrorCode`; `retryable: bool` | 不接受 message、exception、stack trace 或任意 payload；`cancelled`、`deadline_exceeded`、`retry_exhausted`、`correlation_invariant`、`correlation_stale_attempt` 均不可标为 retryable。 |
| `JobCancellationRequest` | `job_id: UUID`; `reason: str` | reason 非空、无首尾空白且是调用方已脱敏的稳定原因；不含 Host run、token 或自由错误正文。 |
| `JobAttemptReceipt` | `tenant_id: TenantId`; `job_id: UUID`; `attempt_id: UUID`; `outcome: AttemptReceiptOutcome`; `result: CanonicalJobDocument \| None`; `receipt: CanonicalJobDocument`; `safe_error_code: SafeJobErrorCode \| None`; `finalized_at: datetime` | `result` 仅 outcome=`succeeded` 时可非空；success 的 `safe_error_code=None`，failed/cancelled 必非空；receipt 始终存在、每 attempt 至多一个且 immutable。 |
| `JobRecoveryResult` | `job_id: UUID`; `attempt_id: UUID \| None`; `job_state: JobState`; `attempt_state: AttemptState \| None`; `receipt: JobAttemptReceipt \| None`; `next_available_at: datetime \| None`; `safe_error_code: SafeJobErrorCode \| None` | 无 attempt 的 ready cancel：attempt/receipt/next_available_at 均为 `None`；handler `fail` retry 时 attempt=`failed`、receipt 非空、job=`ready` 且 next_available_at 非空；非取消 lease-expiry retry 时 attempt=`abandoned`、receipt 非空、job=`ready` 且 next_available_at 非空；cancel-intent recover 时 attempt=`cancelled`、receipt 非空、job=`cancelled`、next_available_at=None；deadline/retry-exhausted terminal 时 job=`failed`、next_available_at=None，结果必须报告真实持久 attempt state，绝不以 DTO 伪装为 `failed`。 |
| `AgentRunCorrelation` | `id: UUID`; `tenant_id: TenantId`; `job_id: UUID`; `attempt_id: UUID`; `idempotency_key: str`; `reserved_host_run_id: str`; `state: CorrelationState`; `observed_at: datetime \| None`; `last_observation_sha256: str \| None`; `created_at: datetime`; `updated_at: datetime`; `version: int` | immutable identity fields 不可更新；reserved ID 精确为 `run_{attempt_id.hex}`；version 正；`observed_at` 与 `last_observation_sha256` 同时为 None 或同时非 None，后者为对应 observation canonical fingerprint。 |
| `AgentRunCorrelationObservation` | `correlation_id: UUID`; `host_run_id: str`; `host_state: HostRunObservationState`; `host_completed_at: datetime \| None`; `sha256: str` | Service 仅由 `HostRunReaderProtocol.get_run(reserved_host_run_id)` 映射：missing → `host_state=missing`、host_run_id=reserved ID、completed_at=None；record 的 `RunState.CREATED/QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED/UNSETTLED` 一一映射到同名 lowercase observation state，且 run_id 必等于 reserved ID。非 terminal state completed_at 必为 None；terminal state必须为 aware UTC 非 None；否则抛 `JobCorrelationInvariantError` 且不调用 store。sha256 是上述四个业务值的 canonical-safe JSON fingerprint。无 observer wall-clock 字段。 |
| `AgentRunStartAuthorizationDecision` | `correlation: AgentRunCorrelation`; `attempt_id: UUID`; `fence: int`; `action: AgentRunStartAuthorizationAction`; `safe_error_code: SafeJobErrorCode \| None` | attempt/fence 必等于 correlation 绑定 attempt 的当前值；`START_REQUIRED` 与 `WAIT` 时 error 为 None，其它 action 按 stable safe code 填充。 |
| `AgentRunTerminalReconciliationDecision` | `correlation: AgentRunCorrelation`; `observation: AgentRunCorrelationObservation`; `attempt_id: UUID`; `fence: int`; `action: AgentRunTerminalReconciliationAction`; `receipt: JobAttemptReceipt \| None`; `safe_error_code: SafeJobErrorCode \| None` | correlation/observation ID 与 host run ID 必匹配；首次 terminalize 与其 `ALREADY_*` 重放均返回同一 immutable receipt；`NO_HOST_RUN`、`HOST_ACTIVE_WAIT`、`STALE_*`、invariant 均无 receipt。 |

`CanonicalJobDocument` 是唯一 payload/result/receipt 表示：UTF-8、无 BOM、无重复 key、对象 key 字典序、紧凑分隔符、仅 null/bool/int/string/array/object，拒绝 float/NaN/Infinity；输入 bytes 必须与重新编码后的 bytes 完全相同，SHA-256 为小写 64 hex。金额/小数是字符串。持久化只接收调用方已脱敏的 document；queue 永不接收 raw exception、prompt、credential、token、URL query 或原始请求。它递归拒绝 closed 敏感键集合（password、secret、token、authorization、cookie、api_key），日志/metrics 只写 ID、state、safe code、长度和 hash。该规则不虚构“未知业务字段自动脱敏”能力；未来 handler 对外部副作用数据必须先投影为 safe document。

除 Host-origin terminal receipt 外，每一个有 attempt 的 terminal 路径只可调用
`build_generic_attempt_receipt(...)`。常量固定为
`GENERIC_ATTEMPT_RECEIPT_SCHEMA_NAME="dayu.job.generic-attempt-receipt"` 与
`GENERIC_ATTEMPT_RECEIPT_SCHEMA_VERSION=1`；builder 以 `CanonicalJobDocument` 的相同
canonical encoder 产生 bytes/hash，其 object **只且按字典序为**
`attempt_id`、`job_id`、`outcome`、`reason`、`result`、`safe_error_code`、`schema_name`、`schema_version`。
`result` 只可为 null 或恰含 `schema_name`、`schema_version`、`sha256` 的引用对象，绝不重复
`result_bytes`；`JobAttemptReceipt.result` 仍是唯一保存安全业务 result document 的字段/DB 列，failed/cancelled 的 result 恒为 null。builder 的参数来源固定如下：正常 `complete` 为
`(succeeded, "completion", None, completion.result-ref)`；有效 lease 的 `fail` 为
`(failed, "failure", failure.safe_error_code, null)`，若策略使 job terminal 则 safe code 改为
`retry_exhausted`；`cancel` 后 holder 收敛与 cancel-intent recover 均为
`(cancelled, "cancel_intent", cancelled, null)`；heartbeat/deadline terminalization 为
`(failed, "deadline", deadline_exceeded, null)`；非取消 lease-expiry recover 为
`(failed, "lease_expired", lease_expired, null)`，若该次已耗尽 attempts 则 safe code 为
`retry_exhausted`，若 deadline 已到则为 `deadline_exceeded`；ready cancel 无 attempt，因而没有 receipt/builder。
同一 attempt 的重放必须读取既存 immutable row，绝不重新 builder 或改变 bytes/hash。builder 拒绝任何
outcome/safe-code/result-ref 的非本表组合。

本 slice **选择 descriptor-only contract，不定义 `JobHandlerProtocol`，也没有任何 invocation method**。`JobHandlerRegistryProtocol` 与唯一 concrete `JobHandlerRegistry` 都位于 `dayu.services.job_service`，而非 storage；Protocol 只声明：

```python
register_descriptor(descriptor: JobHandlerDescriptor) -> None
get_descriptor(job_type: str) -> JobHandlerDescriptor | None
```

`JobHandlerRegistry` 使用私有 `dict[str, JobHandlerDescriptor]`（不得对外暴露）实现该 Protocol；`register_descriptor` 对同 job_type 的七字段完全相同 descriptor 幂等，不同任一字段即抛固定 `JobInputError`；`get_descriptor` 对不存在返回 `None`，存在时返回该 immutable descriptor。它没有 invoke/handler/payload API。production composition 只构造一次空 `JobHandlerRegistry()` 并注入 `JobService`，故 Slice 2.1 不接收任何业务 job；后续 Slice 2.2 若要执行某一业务 job，必须在其自身明确的 production composition path 显式 `register_descriptor`，不得反向让 store 注册或隐式填充。unit fake 只验证两方法和 enqueue 的 descriptor exactness。

`JobService.__init__(*, job_store: JobStoreProtocol, descriptor_registry: JobHandlerRegistryProtocol, host_run_reader: HostRunReaderProtocol)` 是唯一 application constructor；它持有 reader 与 registry。`JobService.enqueue` 的唯一顺序是：`descriptor_registry.get_descriptor(request.descriptor.job_type)` → 返回 `None` 或与 request descriptor 任一七字段不等时立即抛固定 `JobInputError` 且**不得调用 store/开始 PG transaction** → 完全相等时唯一调用 `job_store.enqueue(scope, request)` 并原样返回 receipt。`PostgresJobStore.enqueue` 的 constructor 始终仅有 `session_factory`；它绝不接收、持有或读取 registry，只在其 DB definition/idempotency transaction 内按已验证 request 做 definition exact-upsert/idempotency。`reconcile_agent_run_terminal` 的重启安全固定顺序为：`job_store.get_agent_run_correlation(scope, correlation_id)` → `host_run_reader.get_run(correlation.reserved_host_run_id)` → 仅在 Service 内 strict mapping 成 observation → `job_store.reconcile_agent_run_terminal(scope, correlation_id, observation)`。每次 live/restart/replay 都执行该四步，绝不用 cache、绝不由 correlation UUID 推导 attempt/reserved ID。`JobService.recover` 是唯一 public recovery orchestration：先调用 `list_expired_agent_run_correlations(scope)`，其结果固定按 `created_at ASC, id ASC`；逐条执行上述四步 reconciliation，只对 `NO_HOST_RUN` decision 以该 decision observation 的 `sha256` 调 `recover_agent_run_after_no_host`，`HOST_ACTIVE_WAIT`、任一 terminal、stale 或 invariant decision 均不得进入任一 recover primitive；最后且仅最后调用一次 `job_store.recover(scope)` 收敛无 committed correlation 的 attempt。返回 tuple 仅包含本调用实际产生的非 `None` `JobRecoveryResult`，先按已排序 correlation 的 targeted 成功结果，后接 generic result 按 `(job_id ASC, attempt_id ASC NULLS FIRST)`；不得暴露 targeted method 为 JobService public API。两类 decision 都不含 `ExecutionContract`、回调、handler、payload 或 raw lease token。不得设计 `lease: JobLeaseHandle | None`、可选 fence 或同一含混 reconcile API。所有 caller supplied `observed_at` 自公共 Service/Store 契约删除：生产 `PostgresJobStore` 只使用同一 PG transaction 内的 `transaction_timestamp()`/`clock_timestamp()` 作为 lease、deadline、backoff、event 和 observation persistence 的唯一权威；不得接受、忽略后悄然使用或以本机时钟替代调用方时间。unit fake clock 只可模拟 fake store 的数据库时钟，不能改变 production store 的语义。

## 4. 状态机、事务与故障算法

### 4.1 闭合转换

| 对象 | 合法转换 | 触发者 |
| --- | --- | --- |
| Job | `ready→leased→succeeded/failed/cancel_requested`；`ready→cancelled/failed`；`cancel_requested→cancelled`；`leased→ready`（仅 retry）；所有 terminal 吸收 | JobStore transaction；`cancel_requested→cancelled` 也由 `recover` 在 lease 过期且已有 cancel intent 时触发，绝不 retry |
| Attempt | `leased→succeeded/failed/cancelled/abandoned`；终态吸收 | 持有效 lease 的调用或 recover |
| Correlation | `reserved→host_created/host_running/host_succeeded/host_failed/host_cancelled/host_unsettled`；`host_created→host_running/terminal`；`host_running→terminal`；terminal 吸收 | query-before-retry observation |

`correlation_missing` 不是重建分支，但也不是 claim 成功后立即的数据库损坏：Transaction 1 已提交而 Transaction 2 尚未 reserve 时，进程崩溃会留下一个无 correlation 的 leased attempt；这是一段预期 incomplete-operation window，尚未发生 Host side effect。该 attempt 只能等待 lease expiry 后由 generic `recover` abandon 并按 retry policy 重试；任何 caller 均不得据此创建 Host run，也不得为旧 attempt 补建 correlation。`reconcile_agent_run_terminal` 必须已有 correlation ID，因而绝不处理此窗口。`SafeJobErrorCode.correlation_missing` 的**唯一生产返回点**是 `authorize_agent_run_start`：有效 current lease 已通过 tenant/job/attempt/fence/token/expiry 验证，但以 `(tenant_id, correlation_id, attempt_id)` 找不到 committed correlation 时，零业务状态/receipt 变更地返回 `INVARIANT_FAILURE + correlation_missing`，并只写一个 deduped safe `correlation_missing` event；同一请求重放不追加 event。所有其它 correlation 缺失读取（含 `get_agent_run_correlation`）一律是 tenant-scoped `JobNotFoundError`，不得返回该 safe code。仅在 correlation 曾成功提交后其行后来消失、或 correlation identity/Host observation 与不可变 identity 矛盾时，才记 `correlation_invariant` 并 `INVARIANT_FAILURE`。PG committed correlation 而 Host run 不存在仍可由持有效 token 的 start authorization 返回 `START_REQUIRED`，以同一个 reserved ID 进入 Host ensure；Host ensure 仍是唯一的本地模型 at-most-once 栅栏。

### 4.2 Enqueue、claim、heartbeat、terminal

各算法在其唯一 PG transaction 开头取得并只使用数据库时钟：需要稳定同事务时间的写入使用 `transaction_timestamp()`，需要与 expiry/deadline 比较的即时判断使用 `clock_timestamp()`；SQL 以该值写入/比较，绝不读 Python 本机时间或 caller 时间。每次写 event 前先锁定该 `job_runs` 行，再在**同一事务及该行锁期间**用该 job 的原子 next counter 生成 sequence（例如锁定行上的 `next_event_sequence` 计数器并递增，或等价的受行锁保护计数器）；禁止裸 `MAX(sequence_number)+1`。

1. **enqueue**：先严格按 §3.2 的 `JobService.enqueue` 完成 Service registry gate；registry missing/mismatch 时不进 store。只有 Service 已验证的 request 才进入 `PostgresJobStore.enqueue`：该方法不做 registry lookup，idempotency scope 精确为 `(tenant_id, descriptor.job_type, idempotency_key)`，request fingerprint 精确覆盖 descriptor 的全部七字段、payload `schema_name/schema_version/sha256`、available/deadline。单 PG transaction `SET LOCAL app.tenant_id`，exact existing fingerprint 返回同 definition/job 与 `idempotency_reused=True` 的 receipt；同 key 不同 fingerprint 抛 `JobIdempotencyConflictError`；否则 exact-upsert descriptor 对应 definition、插入 ready job/event 并返回 `idempotency_reused=False`。disabled definition 拒绝。
2. **claim（Transaction 1）**：单 transaction 先把 deadline 已到的 ready job 标记为 job=`failed`、`safe_failure_code=deadline_exceeded`，并只写一个 `job_deadline_exceeded` event；该路径不创建 attempt、lease 或 receipt，job 已非 ready 的重放不追加 event。随后 `SELECT ... FOR UPDATE SKIP LOCKED` 在同 tenant 的 `ready AND available_at<=database_now AND deadline_at>database_now` 中按 `available_at,id` 取一行。创建 attempt、lease 和 claimed event，递增 attempt/fence，写入仅 hash 的 256-bit lease token、expiry，job 转 leased，commit 后返回唯一一次 raw token。此 transaction 必须先 commit；它不创建 correlation。没有 worker loop；调用方何时轮询属于 Slice 2.2。
3. **heartbeat**：先以 tenant/job/attempt/fence/token-hash 锁 current job、attempt、lease；若 lease 已失效或 fence/token 不匹配，抛 `JobLeaseLostError`；若 job=`cancel_requested`，抛 `JobStateConflictError`，两者均零写。若 lease 尚有效但 `now >= deadline_at`，在**同一 transaction**将 attempt=`failed`、job=`failed`、lease release reason=`deadline`，以 generic builder 写唯一 `(failed, "deadline", deadline_exceeded, null)` receipt 和一个 deadline event，然后抛 `JobDeadlineExceededError`；绝不返回 `JobClaim`。只有 `now < deadline_at` 才更新 expiry 为 `min(now + lease_duration, deadline_at)`；若该值不严格晚于 now 则走前述 deadline 分支，因此不会返回 expiry 已在过去或等于当前时刻的成功 claim。
4. **complete**：相同 fence predicate 锁定 job/attempt，固定判定顺序为 **cancel intent → deadline → success**。有 cancel intent 时无论是否同时到 deadline，attempt/job 均收敛 cancelled、release lease、写唯一 `(cancelled, "cancel_intent", cancelled, null)` receipt/event 并返回该 immutable receipt；不得写 deadline 或 success receipt/event。仅无 cancel intent 而到 deadline 时，attempt/job 收敛 failed、release lease、写唯一 `(failed, "deadline", deadline_exceeded, null)` receipt/event 后抛 `JobDeadlineExceededError`。仅无 cancel 且未到 deadline 时，attempt/job 同时 succeeded，调用 generic builder 写 immutable `(succeeded, "completion", None, completion.result-ref)` receipt、release lease/event。
5. **fail**：仅有效 lease 可写 safe failure。若 cancel intent，attempt/job 直接 cancelled 并写 `(cancelled, "cancel_intent", cancelled, null)`；否则按 `min(retry_max_seconds, retry_base_seconds * 2**(attempt_number-1))` 计算无 jitter backoff；retryable、剩余 attempt 且 `next_available_at < deadline_at` 时 attempt=`failed`、调用 generic builder 写 `(failed, "failure", failure.safe_error_code, null)`、job=`ready`；否则 attempt/job=`failed`、写唯一 `(failed, "failure", retry_exhausted 或 failure.safe_error_code, null)` receipt。任何 retry 都新建 attempt，绝不重用 fence/token。
6. **cancel**：锁 job。ready 直接 job cancelled，**没有 attempt 时只写 job terminal state 与 event，绝不写 `job_attempt_receipt`**；leased 转 cancel_requested，记录首次 cancel intent，重复 cancel 返回同一状态。receipt 只允许在已有 attempt 时写入，且必须关联该 attempt。执行者 heartbeat/recover 发现 intent 后返回 closed cancellation decision；本 slice 不投射 Host cancel。有效 holder fail/complete 后不得成功。lease 到期时 recover 把 attempt 直接收敛为 `cancelled`（不是 abandoned）、job=`cancelled`，并写 generic `(cancelled, "cancel_intent", cancelled, null)` receipt。
7. **`recover(scope)`（generic PG transaction）**：只锁定过期 leased/cancel_requested attempt，且 SQL 必须以 `NOT EXISTS (SELECT 1 FROM agent_run_correlations correlation WHERE correlation.tenant_id = attempt.tenant_id AND correlation.attempt_id = attempt.id)` 证明该 attempt **从未提交 correlation**；不得触碰任何 correlation-attached attempt。对允许行 release lease：cancel intent 时 attempt=`cancelled`、job=`cancelled`、写 generic cancel-intent receipt/event；非取消时 attempt=`abandoned`、写 generic `(failed, "lease_expired", lease_expired, null)` receipt/event，再以失败重试策略使 job=`ready` 或 `failed`：deadline 已到时 job=`failed`、safe code=`deadline_exceeded`；已耗尽 attempts 时 job=`failed`、safe code=`retry_exhausted`；否则 job=`ready` 且有 next_available_at。若终态 code 覆盖 lease_expired，receipt 的 safe_error_code 必同步为该终态 code、reason 仍为 `lease_expired`。返回固定按 `(job_id ASC, attempt_id ASC)` 排序。它不读 Host、不能 start Host、也不调用 terminal reconciliation；无 correlation 的过期 attempt（含 claim 后 reserve 前崩溃）由它收敛。所有 stale complete/fail/heartbeat 均因 fence+token+expiry predicate 失败，不能覆盖新 attempt。

8. **`recover_agent_run_after_no_host(scope, correlation_id, observation_sha256)`（targeted PG transaction）**：只供 `JobService.recover` 在同一轮刚得到 `NO_HOST_RUN` 后调用，绝不供任意 caller bulk 恢复。单 transaction `SET LOCAL app.tenant_id` 并以同一 job-row serialization point 锁 job、attempt、lease、correlation；仅当 correlation 仍属 job current attempt、state=`reserved`、其持久 `last_observation_sha256` 与参数完全相等且对应已持久 missing observation、attempt/job 仍为 leased/cancel_requested、lease 已过期、没有更高 attempt number/fence 时，才对**该一条**执行上述非 Host generic 的相同 release/retry/receipt/event 状态机并返回 `JobRecoveryResult`。任一前提变化（包括 fingerprint、state、fence 或 current-attempt 变化）均返回 `None`，零 mutation、receipt、event；不得创建新 attempt、不得读取或进入 Host。

下表是 generic terminal/recovery 的唯一状态矩阵；`result` 列指 `JobAttemptReceipt.result` 与对应 result DB 四元组，未列路径不得生成第二种组合。

| 路径 | attempt / job 最终 state | receipt outcome / reason / safe code | result / next_available_at / API result |
| --- | --- | --- | --- |
| `complete`，无 cancel、未到 deadline | `succeeded / succeeded` | `succeeded / completion / null` | 安全 `completion.result` 完整保存一次、receipt 仅引用；next=None；返回 receipt。 |
| `fail` 且可 retry | `failed / ready` | `failed / failure / failure.safe_error_code` | result=None；next=确定性 backoff 且 `< deadline`；返回 `JobRecoveryResult`。 |
| `fail` 不可 retry 或耗尽 attempts | `failed / failed` | `failed / failure / failure.safe_error_code`（耗尽时 `retry_exhausted`） | result=None；next=None；返回 `JobRecoveryResult`。 |
| valid lease heartbeat 或 complete 遇 deadline | `failed / failed` | `failed / deadline / deadline_exceeded` | result=None；next=None；heartbeat/complete 均抛 `JobDeadlineExceededError`。 |
| leased job 的 cancel intent 由 fail/complete/recover 收敛 | `cancelled / cancelled` | `cancelled / cancel_intent / cancelled` | result=None；next=None；返回 receipt 或 `JobRecoveryResult`。 |
| 非取消 lease-expiry recover，可 retry | `abandoned / ready` | `failed / lease_expired / lease_expired` | result=None；next=确定性 backoff；返回 `JobRecoveryResult` 且如实报告 `abandoned`。 |
| 非取消 lease-expiry recover，deadline/耗尽 | `abandoned / failed` | `failed / lease_expired / deadline_exceeded` 或 `retry_exhausted` | result=None；next=None；返回 `JobRecoveryResult` 且如实报告 `abandoned`。 |
| ready cancel，无 attempt | `None / cancelled` | 无 receipt | result=None；next=None；返回无 attempt/receipt 的 `JobRecoveryResult`。 |

### 4.3 Agent correlation：两个显式事务、两类不可混用决策

`claim` 与 `reserve_agent_run_correlation` 是两个独立公开调用、两个明确的 PostgreSQL transaction，绝不声称共享 transaction context。Transaction 1 是 §4.2 的 claim：commit attempt/lease/fence/token-hash/job=leased 后返回 raw `JobLeaseHandle`。Transaction 2 是 `reserve_agent_run_correlation(scope, lease)`：在自己的 transaction 中用 `SET LOCAL app.tenant_id`、`clock_timestamp()` 和同一 job-row serialization point 锁定 job，再锁 attempt、lease 与 correlation slot；它仅当 raw token 的 SHA-256、tenant/job/attempt/fence、attempt=`leased`、job=`leased`、lease expiry 尚未到达、无 cancel intent 且 deadline 未到完全匹配时，插入 immutable `(tenant_id, job_run_id, attempt_id, idempotency_key, reserved_host_run_id=run_{attempt_id.hex}, state=reserved)` 与 `correlation_reserved` event。相同 attempt 的已存在 correlation 必须逐字段 immutable compare 后返回；不一致抛 `JobCorrelationInvariantError`。Transaction 2 commit 前不得读/写 Host。claim commit 后、reserve commit 前崩溃没有 Host side effect，按 §4.1/§4.2.7 lease expiry recover；missing correlation 在这里是预期窗口，不是 corruption。

live start authorization 与 tokenless terminal crash reconciliation 是两个 API，既不以 optional lease 合并，也不共享 action enum：

1. **`authorize_agent_run_start(scope, lease, correlation_id)`（持 token 的 live authorization）**：最终授权只在本 API 的单 PG transaction 内产生。该 transaction 以 job row `FOR UPDATE` 串行化，锁 attempt 后以 `(tenant_id, correlation_id, attempt_id)` 锁 correlation，并重新计算 raw token hash；有效 lease 但缺 committed correlation 的唯一结果按 §4.1 返回 `INVARIANT_FAILURE + correlation_missing`。只有 correlation 的 tenant/job/attempt/id、attempt number/fence、lease token hash、lease expiry、job current attempt、job=`leased`、attempt=`leased`、无 cancel intent、`clock_timestamp() < deadline_at` 与 correlation=`reserved` 全部匹配，才返回 `START_REQUIRED`。correlation=`host_created` 或 `host_running` 时返回 `WAIT`、error=None、零写入；任一 correlation terminal state 返回 `INVARIANT_FAILURE`、safe error=`correlation_invariant`、零写入。它**不读 Host**；reserved Host entry 的 `ensure_reserved_run` created/existing 分支是 read-to-entry race 的唯一栅栏。缺 lease、过期 token、wrong tenant/job/attempt/fence/token、非 current attempt、cancel intent 或 deadline 一律不能返回 `START_REQUIRED`，分别给 `LEASE_LOST`、`CANCEL`、`DEADLINE_EXCEEDED` 或 `INVARIANT_FAILURE`，并只按既有 cancel/deadline 算法收敛。`START_REQUIRED` 后 future async handler 才以已验证 immutable `ExecutionContract` 调 Host reserved Agent entry，绝不形成第二次 Agent entry。

2. **`JobService.reconcile_agent_run_terminal(scope, correlation_id)`（无 token 的 terminal-only reconciliation）**：调用前 correlation ID 必须已经由 Transaction 2 提交；Service 先以 correlation 的 `reserved_host_run_id` 调其 injected `HostRunReaderProtocol.get_run`，只在 Service 内按 §3.2 表映射 `RunRecord | None` 为 `AgentRunCorrelationObservation`，再调用 `JobStoreProtocol.reconcile_agent_run_terminal(scope, correlation_id, observation)`。Service 不构造 `ExecutionContract`、不调用 async Agent entry、不把 reader、`RunRecord` 或 Host metadata 传给 store。`PostgresJobStore` 仅消费 observation，在自己的 PG transaction 以 **同一个 job row `FOR UPDATE` serialization point** 锁 job、attempt、correlation；`RunRecord.completed_at` 只是 DTO evidence，绝不与 PG clock 比较或决定优先级。

   - **missing / active / invariant**：correlation=`reserved` 且 observation=`missing` 时，首次把 state 保持 `reserved`、写 fingerprint/PG `observed_at` 和一个 `correlation_no_host_run` event，返回 `NO_HOST_RUN`；相同 fingerprint 重放不 UPDATE、不追加 event，仍返回 `NO_HOST_RUN`。observation=`created` 或 `queued` 时唯一持久 correlation state 是 `host_created`；observation=`running` 时唯一是 `host_running`。首次或 observation fingerprint 改变才写该 state、fingerprint/PG observed time 与一个 `correlation_host_active` event，返回 `HOST_ACTIVE_WAIT`；完全相同 active observation 重放不 UPDATE、不追加 event，仍返回 `HOST_ACTIVE_WAIT`，job/attempt/receipt 不变。已记录 `host_created`、`host_running` 或任一 Host terminal state 后得到 `missing`，首次写 `correlation_invariant` event 与 fingerprint，返回 `INVARIANT_FAILURE`；相同 missing 重放不追加 event，仍返回该 action。
   - **首次 terminalize**：若 correlation attempt 仍是 job current attempt、attempt=`leased`、job=`leased` 或 `cancel_requested`、没有更高 attempt number/fence，且 recover 尚未使该 attempt `abandoned`/使 job `ready`，严格按 **cancel intent → deadline → Host terminal outcome**：cancel 先写 cancelled receipt/state/event，返回 `TERMINALIZED_CANCEL`；否则 deadline 写 failed receipt/state/event，返回 `TERMINALIZED_FAILURE`；其后 Host success 写 succeeded receipt/state/event，返回 `TERMINALIZED_SUCCESS`；Host failed 以 retry algorithm 写 failed receipt/state/event 并返回 `TERMINALIZED_FAILURE`；**Host UNSETTLED 唯一映射为** `CorrelationState.host_unsettled`、Host-origin receipt `outcome=failed`、`safe_error_code=host_run_unsettled`、action=`TERMINALIZED_FAILURE`，再走与 Host failed 相同的 retry policy；Host cancelled 写 cancelled receipt/state/event 并返回 `TERMINALIZED_CANCEL`。不得将 UNSETTLED 写为 `host_failed`、`host_run_failed` 或任何其它 outcome/code。Host-origin receipt 使用常量 `AGENT_RUN_TERMINAL_RECEIPT_SCHEMA_NAME="dayu.job.agent-run-terminal-receipt"`、`AGENT_RUN_TERMINAL_RECEIPT_SCHEMA_VERSION=1`；其 canonical object **只且按此 key 集合**为 `correlation_id`、`reserved_host_run_id`、`host_state`、`host_completed_at`、`outcome`、`safe_error_code`，无 result、raw Host error 或 metadata。所有 receipt 为每 attempt 一条 immutable row，所有 event 通过 job-row counter 分配。
   - **terminal 重放**：若同 attempt 已有 terminal receipt 且 correlation state 与 observation 的 terminal state 一致，store 不 UPDATE、不写 receipt、不追加 event，返回 `ALREADY_TERMINALIZED_SUCCESS` / `ALREADY_TERMINALIZED_FAILURE` / `ALREADY_TERMINALIZED_CANCEL`（与既有 receipt outcome 对应），并在 decision 中复用该 row 映射出的同一 `JobAttemptReceipt`。若 terminal observation 与已持久化 terminal state/receipt outcome 矛盾，首次写 `correlation_invariant` event，返回 `INVARIANT_FAILURE`；相同 fingerprint 重放不再写 event。
   - **stale 重放**：若 recover 先取得 job lock，已将旧 attempt abandoned、job ready/terminal，或已创建更高 attempt/fence，首次把 correlation 更新为 terminal observation、写 fingerprint/PG observed time 与一个 `correlation_stale_attempt` event，返回 `STALE_ATTEMPT`、safe error=`correlation_stale_attempt`、receipt=None；它不得改回旧 attempt、不得写/替换旧 receipt、不得改写 current job。相同 stale observation 的第二及后续调用不 UPDATE、不追加 event，返回 `ALREADY_STALE_ATTEMPT`、同一 safe error、receipt=None。future worker 仅把它作为 safe observation，永不再执行旧 correlation。

future worker 只能调用 `JobService.recover(scope)`，其固定 correlation-safe 顺序与稳定返回顺序见 §3.2；不得直连 `JobStoreProtocol` 的 targeted method 或把 `NO_HOST_RUN`、`HOST_ACTIVE_WAIT`、terminal/stale/invariant decision 降格为 generic recover。`HOST_ACTIVE_WAIT` 的 future owner 是 Slice 2.2 worker：它必须以自己的显式正数 `host_active_reobserve_interval_seconds` 重观测同一 correlation，并以 persisted `deadline_at` 作为该 active-wait loop 的硬上界；到 PG `clock_timestamp() >= deadline_at` 时，worker 停止 normal recovery/claim，向既有 Host lifecycle 发出幂等 `cancel_run(reserved_host_run_id)` 请求，并继续只重观测同一 correlation 至 Host terminal/unsettled，期间绝不调用 generic recover 或 claim 新 attempt。Host cancel 的发送去重、重试与治理是 Slice 2.2 worker/Host 的明确 owner；Slice 2.1 既不注册该 worker，也不投射 Host cancel；本段只锁定其未来 owner、deadline 上界与禁止 retry 的契约。future handler 的其他唯一调用点是 reserve Transaction 2 commit 后、Host entry 前调用 start authorization，和 Host entry 返回/重启后调用 terminal-only reconciliation。它不调用 `cleanup_orphan_runs`、handler 或 Agent。

此设计仅锁定本地 Host “一个 correlation ID 至多一次进入模型”。已取得 `START_REQUIRED` authorization、但在 Host `ensure_reserved_run` 前长期暂停并跨过 lease expiry 时，仍存在跨 PG/Host store 的 read-to-entry TOCTOU：后续 safe recovery 可使 job 前进，而原 caller 仍可能进入其已授权 correlation。Slice 2.2 以 immediate Host entry、heartbeat/governance、re-observe/cancel owner 收敛该 residual；本 slice 不声称跨 store distributed exactly-once。模型供应商、工具和未来 connector 的 exactly-once 必须在其自身 protocol 上用独立 idempotency key 实现。

## 6. Composition, lifecycle, tenancy, errors and observability

为同时保持 Phase 1 的 PG admission 在任何 Host 侧作用前完成、又把真实 Host reader 注入 application Service，`dayu.services.startup_preparation` 把 default-production composition 拆为两个**私有**且唯一职责的阶段：

1. `_prepare_production_platform_dependencies(settings)` 仍在既有 startup 顺序的 provider admission 位点运行：读取 DSN、创建并 probe 唯一 engine/session factory、构造 `PostgresIdentityRepository` 与 `InvestmentIdentityService`，返回只含这三项的私有 preparation；此阶段任一失败时 Host/Fins 未构造且恰好 dispose engine 一次。
2. `Host(...)` 构造成功后、`recover_host_startup_state(...)` 前，`_build_production_services_provider(preparation, *, host_run_reader: HostRunReaderProtocol)` 只做内存装配：`PostgresJobStore(session_factory=preparation.session_factory)`（**唯一 constructor 参数，绝无 Host reader/registry）→ `JobService(job_store=job_store, descriptor_registry=JobHandlerRegistry(), host_run_reader=host)`。该 `JobHandlerRegistry` 是 §3.2 services owner 的唯一 concrete 空实例；不得在 Slice 2.1 注册 descriptor。`host` 是刚构造的真实 `Host`，以其既有 `get_run` 结构满足 services-layer protocol；不得改用 `SQLiteRunRegistry`、HostStore 直读、adapter/wrapper、callback 或 lazy lookup。该阶段不连接 PG、不启动 thread/timer/connection/atexit，因而不会引入第二 lifecycle owner。

Every repository method receives `TenantScope`; cross-tenant reads look like not-found and cross-tenant writes fail by RLS/predicate. Stable errors are `JobInputError`, `JobNotFoundError`, `JobIdempotencyConflictError`, `JobLeaseLostError`, `JobStateConflictError`, `JobDeadlineExceededError`, `JobCorrelationInvariantError`, `JobRepositoryFailureError`, `ReservedRunIdentityConflictError`, and `ReservedAgentRunExistsError`; no error interpolates payload, result, DSN, SQL, raw exception or lease token.

Metrics/log fields are counters/histograms by safe `job_type`, state transition, safe error code, claim latency, lease expiry and correlation reconciliation outcome; logs include tenant/job/attempt IDs only after existing logging redaction rules. No payload/result/receipt bytes, token, host metadata, prompt or stack trace is emitted. This slice creates no notification/audit outbox; append-only job events are the local observability truth.
