### H1-未修复-高-downgrade admission 与破坏性 DDL 之间可并发写入并静默丢失 0005 数据
- **入口/函数**: Alembic `downgrade()` -> `_downgrade_admission()` -> `_revoke_drop_guard_and_new_tables()` / `_restore_snapshot_baseline()` / `_restore_source_runs_baseline()`
- **文件(行号)**: `dayu/investment/storage/migrations/versions/0005_source_connectors_health.py:1527`、`:1532`、`:1575`、`:1590`、`:1618`、`:1639`、`:1702`
- **输入场景**: 0005 当前为空且 admission 的业务行/新增列检查刚返回零；同时另一个持有 app role 的事务在 admission 之后向三张新表、`source_sync_runs` 的 0005 core，或 `source_health_snapshots.health_state_version` 写入并提交。
- **实际分支**: `_downgrade_admission()` 只做 `SELECT count(*)`，未先锁定任何被检查/删除的表；随后 downgrade 撤销权限、删除新表并删除扩展列。
- **预期行为**: fail-closed downgrade 的“无 0005 业务数据”判定必须在线性化点上成立；admission 成功后不能再允许会被 DROP TABLE/DROP COLUMN 吞掉的新业务写入。
- **实际行为**: PostgreSQL 的普通 `SELECT` 不阻塞并发 INSERT。另一个事务可在检查后提交，downgrade 随后的 ACCESS EXCLUSIVE DDL 再取得锁并直接删除该事务刚写入的表/列；迁移成功但业务事实永久丢失。
- **直接证据**: `_downgrade_admission()` 在 `1532`--`1550` 查询三新表、14 个 run 字段和 snapshot version，但整个函数没有 `LOCK TABLE`；第一个锁定写入者的操作只会隐式发生在后续 `REVOKE`/`DROP`/`ALTER`（`1578` 起）。accepted plan §8.5 明确要求 downgrade admission 先拒绝上述数据再破坏性回滚，而当前测试 `test_0005_downgrade_admission...` 只构造静态 dirty state，没有双连接 barrier 覆盖检查后的并发提交。
- **影响**: 可恢复性边界上的静默、不可逆数据丢失；数据库版本回到 0004，丢失事实不会由 schema 或 Alembic 状态暴露。
- **建议改法和验证点**: 在任何 admission 查询前以确定的依赖顺序取得覆盖所有会被删除/缩窄对象的写阻塞锁（至少三新表、`source_sync_runs`、`source_health_snapshots`、`source_subscriptions` 与相关 parent），并把锁保留到同一 Alembic transaction 提交；再运行 catalog/data/dependency checks。增加真实 PostgreSQL 双连接 barrier 测试：downgrade 在锁内检查期间并发 app INSERT 不能提交到“检查后/删除前”窗口，且 dirty row 必须导致整次 downgrade 回滚而不是被删除。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
