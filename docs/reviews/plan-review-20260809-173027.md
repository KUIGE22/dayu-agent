## Adversarial review

### Architecture boundary

计划把状态转移留在 acceptance CLI owner，并复用 evaluator builder/strict parser；没有复制 rubric、扩 contracts、修改 `dayu/` 或引入第二套 pending schema。两文件 future allowlist 与真实 owner 足够。

### State machine and recovery

计划明确区分：

- planned failure：持久化 truthful failed phase receipt并停止；
- exact pending skeleton：exit 3、无 terminal process/receipt、无 acceptance outputs；
- operator 完整填写后独立 verify：允许 terminal 缺席，输出 PASS/FAIL，不改 planned receipts；
- persisted terminal：仍为 passed-only；旧 non-passed terminal fail closed；
- repeated same-plan run：仍 no-resume。

没有发现 pending 被误编码为 failed、terminal 缺席被误判、或人工步骤绕过 existing-receipt gate 的剩余契约缺口。

### Validation adequacy

Required tests覆盖 exact skeleton、非 exact/partial pending、PASS/FAIL manual review、malformed/secret/drift、旧 non-passed terminal、planned receipt byte stability、Popen/evaluator call counts与 same-plan no-resume。它们足以证明本次状态机修正，不需要扩大到 contracts/evaluator/dayu。

### Optimality / overengineering / overcoupling

与新增“resume action”、人工授权 marker 或 receipt schema相比，显式 handoff 是更小且更安全的修复；它不改变未来 same-plan recovery 的独立 ownership，也不把人工 review 时间塞入 subprocess wall-clock。未发现无需求抽象或跨层耦合。
