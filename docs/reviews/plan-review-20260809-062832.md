## 二、Findings

### PR-001-已修复-[高]-live lane 缺少显式 `process` 阶段，导致硬门禁要求的 processed snapshot 结构性不可得

- **位置**：第 5.2 节「源清单逐文档记录 …… processed snapshot SHA-256/状态」、第 5.2 节「缺 primary/processed …… 均为硬失败」、第 10 节 runner argv 序列（download → write preflight → write+materialize → validators → verify）、第 4.1 节 live lane 阶段列表、第 8.1 节恢复列表
- **问题类型**：契约缺失 / 不可直接实施 / 状态机漏洞
- **当前写法**：runner 只执行 `dayu.cli download` → `write --preflight-only` → `write --materialize-research` → 各 validators → `verify`。第 5.2 与 6.1.8 却把「每个必需 filing 都有 processed snapshot」列为硬失败门禁。
- **反例/失败场景**：SEC lane 的 `download` 与 `process` 是两条独立入口（`dayu/fins/pipelines/sec_pipeline.py:368` `download`、`:1597` `process`；`dayu/cli/command_names.py:15` 独立注册 `process` 子命令）。SEC 下载路径只写 source meta 并在必要时把既有 processed 标记为 `reprocess_required`（`dayu/fins/pipelines/sec_download_source_upsert.py:136-143`、`sec_download_filing_workflow.py:123`），**从不创建 processed 文档**；唯一创建点在 `dayu/fins/pipelines/processing_helpers.py:280` `repository.create_processed(...)`，由 `process` 流程调用。因此在全新 `<run-root>/data-workspace` 上执行 plan 定义的 argv 序列后，`ProcessedDocumentRepositoryProtocol.get_processed_meta` 对每一份 filing 都会抛 not-found。
- **为什么有问题**：这不是概率性失败，而是必然失败。Slice 5 授权后的第一次 live run 会在最贵的 `write` 阶段之后、`verify` 阶段一次性 FAIL 全部必需 filing，付费 token 已经消耗但拿不到有效验收结果；而 Slices 0–4 因为全部使用 fixture 与 fake runner，无法暴露该缺口——plan 自身把它变成一个只会在付费阶段引爆的延迟错误。同时 `FinsToolService` 明确声明「不依赖 `processed/*.json` 产物」（`dayu/fins/tools/service.py:124`），说明 write 阶段也不会顺带触发处理。
- **直接证据**：
  - `dayu/cli/command_names.py:15`（`process` 为独立命令）
  - `dayu/fins/pipelines/sec_pipeline.py:368` / `:1597`（download 与 process 分离）
  - `dayu/fins/pipelines/sec_download_source_upsert.py:136-143`（download 只做 `mark_processed_reprocess_required`）
  - `dayu/fins/pipelines/processing_helpers.py:280`（processed 唯一创建点）
  - `dayu/fins/tools/service.py:124`（工具服务不依赖 processed 产物）
  - `README.md:1714-1722`（`process` 是需要显式执行的独立命令）
  - plan 第 5.2、6.1.8、10 节
- **影响**：付费 live run 必然 FAIL / 验收链无法闭合 / 实施 Agent 可能在实现期擅自改写门禁或在 `utils/` 里自造 processing 调用绕过 / 返工与二次付费
- **建议改法和验证点**：
  1. 在第 10 节 runner argv 序列中，于 `download` 之后、`write --preflight-only` 之前显式加入
     `python -m dayu.cli process --ticker AAPL --base <run-root>/data-workspace`（`--config` 见 PR-004），并为其增加 `phase-receipts/process.json`；
  2. 同步更新第 4.1 lane 描述、第 8.1 恢复清单（新增 process 失败的恢复语义：processed 可安全重跑，不删 `data-workspace`）、第 13 stop conditions；
  3. 若判定 processed snapshot 并非验收必需，则必须反向删除第 5.2 与 6.1.8 中的 processed 硬门禁，二选一，不能两者并存；
  4. 验证点：Slice 2/3 用 fake command runner 断言 argv 序列中 `process` 严格位于 `download` 之后且早于任何付费 `write`；Slice 1 增加「processed 缺失 → 硬失败」的 fail-closed 用例，确保门禁与阶段编排同源。
- **修复风险（低）**：仅调整 plan 文本与 argv 契约，不触碰生产代码。
- **严重程度（高）**

### PR-002-已修复-[中]-「禁止 Any/object」的表述与既有公开边界矛盾，会迫使实施 Agent 越界改生产代码或自造适配层

- **位置**：第 4.2 节「不得使用 `Any`、`object` 或无类型签名」、第 9 节 Slice 1「禁止 `Any/object`」、第 11 节 `pyright` 验证命令
- **问题类型**：架构边界 / 不可直接实施 / 过度耦合
- **当前写法**：plan 对验收模块下达无条件禁令，但没有说明该禁令的作用域是「新模块自身签名」还是「包括与既有 owner 交互的返回值」。
- **反例/失败场景**：验收器必须消费的既有公开边界本身就是 `object`/`Any` 载荷：`dayu/cli/commands/research_workbook.py:216` `validate_research_workbook_payload(payload: dict[str, object]) -> dict[str, object]`、`:128` workbook payload builder、`:377` `build_research_workbook_report(workbook_payload: dict[str, object])`；更关键的是 `dayu/fins/domain/document_models.py:23` 直接定义 `DocumentMeta = dict[str, Any]`，而 `ProcessedDocumentRepositoryProtocol.get_processed_meta`（`dayu/fins/storage/repository_protocols.py:207`）与 `SourceDocumentRepositoryProtocol.get_source_meta` 的返回类型就是它。全仓 `dict[str, object]` 出现 140 处。实施 Agent 面对「必须调用返回 `dict[str, Any]` 的协议」与「禁止 `Any`」的冲突时，只有三条路：改 `dayu/` 生产签名（违反第 4.2 节「禁止反向修改 `dayu/` 生产代码」与第 13 节 stop condition）、在 `utils/` 造一层透传适配（违反 AGENTS「禁止兼容性 wrapper / facade」与「禁止胶水 seam」）、或滥用 `cast`/`hasattr` 逃逸（违反 AGENTS `hasattr`/`getattr` 约束）。三条都是坏结果。
- **为什么有问题**：plan 的可实施性依赖于边界表述精确。当前表述在实现第一天就会产生一次架构级歧义，而歧义的三种解法各自违反不同的项目硬约束，实施 Agent 无法自行安全裁决。
- **直接证据**：
  - `dayu/fins/domain/document_models.py:23`（`DocumentMeta = dict[str, Any]`）
  - `dayu/fins/storage/repository_protocols.py:207`、`:211`（协议返回 `DocumentMeta` / `DocumentSummary`）
  - `dayu/cli/commands/research_workbook.py:128`、`:216`、`:377`（公开 `dict[str, object]` 边界）
  - AGENTS.md「禁止使用 `object`、`Any`」与「禁止兼容性 wrapper / facade」「禁止胶水 seam」同时成立
  - plan 第 4.2、9（Slice 1）节
- **影响**：实施 Agent 跑偏 / 越界修改生产签名触发 stop condition / 引入被 deepreview 判为兼容层的胶水代码 / 逐 slice 返工
- **建议改法和验证点**：把禁令改为作用域明确的两段式：(1) `utils/investment_agent_acceptance*.py` **自身导出的所有函数与数据结构签名**禁止 `Any`/`object`/无类型；(2) 从既有 owner 读入的 `dict[str, object]` / `DocumentMeta` 载荷必须在**单一收敛点**立即解析成 frozen dataclass/TypedDict，解析失败即 fail-closed，禁止把宽类型继续向验收内部传播，也禁止为此修改 `dayu/` 签名。验证点：Slice 1 断言验收模块公开签名无 `Any`/`object`；断言未知字段/类型不符时解析抛错而非静默透传；`pyright` 在 strict 下对该三个模块零报错。
- **修复风险（低）**：纯 plan 文本澄清。
- **严重程度（中）**

### PR-003-已修复-[中]-source inventory 要求的 processed snapshot SHA-256 在现有仓储协议下无真源

- **位置**：第 5.2 节「primary file SHA-256、processed snapshot SHA-256/状态」、第 6.1.8 hard gate、第 8.2 节 inventory 排序与指纹
- **问题类型**：契约缺失 / 不可直接实施
- **当前写法**：要求逐文档记录 processed snapshot 的 SHA-256。
- **反例/失败场景**：四项字段的可得性并不一致。**可得**：`document_id`/`form`/`filing_date`/`fiscal_year`/`period` 来自 `DocumentSummary`（`dayu/fins/domain/document_models.py:530-548`）与 `get_source_meta`；source URI 与 primary file SHA-256 来自 `SourceDocumentRepositoryProtocol.get_primary_file` 返回的 `FileObjectMeta.uri` / `.sha256`（`repository_protocols.py`；`_fs_source_document_core.py:582-613`），且 `sha256` 在 SEC 下载持久化时确实写入（`dayu/fins/pipelines/sec_download_persistence.py:116`），底层由 `local_file_store.py:85` 计算；`ingest_complete` 存在于 source meta（`sec_download_source_upsert.py:209`），可经 `get_source_meta` 读到。**不可得**：processed 侧唯一的元数据构造 `build_processed_payload`（`dayu/fins/pipelines/processing_helpers.py:165-216`）产出的 meta 字段为 `source_fingerprint`/`schema_version`/`parser_version`/`quality`/`section_count`/`table_count`/`has_xbrl` 等，**没有任何 processed 内容的 SHA-256**；`ProcessedDocumentRepositoryProtocol` 也未暴露 processed blob 的摘要接口。
- **为什么有问题**：这是一个 plan 级的 hard gate 依赖一个不存在的数据项。实施 Agent 要么自行读取 processed 文件重算 SHA（等于绕过仓储协议做目录扫描，直接违反 plan 第 5.4 节「仅通过仓储协议审计」与第 2 节 non-goal「不让验收器直接读取 `workspace/portfolio/...` 私有目录」），要么扩展 `dayu.fins` 协议（触发 stop condition）。注意本条与 PR-001 独立：即使补上 `process` 阶段，SHA 仍然取不到。
- **直接证据**：
  - `dayu/fins/pipelines/processing_helpers.py:165-216`（processed meta 字段全集，无 sha256）
  - `dayu/fins/storage/repository_protocols.py:203-211`（processed 协议方法仅 handle/meta/list）
  - `dayu/fins/pipelines/sec_download_persistence.py:116`、`dayu/fins/storage/local_file_store.py:85`（primary sha256 有真源，形成对照）
  - plan 第 5.2、5.4、6.1.8 节与第 2 节 non-goal
- **影响**：验收器无法在既定边界内实现该门禁 / 诱发目录扫描绕过仓储协议 / 或诱发扩展生产协议触发 stop condition
- **建议改法和验证点**：把 processed 侧字段收敛为协议真实可得项——`source_fingerprint` + `schema_version` + `parser_version` + `quality` + `reprocess_required` + processed 存在性，作为 processed 状态指纹；删除「processed snapshot SHA-256」表述，或明确标注其为需要独立生产 slice 支撑的 deferred 项（本 work unit 不实现）。验证点：Slice 1 的 inventory 构建测试断言全部字段均来自协议返回对象，测试中不出现任何 `workspace/portfolio` 路径拼接或目录遍历。
- **修复风险（低）**：plan 文本收敛，不改生产代码。
- **严重程度（中）**

### PR-004-已修复-[中]-live argv 契约缺少 `--config` 与 workspace init 前置，隔离 run-root 下的凭据/配置解析路径未定义

- **位置**：第 10 节全部 argv 块、第 5.1 节「live run 开始前工作区目标路径必须不存在」、第 15 节第 3 项（凭据仅存在性）
- **问题类型**：契约缺失 / 不可直接实施
- **当前写法**：所有 argv 只传 `--base <run-root>/data-workspace`，未传 `--config`；plan 也未说明该隔离 run root 是否需要先经 `dayu-cli init` 或复用既有 `workspace/config`。
- **反例/失败场景**：`--config` 默认值为 `None`，语义为「默认 `workspace/config`」（`dayu/cli/arg_parsing.py:89-93`）。plan 把 `--base` 指向一个全新的 `<run-root>/data-workspace`，同时第 5.1 节又要求「目标路径必须不存在」。此时配置目录到底解析到仓库默认 `workspace/config`、还是 `<run-root>/data-workspace/config`（一个刚被要求不存在的路径），plan 未定义。若解析到后者，模型目录、scene manifest、SEC User-Agent 配置全部缺失，`write --preflight-only` 必然失败；而 plan 第 5.1 节把「package config SHA-256、scene manifest SHA-256」写入 receipt 绑定，这些指纹的来源目录同样悬空。SEC 下载对 `SEC_USER_AGENT` 的要求可经环境变量或 `dayu-cli init` 满足（`dayu/fins/downloaders/sec_downloader.py:1681`），但 plan 只承诺检查环境变量名 presence，未覆盖「配置目录未初始化」这一独立失败面。
- **为什么有问题**：这是 live gate 的前置条件缺口。它不会在 Slices 0–4 暴露（fake runner 不解析真实配置），但会在授权后的第一次 live run 的 preflight 或 download 阶段失败；更糟的情况是解析到仓库共享 `workspace/config`，使「隔离 run root」的声明只对数据成立、对配置不成立，与第 8.2 节「任何配置变化都生成新 plan」的指纹语义不一致。
- **直接证据**：
  - `dayu/cli/arg_parsing.py:89-93`（`--config` default `None`，默认 `workspace/config`）
  - `dayu/fins/downloaders/sec_downloader.py:1681`（User-Agent 需环境变量或 init 配置）
  - `dayu/cli/commands/init.py`（workspace 初始化为独立显式流程）
  - plan 第 5.1、10、15 节
- **影响**：live preflight/download 阶段失败 / 隔离语义不完整 / config 指纹来源不确定使 plan fingerprint 语义含糊
- **建议改法和验证点**：在第 10 节所有 argv 中显式加入 `--config <resolved-config-dir>`，并在第 5.1 节明确：run root 隔离仅覆盖数据与产物，配置目录为显式传入的既有已初始化目录（该目录的 SHA-256 即 receipt 中的 package config 指纹）；同时在第 15 节前置中补充「配置目录已初始化且可读」为 live gate 检查项。验证点：Slice 2 断言构建的每条 argv 都含 `--config` 且指向 plan 中被指纹化的同一路径；Slice 2 增加「config 目录缺失/指纹漂移 → subprocess 前 fail」用例。
- **修复风险（低）**：plan 文本与 argv 契约补全。
- **严重程度（中）**

## 三、已核对但**不**构成 finding 的候选

- **候选 E（切片与测试粒度）**：未发现过度设计。Slices 0–4 白名单文件收敛在 `utils/` 三个模块、一个新测试文件、两处文档，每片有可证伪断言；Slice 1 的 fail-closed 清单（缺 bear case、断 citation、future source、blocked budget、audit skipped、超限、tamper、secret shape、symlink 越界）覆盖了真实失败面而非 happy path。三模块划分（contracts / evaluator / CLI）与「评分真源不落在 CLI」的约束匹配，不构成多余抽象。
- **write argv 参数存在性**：`--preflight-only`、`--materialize-research`、`--research-template`、`--research-base`、`--overwrite-research`、`--write-max-model-requests`、`--write-max-total-tokens`、`--write-max-estimated-cost`、`--write-budget-currency` 均在 `arg_parsing.py` 实际存在；`--no-resume` 由 `--resume` 的 `BooleanOptionalAction`（`:619-623`，default `True`）派生，plan 写法可用。`--forms` 为 `nargs="+"`（`:307-312`），plan 的 `--forms 10K 10Q 8K DEF14A` 形状正确。

## 四、Open Questions

## 六、结论
