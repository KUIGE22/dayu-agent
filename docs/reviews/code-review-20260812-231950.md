### 1-未修复-[低]-`__all__` 门禁仍可通过模块命名空间的间接引用绕过

- **入口/函数**: `_literal_all_names`，并由 `_top_level_defined_symbols` 与 `_package_root_reexported_source_symbols` 共同调用
- **文件(行号)**: `tests/investment/test_architecture_boundaries.py:2534-2565`、`tests/investment/test_architecture_boundaries.py:2651-2693`、`tests/investment/test_architecture_boundaries.py:2696-2787`
- **输入场景**: owner 或 package root 保留唯一 literal `__all__ = ["Owned"]`，然后通过 module namespace 的等价入口和 computed key 做 runtime mutation，例如：
  1. `key = "__" + "all__"; locals()[key].append("_Foreign")`；
  2. `key = "__" + "all__"; sys.modules[__name__].__dict__[key].append("_Foreign")`；
  3. `namespace = vars; key = "__" + "all__"; namespace()[key].append("_Foreign")`。
- **实际分支**: helper 只拒绝 `ast.Name(id="__all__")` 的额外 reference、字面值 `"__all__"`、以及 func 直接是 `ast.Name("globals"|"vars")` 的 call。上述输入既没有额外 `Name("__all__")` 或常量 `"__all__"`，也分别使用 `locals`、module `__dict__`、或 alias 后的 `vars`，所以三个 collector 全部返回成功。
- **预期行为**: closure contract 要求五 owner 与两个 package root 除唯一 literal assignment 外，任何 `__all__` reference/mutation 均 fail closed；runtime exports 必须与 exact manifest 一致。
- **实际行为**: 只读 synthetic AST probes 对上述三个反例在 `_literal_all_names`、`_top_level_defined_symbols` 和 `_package_root_reexported_source_symbols` 三层均输出 accept。第一个反例在 Python module scope 的 `locals()` 就是 module globals，因而真实执行会把 `_Foreign` 加入 runtime `__all__`，而 named architecture tests仍绿。
- **直接证据**: 行 2665-2671 的识别集合是额外 `Name("__all__")`、literal `Constant("__all__")` 和 direct `globals/vars` calls；它不是对七个受控模块 top-level syntax 的 allowlist。新增 tests 行 2960-2971 已覆盖 `+=`、append/extend、dynamic builder、helper-pass、direct `globals/vars`、computed key direct `globals/vars` 与 generic literal subscript，但未覆盖 `locals`、module `__dict__` 或 callable alias。真实五 owner 与两个 roots 当前均为单次 literal assignment并通过，因此当前 production export 未漂移。
- **影响**: 这是 future architecture-ratchet 缺口；后续 compat re-export 可在 exact owner/root tests全绿时进入。当前冻结 production 无触发模式，不造成现有 runtime correctness 故障，故为低风险。
- **建议改法和验证点**: 不再枚举可能访问 module namespace 的黑名单语法；对这七个受控模块采用 allow-syntax fail-closed 策略：除唯一 top-level literal `__all__` assignment 外，拒绝任何可能写 module namespace/export manifest 的 top-level `AugAssign`、expression mutation call、generic subscript write、namespace introspection/alias。或者在隔离环境执行模块并把 runtime `tuple(module.__all__)` 与 AST manifest逐值比对，同时保留 AST ownership/provenance checks。加入上述 locals dynamic-key、`sys.modules[__name__].__dict__` 与 vars alias 三个 negative fixtures。
