## Findings

### 1-MEDIUM — `format_*_report` 中的 `changed_roles` isinstance guard 接受 dict/str 导致静默迭代语义错误

- **入口/函数**: `format_write_model_challenger_promotion_report`（`:1008-1012`）、`format_write_model_configuration_change_request_report`（`:1485-1490`）
- **文件(行号)**: `write_model_challenger_promotion.py:1008-1012`、`write_model_configuration_change.py:1485-1490`
- **输入场景**: `payload` 中 `model_plan_review.changed_roles`（或 `target.changed_roles`）为 dict 或 str 而非预期的 list
- **实际分支**: `isinstance(changed_roles, (dict, list, str))` 条件为 True → 进入 join 迭代
- **预期行为**: 应拒绝非 list 的 changed_roles 值（报告函数被调用时数据应已通过 validate 函数校验）
- **实际行为**:
  - dict 输入: `", ".join(...)` 产出 dict 的 **键名** 而非值，报告呈现 `"key1, key2, ..."` 而非预期角色名
  - str 输入: `", ".join(...)` 逐字符展开，产出 `"c, h, a, n, g, e, d, ..."`
- **直接证据**:
  - `write_model_challenger_promotion.py:1008`: `if not isinstance(changed_roles, (dict, list, str))` — 显式允许 dict 和 str
  - `write_model_challenger_promotion.py:1030-1031`: `", ".join(str(value) for value in changed_roles)` — 对 dict 迭代键名，对 str 迭代字符
  - `write_model_configuration_change.py:1485`: 同模式
- **影响**: 仅影响 operator-facing report 输出。validate 路径已拒绝非法 payload，此 guard 是 defense-in-depth。但 guard 允许的 dict/str 输入会产生误导性报告文本，削弱 defense-in-depth 价值。错误消息 `"must be a list"` 与 guard 条件 `(dict, list, str)` 不一致。
- **建议改法和验证点**: 将 isinstance 检查改为仅允许 `list`：`if not isinstance(changed_roles, list): raise TypeError(...)`。或至少将错误消息改为 `"must be a list"` 且保证检查只通过 list。验证：补充 dict/str changed_roles 的 format 测试用例，确认 TypeError 被正确触发。
- **修复风险（低）**: format 函数仅被 CLI report 命令调用，收紧 guard 不会影响核心 write 流程。
- **严重程度（中）**: defense-in-depth 的弱化 + 错误消息与实现不一致。不影响核心安全或数据完整性，但降低 operator 对异常数据的感知能力。

### 2-LOW — rollback `receipt_source_path` 类型守卫使用 `TypeError` 而非 `ValueError`

- **入口/函数**: `build_write_model_configuration_operator_rollback_approval`（`:1394-1397`）、`verify_write_model_configuration_operator_rollback_approval`（`:1749-1752`）
- **文件(行号)**: `write_model_configuration_rollback.py:1394-1397`、`:1749-1752`
- **输入场景**: `source_application_receipt.path` 值为非 str（如 int、None、dict）
- **实际分支**: `if not isinstance(receipt_source_path, str): raise TypeError(...)`
- **预期行为**: 与旧代码一致——旧代码 `_absolute_path(receipt_source["path"], ...)` → `_required_text()` → `ValueError("... must be a string")`。此模块其他所有参数校验均使用 `ValueError`
- **实际行为**: `TypeError("source_application_receipt path must be a string")` — 错误类型与模块内全部其他校验不一致
- **直接证据**:
  - `write_model_configuration_rollback.py:1394-1397`: `raise TypeError("source_application_receipt path must be a string")`
  - 同模块其他校验：`require_mapping` → `ValueError`、`validated_fingerprint` → `ValueError`、`absolute_path` → `ValueError`、`require_text` → `ValueError`
  - 旧代码路径：`_absolute_path` 内 `_required_text` 抛出 `ValueError`
- **影响**: 调用方若按模块惯例 `except ValueError` 捕获校验错误，此守卫会泄漏为未处理 `TypeError`。虽在正常流程中不会触发（receipt 格式已由上游校验保证），但错误类型不一致增加维护者理解成本。
- **建议改法和验证点**: 改为 `raise ValueError(...)` 以保持模块内错误类型一致。验证：补充 `receipt_source` path 为非 str 的测试用例，确认抛出 `ValueError` 且消息正确。
- **修复风险（低）**: 仅改异常类型，不影响正常流程。
- **严重程度（低）**: 错误类型不一致，正常流程不会触发。不阻塞 merge。
