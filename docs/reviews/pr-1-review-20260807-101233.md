## Findings

### 经严格 adversarial 审查，未发现实质性问题。

逐一核对了以下关键路径，均有直接证据支撑：

#### 1. CI 入口语义（`github.sha` / pull_request checkout）

- `actions/checkout@v4` 在 `pull_request` 事件中的默认 checkout 目标是 **synthetic merge commit** `refs/pull/N/merge`，而非 PR head commit。
- `github.sha` 在 `pull_request` 事件中被设为该 merge commit 的 SHA（即 `refs/pull/N/merge` 上的最后一个提交）。
- `_verify_and_resolve_head()` 比较 `git rev-parse HEAD`（实际 checkout 的 merge commit）与 `git rev-parse --verify $head`（`github.sha` 传入的 merge commit SHA），二者一致则通过。
- `git diff --name-status base_sha merge_commit_sha` 以 merge commit 为 head 端做双点 diff，正确反映 PR 引入的文件变更。
- **结论**: `--head "${{ github.sha }}"` 语义正确，与 `actions/checkout@v4` 的 PR merge-commit checkout 行为自洽。实现不依赖 `github.sha` 等于 `pull_request.head.sha`。

#### 2. 浅克隆 / 双点 diff / depth=1 fetch

- `_parse_changed_entries` 使用双点 `git diff --name-status base head`，**不依赖 merge-base**。
- `_ensure_ref_available` 对 base SHA 做 `cat-file -e` 检测，缺失时 `git fetch --no-tags --depth=1 origin <sha>`。
- `test_shallow_clone_direct_comparison` 用 `file://` bare origin + `--depth=1` clone + fetch base 后断言 `merge-base` 仍不可用、双点 diff 正常工作。
- **结论**: 浅克隆无 merge-base 场景已覆盖，不会因历史缺失而假阴性。

#### 3. 诊断分类全路径（rename / copy / delete / 空 diff / 未变更）

- **Rename (R)**: `parts[1]=old_path, parts[2]=new_path` → `modified_files` + `rename_new_to_old[new]=old`。行映射时取 BASE 旧路径内容与 HEAD 新路径内容 diff，经 `old_to_new` 再映射 BASE 诊断的文件路径到新路径。测试覆盖 `test_includes_added_modified_renamed_and_deleted`。
- **Copy (C)**: `parts[2]=new_path` → `new_files.add(new)`。复制文件全部诊断视为新增，无需行映射。测试覆盖 `test_copy_status_new_path_is_parts2`。
- **Delete (D)**: 删除文件不出现在 HEAD 诊断中，若出现则忽略。测试覆盖 `test_deleted_file_not_in_errors`。
- **空 Python diff**: `has_any_py_changes=False` → 打印提示后仍执行全仓 HEAD/BASE pyright 比较，防止 pyrightconfig/依赖变更引发 unchanged consumer 新诊断。测试覆盖 `test_no_py_changes_still_runs_full_compare`。
- **Unchanged consumer**: 未变更文件用 identity 行映射，诊断在 BASE Counter 中匹配消耗；无匹配→新增。测试覆盖 `test_unchanged_file_new_diagnostic_fails` 与 `test_unchanged_file_matching_passes`。

#### 4. Counter 多重集 / 0→1 行号 / 路径归一化 / 异常退出

- **Counter**: `remaining[base_tuple] > 0` 后 `-=1`，一条 BASE 诊断不可消耗两次。测试覆盖 `test_one_base_diag_cannot_match_two_head`。
- **行号**: pyright JSON `range.start.line` 为 0-indexed，统一 `+1` 转 1-indexed。`test_line_index_converts_0based_to_1based` 验证。
- **0/1 行号边界**: 第 0 行（0i）→ 第 1 行（1i）；`_validate_and_build_diagnostics` 显式拒绝负数和 bool 伪装 int。`test_negative_line_exits_3`、`test_bool_rejected_as_int_exits_3` 覆盖。
- **路径**: `Path.resolve()` + `relative_to()` + try-catch fallback。worktree 前缀移除与 repo_root 提取均经过归一化处理。
- **Fail-closed**: --head 不一致→退出 2、diff name-status malformed→退出 2、pyright 异常退出→退出 3、JSON 结构非法→退出 3。对应测试全部通过 `pytest.raises(SystemExit)` 验证退出码。

## Residual Risk

1. **`cast(dict[str, JsonValue], real_materialize(...))`**（`test_research_template_command.py:180`）：`cast` 是运行时 no-op，若 `materialize_research_workspace` 返回类型与 `dict[str, JsonValue]` 不兼容，测试运行时才会暴露。但原代码为 `dict[str, object]` 返回值类型，本次改进已将 `object` 替换为 `JsonValue`，属于类型收窄。风险低。

2. **`--depth=1 fetch` 对极古老 SHA**：GitHub 若对古老 commit 做 GC，`git fetch --depth=1 origin <sha>` 可能失败，脚本以非零退出（fail-closed）。这是可接受的基础设施限制，非代码缺陷。
