## Findings

### S14-FINAL-01-未修复-[高]-Host 场景的真实 Fins tool path 自行构造 FS runtime，绕过 S3 store 与 writer lease

- **入口/函数**：带 `fins` 或 `ingestion` toolset 的 Host scene：`ScenePreparer._build_tool_registry()` → registrar → `_get_cached_fins_runtime()`。
- **文件(行号)**：`dayu/host/scene_preparer.py:758-783`；`dayu/fins/toolset_registrars.py:16-30,46-77`；`dayu/contracts/toolset_registrar.py:42-66`；计划 S14-CTRL-03/05/09。
- **输入场景**：production+enabled 的 `prepare_host_runtime_dependencies()` 已按计划创建并持有 S3 store/全局 writer lease，随后 Host 准备一个启用 `fins` 或 `ingestion` 的 scene。
- **实际分支**：ScenePreparer 仅向 `ToolsetRegistrationContext` 传 workspace/config/permissions；registrar 以 workspace 路径调用 `DefaultFinsRuntime.create(workspace_root=...)`，没有任何 `file_store`、`repository_set` 或 lease 参数。
- **预期行为**：S3 模式下所有真实 Fins byte path 都应使用 startup 已注入的唯一 S3-backed repository set，并受 S14-CTRL-09 的 writer admission 约束；不得回退/双写本地 blob。
- **实际行为**：该 runtime 使用 `DefaultFinsRuntime.create()` 的默认 FS repository set。读取、ingestion、处理和 evidence 的 Agent tool path 因此与 `PreparedHostRuntimeDependencies.fins_runtime` 分裂；它既不使用 S3 authoritative bytes，也不持有 writer lease。
- **直接证据**：registrar 的两个分支均在第 30/46/73 行无参创建/缓存 runtime；Host 第 775-782 行构造的 context 无 Fins runtime 字段。计划 allowlist 不包含 registrar、Host scene preparer 或其跨层 contract，故本 Slice 无法把唯一 runtime 注入此真实生产路径。
- **影响**：S14-01（全路径 FileStore owner）、S14-03（单 writer）以及 Slice 1.3 的 Agent evidence bytes 一并失效；同一 workspace 可同时存在 S3 metadata 视图和 Host tool 的本地 FS 视图。
- **建议改法和验证点**：先将“Host toolset 如何依赖已装配的 Fins runtime/service factory”定义为稳定的 Service/Host→Fins contract，并把最小所需文件加入 allowlist；不得让 Agent 接触 bucket/key。新增 production S3 startup 的 Host scene black-box：read、ingestion、process、evidence 均证明使用同一 repository set，第二 writer 也被拒绝。
- **修复风险（低/中/高）**：高（触及 Host→toolset adapter 装配边界，必须避免反向依赖）。
- **严重程度（低/中/高/严重）**：高。

### S14-FINAL-02-未修复-[高]-remote journal 没有跨越真实的 blob 写入与随后的 FS metadata 写入，publish-before-swap 无法成立

- **入口/函数**：上传与 tool snapshot 路径：`DocumentBlobRepositoryProtocol.store_file()` 后再 `SourceDocumentRepositoryProtocol.create/update_*()` 或 `ProcessedDocumentRepositoryProtocol.update_processed()`。
- **文件(行号)**：`dayu/fins/pipelines/docling_upload_service.py:216-245,546-564`；`dayu/fins/pipelines/tool_snapshot_export.py:812-872`；`dayu/fins/storage/_fs_blob_core.py:115-151`；`dayu/fins/storage/_fs_storage_infra.py:295-335`；计划 S14-CTRL-04/08。
- **输入场景**：上传一个新文件或生成多个 tool snapshot；任一 `store_file` 成功后、source/processed meta 的独立更新前进程崩溃，或写同 key 覆盖旧 bytes 后 meta 更新失败。
- **实际分支**：`store_file` 直接 `file_store.put_object()`，不进入 `_execute_with_auto_batch()`，也不接收/创建可跨下一次 repository 调用使用的 BatchToken。现有 pipeline 从不调用 `BatchingRepositoryProtocol`；随后 meta 更新才各自启动并提交另一个 auto-batch。
- **预期行为**：S14-CTRL-04 的同一 operation_id/batch token 应同时承载全部 staged targets 与其 metadata staging，所有 final 验证后才 swap metadata；崩溃后能判定并 roll-forward 或 fail closed。
- **实际行为**：计划虽要求 `_fs_storage_infra` 在 begin/store/commit 调 journal，却没有给这条跨窄仓储的调用链定义 token 传播或允许修改 pipeline。若把 `store_file` 单独 auto-batch，它会在后续 metadata 更新前发布 final；覆盖场景中旧 meta 仍保存旧 SHA，却已指向新 final。若不 auto-batch，则 put 后 crash 无法创建/保留与 metadata 相连的 operation journal。
- **直接证据**：上述两个 pipeline 均是顺序的 blob→metadata 调用，且 S14-CTRL-08 仅要求 auto/explicit batch 和 round-trip，未要求这些真实路径的 shared-token crash tests。允许文件未包含两条 pipeline，公共窄协议也未新增能表达该事务边界的操作。
- **影响**：S14-02 与 MiM M1 的核心恢复保证仍不成立；会产生 metadata/hash drift 或无引用 final，且 restart 无法以计划定义的 per-target 状态安全收敛。
- **建议改法和验证点**：先在 Fins storage 层定义可由真实调用链持有的原子 write session/operation boundary（而不是隐藏的全局 batch），并将所有 blob+metadata producer 纳入 allowlist；或把该完整编排收敛为一个已有 Fins storage operation。必须以真实 docling upload、tool snapshot、SEC/CN write 触发“每个 blob 后 kill、metadata 前 kill、overwrite 后 kill”的 restart tests。
- **修复风险（低/中/高）**：高（当前窄仓储契约与 pipeline 编排需要共同调整）。
- **严重程度（低/中/高/严重）**：高。

### S14-FINAL-03-未修复-[高]-delete/reset/cleanup 的先删 S3 bytes 后删 FS metadata 顺序不可恢复，journal 未建模 delete target

- **入口/函数**：`delete_entry`、source reset、processed delete/clear、filing clear/stale cleanup。
- **文件(行号)**：`dayu/fins/storage/_fs_blob_core.py:105-113`；`dayu/fins/storage/_fs_source_document_core.py:242-268,504-548`；`dayu/fins/storage/_fs_processed_core.py:76-110,226-251`；`dayu/fins/storage/_fs_maintenance_core.py:324-351,383-456`；计划 S14-CTRL-03/04。
- **输入场景**：一个文档含已由 metadata 引用的 final bytes，执行 reset、clear、stale cleanup 或 processed delete；S3 `delete_object` 已成功，随后本地 metadata staging/swap 或进程失败。
- **实际分支**：计划 S14-CTRL-03 明定这些路径“按 `meta.files` 枚举删 S3 字节，再删本地元数据目录/manifest”。S14-CTRL-04 的 target 仅有 `staging_key/final_key/sha256/size/publish_state`，状态机只描述 copy publish、metadata roll-forward 与 staging cleanup；没有 delete intent、已删状态、metadata-first publish 或 compensation 规则。
- **预期行为**：不能恢复已删除的旧 bytes（计划自身禁止旧 bytes backup），所以删除必须先原子提交不再引用该对象的 metadata，再把 remote delete 作为可重试的 post-commit cleanup；崩溃时 journal 应保留每个 delete target，且绝不把“metadata 仍引用”与“final 已删”混为成功。
- **实际行为**：S3 先删后崩溃会让旧 metadata 永久悬挂至缺失 bytes。按现有恢复的 metadata roll-forward/rollback 都不能取回对象；而“永不删 final”规则也与删除需求冲突。测试矩阵覆盖 publish crash，却没有 delete/reset/clear/stale cleanup 的每步 crash/restart。
- **直接证据**：现有各删除方法均由 auto-batch 包裹本地目录删除；计划把 bytes 删除插在该 metadata swap 之前，却没有扩展 remote journal 的 action/state。该缺陷和执行的 remote delete side effect/metadata state 写入处在同一条路径，不是抽象担忧。
- **影响**：S3 authoritative bytes 下会出现不可读 document、evidence 失败与不可恢复的数据错配；S14-01/02 的“delete/reset/cleanup 全路径”闭合声明不成立。
- **建议改法和验证点**：将 remote journal 拆为 publish 与 delete 两种 target action；delete 使用 metadata-first、post-commit idempotent remote cleanup，并对 reset、clear processed、clear/stale filing、single entry、missing/delete ambiguity 分别作 SIGKILL/restart matrix。若无法在本 Slice 内实现该状态机，应触发既定 stop condition。
- **修复风险（低/中/高）**：高（涉及所有 destructive byte paths，且必须保持无全前缀扫删）。
- **严重程度（低/中/高/严重）**：高。

### S14-FINAL-04-未修复-[中]-“已验证、seekable、caller-owned BinaryIO”与冻结的公共协议文档不一致

- **入口/函数**：`FileStore.get_object()` 与 `Source.open()` 的公共消费者。
- **文件(行号)**：`dayu/fins/storage/file_store.py:38-49`；`dayu/engine/processors/source.py:42-55`；计划 S14-CTRL-03/06 与 allowlist。
- **输入场景**：任一调用方根据当前公共 Protocol 使用 `get_object()` 或 `Source.open()`，尤其是需要判断 close owner、seekability 或 checksum failure 行为时。
- **实际分支**：计划把 S3 的返回值升级为“全量校验、seekable、caller 负责 close、底层 StreamingBody 已关闭”，但 allowlist 明确禁止修改 `file_store.py` 除 `list_objects` docstring，且不允许修改 engine `Source` protocol。
- **预期行为**：S14-CTRL-06 所声称的资源所有权、完整性和异常语义应由拥有该跨实现协作语义的公开 Protocol 明确，而非只写在 implementation plan 或私有 adapter docstring。
- **实际行为**：两个 Protocol 仅承诺“二进制流”和 `FileNotFoundError/OSError`，没有 owner、seekable、checksum 或网络失败的统一契约；实现者可以让 Local/S3 的 consumers 获得不同资源语义而仍“符合”冻结协议。
- **直接证据**：`FileStore.get_object` 的 Returns/Raises 只有第 44-49 行；`Source.open` 的第 48-52 行同样无上述语义。计划同时称“方法签名与语义不改”并要求严格的新 S3 read contract。
- **影响**：该协议无法成为可替换存储的稳定边界；测试只能锁定 S3 私有实现，不能防止 future caller 漏 close 或假设非 seekable stream，违反项目要求的完整中文 public docstring 与最小接口边界。
- **建议改法和验证点**：把跨实现必需的 ownership/seekability/read-integrity/exception contract 放进正确的公共 owner（若只对 S3 有效，则新建私有能力 Protocol 并让 Source adapter 的公共 contract 明确其返回语义），并把对应 public 文件纳入 allowlist；避免以 `getattr/hasattr` 侦测能力。用 Local 与 S3 contract tests 验证同一 consumer 语义。
- **修复风险（低/中/高）**：中。
- **严重程度（低/中/高/严重）**：中。
