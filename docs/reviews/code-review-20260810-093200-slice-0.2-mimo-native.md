## Findings

### 1-未修复-高-PlatformComposition 不做运行时类型守卫，可注入任意 object

- **入口/函数**: `dayu/startup/platform.py:build_platform_composition` → `PlatformComposition.__init__`
- **文件(行号)**: `dayu/investment/composition.py:35`（`services: Mapping[str, ServiceProtocolT]`）
- **输入场景**: `build_platform_composition` 将 `provider.provide_services()` 的返回值直接赋给 `PlatformComposition.services`。若 provider 实现有缺陷返回了非 `BaseServiceProtocol` 实例（如裸 object、dict、字符串），运行时不会被拒绝。
- **实际分支**: `build_platform_composition` 第 51-53 行：`PlatformComposition(enabled=True, services=provider.provide_services())`，无任何运行时类型断言。
- **预期行为**: 由于 `PlatformComposition` 声明泛型类型参数 `ServiceProtocolT` 并以 `BaseServiceProtocol` 绑定，组合根应只接受 Service 协议实例；注入任意 object 时应 fail closed。
- **实际行为**: 验证证明（python3 交互式）：`PlatformComposition[BaseServiceProtocol](enabled=True, services={'svc': 'not-a-service'})` 成功构造，字符串被接受为 "service"。TypeVar 只在静态类型检查时约束，Python runtime 不执行泛型约束。
- **直接证据**: `composition.py:35` — `services: Mapping[str, ServiceProtocolT]` 无 `__post_init__` 类型断言；`platform.py:51-53` — 直接透传无守卫；交互式验证输出 `"not-a-service"` 被接受。
- **影响**: 若未来 provider 实现有 bug 返回错误类型，问题会延迟到消费者实际调用 service 方法时才暴露（AttributeError / TypeError），而非在组合装配期 fail-fast。当前 slice 无真实 provider，风险窗口小；但一旦 1.2 首次真实装配引入 provider，此缺口变为生产风险。
- **建议改法和验证点**: 在 `build_platform_composition` 中对 `provider.provide_services()` 返回的每个值做 `isinstance(v, BaseServiceProtocol)` 运行时校验（`BaseServiceProtocol` 已标记 `@runtime_checkable`），非协议实例即抛 `PlatformCompositionError`。或在 `PlatformComposition.__post_init__` 中增加校验。验证点：新增测试用例 `test_provider_returning_non_protocol_raises`。
- **修复风险（低）**: 改动局限在 `build_platform_composition` 函数内部，不影响既有调用方；运行时校验只在新增的 enabled+provider 路径执行。
- **严重程度（高）**: 类型安全缺口——组合根的"只接收 Service Protocol"契约依赖静态类型检查而非运行时保证，违反 fail-closed 设计原则。

### 2-未修复-中-load_platform_settings 存在冗余双重校验

- **入口/函数**: `dayu/investment/config.py:load_platform_settings`
- **文件(行号)**: `dayu/investment/config.py:266-276`
- **输入场景**: 任何 `load_platform_settings(env)` 调用。
- **实际分支**: 第 266 行 `settings = PlatformSettings(...)` — `PlatformSettings.__post_init__` 调用 `self.validate()`；第 275 行 `settings.validate()` — 再次调用同一方法。两次执行完全相同的校验逻辑。
- **预期行为**: 构造后校验一次即可；`__post_init__` 已保证构造即校验。
- **实际行为**: `validate()` 被执行两次，输出结果相同（第二次不会改变任何状态，因为 frozen dataclass 不可变）。
- **直接证据**: `config.py:71-84` — `__post_init__` 调用 `self.validate()`；`config.py:275` — `settings.validate()` 显式调用。
- **影响**: 无功能影响，但冗余调用降低代码可读性，暗示开发者可能不信任 `__post_init__` 保证，或遗留自开发过程中的调试代码。对维护者造成认知负担："为什么 validate 了两次？是否遗漏了什么？"
- **建议改法和验证点**: 删除 `config.py:275` 的 `settings.validate()` 调用；`__post_init__` 已覆盖所有构造路径。验证点：现有 28 个测试全部通过不依赖此冗余调用。
- **修复风险（低）**: 纯删除冗余行，不改变任何行为。
- **严重程度（中）**: 代码清晰度问题；不影响正确性但影响可维护性。
