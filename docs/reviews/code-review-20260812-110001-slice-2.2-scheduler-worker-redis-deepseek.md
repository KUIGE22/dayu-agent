### 1-未修复-[中]-Worker 每轮 poll 重复 SUBSCRIBE 会把陈旧 hint 帧误判为 subscribe ACK 失败并计入连接失败，可造成虚假 degraded 降级

- **入口/函数**: `PlatformWorker._wait_event_assisted_poll` → `_ensure_subscription` → `RedisWakeupSubscriber.resubscribe`
- **文件(行号)**: `dayu/host/worker.py:1334, 1441-1451, 1507-1528`；`dayu/host/redis_wakeup.py:205-230, 720-751`；redis-py 8.1.0 `redis/client.py` `PubSub.subscribe`（仅 `execute_command` 发送，不消费响应）与 `get_message`（`parse_response` 按 socket FIFO 读下一帧）
- **输入场景**: event-assisted 模式下，上一轮 hint 触发的 wakeup 已提前退出 `_read_redis_until_deadline`（worker.py:1375-1376 读到 WAKEUP 即 `return True`），随后 claim/handler 执行期间或 poll 等待窗口内又有新 hint 发布到 PubSub socket buffer；下一轮 poll 的 `resubscribe()` 执行 `subscribe()` 后立即 `get_message()` 读取的第一帧是缓冲区内**最旧的 message 帧**（Redis 输出缓冲 FIFO：先到的 message 排在本次 SUBSCRIBE 的 ACK 之前）
- **实际分支**: `redis_wakeup.py:222-230`：`self._pubsub.subscribe(...)`（只发送命令）→ `get_message(ignore_subscribe_messages=False, timeout=...)` 返回 message 帧 → `_is_exact_subscribe_ack`（redis_wakeup.py:720-751）对 `type != "subscribe"` 返回 `False` → `resubscribe()` 返回 `False` → worker.py:1447-1449 `if subscribed is not True: self._record_redis_failure(); return False`
- **预期行为**: 计划 §7.2 只允许真实连接失败计入 `redis_failure_threshold`（"no-message 是成功操作并重置连续失败计数；invalid hint 是协议拒绝，不计连接 failure"）；合法 hint 帧与 subscribe ACK 都不应被当作连接失败
- **实际行为**: 一个合法 hint 帧被计数为一次连接失败且该 hint 被丢弃；每轮 `resubscribe` 恰好消费 1 帧，hint 突发（≥3 个 pending 帧连续命中）时即使 Redis 连接完全健康也会触发 `POLLING_DEGRADED` 虚假降级（worker.py:1521-1528）；降级后健康探针（worker.py:1503）每 30s 也只消费 1 帧，持续 hint 流量下可长期滞留 degraded，event-assist 失效；缓冲堆积超过 pubsub output-buffer 上限还有被服务端断连的次生风险
- **直接证据**: worker.py:1441-1449（每轮 poll 无条件 `resubscribe` + 非 True 即 `_record_redis_failure`）；redis_wakeup.py:222-230（subscribe 发送与 get_message 读取分离）；已核验 redis-py 8.1.0 `PubSub.subscribe` 只 `execute_command("SUBSCRIBE", ...)` 不读响应、`get_message` 走 `parse_response` FIFO 读帧；`_is_exact_subscribe_ack` 只接受 `type=="subscribe"` 帧
- **影响**: 仅局部行为错误/静默失效——PG 仍是 claim/真源，job 正确性不受影响；但 §7.2 失败计数语义被违反，hint 流量下 event-assist 被虚假关闭（唤醒延迟回到 poll_interval），并可能触发服务端 output-buffer 断连；现有 fake 测试（只追加一个 ACK 帧）与真实 Redis lane 均未覆盖该窗口
- **建议改法和验证点**: 正常 poll 路径不重复 `SUBSCRIBE`（仅在新建 subscriber 与 degraded 恢复探活时 resubscribe；断连检测已由 `get_message` 的 `RedisError` 收窄覆盖），或在 `resubscribe()` 内做有界 drain：连续消费非 ACK 帧直到读到本 channel 的 exact ACK 再返回；验证点：在 `tests/application/test_redis_wakeup.py` 的 fake PubSub 增加"buffer 中先入 message 帧再入 ACK 帧"用例断言 `resubscribe()` 返回 `True` 且不计数连接失败；真实 Redis lane 增加"worker 处于 poll wait 时持续发布 hints"场景观测 failure counter 与 degraded 转换
- **修复风险（中）**: 修改 worker/redis_wakeup 两文件的核心订阅路径，需同步调整 fake/真实 lane 的 subscribe 语义断言；属行为修复而非契约变更
- **严重程度（中）**:
