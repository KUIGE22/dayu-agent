## Findings

### 0001-未修复-[中]-JobHandlerRegistryProtocol 缺少 seal/is_sealed/registered_job_types/registered_count 方法声明

- **位置**: §6.1 production descriptor/registry；代码 `dayu/services/job_service.py:230-316`
- **问题类型**: 契约缺失
- **当前写法**: plan §6.1 要求"给 `JobHandlerRegistry`/`JobExecutionRegistry` 加 `seal()`、只读 `is_sealed`、`registered_job_types()`、`registered_count()`。seal 后所有 register 都 `JobInputError`。startup 精确顺序：new registries -> register descriptor -> register same descriptor+handler -> 断言两个 registry 均仅该 job type -> descriptor 后 execution seal。"
- **反例/失败场景**: `JobHandlerRegistryProtocol`（`job_service.py:230-254`）是 `@runtime_checkable` Protocol，只声明 `register_descriptor` 和 `get_descriptor`。`JobService.__init__` 接受 `JobHandlerRegistryProtocol` 类型参数。如果 startup 代码使用协议类型引用 registry 并调用 `seal()`，mypy/pyright 会在类型检查时报错。虽然运行时 Python 不做 Protocol dispatch 所以实际能调用，但违反 AGENTS.md 的"禁止胶水 seam"和"任何新增或修改代码都必须通过 pyright"硬约束。
- **为什么有问题**: Protocol 是稳定公共契约（AGENTS.md §架构硬约束：设计下层组件接口时必须假设上层组件不存在）。添加公开方法但不更新 Protocol，等于契约和实现脱节。startup 代码对 Protocol-typed 变量调用 `seal()` 会 pyright 报错。
- **直接证据**: `job_service.py:230-254`（Protocol 声明）；`job_service.py:264-316`（concrete class）；plan §6.1（要求加 seal 方法）
- **影响**: 实现者 pyright 失败 / 不得不在 startup 代码中做 `cast` 或 `type: ignore`，违反 AGENTS.md 编码硬约束
- **建议改法和验证点**: plan §6.1 显式声明：`JobHandlerRegistryProtocol` 新增 `seal() -> None`、`is_sealed: bool`（read-only property）、`registered_job_types() -> frozenset[str]`、`registered_count() -> int`。`JobExecutionRegistry` 同理。测试验证 `isinstance(registry, JobHandlerRegistryProtocol)` 在 sealed 后仍返回 True。**或者**，如果 seal 只应被 concrete class 的直接持有者调用（startup 直接 import concrete class），则 plan 必须显式说明 startup 不通过 Protocol 引用 registry，且允许 pyright 按 concrete type 推导。
- **修复风险**: 低
- **严重程度**: 中

### 0002-未修复-[低]-两个 crash cut point 的 fault injection 实现路径未细化

- **位置**: §10 S23-C；§6.2 A/B overlap 时序
- **问题类型**: 测试缺口
- **当前写法**: plan §10 S23-C 要求"Real PG16+offline Fins fixture fault cases must cut at (a) Fins return before PG commit and (b) PG commit before Job completion; no sleep-based race test, no real provider." §6.2 描述了完整 A/B overlap 时序。
- **反例/失败场景**: 两个 crash cut point 是本 slice 最高风险的验证点。plan 描述了**语义**（"Fins 返回后 PG commit 前崩溃"、"PG commit 后 Job completion 前崩溃"），但没有说明**实现机制**。实现者可能：(a) 用 `asyncio.sleep` 模拟时序（plan 明确禁止）；(b) 在 handler 内部注入 checkpoint 但需要额外 production 代码；(c) 用 PG session-level fault injection（如 `pg_backend_simulation`）但需要额外依赖。不同选择的复杂度和可靠性差异很大。
- **为什么有问题**: 这两个 cut point 是验证 operation head generation fencing 和 terminal replay 正确性的唯一方式。如果实现者选了不正确的 fault injection 方式，测试可能看起来通过但实际没有覆盖真实的 crash 场景。
- **直接证据**: plan §10 S23-C；plan §6.2 时序描述；handoff §3 A/B overlap 时序
- **影响**: 实现者可能采用不充分的 fault injection，导致测试覆盖不真实
- **建议改法和验证点**: plan §10 S23-C 补充一句实现指引：建议使用 PG session-level savepoint + 强制 disconnect 模拟 crash，或使用 async fixture 在 handler 内部特定点注入 `asyncio.CancelledError` + PG rollback。两种方式都满足"no sleep-based race test"约束。不强制具体实现，但给出推荐路径可以减少实现者的设计时间。**或者**，明确将 fault injection 机制的设计留给实现者（作为 STOP 条件的一部分），但要求 completion report 中报告实际使用的机制和验证结果。
- **修复风险**: 低
- **严重程度**: 低

### 0003-未修复-[低]-`source_sync_runs` 0005 扩展列与现有 0001 row 的兼容边界需显式声明

- **位置**: §7.1 source_sync_runs 的终态 receipt 方式；§7.2 health/outbox/operation tables
- **问题类型**: 迁移兼容 / open question 未收敛
- **当前写法**: plan §7.1 说"保留 0001 table 和历史 row；2.3 不读写旧 `planned/running`。0005 新增 `job_run_id/job_attempt_id/job_payload_sha256/receipt_schema_name/receipt_schema_version/receipt_bytes/receipt_sha256/outcome/retryable`。" §2 硬边界 1 说"0001 的 `source_sync_runs`/`source_health_snapshots` 是 append-only，app role 只有 `SELECT, INSERT`；禁止原地 `planned -> running -> terminal`。"
- **反例/失败场景**: 0005 为 `source_sync_runs` 添加新列（`job_run_id` 等）但保留旧 row。旧 row 的新列全部为 NULL（因为 0001 没有这些列）。plan 说"旧 row 以 `job_attempt_id IS NULL` 继续合法"。但 0005 的 terminal check 约束（"新 attempt row 必须 complete terminal status、finished time、source receipt schema/v1、bytes/hash、closed outcome/retryable"）只约束新 row，旧 row 不受影响。这在语义上是正确的，但实现者需要注意：(a) 新列是否都有 DEFAULT（否则旧 row 违反 NOT NULL）；(b) terminal check 是 `CHECK` constraint 还是 trigger；(c) app role 是否仍为 INSERT/SELECT（0005 是否给新列额外 UPDATE grant）。
- **为什么有问题**: 如果新列有 NOT NULL 约束但没有 DEFAULT，Alembic migration 对已有 row 的 ALTER TABLE ADD COLUMN 会失败。如果 terminal check 用 CHECK constraint 而非 trigger，则约束只在 INSERT/UPDATE 时生效，旧 row 不受影响（正确），但实现者必须确认 CHECK 的 WHERE 条件。
- **直接证据**: `models_identity.py:332-388`（现有 source_sync_runs 列）；plan §7.1（新增列和约束）
- **影响**: migration 脚本可能在有旧 row 的数据库上失败
- **建议改法和验证点**: plan §7.1 显式声明：(a) 新列全部 `NULL` 允许（`ALTER TABLE source_sync_runs ADD COLUMN ... NULL`）；(b) terminal check 为带 WHERE 条件的 CHECK constraint，只约束 `job_attempt_id IS NOT NULL` 的 row；(c) 0005 不改变 app role 的 source_sync_runs grant（仍为 INSERT/SELECT）。测试验证：有旧 planned/running row 的数据库执行 0005 migration 后，旧 row 仍可读、新 terminal row 可插入。
- **修复风险**: 低
- **严重程度**: 低
