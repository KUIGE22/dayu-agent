### MEDIUM-02: Selector 直接字段访问 vs HEAD getattr fallback

**严重度**: MEDIUM

**事实**: Plan 的 `_resolve_research_template_action` (line 1523–1524):
```python
def _resolve_research_template_action(args: ResearchTemplateDispatchArguments) -> str:
    return args.research_template_action.strip().lower()
```
直接访问 `args.research_template_action`，无 fallback。

HEAD (line 101):
```python
action = str(getattr(args, "research_template_action", "") or "").strip().lower()
```
使用 `getattr` + 默认空字符串 + `str()` 包裹 + `or ""` 短路。

- HEAD: `args` 缺少 `research_template_action` → 返回空字符串 → 无匹配 → return 1
- Plan: `args` 缺少 `research_template_action` → `AttributeError` 传播

Protocol 的静态检查在此处不起作用（`DayuCliArguments` 是 `argparse.Namespace` 子类，pyright 不强制 Protocol 字段存在性）。这不是 bug（正常路径不会触发），但 plan 应在 erratum 中明确指出: "直接字段访问依赖 parser 注册正确性，不保留 HEAD 的 getattr 防御"。

## 3. 建议 Erratum（最小 code-generation-ready exact 文案）

### 3.1 保留 try/except — mapping lookup 和 runner 调用仍在 try 内

Plan entry example 应修正为:

```python
def run_research_template_command(args: DayuCliArguments) -> int:
    """Dispatch ``research-template`` 子命令。

    Args:
        args: 解析后的 CLI 参数。

    Returns:
        退出码：0 成功，1 业务/未知错误，2 未知子命令。

    Raises:
        不传播——内部捕获 FileNotFoundError / FileExistsError / ValueError。
    """
    setup_loglevel(args)
    action = _resolve_research_template_action(args)
    try:
        runner = _RESEARCH_TEMPLATE_ACTION_DISPATCH.get(action)
        if runner is None:
            print(f"research-template error: unknown action {action!r}", file=sys.stderr)
            return 1
        return runner(args)
    except (FileNotFoundError, FileExistsError, ValueError) as exc:
        print(f"research-template error: {exc}", file=sys.stderr)
        return 1
```

### 3.2 行为等价性约束

| 路径 | HEAD 行为 | Erratum 行为 | 等价? |
|---|---|---|---|
| 已知 action, runner 正常返回 0 | return 0 | return 0 | ✓ |
| 已知 action, runner 抛 FileNotFoundError | stderr "research-template error: ..." + return 1 | stderr "research-template error: ..." + return 1 | ✓ |
| 已知 action, runner 抛 ValueError | 同上 | 同上 | ✓ |
| 已知 action, runner 抛 FileExistsError | 同上 | 同上 | ✓ |
| 未知 action | return 1 (无日志) | stderr + return 1 | ⚠️ 新增 stderr 行为 |

**erratum 选择**: 未知 action 新增 stderr 输出是可接受的行为增强（不改变退出码，只增加诊断信息），但 plan 应明确记录此差异，或保持 HEAD 的无输出行为:

```python
        if runner is None:
            return 1  # 与 HEAD 完全一致：无 stderr，return 1
```

### 3.3 runner None 触发 — 两种选项

**选项 A（完全保持 HEAD 行为，推荐）**: 未知 action 无 stderr、return 1:

**选项 B（新增 stderr 但保持 return 1）**: 未知 action 有 stderr、return 1:

### 3.4 Log.error → print 保持

Plan 应删除 entry example 中的 `Log.error(...)` 和 `MODULE` 引用，改用 HEAD 的 `print(..., file=sys.stderr)` 模式。或者:

如果 plan 确实希望引入 `Log`，则:

2. 定义 `MODULE = "APP.RESEARCH_TEMPLATE"` 或类似常量

## 4. Protocol / DayuCliArguments / mapping / 签名审计

### 4.1 DayuCliArguments runtime identity

**当前**: `parse_arguments() -> argparse.Namespace`，返回普通 Namespace。

**Plan**: `parse_arguments() -> DayuCliArguments`，通过 `parser.parse_args(namespace=DayuCliArguments())` 返回子类实例。

**审计**: `argparse.ArgumentParser.parse_args(namespace=...)` 确实会在传入的 namespace 对象上设置属性并返回同一对象。如果 `DayuCliArguments` 继承 `argparse.Namespace`，此机制正确返回子类实例。`isinstance(result, DayuCliArguments)` 应为 True。无 gap。

### 4.2 ResearchTemplateDispatchArguments Protocol

**Plan 定义** (lines 1500–1503):
```python
class ResearchTemplateDispatchArguments(Protocol):
    research_template_action: str
```

**审计**: Protocol 只声明 `research_template_action: str`。HEAD 的 runner 还通过 `getattr(args, "name", ...)` 等访问其他字段（如 `_run_scorecard` 的 `name`、`json`）。这些字段不在此 Protocol 中。

**分析**: Protocol 的定位是 "dispatch 层需要的最小字段集"，不是 "runner 需要的全部字段"。runner 接收 `DayuCliArguments`（有全部字段），Protocol 只约束 dispatch helper。无 gap。但 plan 应在注释中明确: "Protocol 仅覆盖 dispatch 路径；runner 使用完整 `DayuCliArguments`，Protocol 不约束 runner 的字段访问"。

### 4.3 39 mapping entries vs 39 argparse subparser choices

**审计**: Plan mapping (lines 1551–1591) 的 39 key 与 `arg_parsing.py:_register_research_template_subcommands` (line 1463) 注册的 39 个 subparser choices 一一对应。测试 `test_parser_choices_match_action_runner_map` (test_write_cli_dispatch.py:1386–1425) 验证此一致性。

**注意**: Slice 10 引入 mapping 后，此测试应从验证 if-chain 一致性改为验证 mapping 一致性。Plan (line 1609) 已提及: "39-key parser→selector→runner 参数化矩阵"。

### 4.4 DayuCliArguments 字段完整性

**审计**: `DayuCliArguments(argparse.Namespace)` 类体为空（只有 docstring）。所有字段由 `argparse` 的 `parse_args` 动态写入。这意味着:
- pyright 不会在 `DayuCliArguments` 上检查字段存在性
- Protocol 的静态检查只对显式声明的 Protocol 方法/属性有效
- 运行时 `getattr` / 直接访问依赖 parser 注册正确性

这不是 gap — 是 `argparse.Namespace` 子类的固有特性。Plan 通过 targeted rg gate 和 runtime isinstance 测试弥补。

### 4.5 签名传播表完整性

Plan (lines 1529–1537) 列出的传播目标:

| 模块 | 目标 | 当前 | 目标 | 验证 |
|---|---|---|---|---|
| arg_parsing.py | parse_arguments() 返回 | `argparse.Namespace` | `DayuCliArguments` | ✓ |
| research_template.py | run_research_template_command | `argparse.Namespace` | `DayuCliArguments` | ✓ |
| research_template.py | 39 _run_* runners | `argparse.Namespace` | `DayuCliArguments` | ✓ |
| write.py | run_write_command | `argparse.Namespace` | `DayuCliArguments` | ✓ |
| _write_config_application.py | 2 函数 | `argparse.Namespace` | `DayuCliArguments` | ✓ |

合计: 1 + 1 + 39 + 1 + 2 + 2 = 46 个签名 + 1 返回类型 = 47 个变更点。Plan 说 45 + 1 = 46 (lines 1538)。差 1 — 因为 plan 将 `_write_config_application.py` 的 2 函数和 `_write_snapshot_builder.py` 的 2 函数分开计数，但 write entry 本身是 1，加上 parse_arguments 返回是 1。实际应为 1(parse_arguments 返回) + 1(write entry) + 39(runners) + 2(config_application) + 2(snapshot_builder) + 1(rt entry) = 46。Plan 的 45 + 1 与此一致（45 是 args 签名，1 是 parse_arguments 返回）。无 gap。
