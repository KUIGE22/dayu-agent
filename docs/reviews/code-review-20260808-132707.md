## Findings

### F-01: Phase F bare `assert` 在 `-O` 模式下被消除

**Severity**: HIGH
**File**: `dayu/cli/commands/write.py:631`
**Status**: OPEN

```python
if bool((args.routing_challenger_run_approval_input or "").strip()):
    assert challenger_run_plan is not None
    run_approval_exit_code = _verify_and_consume_challenger_run_approval_before_host(...)
```

`assert` 在 `python -O` 下被完全消除。若生产环境以优化模式运行，`challenger_run_plan` 为 `None` 时将直接传入 `_verify_and_consume_challenger_run_approval_before_host`，行为取决于该函数对 `None` plan 的容错能力。设计意图是 fail-loud，但 `assert` 不是生产级 fail-loud 机制。

**建议**: 替换为显式 `if challenger_run_plan is None: raise RuntimeError(...)` 或 `raise AssertionError(...)` 显式抛出，不受 `-O` 影响。注意：HEAD 原代码同样使用 `assert`，此问题在 Slice 11 之前已存在，但 review scope 内应标记。

### F-02: Phase H materialize `except Exception` 过宽

**Severity**: HIGH
**File**: `dayu/cli/commands/write.py:1002`
**Status**: OPEN

```python
except Exception as exc:  # noqa: BLE001
    Log.error(f"研究工件 materialize 失败: {type(exc).__name__}: {exc}", module=MODULE)
    return 2
```

docstring 声明捕获 `OSError/ValueError/FileNotFoundError/FileExistsError/RuntimeError`，但实际捕获所有 `Exception`。虽然注释解释了设计意图（write report 已落盘，materialize 失败是 partial success），但这会掩盖 `KeyboardInterrupt` 之外的所有异常，包括 `SystemExit`（虽然是 BaseException 不被捕获）、编程错误（`TypeError`, `AttributeError`）和数据损坏（`pickle.UnpicklingError`）。

**建议**: 收窄为 `except (OSError, ValueError, FileNotFoundError, FileExistsError, RuntimeError) as exc`，与 docstring 声明的五类异常对齐。保留 `# noqa: BLE001` 注释移除。HEAD 原代码使用同样写法，此问题在 Slice 11 之前已存在。

### F-03: 测试 fixture 与 Protocol 字段紧耦合

**Severity**: MEDIUM
**File**: `tests/application/test_write_cli_dispatch.py:118-171`
**Status**: OPEN

`_make_write_args` 手动枚举全部 20+ dispatch 字段的默认值。若 `WriteDispatchArguments` Protocol 新增字段，此 fixture 不会自动失效——测试可能因新字段未初始化而产生 AttributeError，但不会明确指出"fixture 缺少新字段"。

**建议**: 在 `TestWritePhaseTableStructure` 中增加一项 AST 测试，断言 `_make_write_args` 的 base dict keys 超集覆盖 `WriteDispatchArguments` 的全部字段。这样新增字段时测试会立即失败并明确指出遗漏。

### F-04: summary 路径 10 处 `getattr` + `Path.resolve()` 重复模式

**Severity**: MEDIUM
**File**: `dayu/cli/commands/write.py:640-755`
**Status**: OPEN

summary 路径有 10 个完全同构的 getattr + None check + Path resolve 块：

```python
raw_xxx = getattr(args, "xxx", None)
xxx = Path(str(raw_xxx)).expanduser().resolve() if raw_xxx else None
```

每块 4 行，共 40 行样板代码。新增 routing/challenger 字段时必须在此处同步添加，遗漏会导致 `None` 被传给 `WriteService.print_report`。

**建议**: 抽取 `_resolve_optional_path(args: argparse.Namespace, attr: str) -> Path | None` 私有辅助函数。10 处调用变 10 个单行，新增字段只需加一行调用。

### F-05: `_install_write_baseline_mocks` 覆盖全量 16 runner 的维护成本

**Severity**: MEDIUM
**File**: `tests/application/test_write_cli_dispatch.py:177-356`
**Status**: OPEN

该 helper mock 了全部 16 个 runner + 基础设施（7 个 monkeypatch），为后续 20+ 测试提供基础。新增 runner 时必须同步更新 `_phase_a_runners` / `_phase_b_runners` 列表、sentinels 和 call_counts，否则新 runner 不会被 mock 而可能导致测试访问真实依赖。

**建议**: 与 F-03 同源——增加 AST 断言验证 `_phase_a_runners` + `_phase_b_runners` 的 runner_attr 集合与 `write.py` 中 `_adapter` 后缀函数集合精确匹配。当前 `test_phase_tables_bind_exact_adapter_order` 已验证 table 结构，但未验证 mock helper 的完整性。

### F-06: Phase A `_build_execution_options` 调用不一致

**Severity**: LOW
**File**: `dayu/cli/commands/write.py:247,268,346`
**Status**: OPEN

Phase A 14 个 entry 中，只有 3 个（clear/verify/recover）在 adapter 内联调用 `_build_execution_options`，其余 11 个不调用。这不是 bug——设计意图是只有需要 `execution_options` 的 runner 才构造。但这意味着如果未来某个"不需要 execution_options"的 runner 变为需要，必须同时修改 adapter 函数和测试的 `calls_beo` 参数，两处修改不同步会导致测试通过但生产行为不一致。

**建议**: 可接受当前设计。文档化"adapter 是否调用 `_build_execution_options` 必须与 runner 签名同步"的约束。当前测试已逐路径断言 `beo` 调用次数，足够防护。

**Status**: OPEN

### F-08: 16 个 adapter 是纯透传 wrapper

**Severity**: LOW
**File**: `dayu/cli/commands/write.py:82-391`
**Status**: OPEN

16 个 adapter 中，13 个是纯透传（`return _run_xxx(args=ctx.args, paths_config=ctx.paths_config)`），仅 3 个在透传前调用 `_build_execution_options`。这些 wrapper 的唯一价值是将 `_WriteCommandContext` / `_WriteConfigurationContext` 解包为底层 runner 的 keyword args。

**建议**: 可接受当前设计。adapter 的存在价值是：(1) 类型边界——phase table 的 `runner` 签名统一为 `Callable[[Context], int]`；(2) 3 个 adapter 有额外逻辑（构造 execution_options）。若未来 runner 签名统一接受 context 对象，adapter 可消除。当前不建议改动。
