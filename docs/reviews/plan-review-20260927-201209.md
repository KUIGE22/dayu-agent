## Assumptions tested

1. **动机及真因**：当前 `_auth_row` 确实把 64 位 hash 作为 SQL bind；平台 Engine `hide_parameters=False`，`echo=False` 不能阻断 SQLAlchemy INFO 参数日志。增补只解决既有 §3.3 的明示保密要求，动机成立。
2. **同一连接保证**：增补 §3.2 要求先取本次事务 `Session.connection()`，核 `Connection.engine.hide_parameters is True`，再在该 `Connection` 运行 SET LOCAL、readback 与授权 SELECT。当前代码使用 `Session.execute`，增补明确要求改到已核的 Connection，避免只检查默认 bind 而改用另一 bind。对现有 SQLAlchemy 版本做最小 API 检查：事务内两次 `Session.connection()` 为同一对象，`Connection.engine.hide_parameters=True` 可读取；这只证明 API 形状，不替代计划中的真 PG 测试。
3. **fail closed 与异常**：`hide_parameters=False` 的外部 Session 必须在 hash-bound SELECT 前以固定 storage 错结束；hash 可先在内存形成，但不能成为 SQL bind。SQLAlchemy 连接/SQL 故障仍在 except 外生成固定异常，原异常链不可外露。真实 PG INFO logger 正反例、无授权 SELECT 事件计数、回滚复用均已列为验收。
4. **授权语义不漂移**：两个动作各保留一条普通授权 SELECT；SET LOCAL/readback、READ COMMITTED、token-derived 见证、grant 排序和撤销快照继承 V9。增补不改 issuer/API、0001–0007 或六表。
5. **范围及顺序**：V9 §2 未包含 `db.py`。增补 §2 只增加该文件的 Engine 参数与 docstring、S31-Auth 当前文件的最小修复；§4 规定独立 planreview、Controller 接受和单独 commit 后才修代码、验 PG、再独立 code re-review，旧 M 不因计划通过而关闭。该序列没有让 S31-A 提前开始。

## Required lenses

- **Architecture boundary**：变更限 storage 基础设施与私有 auth helper，不新增公开认证入口或反向依赖；没有越到 Fins/issuer/迁移。
- **Best practice / optimal solution**：仅依赖 `echo=False` 或 README 约定无法约束 Engine INFO logger。受控 factory 的 `hide_parameters=True` 加 helper 对外部 Session 的实际 bind 校验，分别覆盖默认与非默认连接；用 INFO 日志实测而非静态断言收尾。
- **Overengineering / overcoupling**：`db.py` 的 Engine 级参数隐藏会影响平台全部 Engine 的参数可观察性，这是该工厂统一的敏感参数边界；增补未引入 wrapper、全局日志过滤器、数据库函数或新协议。测试仍区分通用 SQLAlchemy 日志实验与 PG RLS/授权事实。
- **Failure and sequencing**：连接获取、未隐藏 Engine、SQL 失败及 READ COMMITTED 撤销场景均有失败路径；增补明确异常链与调用者事务回滚。它不宣称能阻止可信进程自定义 event hook 主动记录参数，边界与 V9 的 trusted app-role 进程一致。
