## 2. Findings

### 2.1 F-01 HIGH: Slice 6 前向依赖未声明的 `DayuCliArguments`

**位置**: 计划 §5 Slice 6（line 960）

**问题描述**:

Slice 6 定义 `_write_snapshot_builder.py` 的新函数签名为：

```python
def _build_snapshot_for_args(
    args: DayuCliArguments, *, paths_config: WorkspaceConfig,
    execution_options: ExecutionOptions, run_label: str = "configuration-application"
) -> Mapping[str, ModelConfigJsonValue]:
```

但 `DayuCliArguments` 在 Slice 6 执行时不存在。该类型应定义在 `dayu/cli/arguments.py` 中（计划 §2.1 line 389），而没有任何 Slice 显式承担创建该文件的职责。

**依赖链分析**:

```
Slice 6  _build_snapshot_for_args(args: DayuCliArguments)  ← 类型不存在
Slice 10 _RESEARCH_TEMPLATE_ACTION_DISPATCH: Mapping[str, Callable[[DayuCliArguments], int]]  ← 类型不存在
Slice 11 _WriteCommandContext.args: DayuCliArguments  ← 类型不存在
         from dayu.cli.arguments import DayuCliArguments, WriteDispatchArguments  ← 文件不存在
```

计划 §0 Protocol Spike 验证了 `WriteDispatchArguments` Protocol 的 pyright 行为，但 Spike 使用的是临时文件 `/tmp/protocol_spike_*.py`，未在仓库中创建 `arguments.py`。计划 header 说"（已定义）"（line 1021），但源码中不存在。

**影响**:

- Slice 6 commit 若严格按计划执行，pyright 会报 `DayuCliArguments` 未定义
- 实施者被迫在 Slice 6 临时创建空子类或改用 `argparse.Namespace`，引入计划未覆盖的实现决策
- 如果实施者在 Slice 6 前偷偷创建 `arguments.py`，则破坏了 Slice 的原子性承诺

**当前代码实际情况**:

`_build_fresh_application_routing_snapshot`（`write.py:481`）的 `args` 参数仅传递给 `setup_write_config(args, ...)`，后者通过 `getattr(args, ...)` 访问字段。整个调用链不需要 `DayuCliArguments` 特有的任何属性或方法——`argparse.Namespace` 完全足够。

### 2.2 F-02 MEDIUM: `DayuCliArguments` 创建职责隐式漂移

**位置**: 计划 §2.1（line 389）、§5 Slice 10（line 1021）、§5 Slice 11（line 1098–1139）

**问题描述**:

计划的目标文件结构（§2.1）列出了 `arguments.py` 及其内容：

```
dayu/cli/
├── arguments.py    # DayuCliArguments(argparse.Namespace)
│                   #   + WriteDispatchArguments(Protocol)
│                   #   + ResearchTemplateDispatchArguments(Protocol)
```

但没有对应的 Slice 声明"创建 `arguments.py`"。相关引用分散在：

- Slice 0（line 561）: 测试"构造 `DayuCliArguments`"——隐式假设类型已存在
- Slice 6（line 960）: `_build_snapshot_for_args(args: DayuCliArguments)`——类型注解
- Slice 10（line 1021–1035）: Protocol 定义 + dispatch mapping 使用 `DayuCliArguments`
- Slice 11（line 1098–1139）: Protocol 定义 + context dataclass + `from dayu.cli.arguments import`

计划对 `arguments.py` 的定位是"仅定义数据类型，零 import `dayu.cli` 模块"（line 463, 1787），这是一个纯数据模块。但它应该在哪个 Slice 创建？

**最可能的隐含假设**: 计划认为 `arguments.py` 在 Protocol Spike（§0）阶段已经"锁定"，实施时作为 Slice 10/11 的一部分创建。但 Slice 6 先于 Slice 10 执行，形成了时间线矛盾。

## 3. 最小 v4.8 修正方案评估

### 3.1 方案 A（推荐）: Slice 6 使用 `argparse.Namespace`，`arguments.py` 创建归 Slice 10

**变更**:

1. **Slice 6**（line 960）: `_build_snapshot_for_args` 签名改为 `args: argparse.Namespace`
   - 理由: 当前 `_build_fresh_application_routing_snapshot` 已经使用 `argparse.Namespace`，snapshot builder 的实际调用链（`setup_write_config` → `getattr(args, ...)`）不需要 `DayuCliArguments`
   - 同时将 `execution_options: ExecutionOptions` 和 `Mapping[str, ModelConfigJsonValue]` 类型修正保留（这些类型已存在）

2. **Slice 10**（新增前置步骤）: 创建 `dayu/cli/arguments.py`，定义：
   ```python
   class DayuCliArguments(argparse.Namespace):
       """CLI 参数容器，强类型替代 argparse.Namespace。"""
       pass

   class ResearchTemplateDispatchArguments(Protocol):
       research_template_action: str
   ```

3. **Slice 10**: dispatch mapping 使用 `Callable[[DayuCliArguments], int]`，`run_research_template_command` 签名从 `argparse.Namespace` 改为 `DayuCliArguments`

4. **Slice 11**: `WriteDispatchArguments` Protocol 定义、context dataclass、`from dayu.cli.arguments import` 均在本 Slice 创建

5. **`arg_parsing.py`**: `parse_arguments()` 返回类型从 `argparse.Namespace` 改为 `DayuCliArguments`（Slice 10 或 11）

6. **`main.py`**: 无需修改（`args` 的传递链自然通过）

**优点**:
- 每个 Slice 的类型依赖都在本 Slice 或更早 Slice 中满足
- Slice 6 不引入前向依赖
- `DayuCliArguments` 创建时机与其首次语义需求（dispatch mapping 需要精确类型注解）对齐
- 零空子类/cast/glue

**风险**:
- Slice 10/11 需要同时修改 `arg_parsing.py` 和 `main.py` 的类型签名（但这是计划的隐含预期）

### 3.2 方案 B: Slice 6 前置创建 `arguments.py`（仅 `DayuCliArguments` 空子类）

**变更**: Slice 6 commit 前先创建 `arguments.py`，定义 `DayuCliArguments(argparse.Namespace): pass`

**缺点**: 创建空子类仅为了类型注解，违反"禁止兼容性 wrapper"约束；`DayuCliArguments` 在 Slice 10/11 才有语义内容

### 3.3 方案 C: 不创建 `DayuCliArguments`，全文使用 `argparse.Namespace`

**变更**: 删除计划中所有 `DayuCliArguments` 引用，统一使用 `argparse.Namespace`

**缺点**: 丢弃了计划的类型安全设计意图（Protocol dispatch 需要精确类型）

## 4. 审计: Slice 10/11 的 `DayuCliArguments` 使用

### 4.1 Slice 10 — `DayuCliArguments` 使用点

| 位置 | 使用方式 | 是否需要 `DayuCliArguments` |
|---|---|---|
| `_RESEARCH_TEMPLATE_ACTION_DISPATCH` 值类型 | `Callable[[DayuCliArguments], int]` | 是（dispatch 签名一致性） |
| `run_research_template_command` 参数 | `args: DayuCliArguments` | 是（与 dispatch mapping 对齐） |
| `_resolve_research_template_action` 参数 | `args: ResearchTemplateDispatchArguments` | 否（Protocol，不依赖 `DayuCliArguments`） |
| 39 个 `_run_*` 函数参数 | 未在计划中显式标注 | 需确认 |

**关键**: 39 个 `_run_*` runner 在当前代码中签名均为 `(args: argparse.Namespace)`（或无注解）。Slice 10 若将 dispatch mapping 值类型声明为 `Callable[[DayuCliArguments], int]`，则 39 个 runner 签名也需要同步修改为 `DayuCliArguments`，或者 `DayuCliArguments` 必须是 `argparse.Namespace` 的子类（当前方案）。由于 `DayuCliArguments` 计划为 `argparse.Namespace` 的子类，协变性允许 `Callable[[DayuCliArguments], int]` 赋值给 `Callable[[argparse.Namespace], int]`，但反向不行——因此 dispatch mapping 的值类型必须使用 `DayuCliArguments`，runner 签名也必须使用 `DayuCliArguments`。

### 4.2 Slice 11 — `DayuCliArguments` 使用点

| 位置 | 使用方式 | 是否需要 `DayuCliArguments` |
|---|---|---|
| `from dayu.cli.arguments import DayuCliArguments, WriteDispatchArguments` | import | 是 |

| `_WriteConfigurationContext.args` 类型 | `DayuCliArguments` | 是 |
| `run_write_command` 参数 | `args: DayuCliArguments` | 是 |
| `_EarlyWriteSubcommandEntry.runner` | `Callable[[_WriteCommandContext], int]` | 间接 |
| `_ConfigurationWriteSubcommandEntry.runner` | `Callable[[_WriteConfigurationContext], int]` | 间接 |

| 16 adapter 函数 | 参数为 context dataclass | 间接 |

### 4.3 测试注解

Slice 0 测试（line 561）提到"构造 `DayuCliArguments`"——这在当前 HEAD 下实际是构造 `argparse.Namespace`（因为 `DayuCliArguments` 不存在）。Slice 0 测试应在 Slice 0 执行时使用 `argparse.Namespace`，Slice 10/11 后迁移为 `DayuCliArguments`。计划未说明此迁移。
