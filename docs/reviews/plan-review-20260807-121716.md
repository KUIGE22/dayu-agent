### NN-1 | CLOSED | `asyncio.shield` 重复取消穿透

**Closure Evidence**: v4 §6 删除双重 shield，改为 `while not release_task.done(): try/except CancelledError/continue` 循环。伪代码逻辑正确：有限次 cancel 只记录第一份并 continue，worker 完成后才传播。§6 语义表覆盖零次/单次/重复/worker 异常/to_thread 失败场景。

**补充验证**:
- `task.exception()` 对 cancelled task 抛 `CancelledError` 而非返回异常对象（Python API）。v4 §6 伪代码 `worker_exc = release_task.exception()` 在 worker 被 cancel 时会直接抛 `CancelledError`，不会走到 `if worker_exc is not None`。这在 shield 保护下不会发生（release_task 不会被 cancel），但若 `to_thread` 提交失败导致 release_task 立即以异常完成，`exception()` 会正确返回异常对象。语义正确。

## New Findings

### NN-2a | 未修复 | 严重度: MEDIUM | monkeypatch `_start_run` 泄漏原始 CancellationBridge/RunDeadlineWatcher

**位置**: v4 §9 Slice 3 测试代码

**问题类型**: 测试资源泄漏

**当前写法**:
```python
original_start_run = executor._start_run

def _patched_start_run(*, spec, run_id, include_agent_lane):
    result = original_start_run(
        spec=spec, run_id=run_id, include_agent_lane=include_agent_lane,
    )
    executor._run_resources[run_id] = _RunResources(
        bridge=bridge,  # 覆盖为 blocking bridge
        deadline_watcher=_NoopWatcher(),
        permits=[],
    )
    return result
```

**问题**:
1. `original_start_run` 创建真实的 `CancellationBridge`（启动 polling thread）和 `RunDeadlineWatcher`（启动 timer）
2. 覆盖 `_run_resources[run_id]` 后，原始 bridge 的 polling thread 和 watcher 的 timer 继续运行
3. 原始资源永远不会被 `stop()`/`cancel()`，造成线程/timer 泄漏
4. 测试结束后 daemon 线程残留，timer 可能触发意外行为

**直接证据**:
- `executor.py:1455-1461`: `_start_run` 创建 `CancellationBridge` 并调用 `bridge.start()`
- `executor.py:1462-1467`: `_start_run` 创建 `RunDeadlineWatcher` 并调用 `watcher.start()`
- 覆盖 registry entry 后，原始 bridge/thread 引用丢失

**影响**:
- 测试中 daemon 线程和 timer 泄漏
- 可能导致后续测试出现意外行为（timer 回调、bridge polling）
- CI 中线程数累积可能导致资源耗尽

**建议改法**:
```python
# 方案 A：不调用 original_start_run，直接构造所需对象
def _patched_start_run(*, spec, run_id, include_agent_lane):
    # 不调用 original_start_run，避免创建真实资源
    # 直接构造最小 HostedRunContext
    context = HostedRunContext(...)  # 需要构造最小上下文
    return context, bridge, _NoopWatcher(), []

# 方案 B：调用 original_start_run 后立即 stop 原始资源
def _patched_start_run(*, spec, run_id, include_agent_lane):
    result = original_start_run(...)
    context, orig_bridge, orig_watcher, orig_permits = result
    orig_bridge.stop()  # 立即停止原始 bridge
    orig_watcher.stop()  # 立即停止原始 watcher
    executor._run_resources[run_id] = _RunResources(
        bridge=bridge,
        deadline_watcher=_NoopWatcher(),
        permits=[],
    )
    return context, bridge, _NoopWatcher(), []
```

**验证点**: 运行测试后检查活跃线程数是否增加

**修复风险**: LOW — 方案 B 只需加两行

**严重度**: MEDIUM — 测试资源泄漏，可能导致 flaky

**标签**: `accepted-candidate`

### NN-8 | 未修复 | 严重度: LOW | `release_task.exception()` 对 cancelled task 抛异常而非返回

**位置**: v4 §6 伪代码注释

**问题类型**: Python API 行为描述不精确

**当前写法** (v4 §6 语义表):
> worker 自身 cancelled | `worker_exc` 是 `CancelledError` → raise 它（inner 状态传播）

**实际行为**:
```python
# task.exception() 对 cancelled task 抛 CancelledError，不返回异常对象
task = asyncio.create_task(asyncio.sleep(10))
task.cancel()
await asyncio.sleep(0)
task.exception()  # 抛 CancelledError，不返回
```

**影响**:
- 在 shield 保护下 `release_task` 不会被 cancel，此路径实际不可达
- 若 `to_thread` 提交失败导致 `release_task` 以异常完成，`exception()` 正常返回异常对象
- 语义正确，但注释误导

**建议改法**: 修正注释为"worker 被 cancel 时 `exception()` 直接抛 `CancelledError`（shield 下不可达）"

**验证点**: Python API 文档确认

**修复风险**: N/A — 仅注释

**严重度**: LOW — 不影响正确性

**标签**: `defer-candidate`
