## Findings

### F-1 | 未修复 | 严重度: HIGH | async generator finally 块实际支持 await

**位置**: Plan §2.3 "为什么不能一刀切改成 async"

**问题类型**: 事实错误导致方案选择偏差

**当前写法**:
> Python 的 `async generator` finally 块不支持 `await`，无法在其中直接调用 async release

**反例**:
```python
# Python 3.11+ 中 async generator finally 块完全支持 await
async def my_gen():
    try:
        yield 1
    finally:
        await asyncio.sleep(0.1)  # 合法，不会抛异常
```

**直接证据**:
- Python 3.11 release notes: "PEP 654 – Exception Groups and `except*`" 配合 async generator 改进
- CPython 源码 `Objects/genobject.c` 中 `_PyAsyncGenValueWrapperNew` 处理
- 实际测试可在 Python 3.11 REPL 中验证

**影响**:
- 计划的基础假设之一被推翻
- 方案 A（新增 `signal_stop()` + 事件循环检测）的必要性降低
- 可以直接在 async finally 中 `await bridge.async_stop()` 而无需运行时检测

**建议改法**:
1. 在 async 路径中新增 `async def async_stop(self) -> None` 方法
2. 在 `_release_resources` 中区分同步/异步调用者，或提供两个版本的 release 方法
3. 无需 `asyncio.get_running_loop()` 运行时检测

**验证点**:
```python
import asyncio
async def test_finally_await():
    async def gen():
        try:
            yield
        finally:
            await asyncio.sleep(0)
            print("finally await works")
    async for _ in gen():
        pass
asyncio.run(test_finally_await())
```

**修复风险**: LOW — 需要重构方案但逻辑更清晰

**严重度**: HIGH — 基础假设错误导致方案选择偏差

**标签**: `accepted-candidate`

### F-2 | 未修复 | 严重度: MEDIUM | `asyncio.get_running_loop()` 运行时检测的脆弱性

**位置**: Plan §5.2, §6 方案 A

**问题类型**: 运行时猜测替代显式标记

**当前写法**:
```python
try:
    asyncio.get_running_loop()
    resources.bridge.signal_stop()  # 事件循环上：不阻塞
except RuntimeError:
    resources.bridge.stop()  # 非事件循环：完整 join
```

**反例**:
1. 在 `run_operation_sync` 中，如果调用者恰好在一个有事件循环的线程中（如 Jupyter notebook），`get_running_loop()` 不会抛异常，会错误走 `signal_stop()` 路径
2. 在嵌套事件循环场景中（如 `nest_asyncio`），检测结果不可靠
3. 信号处理器中调用时，事件循环状态不确定

**直接证据**:
- `executor.py:475` 的 `run_operation_sync` 是同步方法，但计划 §4 路径区分表显示它与 async 路径共享 `log_origin="finish_run"`
- 计划 §21 Residual Risks 承认此风险但未给出确定性解决方案

**影响**:
- 同步路径可能误走 `signal_stop()` 路径，导致线程清理不确定
- 调试困难：行为取决于运行时环境而非代码路径

**建议改法**:
1. **显式标记方案**：在 `_release_resources` 中增加 `is_async: bool` 参数，由调用者显式传入
2. **双方法方案**：提供 `_release_resources_async()` 和 `_release_resources_sync()` 两个方法
3. **上下文方案**：使用 `contextvars.ContextVar` 标记当前是否在异步上下文

**验证点**:
- 在 Jupyter notebook 中测试 `run_operation_sync` 是否走对路径
- 在嵌套事件循环中测试行为

**修复风险**: MEDIUM — 需要修改更多调用点

**严重度**: MEDIUM — 运行时行为不确定

**标签**: `needs-evidence`

### F-3 | 未修复 | 严重度: MEDIUM | `signal_stop()` 不清理 `_thread` 引用

**位置**: Plan §8 Slice 1

**问题类型**: 状态管理不完整

**当前写法**:
```python
def signal_stop(self) -> None:
    self._stop_event.set()
    # 不设 self._thread = None
```

**反例**:
```python
bridge.start()
bridge.signal_stop()
# 此时 bridge._thread 仍指向已退出的线程对象
# 如果代码检查 bridge._thread is not None 判断是否启动过，会误判
```

**直接证据**:
- `cancellation_bridge.py:79` 定义 `self._thread: threading.Thread | None = None`
- `start()` 方法 `:87` 检查 `if self._thread is not None and self._thread.is_alive()`
- `stop()` 方法 `:107` 设置 `self._thread = None`

**影响**:
- 对象状态不一致：`_thread` 非 None 但线程已退出
- 如果后续代码依赖 `_thread is None` 判断"已停止"，会误判
- 虽然 `stop()` 可以安全处理（`is_alive()` 返回 False），但状态语义不清

**建议改法**:
1. 在 `signal_stop()` 中也设置 `self._thread = None`（线程引用不再需要）
2. 或在 `_poll_loop` 退出时自行清理 `self._thread = None`（需要锁保护）
3. 或明确文档说明 `signal_stop()` 后 `_thread` 语义是"最后一次启动的线程引用"

**验证点**:
- 测试 `signal_stop()` 后 `bridge._thread` 的状态
- 测试 `signal_stop()` 后再 `start()` 是否正常

**修复风险**: LOW — 状态清理逻辑简单

**严重度**: MEDIUM — 状态语义不清可能导致后续代码错误

**标签**: `accepted-candidate`

### F-4 | 未修复 | 严重度: MEDIUM | monkey-patch `Thread.join` 的可行性未验证

**位置**: Plan §8 Slice 6

**问题类型**: 测试方案可行性存疑

**当前写法**:
```python
bridge._thread.join = spy_join  # type: ignore[method-assign]
```

**反例**:
- CPython 中 `Thread.join()` 是用 C 实现的 (`_thread.start_new_thread`)，可能无法被 Python 层 monkey-patch
- 不同 Python 实现（PyPy, Jython）行为可能不同

**直接证据**:
- `threading.py` 源码中 `Thread.join()` 是纯 Python 方法，理论上可 patch
- 但 `type: ignore[method-assign]` 注释暗示 pyright 已警告此操作

**影响**:
- 如果 monkey-patch 失败，核心回归测试无法工作
- 测试可能在某些环境下 pass，在其他环境下 fail

**建议改法**:
1. **Mock 方案**：使用 `unittest.mock.patch.object(Thread, 'join')` 替代直接赋值
2. **子类方案**：创建 `_SpyThread(Thread)` 子类，重写 `join()` 方法
3. **验证方案**：先写一个最小测试验证 monkey-patch 在目标 Python 3.11 上可行

**验证点**:
```python
import threading
t = threading.Thread(target=lambda: None)
t.start()
original_join = t.join
t.join = lambda timeout=None: original_join(timeout=timeout)
t.join(timeout=1.0)  # 是否成功？
```

**修复风险**: LOW — 有多个备选方案

**严重度**: MEDIUM — 测试基础设施可靠性

**标签**: `needs-evidence`

### F-8 | 未修复 | 严重度: INFO | atomic-pop 后 await 遭 cancellation 的语义

**位置**: Plan §10

**问题类型**: 未覆盖的边界场景

**当前写法**:
> atomic-pop 在 `_release_resources` 调用之前完成，两个路径共享同一把锁

**反例**:
```python
# 场景：atomic-pop 成功后，await 之前被取消
with self._run_resources_lock:
    resources = self._run_resources.pop(run_id, None)
# <-- 此处如果发生 cancellation（如 asyncio.Task.cancel()）
await resources.bridge.async_stop()  # 永远不会执行
```

**直接证据**:
- Python asyncio 中，`await` 点是 cancellation 的检查点
- 如果使用 F-1 建议的 async 方案，需要考虑此场景

**影响**:
- 资源可能泄漏（bridge 线程未停止）
- 但 daemon 线程不阻止进程退出，影响有限

**建议改法**:
1. 在 async release 中使用 `asyncio.shield()` 保护关键清理
2. 或在 `finally` 块中确保清理执行
3. 或保持当前方案（`signal_stop()` 是同步的，无 cancellation 点）

**验证点**:
- 测试 `Task.cancel()` 后资源是否正确清理

**修复风险**: LOW — 有成熟模式处理

**严重度**: INFO — 当前方案已规避（`signal_stop()` 同步）

**标签**: `defer-candidate`

## 最终结论

**FAIL — 存在一个 HIGH 严重度 finding 需要先解决**

计划存在一个基础假设错误（F-1）：Python 3.11 的 async generator finally 块**支持** `await`，这推翻了计划中"为什么不能一刀切改成 async"的核心论点。这导致方案选择可能不是最优的。

**建议**：
1. 先验证 F-1（async generator finally 的 await 支持）
2. 如果验证通过，重新评估方案：直接提供 `async_stop()` + `_release_resources_async()` 可能比 `signal_stop()` + 运行时检测更清晰
3. 解决 F-2（运行时检测脆弱性）和 F-3（状态管理）后再进入实现

**可以带风险继续的前提**：
- 如果团队决定坚持当前方案（`signal_stop()` + 运行时检测），需要：
  1. 明确接受 F-2 的风险并添加 `log_origin == "sigint_release"` 硬覆盖
  2. 补充 F-3 的 `_thread` 清理逻辑
  3. 验证 F-4 的 monkey-patch 可行性
