## Adversarial Failure Review

### 攻击面 1: TypedDict 运行时无强制 → 绕过类型系统

**场景**: 在 `_append_research_workbook_section` 或 `build_research_workbook_payload` 内构造 dict 时，若字段名拼错（如 `"evidenc"` 而非 `"evidence"`），pyright 会报错但运行时静默通过。

**缓解**:
- pyright 零错误验证确保无此行级拼写错误。
- `validate_research_workbook_payload` 对所有字段做运行时校验（`evidence` 键的 list 类型检查在行 321: `isinstance(evidence, list)`）。
- TypedDict 在此处作为静态类型文档和 pyright 检查之用，与运行时 `dict` 构造兼容。

**判定**: 无实际风险。✅

### 攻击面 2: 截断哈希碰撞

**场景**: section_key 仅取 SHA-256 前 10 hex chars（40 bits），item_key 仅取前 12 hex chars（48 bits）。同一模板内碰撞概率极低（40-bit 空间内 ~2^40 约 1 万亿个可能值），且哈希材料包含位置索引进一步降低碰撞。

**缓解**: 碰撞概率 ≈ N²/2^(bits+1)，20 sections × 100 items = 2000 items → 碰撞概率 ≈ 2000² / 2^49 ≈ 4×10⁶ / 5.6×10¹⁴ ≈ 7×10⁻⁹。极低。

**判定**: 可接受风险，与原实现一致。✅

### 攻击面 3: null byte 注入

**场景**: 若 `current_category`、`current_title`、`normalized` 或 `prompt` 包含 `\0`，哈希材料的字段边界会被破坏，可能导致不同输入产生相同哈希。

**缓解**:
- `normalized` 由 `_normalize_template_name` 生成，已 strip+lower，且拒绝 `\`、`/`、`:`、`..`，但不拒绝 null byte。理论上攻击者可构造含 `\0` 的模板名。
- `current_title` 来自模板 Markdown 的 `## ` 行内容，`current_category` 由 `_research_workbook_section_category` 返回，值域为预定义 frozenset（不含 null byte）。
- `prompt` 来自模板 Markdown 行内容，由用户控制。精心构造的模板可注入 null byte。

**严重性评估**: 即使发生哈希碰撞，结果仅影响 ID 唯一性，不会导致数据损坏或安全漏洞。且 `validate_research_workbook_payload` 的 duplicate ID 检查会捕获碰撞。低严重性。

**判定**: 极低风险，且为存量行为（非 W16 引入）。✅

### 攻击面 4: `sections` 参数被外部 code path 修改

**场景**: helper 接收 `sections` 引用并原地修改（`sections.append(...)`）。若未来有调用者在 helper 返回后继续持有 `sections` 引用，可能意外修改已构建的 section 列表。

**缓解**: helper 为模块私有（`_` 前缀），仅有两处调用均在同一 builder 函数内。builder 在 helper 返回后继续追加 sections 是设计意图。无外部 code path。

**判定**: 无风险。✅

### 攻击面 5: coverage 缺口

**场景**: 85.79% branch coverage 意味着有 ~14% 分支未覆盖。未覆盖分支可能隐藏 bug。

**缓解**:
- 15 个 `dict[str, object]` 函数的存量验证逻辑（如 `validate_research_workbook_payload` 的 200+ 行条件分支）是主要未覆盖区域。这些均不在 W16 scope。
- 新增代码（helper + 修改后的 builder）的 3 条路径（early return、正常追加、空 sections）均由 35 项聚焦测试覆盖。

**判定**: 新增代码覆盖率充分。✅
