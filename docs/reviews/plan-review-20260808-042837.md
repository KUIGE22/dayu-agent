## 3. Import DAG 与循环风险分析

### 3.1 Plan 声明的依赖方向

```
write.py → _write_snapshot_builder.py → _write_config_application.py
```

Plan §2.2:
> `_write_snapshot_builder.py` → `_write_config_application.py`：两者在 Slice 6 同一 commit 创建，前者从后者顶层 import，**无反向路径**

### 3.2 循环触发条件

只有当 `_write_config_application.py` 也 import `_write_snapshot_builder.py` 时才会形成：

```
_write_config_application.py ←→ _write_snapshot_builder.py   (CYCLE)
```

具体触发路径：闭包 #1 迁移后在 `_write_config_application.py` 内的 `_run_write_model_configuration_application` 中，如果尝试使用 `build_snapshot_builder` 而非直接 `functools.partial(_build_fresh_application_routing_snapshot, ...)`：

```python
# _write_config_application.py —— 危险写法
from dayu.cli.commands._write_snapshot_builder import build_snapshot_builder  # ← 循环！

def _run_write_model_configuration_application(*, args, paths_config, execution_options):
    snapshot_builder = build_snapshot_builder(   # ← 同一模块已有 _build_fresh...
        args=args, paths_config=paths_config, execution_options=execution_options
    )
```

### 3.3 Plan 中促发歧义的两处措辞

**歧义点 1** — Slice 6 step 3（§5，行 969）:

> `write.py`: 替换 5 处 `_snapshot_builder` 嵌套定义

这个 "5 处" 的表述把闭包 #1（迁移后与 `_build_fresh_application_routing_snapshot` 同模块）与闭包 #2–#5（迁移后分别位于 `write.py`→`_write_manual_recovery.py`/`_write_config_rollback.py`）不加区分地合并。implementation agent 可能解读为"5 处均替换为 `build_snapshot_builder(...)` 调用"，从而把对 `_write_snapshot_builder` 的 import 带进 `_write_config_application.py`。

**歧义点 2** — Ready-for-Review checklist item 13（§11，行 1873）:

> `_write_snapshot_builder.py` 零反向 import

该 gate 只检查 `_write_snapshot_builder.py` 是否反向 import `write.py`，不检查 `_write_config_application.py` 是否反向 import `_write_snapshot_builder.py`。Slice 6 验证 gate table 同样只列了 `_write_snapshot_builder.py` 反向 import `write.py` 为 0。虽然 §2.2 "无反向路径" 的设计意图明确，但 implementation agent 的检查清单中缺少对应的可执行验证命令。

### 3.4 正确实施（方案 A 无循环）

**闭包 #1**（`_write_config_application.py` 内的 `_run_write_model_configuration_application`）:

```python
# _write_config_application.py —— 正确写法（零 import from _write_snapshot_builder）
import functools

def _run_write_model_configuration_application(
    *, args: argparse.Namespace, paths_config: WorkspaceConfig,
    execution_options: ExecutionOptions,
) -> int:
    ...
    snapshot_builder = functools.partial(
        _build_fresh_application_routing_snapshot,
        args=args,
        paths_config=paths_config,
        execution_options=execution_options,
    )
    ...
```

理由：`_build_fresh_application_routing_snapshot` 在同一模块，无需经过 `_write_snapshot_builder` 间接调用。`functools.partial` 与 `build_snapshot_builder` 的 `functools.partial` 工厂行为完全等价——都产生 `Callable[[], Mapping[str, ModelConfigJsonValue]]`，且 `run_label` 均使用默认值 `"configuration-application"`。

**闭包 #2–#5**（`write.py` → 后续 Slice 7/8 迁移至 `_write_manual_recovery.py` / `_write_config_rollback.py`）:

```python
# write.py (_write_manual_recovery.py, _write_config_rollback.py) —— 正确写法
from dayu.cli.commands._write_snapshot_builder import build_snapshot_builder

# 闭包 #2/#3: 使用默认 run_label
snapshot_builder = build_snapshot_builder(
    args=args, paths_config=paths_config, execution_options=execution_options,
)

# 闭包 #4: run_label="configuration-manual-recovery-verification"
snapshot_builder = build_snapshot_builder(
    args=args, paths_config=paths_config, execution_options=execution_options,
    run_label="configuration-manual-recovery-verification",
)

# 闭包 #5: run_label="configuration-manual-recovery-clearance"
snapshot_builder = build_snapshot_builder(
    args=args, paths_config=paths_config, execution_options=execution_options,
    run_label="configuration-manual-recovery-clearance",
)
```

Import DAG 保持无环:
```
write.py ────────────→ _write_snapshot_builder.py ──→ _write_config_application.py
_write_manual_recovery.py ─→ (same direction)
_write_config_rollback.py ──→ (same direction)
_write_config_application.py ──→ (NO import of _write_snapshot_builder)
```

### 3.5 方案对比

| 方案 | 描述 | 循环风险 | 架构后果 |
|---|---|---|---|
| **A** (plan 意图, 推荐) | 闭包 #1 同模块 `functools.partial`；闭包 #2–#5 用 `build_snapshot_builder`。Builder→application 单向 | **无** | 职责清晰，`_write_config_application` 拥有核心 snapshot 构建逻辑，`_write_snapshot_builder` 是薄 factory |
| **B** (反转所有权) | 把 `_build_fresh_application_routing_snapshot` 移入 `_write_snapshot_builder.py` | 需解决 `_write_config_application.py` 对 snapshot builder 的 import——两个模块倒置但仍是单向 | 所有权倒置：~80 行构建逻辑从 application 模块移至 builder 模块，语义不自然（builder 不应拥有"构建"本身）；`_write_config_application.py` 变为仅含 runner 的薄壳；其他 Slice（7/8）函数原本可直接 import application module 的 runner，现在需同时依赖 builder module |
| **C** (DI/callable/lazy import/glue) | 用 `Callable[[...], ...]` 参数注入、`importlib.import_module` 延迟、或 compatibility wrapper | 增加不必要的抽象层 | 违反 plan 自身的零 `Callable[..., ...]` 约束（§4.3 item 6）、零 glue seam 约束（CLAUDE.md）；在已有清晰单向依赖时引入额外复杂度属过度工程 |

**判决**: 方案 A 是唯一与 plan 设计意图一致且满足项目约束的方案。方案 B 所有权语义错误。方案 C 违反项目硬约束。

| 闭包 | 迁移前 `run_label` | 迁移后 `run_label` | 等价性 |
|---|---|---|---|

### 4.3 Callable 类型合规性

`build_snapshot_builder` 返回 `Callable[[], Mapping[str, ModelConfigJsonValue]]` — 精确参数化，不触发 `Callable[..., ...]` 禁令（§4.3 item 6）。`functools.partial` 产生的 `functools.partial` 对象满足 `Callable[[], Mapping[str, ModelConfigJsonValue]]` 协变（零参数 Callable 的返回类型协变）。

## 7. Findings

### 7-01-未修复-中-Slice6-step3-"替换5处"-措辞歧义导致潜在app↔builder循环

- **位置**: §5 Slice 6 step 3, 行 969
- **问题类型**: 不可直接实施
- **当前写法**: `write.py`: 替换 5 处 `_snapshot_builder` 嵌套定义
- **反例/失败场景**: implementation agent 理解为 "5 处全部替换为 `build_snapshot_builder(...)` 调用"。闭包 #1 位于 `_run_write_model_configuration_application`，该函数在 Slice 6 迁移至 `_write_config_application.py`。若在其内使用 `build_snapshot_builder` 而非 `functools.partial(_build_fresh_application_routing_snapshot, ...)`，则 `_write_config_application.py` 需 `from dayu.cli.commands._write_snapshot_builder import build_snapshot_builder`，与 `_write_snapshot_builder.py` 对 `_write_config_application.py` 的 import 形成双向依赖循环
- **为什么有问题**: plan §2.2 明确声明的 "无反向路径" 靠文档意图保证，无精确的可执行实施指引来区分 5 处闭包的不同处置方式。agent 若机械执行 "替换 5 处" 可能漏掉闭包 #1 的同模块特殊性
- **直接证据**:
  1. 源码：闭包 #1（line 567）在 `_run_write_model_configuration_application`（line 534）内——两者同属 Slice 6 迁移目标 `_write_config_application.py`
  2. 源码：闭包 #2–#5（lines 653/959/1037/1126）分属 `_run_write_model_configuration_rollback`/`_run_write_model_configuration_manual_recovery_application`/`_run_write_model_configuration_manual_recovery_verification`/`_run_write_model_configuration_manual_recovery_clearance`——分属 Slice 8/7/7/7 迁移目标，不在 `_write_config_application.py`
  3. Plan：§2.2 声明 `_write_snapshot_builder → _write_config_application`，"无反向路径"
  4. Plan：Ready-for-Review checklist item 13 只检查 `_write_snapshot_builder.py` 零反向 import（`write.py`），不检查 `_write_config_application.py` 不 import `_write_snapshot_builder.py`
- **影响**: 实施 Agent 若误操作 → 产生 app↔builder 循环 → Slice 6 pyright/pytest 可能不报错（Python 支持循环 import 若顶层符号已定义），但 Slice 7/8 后续迁移时循环暴露 → 返工拆循环或引入 lazy import/glue（违反项目硬约束）
- **建议改法和验证点**:
  1. v4.9 erratum 将 Slice 6 step 3 改为：`write.py`: 闭包 #1 随 `_run_write_model_configuration_application` 迁移消失；闭包 #2–#5 替换为 `build_snapshot_builder(...)` 调用
