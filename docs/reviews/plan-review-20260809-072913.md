## 二、逐点复核证据

### 1. owned 集合是否闭合枚举（A1）

第 116 行把 hard gate 作用域写为「仅约束 acceptance harness-owned outputs：`phase-receipts/*.json`、`acceptance-receipt.json`、脱敏后的可提交 baseline 与 completion report」。这是**枚举式**定义，四项与 fix artifact 第 2 节完全一致，且与第 202 行 hard gate 第 9 项的四项列表逐字对应。

关键点在于 owned 集合与生产集合之间不存在灰区：plan 中被验收器写出的对外产物只有这四类（receipt 分阶段与总的两种、脱敏 baseline、completion report），其余 13 产物全部为生产 validator 产出。第 389 行脱敏 baseline 的保留清单（schema、as-of、指纹、维度分数、阈值、usage 汇总、residual 分类、production artifact 的 package-relative locator/SHA-256）也落在 owned 集合内部，不引入第五类载体。**枚举闭合，实施 Agent 无需自行裁决边界归属。**

对照 PRR-002 原始诉求「第 9 项只约束验收器自己生成的 phase receipt、`acceptance-receipt.json`、脱敏 baseline 与 completion report」——四项一一对应，无缺漏、无扩大。

### 2. 生产 artifacts 是否被双向锁定（A2）

PRR-002 的核心风险是「两种自然解法各撞不同约束」：判 FAIL 撞验收目标，改写产物撞第 4.2 节「禁止反向修改 `dayu/` 生产代码来迁就验收器」。修复必须同时堵住两侧，只堵一侧不算修复。逐锚点核对：

| 锚点 | 否定「判 FAIL」 | 否定「改写」 |
|---|---|---|
| 第 116 行 | 「不因其内嵌 package 绝对路径单独判 FAIL」 | 「verifier 不改写这些文件」 |
| 第 202 行 | 「不因该路径单独 FAIL」 | 「不改写」；并限定为「仅做存在性/validator/字节指纹校验」 |
| 第 310 行 | 「不因该字段单独 FAIL」 | 「不改写原字节」；并追加「该测试不递归扫描或 sanitizer-rewrite 生产产物」 |
| 第 599 行 | 「不单独触发该 stop」 | 由「禁止将其内容摘录到 acceptance-owned output」间接覆盖 |

四处均双向锁定。「单独」一词是必要的精确限定——它保留了生产产物因其它原因（validator 失败、指纹不符、缺失）失败的能力，只豁免「内嵌 package 绝对路径」这一条既有行为，不会被误读为对生产产物全面免检。第 202 行「仅做存在性/validator/字节指纹校验」进一步把验收器对生产产物的合法动作正向枚举为三项，byte-identical 由「字节指纹校验」+「不改写」共同保证。**A2 成立，且限定粒度正确，未过度豁免。**

### 3. 引用形状是否只剩 locator + SHA（A3）

第 116 行给出正向形状并附具体示例（`research/assets/research_templates/research-template.manifest.json` + 文件 SHA-256），同时反向禁止「不记录生产 artifact 内嵌路径或其它原文」。第 389 行在 baseline 生成规则中同口径落地：「production artifact 的 package-relative locator/SHA-256；不提交完整 provider 日志、秘密、生产 artifact 内容片段或其内嵌绝对路径」。第 630 行在 completion report 必含项中同口径落地：「对生产 artifacts 仅报告 package-relative locator + SHA-256，不摘录其内嵌绝对路径/内容片段」。第 599 行 stop condition 侧同样写入「禁止将其内容摘录到 acceptance-owned output」。

四个载体（receipt/baseline/report/stop）口径一致，无残留旧表述。第 310 行进一步把禁止摘录的字段具名到 `template_file`/`source_template_file`，与 071911 第 86-87 行给出的两处代码事实精确对应——即 gate 的边界不是抽象的「不泄漏」，而是绑定到已知的具体泄漏载体。**A3 成立。**

值得指出的是修复选择了「禁止摘录内容」而非「摘录后再脱敏」。后者会把 sanitizer 变成对生产内容的改写器，正是 A2 要否定的方向。这个取舍是本次修复中最正确的一步：它让 owned/生产两个域之间只剩一条单向的、无内容流动的引用边（locator + SHA），从根上消除了两约束相撞的可能，而不是给撞击加一层判例。这是解耦而非加规则。

### 4. Slice 1 测试是否有界且双侧（A4）

第 310 行测试契约包含四段，逐段对应一个可失败方向：

1. **扫描域限定**：「只扫描 acceptance harness-owned JSON（phase receipts、acceptance receipt 与脱敏 baseline payload）」——与第 116/202 行 owned 集合一致；
2. **正向断言**：「任一 POSIX/Windows 绝对 home 路径都 fail」——覆盖跨平台两种 home 形状，防止只测 POSIX 的半覆盖；
3. **反向断言**：对含 package 绝对路径的两个生产 fixture，验证「不改写原字节、不因该字段单独 FAIL，且 acceptance receipt/baseline 只产生 package-relative artifact locator + SHA-256，不摘录 `template_file`/`source_template_file`」——同时证明 A2 与 A3；
4. **越界否定**：「该测试不递归扫描或 sanitizer-rewrite 生产产物」——把「有界」本身变成断言对象，而非仅写在散文里。

第 4 段是这条测试契约里最关键的：没有它，实施 Agent 完全可能写出一个递归扫描全 run root 的 sanitizer，happy path 仍然绿，但生产 fixture 一旦被扫到就会重新引爆 PRR-002。把「不做什么」写成可断言的契约，而不是留给实施 Agent 的隐含理解，符合 Controller 要求的 bounded test。

三段断言（正向 fail、反向 byte-identical + 不 FAIL、引用形状）+ 一段越界否定，均为纯本地 fixture 可测，不依赖跨层集成链路，无过度耦合。**A4 成立。**

### 5. completion report 侧未遗漏（补充核验）

第 630 行是 071911 未直接点名、但属于 PRR-002 影响面的载体（第 200 行第 9 项原文即涵盖 completion report）。本次修复已在该行同步写入引用形状约束，未留下「gate 已限定但 report 仍可能摘录」的缺口。**无残留不一致。**
