### 编号-未修复-[严重程度（高）]-S3模式delete-entry在S3模式下对目录删除仅stage-delete直接子级key但目录下可能存在的meta.json等元数据文件未被纳入delete intent

- **入口/函数**: `_FsBlobMixin._delete_entry_impl_s3`
- **文件(行号)**: dayu/fins/storage/_fs_blob_core.py:240-264
- **输入场景**: S3模式下对一个包含多个文件的文档目录调用 `delete_entry`
- **实际分支**: 代码执行 `_stage_delete_one_key(token, key)` 仅记录一个key的delete intent，然后执行 `path.unlink()` 或 `shutil.rmtree()` 移除本地staging目录
- **预期行为**: 按S14-CTRL-13契约，S3模式下的delete_entry应确保所有相关远端对象最终被删除
- **实际行为**: `_stage_delete_one_key` 仅对传入的单个 `final_key` 记录delete intent。若该key是一个目录前缀下的对象，目录下的其他文件（如meta.json、manifest文件等）未被纳入delete intent，这些元数据文件的远端副本将永远留在S3上
- **直接证据**: `_fs_blob_core.py:255` 只调用 `self._stage_delete_one_key(token, key)`，而 `_stage_delete_one_key` 只记录单个key (`_fs_storage_infra.py:367-413`)
- **影响**: 静默数据残留——被删除文档的元数据文件永久留在S3，无法通过recovery cleanup回收
- **建议改法和验证点**: `_delete_entry_impl_s3` 应在stage-delete单个key后，额外检查该handle下是否有其他已知的元数据文件key需要stage-delete，或者使用 `_stage_delete_source_document_keys` 模式的批量delete intent记录
- **修复风险（中）**: 需要理解哪些元数据文件key需要被清理，可能需要修改多个调用路径

### 编号-未修复-[严重程度（中）]-_recover_single_remote_op中delete target的phase检查逻辑在staged阶段不验证expected sha/size但recovery后直接abort

- **入口/函数**: `_FsStorageInfra._recover_single_remote_op`
- **文件(行号)**: dayu/fins/storage/_fs_storage_infra.py:1065-1094
- **输入场景**: recovery时delete target的journal phase仍为staged（metadata尚未swap），且远端对象的sha/size与expected不匹配
- **实际分支**: 代码检查 `journal.phase == _PHASE_METADATA_COMMITTED` 为False，进入else分支执行stat_object验证，若不匹配则raise RuntimeError
- **预期行为**: 按S14-CTRL-13，delete target在metadata swap前应head验证remote仍匹配expected
- **实际行为**: 在staged阶段，若remote对象的sha/size发生drift（例如被其他进程修改），recovery直接abort fail closed。但实际场景中，这个drift可能是因为该对象已被publish覆盖（overwrite语义），此时abort是错误的——正确的收敛方式是忽略该delete target（因为publish已取代它）
- **直接证据**: `_fs_storage_infra.py:1084-1090` 直接raise RuntimeError，没有考虑该delete target对应的final_key是否已被publish覆盖
- **影响**: 在overwrite场景下，recovery可能abort但实际上系统是安全的，导致不必要的fail closed
- **建议改法和验证点**: 在delete target验证时，检查该final_key是否也在publish_targets中（即被overwrite），若是则跳过该delete target
- **修复风险（中）**: 需要理解overwrite语义的完整状态机
- **严重程度（中）**:

### 编号-未修复-[严重程度（中）]-_commit_s3_batch中publish状态更新和journal持久化之间存在非原子窗口导致重复retry

- **入口/函数**: `_FsStorageInfra._commit_s3_batch`
- **文件(行号)**: dayu/fins/storage/_fs_storage_infra.py:596-631
- **输入场景**: publish_target成功发布后，journal持久化前进程崩溃
- **实际分支**: 代码先调用 `self._publish_one_target(target)` 发布，然后调用 `_update_publish_state` 更新内存journal，最后调用 `write_journal` 持久化
- **预期行为**: publish操作应幂等，重复发布不改变final状态
- **实际行为**: `_publish_one_target` 内部已有重试逻辑（line 687-695），若首次copy成功但journal持久化前崩溃，recovery会再次调用publish_staged（幂等的CopyObject），这本身是安全的。但 `_publish_one_target` 的重试逻辑只重试一次（line 687-695），若首次copy的响应模糊（网络超时等），stat验证后staging仍存在就重试，若重试也失败则raise RuntimeError
- **直接证据**: `_fs_storage_infra.py:662-695` 的重试逻辑仅一次重试
- **影响**: 在网络不稳定环境下，单次重试可能不足以收敛，导致recovery时重复尝试
- **建议改法和验证点**: 考虑增加重试次数或使用指数退避，但当前实现已满足S14-CTRL-04的"bounded retry"要求
- **修复风险（低）**: 当前行为已满足契约，但重试次数可作为防御性改进
- **严重程度（中）**:
