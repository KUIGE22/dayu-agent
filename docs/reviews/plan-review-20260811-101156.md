## Findings

### S15-ERR-01-未修复-[高]-S15-CTRL-15引用不存在的第5项，默认-reader等价与零普通读取无法验收
- **位置**: `S15-CTRL-15` 第 1–4 项；`S15-CTRL-12` 的“secure snapshot adversarial matrix 按 S15-CTRL-15 第5项执行”；`S15-CTRL-13` 的 S15-CTRL-15 adversarial tests gate。
- **问题类型**: 不可直接实施 / 测试缺口 / 契约缺失。
- **当前写法**: S15-CTRL-15 在第 4 项后直接进入状态机文本，未定义第 5 项；但 tests 与 validation 两处都把 secure snapshot 的必跑矩阵委托给“第 5 项”。同时仅笼统要求 `content_reader=None` 时“原路径与原错误/返回语义”及“executable AST（去 docstring）”不漂移。
- **反例/失败场景**: 实现者可以只验证 descriptor symlink，或用一个仅替换 `Path.open` 的局部测试声称 ordinary external read=0，却漏掉 `Path.is_file()`、`read_text()`、`read_bytes()`、`resolve()` 后的下游路径；也可因新增 keyword-only parameter、reader 分支与 helper call 本身必然改变 AST，而在没有基线/归一化规则时随意豁免或无法通过 gate。这样 `reader=None` 的普通 public caller（workbook report、routing、write-manifest）发生错误分类或返回值回归，将没有可判定的拒绝标准。
- **为什么有问题**: 本勘误的唯一目标正是把“最终报错前已读外部 bytes”的路径收敛为可证明的零普通读取。缺少被引用的测试合同，使 coverage、Python 3.11、DAG 和 default-reader gates 只能测到实现自行选择的子集，不能证明该目标；而“AST 等价”若按字面比较又与准许的签名/调用链修改相矛盾。
- **直接证据**: 计划 `:3451-3486` 的 S15-CTRL-15 只编号到 4；` :3595-3596` 明确引用“第5项”；`:3628-3631` 又要求重跑该 adversarial tests。当前 validator 在 `dayu/cli/commands/_research_template_bundle.py:224-394` 直接调用 `_recompute_bundle_monitoring_integrity`、`_recompute_bundle_checklist_integrity`、`_build_write_manifest_binding_semantics` 与 `inspect_research_workbook_report`；后者当前分别使用 `Path.is_file/read_text/open/resolve`（bundle `:124-221`、workbook `:499-538`、helpers `:379-393,607-622`、routing `:83-87`）。
- **影响**: 实施 Agent 跑偏 / review 不可验收 / trust boundary 风险后移。
- **建议改法和验证点**: 补齐 S15-CTRL-15 第 5 项为唯一的参数化矩阵，并逐一固定：(a) descriptor、monitoring rules/source-map、checklist、workbook/report、source-write-manifest/company facets 的 pre-snapshot 与 post-snapshot external-symlink 替换；(b) snapshot 缺失、未知 key、相对/绝对/`..` path 与 regular-file replacement；(c) 对每个 source-tree path 的 ordinary `Path.open/read_bytes/read_text/is_file` 及 helper hash 计数均为 0，允许的读取只发生在明确列出的 no-follow FD snapshot owner；(d) package assets 的正常读取仍成功；(e) 所有 FD success/error/cancellation close；(f) reader=None 的 golden return/error/call-order corpus。明确 AST gate 只比较 reader 为 `None` 的既有执行分支的语义/call graph，或以固定 AST 归一化规则排除新增 reader plumbing；不得声称整个修改后函数 AST 与基线字节相等。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### S15-ERR-02-未修复-[高]-source-root目录FD未绑定身份，root swap可在所有子段O_NOFOLLOW之前逃逸边界
- **位置**: S15-CTRL-15 第 2 项的“从 source-root directory FD”及 Linux/macOS 同一 no-follow contract stop；现有 no-follow 基础实现。
- **问题类型**: 并发恢复风险 / 契约缺失 / 测试缺口。
- **当前写法**: 计划规定对中间组件和 leaf 使用 `O_NOFOLLOW` 并要求任一 component/leaf 变化 fail closed，但没有规定 source root 本身如何以不跟随、身份绑定的方式取得和贯穿整个 snapshot；也没有 root rename/symlink swap 的验证。
- **反例/失败场景**: source root 已 canonicalize 且 descriptor 已通过 `lstat` 后，攻击者将该 root rename，再在原路径创建指向外部目录的 symlink。随后 closure reader 若按当前基础实现从路径打开 root，`os.open(resolved_source_root, O_RDONLY | O_DIRECTORY)` 会跟随该 root symlink；之后即使子组件/leaf 均使用 `O_NOFOLLOW`，读取已在外部目录树内完成。若各 closure member 分别重新按路径打开 root，同一次 snapshot 还可跨两个 root 实体拼接。
- **为什么有问题**: 把 no-follow 只施加在 root 之后的路径段不能证明 source-root containment，也无法满足“任一 component/leaf 变化 fail closed”与 source tree read-only trust boundary。该漏洞恰在本勘误试图消除的 TOCTOU 类别内，最终 validator 使用 snapshot 也不能撤销错误 snapshot 已读取的外部 bytes。
- **直接证据**: 当前 `dayu/cli/commands/_research_template_bundle.py:522-579` 的 `_open_regular_no_follow()` 在 `:548` 以 `os.O_RDONLY | os.O_DIRECTORY` 打开 `resolved_source_root`，该 flags 不含 `O_NOFOLLOW`；只有 `:553-563` 的中间和 leaf 使用 `O_NOFOLLOW`。计划 `:3458-3464` 仅规定中间组件/末端 flags，未定义 root-FD acquisition、`st_dev/st_ino` identity、root replacement handling 或对应 test；现有 closure tests `tests/cli/test_research_template_command.py:5415-5539` 仅覆盖 result、escape、symlink artifact、stale manifest，未覆盖 root swap。
- **影响**: source-root 外 bytes 被读取 / 安全边界失效 / review 不可验收。
- **建议改法和验证点**: 将 root FD 作为一次 inspection 的唯一 capability：从已打开且受信任的 parent dir FD 用 `O_DIRECTORY|O_NOFOLLOW` 打开 root，立即 `fstat` 记录 `(st_dev, st_ino, mode)`；descriptor preflight、全部 member open/read 仅相对此同一 root FD 的 `dir_fd` 进行，且不得在每个 member 按 root pathname 重开。明确文件替换策略：要么在 snapshot 前以同一 FD 打开所有 leaves 并以各 FD snapshot bytes，避免名称替换影响；要么记录并在读取前后比较规定的 identity，任一不一致稳定 fail closed。增加 Linux/macOS root rename→external symlink、root replacement为另一普通目录、member-directory replacement 和取消/异常 FD-close 测试；任一外部 ordinary/no-follow read/hash 计数必须为 0。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 高。

### S15-ERR-03-未修复-[中]-snapshot key与descriptor引用的规范化顺序未唯一化，reader无法确定何时命中、何时拒绝
- **位置**: S15-CTRL-15 第 1–3 项的 `Path` reader Protocol、"original canonical contained path" snapshot key，以及 source-tree `resolve` 禁止重读。
- **问题类型**: 契约缺失 / 状态机漏洞 / 过度耦合。
- **当前写法**: 计划只声明 snapshot 的 key 为“original canonical contained path”，Protocol 接收 `Path`，但未定义 descriptor 中 relative path 的锚点、absolute path 的接受规则、lexical `..` 拒绝点，或 consumer 在 reader mode 下传入 raw path、pre-snapshot canonical key、还是 post-replacement `Path.resolve()` 的次序。也未规定 reader 不能为了 key lookup 再作文件系统 `resolve/stat`。
- **反例/失败场景**: 对合法 bundle，descriptor 可能给同一 file 使用相对、绝对或含 `..` 的拼写；若 core/workbook 的现有 `Path(...).resolve()` 在 snapshot 后遇到被替换的 symlink，会得到外部 canonical path，snapshot reader 因 key miss fail closed，即使安全 snapshot 中已有原 bytes。反之若 reader 自行对 raw path resolve 来匹配 key，它又重引入由未受信任 pathname 驱动的 filesystem access。不同 owner 各自选择规则会让 source manifest、workbook/report 与 routing 分别发生不一致的命中/拒绝。
- **为什么有问题**: neutral reader 的价值是让 parser 保持唯一真源，同时使 key lookup 完全由已验证 snapshot 决定；路径解释若没有单一 owner，就会把 containment/TOCTOU 策略复制到 core/helpers/workbook/routing，违反本勘误的 ownership 与最小 allowlist 意图。
- **直接证据**: 计划 `:3454-3469` 未给出上述 path grammar、canonicalization owner 或 lookup state table。现有代码正存在不同路径处理：bundle `_enumerate_closure_reference_paths()` 返回 `Path(path_raw)`（`:661-702`），validator 用 `Path(source_path_raw).is_file()` 并传 `source_path.resolve()`（`:255-286`），workbook report 在读取前对两输入 `.resolve()`（`:499-538`），routing 则直接 `path.read_text()`（`research_template_routing.py:83-87`）。这证明仅增加同名 `content_reader` 参数不足以唯一决定行为。
- **影响**: 实施 Agent 跑偏 / security fail-closed 误拒绝或重引入普通路径读取 / 后续返工。
- **建议改法和验证点**: 明确 bundle closure 是唯一 canonicalization owner：先按固定 grammar（建议 descriptor references 必须为 source-root-relative POSIX locator，拒绝 absolute、空段、`.`、`..`、平台分隔符）做纯 lexical parse，再以 root FD 逐段打开并产生不可变 canonical locator；snapshot reader 内只保存 `canonical locator -> bytes`，其 `Path` adapter 只能作无 I/O 的 lexical normalization，未知/非canonical输入稳定抛 owner error。所有 reader-mode caller 在进入 core/workbook/routing 前由 bundle owner将 descriptor payload 的 closure references规范为该 canonical form，或改 Protocol 直接接收 `str` canonical locator；两者择一并记录 package asset bypass。测试应覆盖同一文件的等价/非等价拼写、relative escape、post-snapshot symlink replacement 下 key 命中原 snapshot 与 unknown key fail-closed，且每条路径 ordinary external read=0。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 中。
