## Findings

### 1-未修复-[中]-PostgresJobStore 构造与 lifecycle 未被 composition test 覆盖

- **位置**: Plan §6 composition、§7 slice E test `test_production_provider_exposes_real_durable_jobs_service`、当前 `_build_production_identity_provider`
- **问题类型**: 测试缺口 / 契约缺失
- **当前写法**: Plan 声称在 `_build_production_identity_provider`（或等价）中同时构造 `PostgresJobStore` 和 `JobService`，注册为 `{"investment_identity": ..., "durable_jobs": ...}`；测试 `test_production_provider_exposes_real_durable_jobs_service` 验证 `durable_jobs` 暴露。
- **反例/失败场景**: 如果实现者在 provider 中遗漏 `PostgresJobStore` 构造（仅构造 `JobService` 但未注入 store），`durable_jobs` 映射值可能为残缺对象；当前测试只验证 key 存在和 `platform_service_name`，不验证内部 store 注入正确。此外 `PostgresJobStore` 的 session factory 是否与 `InvestmentIdentityService` 共享同一 engine 也无测试覆盖。
- **为什么有问题**: Composition 是 Host 运行时的装配入口，如果 `PostgresJobStore` 未正确构造或 session factory 注入错误，运行时会在首次 PG 操作时才暴露，违背 "启动期 fail-fast" 原则。现有 `test_production_provider_exposes_real_durable_jobs_service` 的断言强度不足以捕获此类装配错误。
- **直接证据**: `dayu/services/startup_preparation.py:304-369` 当前 `_build_production_identity_provider` 仅构造 `PostgresIdentityRepository` + `InvestmentIdentityService`，provider mapping 仅含 `investment_identity`；plan 要求扩展为含 `durable_jobs`，但未指定扩展后的测试断言应检查 `PostgresJobStore` 的构造与 session factory 注入。
- **影响**: Implementation agent 生成的 composition 代码可能遗漏 store 注入；测试通过但运行时 fail，增加调试成本。
- **建议改法和验证点**: 在 `test_production_provider_exposes_real_durable_jobs_service` 中增加断言：(1) provider mapping 包含 `durable_jobs`；(2) `durable_jobs` 的内部 `PostgresJobStore` 使用与 `investment_identity` 相同的 engine/session factory；(3) 如果 `PostgresJobStore` 有构造期 probe（类似 `_probe_production_engine`），验证 probe 被调用。
- **修复风险（中）**: 需要补充测试用例，不改 plan 结构。
- **严重程度（中）**: 不阻塞 plan 通过，但 implementation 阶段如果遗漏此测试，可能导致隐性装配 bug。

### 2-未修复-[低]-reserved_run_id 格式与现有 run_id 格式不一致

- **位置**: Plan §3.1 "reserved_run_id 只接受 run_ 加 32 位小写 hex"
- **问题类型**: 契约缺失 / 最佳实践偏离
- **当前写法**: Plan 要求 reserved run ID 格式为 `run_` + 32 位小写 hex（`run_{attempt_id.hex}`），现有 `register_run` 生成 `run_` + 12 位 hex（`run_{uuid.uuid4().hex[:12]}`）。
- **反例/失败场景**: 如果 `ensure_reserved_run` 的格式校验使用 `len(reserved_run_id) == 35`（`run_` + 32 hex），而某些调用方误传12位格式，会直接被拒绝。这不是 bug，但缺少对"为什么新格式不同于旧格式"的显式说明，可能导致实现者混淆。
- **为什么有问题**: 同一 Host 内两种 run_id 格式并存，如果未来有按格式区分的逻辑（如日志解析、run_id 前缀匹配），可能产生歧义。Plan 未解释选择 32 hex 而非12 hex 的原因。
- **直接证据**: `dayu/host/run_registry.py:188` 现有 `run_id = f"run_{uuid.uuid4().hex[:12]}"`；plan §3.1 "reserved_run_id 只接受 run_ 加 32 位小写 hex"。
- **影响**: 极低风险；reserved run 是新代码路径，不与旧路径冲突。
- **建议改法和验证点**: 在 plan §3.1 补充一句："32 hex 格式与 attempt UUID 完全对齐，便于 correlation 日志关联；现有12 hex 随机格式保持不变，两者在 Host 内无需互操作。"Implementation agent 无需修改。
- **修复风险（低）**: 纯文档补充。
- **严重程度（低）**: 不影响正确性。

### 3-未修复-[低]-cancel_requested 状态在 Job 状态机转换表中缺少显式行

- **位置**: Plan §4.1 转换表
- **问题类型**: 状态机漏洞（微小）
- **当前写法**: Job 合法转换列包含 `cancel_requested→cancelled`，但未明确 `cancel_requested` 的完整转换集（如 `cancel_requested` 是否可被 recover 重新触发 retry？）。
- **反例/失败场景**: 如果 recover 发现 `cancel_requested` 的 job 且 lease 已过期，按 plan §4.2.7 "lease 到期时 recover 把 attempt abandoned 并使 job cancelled"，`cancel_requested→cancelled` 是正确的。但如果 recover 发现 `cancel_requested` 且 job 有 retry budget，是否应 retry？Plan §4.2.7 说 "非取消 job 走与 fail 相同 retry algorithm"，而 `cancel_requested` 的 job 属于取消类，所以不 retry。逻辑闭合，但转换表未显式标注 `cancel_requested` 的 recovery 路径。
- **为什么有问题**: 转换表是状态机的 spec；如果 recovery 路径只在 §4.2.7 正文描述而不在转换表中体现，implementation agent 可能遗漏。
- **直接证据**: Plan §4.1 转换表只写 `cancel_requested→cancelled`，未写 recovery 触发的 `cancel_requested→cancelled` 路径（与 §4.2.7 正文一致但不够显式）。
- **影响**: Implementation agent 需要同时读转换表和 §4.2.7 正文才能理解完整状态机；如果只看转换表可能遗漏 recovery 路径。
- **建议改法和验证点**: 在 §4.1 转换表的触发者列中补充 "recover（lease 过期 + cancel intent）"。
- **修复风险（低）**: 纯 plan 补充。
- **严重程度（低）**: 状态机逻辑已闭合，仅影响 spec 清晰度。

### 4-未修复-[低]-_build_production_identity_provider 重命名条件模糊

- **位置**: Plan §6 "is renamed only if needed to reflect multiple services"
- **问题类型**: 契约缺失
- **当前写法**: Plan 说 "renamed only if needed to reflect multiple services"，但未给出明确的重命名判定条件。
- **反例/失败场景**: Implementation agent 可能选择不重命名（因为原函数名仍可接受），也可能重命名为更长的名字。两种选择都正确，但缺乏一致性。
- **为什么有问题**: 命名是公共 API surface 的一部分；如果两个 implementation agent 做不同选择，后续维护者会困惑。
- **直接证据**: Plan §6 原文。
- **影响**: 极低；纯命名偏好。
- **建议改法和验证点**: 明确为 "重命名为 `_build_production_services_provider` 以反映多 service 职责；或保持原名但添加注释说明扩展范围"。
- **修复风险（低）**: 纯 plan 澄清。
- **严重程度（低）**: 不影响正确性。

## Open Questions

1. **PostgresJobStore 的 engine/session factory 是否与 InvestmentIdentityService 共享？** Plan §6 说 "构造关闭 echo 的 engine/session factory"，暗示共享 engine；但未显式声明。建议 implementation 时显式共享以减少连接池开销，并在 test 中验证。

2. **reconcile_agent_run_correlation 的 Host inspection 依赖是否需要新的窄 Protocol？** Plan §3.2 提到 "Host inspection 只依赖 get_run、cleanup_orphan_runs、cancel_run 的窄 Protocol"，但当前 `protocols.py` 中 `RunAdministrationProtocol` 已包含这些方法。Implementation agent 应判断是否需要新建窄 Protocol 还是复用现有 `RunAdministrationProtocol`。

3. **CanonicalJobDocument 的 "UTF-8、无 BOM" 检查在哪个层执行？** Plan §3.2 描述了 canonical 格式约束，但未明确是在 `enqueue` 时检查还是在构造 `CanonicalJobDocument` 时检查。建议在 DTO 构造期检查，enqueue 只验证 hash。
