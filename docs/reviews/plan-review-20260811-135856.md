# Plan Review: Slice 2.1 — Durable Job Contract 与 PostgreSQL Queue

- **审查目标**: `docs/plans/2026-08-11-slice-2.1-durable-job-queue.md`
- **审查范围**: 全文（§1–§9），重点关注状态机、跨库协调、Reserved identity、implementation sequencing 和 test coverage
- **审查时间**: 2026-08-11 13:58:56
- **审查结论**: `pass-with-risks`

---

## Assumptions Tested

1. Reserved run ID 格式 `run_` + 32 位 hex 与现有 `register_run()` 的 `run_` + 12 位 hex 兼容
2. Host SQLite 与 PG 之间无跨库事务时，correlation commit → Host ensure 的 crash window 可被 reconcile 闭合
3. `ensure_reserved_run` 的并发 INSERT 能被 SQLite UNIQUE 约束正确仲裁
4. RLS `nullif(current_setting('app.tenant_id', true), '')::uuid` 在未 SET LOCAL 时 deny-all
5. `CanonicalJobDocument` 的敏感键 blocklist 覆盖足够
6. Backoff 无 jitter 不会导致 thundering herd
7. `cancel_requested` → lease expiry → recover → cancelled 的完整路径闭合
8. 不修改 `composition.py` 而注册 `durable_jobs` 的方式可行
9. Downgrade 的 `CASCADE` 拒绝策略在运维场景下安全
10. Slice A 的 crash-window test 能真实验证 PG-first correlation 语义

## Findings

### 001-未修复-高-reserved_run_id 格式与现有 register_run 不一致

- **位置**: §3.1 Reserved Host run
- **问题类型**: 契约缺失
- **当前写法**: "reserved_run_id 只接受 run_ 加 32 位小写 hex 的确定性 Host ID；JobService 以 attempt UUID 生成 run_{attempt_id.hex}"
- **反例/失败场景**: 现有 `register_run()` 生成 `run_` + 12 位 hex（`uuid.uuid4().hex[:12]`，见 `run_registry.py:108`）。两条路径产生不同格式的 run_id，但共享同一张 SQLite runs 表和同一套 `RunRecord`。下游查询（`get_run`、`list_runs`）不区分格式，但日志、监控和人工排查时会混淆。更关键的是：如果未来有代码对 run_id 做格式校验（如正则），两条路径的规则不同会导致 bug。
- **为什么有问题**: plan 声称"现有 `register_run()` 的随机生成和所有 generic operation 完全不变"，但没有显式声明两种格式共存的兼容性契约。implementation agent 可能假设 run_id 格式统一。
- **直接证据**: `run_registry.py:108` — `run_id = f"run_{uuid.uuid4().hex[:12]}"`；plan §3.1 — `run_{attempt_id.hex}`（32 位）
- **影响**: 实施 Agent 可能在格式校验、日志解析或测试断言上出错
- **建议改法和验证点**: 在 plan 中显式声明"两种 run_id 格式共存，SQLite schema 不做 format CHECK，下游代码不得假设固定长度"；测试中显式断言两种格式都能被 `get_run` 正确查询
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 002-未修复-高-ensure_reserved_run 并发 INSERT 的 SQLite 仲裁未明确

- **位置**: §3.1 Reserved Host run
- **问题类型**: 并发恢复风险
- **当前写法**: "不存在则 INSERT CREATED 并返回 created=True；存在则比较 immutable identity，完全相同返回既有 record 与 created=False，任一差异抛稳定 ReservedRunIdentityConflictError"
- **反例/失败场景**: 两个并发调用同时执行 SELECT 发现不存在，然后同时 INSERT。SQLite UNIQUE 约束会阻止第二个 INSERT，但 plan 没有指定如何捕获这个 UNIQUE violation 并将其转化为"读取已有记录并比较 identity"的逻辑。如果 implementation agent 只用 try/except 捕获 IntegrityError，需要确保异常类型和处理路径正确。
- **为什么有问题**: 这是 `ensure_reserved_run` 的核心原子性保证。plan 描述了语义但没有指定实现策略（INSERT ON CONFLICT vs SELECT-then-INSERT vs try-except-IntegrityError）。
- **直接证据**: plan §3.1 的 ensure 语义描述；`run_registry.py` 现有 `register_run` 不处理冲突（因为它总是生成新 ID）
- **影响**: 实施 Agent 可能选择不安全的实现策略，导致并发下数据不一致或异常泄漏
- **建议改法和验证点**: 明确推荐 `INSERT ... ON CONFLICT DO NOTHING` + `SELECT` 或 `try INSERT except IntegrityError: SELECT + compare` 策略；测试 `test_ensure_reserved_run_conflict_fails_closed` 必须用线程/进程并发验证
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 003-未修复-中-reconcile_agent_run_correlation 的触发时机未指定

- **位置**: §4.3 Agent correlation query-before-retry
- **问题类型**: 状态机漏洞
- **当前写法**: "reconcile_agent_run_correlation 先 Host.get_run(reserved_host_run_id)：不存在且 correlation 是 reserved 时，以同一 ID 调 Agent entry"
- **反例/失败场景**: plan 描述了 reconcile 的算法，但没有明确谁在什么时候调用它。是在每次 `claim` 之后？是在 `recover` 发现过期 attempt 时？是在 Host 启动时？如果 reconcile 只在特定路径触发，某些 crash window 可能无法被覆盖。
- **为什么有问题**: §4.3 说"此设计仅锁定本地 Host '一个 correlation ID 至多一次进入模型'"，但 reconcile 的触发时机决定了这个保证的实际覆盖面。
- **直接证据**: plan §4.3 描述了 reconcile 算法但未指定调用点；§7 slice D 测试名暗示 reconcile 在 claim 后触发，但 plan 文本未明确
- **影响**: 实施 Agent 可能遗漏 reconcile 调用点，导致某些 crash window 无法恢复
- **建议改法和验证点**: 在 §4.3 或 §7 中显式列出 reconcile 的调用时机（如：claim 成功后立即调用；Host 启动时对所有 reserved correlation 调用；recover 对 abandoned attempt 调用）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 004-未修复-中-CanonicalJobDocument 敏感键 blocklist 的覆盖边界

- **位置**: §3.2 Job contract 与 Protocol
- **问题类型**: 契约缺失
- **当前写法**: "递归拒绝 closed 敏感键集合（password、secret、token、authorization、cookie、api_key）"
- **反例/失败场景**: blocklist 方式无法覆盖未来新增的敏感键（如 `access_token`、`refresh_token`、`private_key`、`session_id`）。plan 说"该规则不虚构'未知业务字段自动脱敏'能力"，但也没有说明 blocklist 的维护责任归属。
- **为什么有问题**: 这是一个安全边界。如果 blocklist 不够完整，敏感数据可能被持久化到 PG 的 `job_runs.payload_bytes` 或 `job_attempt_receipts.receipt_bytes` 中，违反 §3.2 的"queue 永不接收 raw exception、prompt、credential、token、URL query 或原始请求"契约。
- **直接证据**: plan §3.2 的 sensitive key 列表
- **影响**: 敏感数据泄漏到持久化存储，审计困难
- **建议改法和验证点**: 在 plan 中明确"blocklist 是当前已知敏感键的最小集合，未来 handler 负责在投影为 safe document 前自行脱敏"；测试覆盖 blocklist 中每个键的拒绝行为
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 005-未修复-中-backoff 无 jitter 可能导致 thundering herd

- **位置**: §4.2 fail
- **问题类型**: 最佳实践偏离
- **当前写法**: "按 min(retry_max_seconds, retry_base_seconds * 2**(attempt_number-1)) 计算无 jitter backoff"
- **反例/失败场景**: 多个 job 同时失败（如 PG 瞬时不可用），它们的 retry backoff 会完全同步，在同一时刻重试，造成 thundering herd。这在 §8 的 fault matrix 中没有被测试。
- **为什么有问题**: 无 jitter 的 exponential backoff 是分布式系统中的经典反模式。虽然当前 slice 没有 scheduler/worker（非目标），但 backoff 算法是 JobService 的公共契约，后续 slice 会直接使用。
- **直接证据**: plan §4.2 fail 的 backoff 公式
- **影响**: 后续 scheduler slice 引入时可能遭遇 thundering herd，需要修改公共契约
- **建议改法和验证点**: 在 backoff 公式中加入 jitter（如 `random.uniform(0, computed_backoff)`），或在 plan 中显式声明"无 jitter 是有意选择，因为 scheduler 将在 Slice 2.2 引入自己的 jitter 策略"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 006-未修复-低-downgrade CASCADE 拒绝策略的运维影响

- **位置**: §5 PostgreSQL migration 0003_durable_jobs
- **问题类型**: 最佳实践偏离
- **当前写法**: "downgrade first queries catalog dependencies and fails closed on any view/rule/external FK outside these seven tables"
- **反例/失败场景**: 如果运维人员在 migration 后手动创建了引用这些表的 view 或 FK（如监控 view、审计 view），downgrade 会拒绝执行。这可能导致运维无法回滚，需要先手动删除这些依赖。
- **为什么有问题**: 这是安全优先的设计，但 plan 没有说明运维如何处理这种情况。运维文档（README）是否覆盖了这个场景？
- **直接证据**: plan §5 downgrade 描述
- **影响**: 运维回滚受阻，需要人工干预
- **建议改法和验证点**: 在 README 中说明 downgrade 的依赖检查行为和处理方法
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 007-未修复-中-job_events sequence_number 的生成策略未指定

- **位置**: §5 PostgreSQL migration 0003_durable_jobs
- **问题类型**: 契约缺失
- **当前写法**: `job_events` 表有 `sequence_number BIGINT` 和 `UNIQUE(tenant_id,job_run_id,sequence_number)`
- **反例/失败场景**: plan 没有指定 sequence_number 的生成策略。是数据库序列？是应用层 MAX+1？是单调递增？如果用 MAX+1，在并发写入时可能冲突。如果用数据库序列，可能有间隙（gap），但这对事件日志通常可接受。
- **为什么有问题**: implementation agent 需要知道如何生成 sequence_number。不同的策略有不同的并发特性和性能特征。
- **直接证据**: plan §5 job_events 表定义；§4.2 各操作"插入 event"但未指定 sequence 生成方式
- **影响**: 实施 Agent 可能选择不安全的 sequence 生成策略
- **建议改法和验证点**: 明确 sequence_number 的生成策略（推荐：每 job_run 内应用层 `SELECT COALESCE(MAX(sequence_number), 0) + 1` 在同一事务内，或使用数据库序列）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 008-未修复-中-不修改 composition.py 而注册 durable_jobs 的方式未明确

- **位置**: §6 Composition, lifecycle, tenancy
- **问题类型**: 架构边界
- **当前写法**: "不修改 dayu/investment/composition.py 和 dayu/startup/platform.py：既有 PlatformServiceProtocol 与 generic composition 已能承载 durable_jobs"
- **反例/失败场景**: 现有 `PlatformComposition` 的构造逻辑在 `composition.py` 中，它对注册的 service 做严格校验（`platform_service_name` 属性检查）。`durable_jobs` 的 `JobService` 是否实现了 `PlatformServiceProtocol`？如果没有，如何注册到 composition 中？
- **为什么有问题**: plan 说"增加 wrapper 或为了显式类型而让纯 investment composition import Host 都违反依赖边界"，但没有说明 `durable_jobs` 是如何被注册到 composition mapping 中的。
- **直接证据**: `composition.py` 的 `PlatformServiceProtocol` 定义；plan §6 的 composition 描述
- **影响**: 实施 Agent 可能需要修改 composition.py 来注册 durable_jobs，违反 plan 的约束
- **建议改法和验证点**: 明确 `durable_jobs` 是否实现 `PlatformServiceProtocol`，或者 composition mapping 是否接受非 `PlatformServiceProtocol` 的值（当前代码似乎要求 `platform_service_name` 属性）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Final Plan Review Conclusion

**pass-with-risks**

计划整体结构清晰，状态机设计合理，跨库协调的 PG-first correlation 方案是正确的架构选择。主要风险点：

1. **002（高）**: `ensure_reserved_run` 并发 INSERT 的实现策略需要明确，否则 implementation agent 可能选择不安全的路径
2. **001（中）**: Reserved run ID 格式与现有格式不一致需要显式兼容性声明
3. **003（中）**: Reconcile 触发时机需要明确
4. **007（中）**: Sequence number 生成策略需要指定
5. **008（中）**: durable_jobs 注册到 composition 的方式需要澄清

这些 finding 不是 blocker，但 implementation agent 在没有澄清的情况下直接实现可能会做出错误假设。建议在开始实现前至少关闭 002 和 003。
