## 4. Adversarial Validation — Descriptor-First / Member-Second Two-Phase FD Acquisition

### 4.1 Root Capability

**Plan §2 规定**：

- 从 filesystem root FD 开始，对 `resolved_source_root` 的每个 component 逐段以 `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` + `dir_fd` 打开；
- 每段先以相对父 FD 的 `stat(..., follow_symlinks=False)` 记录 `(st_dev, st_ino, mode)`，再 `open`/`fstat` exact；
- 最终 root FD 与 source-root preflight identity exact；
- 作为本次 inspection 唯一 capability 保持打开，禁止按 source-root pathname 重开；
- root rename、root→symlink/root→另一目录替换不得改变唯一 root capability。

**挑战**：root capability 是否完整可实施？实现 agent 能否从 plan 直接推导出 exact code？

**结论**：Plan 完整规定了 root FD acquisition 的每一步：从 `/` FD 逐段 O_NOFOLLOW 打开 → fstat 绑定 identity → 唯一 capability → 禁止重开。root rename/symlink/replacement 不改变 capability 的语义也已明确。测试矩阵覆盖 root rename→external symlink、root 替换为另一 regular directory。**无 open finding。**

### 4.2 Descriptor Identity / Read

**Plan §2 descriptor phase 规定**：

- bundle locator 本身在调用边界已知；
- 仅相对 root FD 逐段执行同一 component identity→`O_NOFOLLOW` open→`fstat` exact，绑定 descriptor leaf FD；
- 只从该 FD 读取一次 bytes，保持 FD 由同一 `ExitStack` 持有；
- strict parse 后得到 immutable descriptor payload。

**挑战**：descriptor 的 identity binding 是否完整？FD 的生命周期是否明确？

**结论**：Descriptor phase 完整定义了 descriptor leaf FD 的 identity preflight→open→fstat exact、byte read（一次）、FD 持有（ExitStack）和 parse 结果（immutable payload）。descriptor FD 不在 member phase 前关闭，ExitStack 在 success/exception/BaseException 路径 exact close。**无 open finding。**

### 4.3 Immutable Lexical Enumeration

**Plan §2 member phase 规定**：

- bundle owner 只对 immutable payload 做纯 lexical reference canonicalization；
- 随后对枚举出的全部 member 逐段执行 component/leaf preflight identity→no-follow open→`fstat` exact。

**挑战**：enumeration 是否在 descriptor parse 后、member open 前？是否为纯词法（不做 filesystem resolve）？

**结论**：Plan 明确 lexical enumeration 依赖 descriptor 的 immutable payload（phase 1 产出），在 phase 2 的 preflight/open 前执行。"纯 lexical reference canonicalization" 不调用 filesystem。§3 进一步规定 reader lookup 是 exact string map、零 filesystem I/O。**无 open finding。**

### 4.4 Member Component + Leaf Preflight → Open → Fstat Exact

**Plan §2 member phase 规定**：

- 对枚举出的全部 member 逐段执行 component/leaf preflight identity→no-follow open→`fstat` exact；
- 并保持全部 leaf FD 打开。

**挑战**：每个 member 的 component/leaf 是否有独立的 identity preflight？是否与 root capability 的逐段方式一致？

**结论**：Plan 对 member 使用与 root/descriptor 相同的逐段 component identity→O_NOFOLLOW open→fstat exact 模式。"逐段"意味着每个 path component 都有独立的 identity 验证。全部 leaf FD 在 member phase 完成前保持打开。**无 open finding。**

### 4.5 All Member FD Binding Before Read

**Plan §2 member phase 规定**：

- 在全部 member FD 成功绑定前禁止读取任何 member bytes；
- 全部绑定后才从这些 FD 各读取一次，形成供所有 validator 共用的 immutable bytes set。

**挑战**：是否明确禁止在部分 member FD 绑定后提前读取？是否要求全部 member FD 同时可用？

**结论**：Plan 明确 "全部 member FD 成功绑定前禁止读取任何 member bytes"，这是 all-or-nothing 语义。全部绑定后 "各读取一次"，形成 "immutable bytes set" 供所有 validator 共用。无部分读取窗口。**无 open finding。**

### 4.6 Non-Filesystem-Wide Atomic Snapshot

**Plan §2 规定**：

- "本合同的 snapshot 边界不是虚构的 filesystem-wide atomic instant：descriptor bytes 在其 FD 绑定时固定，member set 在全部 member FD acquisition 完成时固定。"

**挑战**：是否诚实声明了 snapshot 边界？是否避免了虚假的原子性承诺？

**结论**：Plan 明确不声称 filesystem-wide atomic instant。snapshot point 定义为两个离散事件：(1) descriptor FD 绑定时 descriptor bytes 固定；(2) 全部 member FD acquisition 完成时 member set 固定。这是可实施且可验证的合同。**无 open finding。**

### 4.7 Preflight Before Regular Replacement / Race / FD After Replacement Semantics

**Plan §2 规定**：

- "member 在其 preflight 前被 regular-file 替换，可作为该 member 当前版本进入 acquisition，但仍须通过 descriptor/owner 语义与全部 hash/validation"；
- "preflight 与 open 之间的 component/leaf identity race 必须拒绝"；
- "FD 绑定后的 pathname 替换不得改变已读 bytes"。

**挑战**：三种 replacement 场景是否有完整、不矛盾的语义？

**结论**：

1. **Preflight 前 regular replacement**：成员被替换为另一个 regular file → 它作为 "current member" 进入 acquisition → 但必须通过全部 owner semantics/hash → 如果 hash 不匹配则拒绝。这是合理的：preflight 前的替换不影响已打开的 FD，且新版本必须通过完整性验证。
2. **Preflight→open identity race**：component/leaf 在 preflight stat 与 open 之间被替换 → identity 不一致 → 拒绝。这是标准 TOCTOU 防御。
3. **FD 绑定后 pathname replacement**：FD 已打开并绑定 → pathname 被替换 → 已读 bytes 不变（FD 指向原 inode）→ 不影响 snapshot。这是 FD 语义的自然结果。

三种场景语义完整、不矛盾、可实施。测试矩阵覆盖每种场景。**无 open finding。**

### 4.8 BaseException Close

**Plan §2 规定**：

- "所有 root/intermediate/descriptor/member FD 必须以 `ExitStack`/等价结构在 success/exception/`BaseException` 路径 exact close，不落盘临时正文"。

**挑战**：BaseException 路径是否被显式覆盖？ExitStack 是否保证 close？

**结论**：Plan 明确 "success/exception/BaseException 路径"，BaseException 包括 KeyboardInterrupt、SystemExit 等。`ExitStack.__exit__` 在 `with` 语句中保证调用，即使 BaseException 也如此。"exact close" 意味着每个 FD 都必须 close，不允许泄漏。§6 测试矩阵要求 "root/intermediate/leaf FD success/每个异常/BaseException close count exact"。**无 open finding。**
