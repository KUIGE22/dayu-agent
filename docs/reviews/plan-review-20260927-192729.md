## Findings

### PR8-A01-未修复-[中]-EvidenceLink exact-one target CHECK 未闭合证券字段，复合外键可被 NULL 绕过

- **位置**：V8 §3.1 第 42 行、§3.2 第 50 行、§4 第 64–65 行、§7 第 117 行。
- **问题类型**：schema/storage 契约缺失；数据库三层 closure 的 CHECK/FK 测试缺口。
- **当前写法**：计划要求 Fact 或 `(security_id,完整 locator_json)` 恰有一个目标，并声明 Fact/direct `(company_id,security_id,locator_ticker)` 公共 FK。可是其精确列举的 EvidenceLink CHECK Fact 分支仅要求 `fact_id` 非空、`locator_json`/digest 为 NULL；未要求 `security_id`/`locator_ticker` 为 NULL。direct 分支要求 `security_id`、`locator_json`、digest 非空，却未要求 `locator_ticker` 非空及与 `locator_json->>'ticker'` 在 DB 中相等。Fact 表的 `security_id`、`locator_ticker` 也未被显式声明 NOT NULL 或 generated non-null。
- **反例/失败场景**：在同 tenant/company 下建立 Fact F（证券 S1）及另一有效证券 S2。raw INSERT 一个指向 F 的 EvidenceLink，同时填 S2 的 `security_id`/ticker，留 `locator_json` NULL；所列 Fact-arm CHECK 与 S2 的公共 FK 都可通过，一行同时携带两个不一致的证券身份。再 raw INSERT direct link，`fact_id` NULL、`security_id` S2、合法 locator JSON 的 ticker 为 T，但 `locator_ticker` NULL；BEFORE INSERT trigger 正常算出 digest，direct-arm CHECK 通过，而默认 `MATCH SIMPLE` 的三列外键因一列 NULL 不查目标。即使 `locator_ticker` 非空，如果它匹配 S2 却不等于 JSON ticker，单独的 locator shape CHECK 与证券 FK 也不能证明两者相同。Fact 表同样可在未显式禁止 NULL 时逃过三列 FK。现有 repository 可以尝试在应用层拒绝，但 V8 承诺数据库 FK/约束构成独立的 closure 层。
- **为什么有问题**：V8 §3.2 的 target identity 与主计划 `docs/plans/2026-08-10-investment-platform-restoration.md:1299-1312,1433-1453,4294-4307` 要求同公司/证券/locator 闭合；上述行可绕过或混淆该证明，后续 Claim 引用和 3.2 Fins 核验无法从 DB 记录恢复单一目标。PostgreSQL 16 默认多列 FK `MATCH SIMPLE` 任一引用列 NULL 即不要求匹配，且 CHECK 对 NULL 求值可能被视为满足，见 [PostgreSQL 16 Constraints](https://www.postgresql.org/docs/16/ddl-constraints.html) 与 [CREATE TABLE](https://www.postgresql.org/docs/16/sql-createtable.html)。
- **直接证据**：V8 第 50 行明确定义 target 身份；第 64 行宣称三列 FK；第 65 行的两个分支未列全 `security_id`/`locator_ticker`，第 63 行仅声明 tenant/company NOT NULL；第 117 行没有上述 raw INSERT 负例。0001 当前 securities 有 `(exchange_mic,ticker)` 唯一键，V8 新增 `(company_id,id,ticker)` 键并不能阻止可空引用列绕过。
- **影响**：计划按字面实施可产生与 Fact 冲突的附带证券身份，或未经公共 securities 验证的 direct locator；三层拒绝的 DB 层失效，审查及后续来源归属判断不可靠。
- **建议改法和验证点**：在 0007/ORM 契约中写出完整的 EvidenceLink 双分支 CHECK：Fact arm 需 `fact_id IS NOT NULL` 且 `security_id/locator_ticker/locator_json/digest` 全 NULL；direct arm 需 `fact_id IS NULL`、`security_id/locator_ticker/locator_json/digest` 全非 NULL、32-byte digest，且 ticker 等于 JSON 的 ticker（用 generated stored ticker，或显式使等式为 TRUE，避免 SQL 三值逻辑）。Fact 自身的 `security_id` 与 locator ticker 须 NOT NULL 且 DB 证明 ticker 来自其 JSON；保留三列 FK。真 PG 用绕过 DTO 的参数化 raw INSERT 覆盖 Fact arm 证券残值、direct NULL ticker、direct 错 ticker、Fact NULL security/ticker，核它们均由 DB 拒绝；合法双证券 direct links 仍通过。
- **修复风险（低）**：只补全未上线的 0007/ORM CHECK、列约束或 generated column 与 PG 负例，不改旧迁移。
- **严重程度（中）**：当前计划不能作为精确 DB contract 直接交给实施 Agent。
- **状态**：accepted-candidate，待 Controller 裁决。
