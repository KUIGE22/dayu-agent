## 1. C1 核对点一: `_validate_research_materialization_args` → `_challenger_requested` 依赖与 cycle

### 1.1 源码事实

`_validate_research_materialization_args`（行 2731-~3600）在行 3595 调用 `_challenger_requested(args)`。

v4.5 计划:
- Slice 5 `_write_params_validation.py` 收纳: `_validate_challenger_run_plan_args`, `_validate_live_smoke_plan_args`, `_validate_research_materialization_args`
- Slice 8 `_write_challenger.py` 收纳: Challenger 实验函数（含 `_challenger_requested`）

### 1.2 Cycle 分析

如果 `_challenger_requested` 留在 Slice 8 `_write_challenger`:
- `_write_params_validation` 需 import `_write_challenger._challenger_requested`（跨模块依赖）
- `write.py` 需 import `_write_challenger._challenger_requested`（行 4829/5079/5191）

**无 cycle**: `_write_challenger` 不 import `_write_params_validation`，`_write_params_validation` → `_write_challenger` 是单向依赖。

**但有 ownership 问题**: `_challenger_requested` 是纯 args 查询谓词，语义上属于 params validation 而非 Challenger 实验逻辑。它被 `_validate_research_materialization_args`（params）和 `run_write_command`（dispatch）两处调用，但与 Challenger 运行时逻辑（`_run_champion_challenger_experiment` 等）无直接关系。

### 1.3 用户提案评估: `_challenger_requested` 移入 Slice 5

**方案**: 将 `_challenger_requested` 作为 Slice 5 `_write_params_validation.py` 的第 4 个函数（或 `_write_config_helpers.py`），Slice 8 count 14→13。

**评估**:
- **语义正确**: `_challenger_requested` 是 args 查询谓词，属于 validation/helpers 层
- **无 cycle**: `write.py` import `_write_params_validation._challenger_requested`，单向
- **无 wrapper seam**: write.py 直接 import 使用，不转发
- **Slice 8 count**: 见下方 erratum，实际基数就不是 14

**裁决**: **采纳移动方案**，但目标模块应为 `_write_config_helpers`（纯 args 查询，不涉及验证规则），而非 `_write_params_validation`。

**理由**: `_challenger_requested` 读 args 返回 bool，与 `_resolve_write_model_override_name`（读 args 返回 str）同属 config helpers 语义。`_write_params_validation` 应只包含返回 `str | None`（错误消息）的验证函数。

## 2. C1 核对点二: `setup_model_name` monkeypatch 迁移

### 2.1 源码事实

- `write.py:23`: `from dayu.cli.dependency_setup import ..., setup_model_name, ...`
- `write.py:190-203`: `_resolve_write_model_override_name` 调用 `setup_model_name(args)`
- 测试 monkeypatch: `dayu.cli.commands.write.setup_model_name`（patch write 模块的 import binding）

### 2.2 迁移后依赖链

Slice 5 迁移后:
- `_write_config_helpers.py` 需 import `setup_model_name`（因为 `_resolve_write_model_override_name` 调用它）
- `write.py` 通过 `_write_config_helpers._resolve_write_model_override_name` 间接使用

**两种方案**:

| 方案 | `_write_config_helpers` import | `write.py` import | monkeypatch 目标 |
|------|-------------------------------|-------------------|-----------------|
| A: 直接 import | `from dayu.cli.dependency_setup import setup_model_name` | `from ._write_config_helpers import _resolve_write_model_override_name` | 需 patch `_write_config_helpers.setup_model_name` |
| B: re-export chain | `from dayu.cli.dependency_setup import setup_model_name` | `from ._write_config_helpers import setup_model_name, _resolve_write_model_override_name` | patch `write.setup_model_name` 仍有效 |

### 2.3 方案裁决

**方案 B（re-export）正确且必要**:

1. **不违反禁止 wrapper/seam 约束**: re-export 不是 wrapper（不增加语义），不是 seam（不改变行为），是 Python 标准的依赖链管理
2. **patch 点一致性**: monkeypatch 的黄金法则是 patch 使用点，不是定义点。`write.py` 通过 re-export 的 `setup_model_name` 使用，patch `write.setup_model_name` 正确
3. **测试迁移最小化**: 11 处 monkeypatch 无需修改（仍 patch `write.setup_model_name`）
4. **未来抽取路径**: 当 `_write_config_helpers` 独立使用时，其自身的 `setup_model_name` binding 自然成为 patch 目标

**实施方案**:
```
# _write_config_helpers.py
from dayu.cli.dependency_setup import setup_model_name  # 直接 import

# write.py
from ._write_config_helpers import setup_model_name  # re-export（非 wrapper）
```

**验证要求**:
- pyright: 无新增 import 路径错误
- 11 处 monkeypatch 无需修改，全部保持 `dayu.cli.commands.write.setup_model_name`
- 禁止在 `_write_config_helpers` 中添加 def setup_model_name(...) wrapper
