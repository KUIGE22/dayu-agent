## Findings

### DR-001-已修复-[高]-帮助输出仍会泄露 secret-shaped prog

- **入口/函数**: `RedactingArgumentParser.parse_args(["--help"])` 进入 argparse 帮助输出路径
- **文件(行号)**: `utils/validate_handoff_docs.py:1026`
- **输入场景**: 调用方以包含 secret-shaped 子串的路径作为 `prog`，随后请求 `--help` 或 `-h`
- **实际分支**: argparse 的帮助 action 调用 `print_help()` / `format_help()`；当前改动只重写 `format_usage()` 和 `error()`，该路径不经过这两个脱敏出口
- **预期行为**: 共享 redacting parser 的所有用户可见输出都不包含原始 secret-shaped 文本；帮助仍以退出码 `0` 写入 stdout
- **实际行为**: 帮助输出的 usage 行保留原始 `prog`，例如 `usage: tools/<secret>/gate [-h]`
- **直接证据**: 独立探针得到 `{"exit_code": 0, "secret_exposed": true, "redacted_present": false}`；`tests/test_validate_handoff_docs.py:165` 新增的回归测试稳定失败于 `assert key_value not in captured.out`。DeepSeek implementation artifact 也把 `format_help()` 未覆盖列为 residual risk
- **影响**: 用户仅执行常规 `--help` 就可能把 API key 形状写入终端、CI 日志或采集日志；共享脱敏 parser 的安全边界不完整
- **建议改法和验证点**: 在所有 argparse 输出真正写往 file 前的统一出口执行 `redact_secret_shapes`，避免继续逐个覆盖 `format_usage`、`format_help` 和各类错误路径；必须让 help 回归测试、现有 prog/error 测试和原有 parser-error 测试全部通过，并保持 help 的 stdout、退出码 `0` 与 error 的 stderr、退出码 `2`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
