## 3. Findings

### F1-未修复-中-`source_fingerprint` 无明确定义与获取路径

- **位置**: §6.3 `EvidenceLocatorProjection` 字段列表；S13-CTRL-03 source/processed identity closure
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 列出 `source_fingerprint` 作为 projection 精确字段，S13-CTRL-03 要求 processed 闭合 `source_fingerprint` 与 source meta 的 exact match；但未定义 `source_fingerprint` 的语义、来源或计算方式。
- **反例/失败场景**: Implementation agent 不知道 `source_fingerprint` 是什么——是 `FileObjectMeta.sha256`？是 `meta.json` 中某个字段？是计算出来的？是 processor 产出的？不同假设会导致完全不同的实现。现有 `DocumentMeta = dict[str, Any]`（`domain/document_models.py:23`）是 loose 类型，没有已知字段契约。
- **为什么有问题**: `source_fingerprint` 是 identity closure 的关键字段，用于 source/processed 版本一致性校验。如果定义缺失，implementation agent 只能猜测或发明，违反 AGENTS.md "禁止魔法字符串"和"schema 变更一律按全新 schema 起库"约束。
- **直接证据**: §6.3 列出 `source_fingerprint` 字段；S13-CTRL-03 提到 "source_fingerprint" 但未给定义；`domain/document_models.py:23` 定义 `DocumentMeta = dict[str, Any]`；`repository_protocols.py` 无 `get_source_fingerprint` 方法。
- **影响**: Implementation agent 无法确定实现路径；可能发明第二真源或做出不兼容假设。
- **建议改法和验证点**: Plan 必须精确定义 `source_fingerprint`：(a) 语义——是 source 主文件内容 hash、source meta hash、还是 processor 派生值？(b) 来源——从 `SourceDocumentRepositoryProtocol.get_source_meta()` 的哪个字段读取？(c) 如果当前 meta 中不存在该字段，是 Slice 1.3 新增还是 Slice 1.2 已定义？验证点：implementation agent 无需猜测即可确定 fingerprint 的精确计算/读取路径。
- **修复风险（中）**: 需要在 plan 中补充 2-3 句精确定义。
- **严重程度（中）**: 不阻塞整体架构，但阻塞 implementation agent 的确定性实施。

### F2-未修复-中-XBRL fact canonical bytes 格式未定义

- **位置**: §6.3.2 table 第五行 xbrl_fact locator；S13-CTRL-01 canonical JSON
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 说 xbrl_fact citation bytes 是 "用 exact concept 查询，逐条 canonical fact row 求 SHA；必须恰好一条匹配"。但未定义 "canonical fact row" 的 JSON 序列化格式。
- **反例/失败场景**: `query_xbrl_facts` 返回 `facts: list[dict[str, Any]]`（`result_types.py:289`），每个 fact 是 loose dict。不同 processor 可能返回不同字段集合。如果没有 canonical fact row 的精确字段顺序和内容定义，SHA 计算不可复现，FS/S3 也无法产生相同值。
- **为什么有问题**: §6.3.1 要求 "projection 的 `to_json()` 使用固定字段顺序语义和 canonical JSON"，但 xbrl_fact 的 "canonical fact row" 没有对应的字段清单。implementation agent 必须自行决定哪些字段进入 canonical、排序规则和缺失字段处理。
- **直接证据**: §6.3.2 第五行 xbrl_fact；`result_types.py:283-301` 定义 `XbrlQueryResult` 的 `facts: list[dict[str, Any]]`；`service.py:1160-1187` 显示 `query_xbrl_facts` 通过 cast 桥接 loose dict。
- **影响**: FS/S3 路径下 canonical fact SHA 不可复现；不同 processor 输出不同 SHA 导致 locator 失效。
- **建议改法和验证点**: Plan 应精确定义 xbrl_fact canonical row 的字段集合（至少 concept、value、unit、period_end、decimals），排序规则（字典序 key），缺失值处理（None 不参与还是序列化为 null）。或明确引用 `query_xbrl_facts` 返回的 facts 中哪几个字段构成 canonical。
- **修复风险（低）**: 补充 1-2 句精确定义即可。
- **严重程度（中）**: 阻塞 FS/S3 一致性验证，但不影响 locator 逻辑本身。

### F3-未修复-中-table_cell locator 要求 records data 但未强制格式

- **位置**: §6.3.2 table 第四行 table_cell locator
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: Plan 说 table_cell locator 的 citation bytes 来自 `get_table` 必须为 records data，"row/column 唯一命中后"返回 canonical JSON。但现有 `get_table` 返回 `data: dict[str, Any]`，其 `kind` 可能是 `records`、`markdown` 或 `raw_text`（`service_helpers.py:913-970`）。
- **反例/失败场景**: 如果 processor 返回 `data_format="markdown"`，`_build_table_data_payload` 会返回 `kind: "markdown"` 带 `markdown` 字段。此时 table_cell locator 无法做 row/column 唯一命中。Plan 没有说明 (a) 是拒绝非 records 表格还是 fallback，(b) 如何从 markdown 表格提取 records，(c) markdown 表格的 canonical bytes 是什么。
- **为什么有问题**: table_cell 是五类 locator 之一，其 citation bytes 精确依赖 records data 格式。如果 processor 产出 markdown 表格，locator 无法工作，但 plan 没有说明拒绝策略。
- **直接证据**: `service_helpers.py:913-970` `_build_table_data_payload` 三种输出；§6.3.2 第四行 "get_table 必须为 records data"。
- **影响**: 非 SEC filing（如上传的材料、港股/A股）的表格可能只有 markdown 格式，导致 table_cell locator 对这些文档不可用。Plan 未说明这是预期行为还是缺陷。
- **建议改法和验证点**: Plan 应明确：(a) table_cell locator 拒绝非 records 格式的表格（fail closed），或 (b) 定义 markdown-to-records 的转换规则。选择 (a) 更安全且 implementation 更简单。验证点：测试覆盖 markdown 表格被 table_cell locator 拒绝的场景。
- **修复风险（低）**: 明确 fail closed 即可。
- **严重程度（中）**: 不影响架构，但影响部分文档的 locator 可用性。

### F4-未修复-低-`FileObjectMeta.sha256` 可选语义与 `primary_content_sha256` 计算路径

- **位置**: S13-CTRL-03 `primary_content_sha256` 定义
- **问题类型**: 最佳实践偏离 / 不可直接实施
- **当前写法**: Plan 说 `primary_content_sha256` "始终是 source repository 主文件 exact bytes 的实算 SHA；可选 `FileObjectMeta.sha256` 若存在必须相等，不存在不能跳过实算"。
- **反例/失败场景**: `FileObjectMeta.sha256: Optional[str]`（`domain/document_models.py:36`）确实是可选的。Plan 的 "若存在必须相等，不存在不能跳过实算" 语义清晰，但 implementation agent 需要知道：(a) 从哪个 repository method 读取主文件 bytes（`get_primary_file` 返回 `FileObjectMeta`，`get_primary_source` 返回 `Source` 后者有 `content` bytes），(b) 两者的调用顺序和 error handling。
- **为什么有问题**: Plan 假设 implementation agent 知道 `get_primary_source` 返回 `Source` 对象（`repository_protocols.py:183-186`）且可通过它读取 bytes，但这需要 cross-reference repository protocol 的方法签名。
- **直接证据**: `repository_protocols.py:175-186` `get_primary_file` 和 `get_primary_source` 方法；`domain/document_models.py:36` `sha256: Optional[str] = None`。
- **影响**: 低风险，implementation agent 可从 repository protocol 自行推断。
- **建议改法和验证点**: 在 S13-CTRL-03 补充一句引用 `get_primary_source` 的精确方法签名即可。
- **修复风险（低）**: 补充一句话。
- **严重程度（低）**: 不阻塞实施。

### F5-未修复-低-`FinsToolService` citation 可能泄漏路径/URI

- **位置**: S13-CTRL-01 "任何 DTO/receipt/error/日志不得包含 workspace path、URI、bucket/key、storage handle 或原始 meta `files[].uri`"
- **问题类型**: 测试缺口
- **当前写法**: Plan 的 S13-CTRL-07 tests 包含 "输出递归 path/URI/bucket/handle secret scan"。但 `FinsToolService._build_citation`（`service.py:1450-1464`）从 meta.json 读取数据构建 citation dict。现有 meta.json 的 `files[].uri` 字段包含本地路径。如果 evidence locator 的 citation 复用现有 citation 方法，可能泄漏路径。
- **反例/失败场景**: `get_document_sections` 返回的 `citation` dict 可能包含 meta.json 中的 `files[].uri`（本地路径）。如果 evidence locator 的 `read_citation_projection` 复用或包含此数据，违反 S13-CTRL-01。Plan 的测试要求 "secret scan" 但没有定义 scan 的具体模式。
- **为什么有问题**: 现有 citation 方法是 tool 层面的，不是 evidence locator 层面的。evidence locator 的 citation 应该只包含 canonical bytes 的 SHA，而不是原始路径。但 plan 没有明确区分这两层 citation。
- **直接证据**: `service.py:1450-1464` `_build_citation`；S13-CTRL-01 禁止路径泄漏；S13-CTRL-07 要求 secret scan。
- **影响**: 低风险，implementation agent 应该能区分 tool citation 和 evidence citation。
- **建议改法和验证点**: 在 S13-CTRL-06 call path 明确 evidence locator 的 citation 只来自 canonical bytes SHA，不复用 `_build_citation` 的 path 数据。
- **修复风险（低）**: 补充一句说明。
- **严重程度（低）**: 不阻塞实施。

### F6-未修复-中-document locator 的空 payload `{}` 与 artifact_kind 组合语义模糊

- **位置**: §6.3.2 table 第一行 document locator
- **问题类型**: 契约缺失
- **当前写法**: Plan 说 document locator 的 strict payload 是 `{}`，citation bytes 分别为 "source 为主文件原始 bytes" 和 "processed 为 canonical JSON"。但 `{}` payload 不携带任何区分信息，完全依赖 `artifact_kind` 字段区分 source/processed。
- **反例/失败场景**: 当 `artifact_kind=source` 时，citation bytes 是 "主文件原始 bytes"。但 "主文件" 的定义不明确——是 `get_primary_source` 返回的 `Source.content`？还是 `FileObjectMeta` 指向的文件？对于 filing，主文件是 XBRL instance 还是 HTML？对于 material，主文件是 PDF 还是 markdown？Plan 没有定义 "主文件" 的选取规则。
- **为什么有问题**: document locator 是最基础的 locator kind，如果 "主文件" 语义不明确，所有下游 locator 的 `primary_content_sha256` 都无法计算。
- **直接证据**: §6.3.2 第一行 "source 为主文件原始 bytes"；`repository_protocols.py:183-186` `get_primary_source` 方法。
- **影响**: implementation agent 必须自行决定 "主文件" 选取规则。
- **建议改法和验证点**: Plan 应明确 "主文件" 等同于 `SourceDocumentRepositoryProtocol.get_primary_source()` 返回的 `Source` 对象的 bytes。验证点：所有 source kind 的主文件都通过 `get_primary_source` 获取。
- **修复风险（低）**: 补充一句引用 repository method。
- **严重程度（中）**: 阻塞 document locator 的确定性实施。

### F7-未修复-中-citation exact bytes 的 canonical JSON 格式对 document processed 不完整

- **位置**: §6.3.2 table 第一行 document locator processed citation
- **问题类型**: 契约缺失
- **当前写法**: Plan 说 document processed citation bytes 是 `canonical JSON {"sections": <get_document_sections result>, "tables": <list_tables result>}`。但 `get_document_sections` 和 `list_tables` 返回的 result 包含 `citation` 字段（含 meta 数据）和 `ticker`/`document_id` 等冗余字段。如果直接序列化整个 result，canonical bytes 会包含这些冗余信息，且 `citation` 字段可能包含路径。
- **反例/失败场景**: `get_document_sections` 返回 `DocumentSectionsResult` 含 `ticker`、`document_id`、`sections`（含 `citation`），`list_tables` 返回 `TablesListResult` 含 `ticker`、`document_id`、`tables`（含 `citation`）。如果 canonical JSON 包含这些，(a) `citation` 中的路径泄漏到 canonical bytes，(b) canonical bytes 包含冗余的 ticker/document_id，(c) 非确定性（`citation` 中可能有 timestamp 等动态字段）。
- **为什么有问题**: canonical JSON 的目的是产生可复现的 SHA。如果包含动态或路径数据，SHA 不可复现。
- **直接证据**: §6.3.2 第一行 "canonical JSON `{"sections": <get_document_sections result>, "tables": <list_tables result>}`"；`result_types.py:96-102` `DocumentSectionsResult` 含 `citation: dict[str, Any]`。
- **影响**: canonical bytes 不可复现；FS/S3 无法产生相同 SHA。
- **建议改法和验证点**: Plan 应明确 document processed citation bytes 只序列化 sections 的结构化数据（ref/title/heading）和 tables 的结构化数据（table_ref/headers/row_count），不包含 `citation`/`ticker`/`document_id` 等动态或冗余字段。或定义一个 "canonical sections/tables projection" 子集。
- **修复风险（中）**: 需要定义 canonical projection 的精确字段子集。
- **严重程度（中）**: 阻塞 FS/S3 一致性。

## 4. Open questions

## 6. Conclusion

**PASS-WITH-RISKS**

Plan 的整体架构设计合理：logical repository namespace、五类 locator、source/processed closure、public reference 边界、FinsService delegate 和 allowlist 都是正确的方向。S13-CTRL-01..08 的约束粒度适当。

但有 4 个 Medium finding 阻塞确定性实施：`source_fingerprint` 定义缺失（F1）、XBRL fact canonical bytes 格式未定义（F2）、table_cell records 强制未明确（F3）、document "主文件" 语义模糊（F6）、document processed canonical JSON 格式不完整（F7）。这些都需要 plan 补充精确定义后才能交给 implementation agent。

Open: 0 High / 4 Medium / 1 Low。
