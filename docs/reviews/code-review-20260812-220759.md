### 1-未修复-[高]-合法 0001 legacy health snapshot 因 created_at 与 observed_at 不同而无法投影

- **入口/函数**: `SourceHealthSnapshotProjection.__post_init__`
- **文件(行号)**: `dayu/investment/domain/source_health.py:162`、`dayu/investment/domain/source_health.py:164`
- **输入场景**: 读取 0001 已存在的 legacy snapshot（`health_state_version=None`），其业务 `observed_at` 由写入方提供，而 `created_at` 由数据库 `DEFAULT transaction_timestamp()` 生成；两者合法地不同。
- **实际分支**: constructor 在判断 `health_state_version is None` 之前，无条件要求 `created_at == observed_at`，因此直接抛 `ValueError`，永远到不了行 166–171 的 legacy 分支。
- **预期行为**: 0005 只给 legacy row 增加 nullable version 并保留其可读性；`created_at == observed_at` 是新 provider/operator snapshot 的单时钟契约，不能追溯施加给 0001 历史数据（计划 §3.2.3、§8.2）。
- **实际行为**: 任何历史上以回填/业务 observation 时刻写入、而在另一个 transaction 时刻创建的合法 row，都无法构造成计划声明支持的 legacy projection。
- **直接证据**: 当前 DTO 行 162–165 先校验两个时间相等，行 166 才识别 legacy。accepted 0001 migration `dayu/investment/storage/migrations/versions/0001_platform_foundation.py:479` 把 `observed_at` 定义为显式 NOT NULL，而行 484 给 `created_at` 独立的 `transaction_timestamp()` default，没有相等 CHECK。现有 direct test 的所谓 legacy 只是 `replace(provider, health_state_version=None)`，沿用了本来就相等的两个时间，未证明真实 0001 shape。
- **影响**: 升级后合法历史 health 数据在查询/分页时触发领域不变量错误，导致整个 subscription 的历史读取失败；这违反计划明确保留 legacy row 可读性的升级边界。
- **建议改法和验证点**: 先按 `health_state_version` 分支：legacy 只验证两个时间各自 aware UTC，不要求相等；version>0 的 provider/operator snapshot 再要求 single-clock equality。新增一个 `version=None, created_at != observed_at` 的 direct test，并在真实 migration/read lane 插入 0001 legacy row后升级、读取验证。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-[中]-连续失败会因配置阈值变化把 health 从 failing 反向降为 degraded，并发送反向告警

- **入口/函数**: `build_source_health_transition` → `_derive_alert_kind`
- **文件(行号)**: `dayu/investment/domain/source_health.py:442`、`dayu/investment/domain/source_health.py:444`、`dayu/investment/domain/source_health.py:460`、`dayu/investment/domain/source_health.py:507`
- **输入场景**: 已持久化的 `current` 为 `FAILING / consecutive_failures=2 / provider_unavailable`；subscription config 后来调整为 `failing_after=5, disable_after=8`；下一次 observation 仍是相同 `FAILED / provider_unavailable`。这是合法输入：health DTO 不把历史状态与当前阈值绑定，config 也是每次调用传入的当前事实。
- **实际分支**: failure 分支先把次数增为 3，再只按当前 config 阈值重新计算状态；3 小于 5，因此赋值 `DEGRADED`。`_derive_alert_kind` 只判断状态/错误是否相同，随后返回 `SourceAlertKind.DEGRADED`。
- **预期行为**: 持续失败只能保持或升级 non-healthy 状态；只有成功/no-change 才恢复 healthy。告警只允许“进入/升级 degraded/failing/disabled”或“同状态 error 改变”，不得为 failing→degraded 的逆向转换写 degraded alert（计划 §7.1–§7.2）。
- **实际行为**: 同一错误继续失败时，公开 health 从 failing 变得更健康，同时产生一个 degraded 告警。只读复现得到 `failing -> degraded, alert=degraded`。
- **直接证据**: `failures = current.consecutive_failures + 1` 后，行 444–449 完全按新阈值覆盖 `status`；行 507–511 对任何非 healthy 且状态不同的转换都发 alert，没有 severity 单调性判断。现有测试只覆盖 healthy→degraded→failing→disabled，以及 degraded 在阈值内保持；没有覆盖 config drift 下的既有 failing/disabled 以外状态。
- **影响**: 监控/read model 会在实际故障继续累积时显示错误改善，并产生语义相反的告警，破坏 health 状态与告警的确定性含义。
- **建议改法和验证点**: 对 partial/failed 先按新 failure count 计算候选状态，再与 `current` 的 non-healthy severity 取不降级结果；success/no-change 仍显式重置 healthy。`_derive_alert_kind` 应只允许 severity 上升，或同状态 `safe_error_code` 变化。新增 failing 状态下提高/降低 thresholds、同/异 error 的表驱动测试，断言状态、version 和 alert。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-[中]-官方 payload/snapshot builder 可生成同模块 parser 必然拒绝的超限文档

- **入口/函数**: `build_source_execution_snapshot_document`、`build_manual_source_sync_payload_document`、`build_scheduled_source_sync_payload_document` → 对应 parser
- **文件(行号)**: `dayu/investment/domain/source_payload.py:482`、`dayu/investment/domain/source_payload.py:560`、`dayu/investment/domain/source_payload.py:590`、`dayu/investment/domain/source_payload.py:633`
- **输入场景**: 构造合法 typed scheduled payload，但给未设长度上限的 `schedule_key` 一个足够长的非空字符串，再调用 public builder。Snapshot/manual 路径也可由未设长度上限的强标识、forms/text 字段形成相同问题。
- **实际分支**: 三个 builder 直接调用通用 `build_canonical_document` 并返回，不检查 `MAX_SOURCE_DOCUMENT_BYTES`；parser 随后经 `_decode_source_document(..., max_bytes=8_388_608)` 拒绝。只读复现中 builder 返回 `8,388,916` bytes，立即交给 `parse_source_sync_payload` 得到 `ValueError: canonical document 超过大小上限`。
- **预期行为**: canonical builder/parser 对所有可构造 DTO 保持 round-trip；payload/snapshot/evidence/receipt/result 均受 8 MiB cap 约束，超限应在 builder 边界稳定拒绝，不能产生官方不可读 document（计划 §3.2、§3.5）。
- **实际行为**: public builder 成功产生一个自己的 public parser 不能读取的 durable payload；如果 caller 先持久化 Job，失败会延迟到 acquire/parser，形成不可执行的 durable row。
- **直接证据**: 行 495–499、575–587、605–617 的 builder 返回路径没有 cap 校验；行 633–638 parser 才首次施加 8 MiB 上限。现有 round-trip tests 只使用小对象；architecture cap test只验证 decoder one-over，不验证每个 public builder 的对称边界。
- **影响**: 官方构造路径可制造无法执行/恢复的 durable Job payload 或不可读 snapshot，破坏 canonical representation 的单一真源与 response-loss/replay 假设。
- **建议改法和验证点**: 为每个 public canonical builder 在返回前统一验证 `len(document.canonical_bytes) <= MAX_SOURCE_DOCUMENT_BYTES`（或调用同一严格 helper），并对 snapshot/manual/scheduled 分别加入 exact-cap 与 one-over builder→parser 测试；不要只在 parser 或存储层补救。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 5-未修复-[中]-forms 的“防御性复制”会把字符串静默解释为多个合法 form

- **输入场景**: Python caller 违反 `forms: tuple[str, ...]` 签名传入字符串，例如 `forms="10K"`。字符串本身可迭代，且字符 `"1"`、`"0"`、`"K"` 都满足当前 form regex。

- **预期行为**: 新增公开 DTO 的字段类型严格闭合；tuple 只做防御性快照，不能把错误的标量/容器语义转换成合法业务请求。错误类型应在 provider 调用前 fail closed。
- **实际行为**: 无效 caller 输入被接受并改变业务语义，后续 connector 会把三个错误 form 当作真实查询集合。

- **影响**: 错误 provider 查询、无结果或错误 observation 会以合法 typed config 身份继续传播，根因在 public DTO 边界被掩盖。
- **建议改法和验证点**: 在转换前要求 runtime 值为精确 tuple（至少显式拒绝 `str`/`bytes` 与非 tuple iterable），随后再逐个要求精确 `str` 和 canonical form；增加 string、list、generator 以及 tuple subclass 的明确 acceptance/rejection tests。
