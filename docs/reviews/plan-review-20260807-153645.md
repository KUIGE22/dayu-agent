## Findings

### F-01 [HIGH] S11 Phase B execution_options 预计算声明与 adapter 实现矛盾

**计划行号**: §11c 表格行 15–16（行 642–643）、§11e（行 811–825）、§11f 关键特性（行 889–893）

**矛盾描述**:

计划 §11c 表格对 Phase B 条目 15 (`apply`) 和 16 (`rollback`) 的 "Pre-Branch Compute" 列声明为 `_resolve_write_model_override_name + _build_execution_options`，"Adapter-Lazy Compute" 列为空——意味着 adapter 应使用 Phase B 预计算值。

§11f 行 844–846 也在 `run_write_command` 中预计算：
```python
write_model_override_name = _resolve_write_model_override_name(args)
execution_options = _build_execution_options(args)
```

但 §11e 行 813–825 中 `_run_apply_adapter` 和 `_run_rollback_adapter` 的实现体**内部再次调用** `_build_execution_options(ctx.args)`：
```python
def _run_apply_adapter(ctx: _WriteCommandContext) -> int:
    execution_options = _build_execution_options(ctx.args)  # ← 重算！
    return _run_write_model_configuration_application(...)
```

§11f 行 893 的注释自相矛盾：先说"adapter 接受 execution_options 参数"（实际签名 `Callable[[_WriteCommandContext], int]` 不接受），然后说"简洁方案: Phase B adapter 也自己调 `_build_execution_options(ctx.args)`"——这直接否定了表格中"预计算"的声明。

**源码证据**: 当前 `write.py:4810-4821` 确实只计算一次 `execution_options` 后传入函数。计划声称保持"精确一次"语义，但 adapter 实现改为"每 adapter 一次"。

**失败路径**: `_build_execution_options` 如果有副作用（如日志、计数器），Phase B 路径会执行两次；即使纯函数，也违反了计划 §4.2 "行为不变量"——现状计算一次，重构后计算两次。

**v3.5 修改要求**:
1. 二选一：(a) 扩展 `_WriteCommandContext` 添加 `execution_options: ExecutionOptions` 字段，Phase B adapter 从 context 读取；(b) adapter 签名改为接受 `execution_options` 参数，通过闭包或工厂注入。
2. §11c 表格的 "Adapter-Lazy Compute" 列和 "Pre-Branch Compute" 列必须与实际 adapter 实现一致。
3. 删除 §11f 行 893 的矛盾注释，明确选择 (a) 或 (b)。

### F-02 [HIGH] S0 — 两个 Protocol regression fixture 是空测试（`pass`）

**计划行号**: §5 Slice 0 行 346–357

**问题描述**: `test_write_dispatch_protocol_rejects_unknown_field` 和 `test_research_template_dispatch_protocol_rejects_unknown_field` 函数体为 `pass`，不执行任何断言。

```python
def test_write_dispatch_protocol_rejects_unknown_field() -> None:
    """Protocol 拒绝未声明字段 —— 编译期由 pyright 检查，此处文档化。"""

```

**失败路径**:
- pytest 运行 0 个断言的测试会显示为 passed，给人"已验证"的假象。
- 若有人删除 `WriteDispatchArguments` 中的字段但 pyright 未运行（CI 缓存、本地跳过），此测试不会捕获回归。
- 违反 CLAUDE.md "单文件测试覆盖率目标 >= 80%"——空函数覆盖率为 0%。

**v3.5 修改要求**:
1. 至少使用 `typing.get_type_hints(WriteDispatchArguments)` 验证声明的字段集合不为空且包含已知关键字段（如 `revalidate_write_model_configuration_manual_recovery_incident_dossier`）。
2. 或者，直接删除这两个空测试，在 `conftest.py` 中添加 pyright 集成检查，避免用空测试冒充覆盖率。

### F-05 [MEDIUM] 审计命令 grep 模式不完整，无法验证 16 条目

**计划行号**: §11c 行 624

**问题描述**: 审计命令为：
```bash
grep -n "if bool(getattr\|if bool(str(getattr" dayu/cli/commands/write.py | sed -n '4602,5263p'
```

`\|` 没有闭合转义分组（应为 `\(…\|…\)`），虽然 GNU grep 默认 BRE 支持未分组的 `\|`，但此命令只匹配 `if bool(getattr` 和 `if bool(str(getattr` 两种模式。

实际源码中 Phase A 有 **18** 个条件分支（14 个 boolean + 3 个 path predicate + 1 个 `if bool(getattr(args, "recover_..."` ）。但 path predicate 用的是 `if bool(str(getattr(args, ...` 模式——grep 应该能匹配。

我逐行验证后确认：Phase A 确实是 14 个条目（与表格一致），Phase B 2 个，共 16。但 grep 命令的 `sed -n '4602,5263p'` 范围包含了 Phase B–H 的所有分支（不仅 Phase A），读者无法从命令输出区分 Phase A 和 Phase B。

**v3.5 修改要求**: 修正 grep 命令，添加行号范围限定到 Phase A（`sed -n '4636,4808p'`），或在命令后注明"输出包含所有 phase，Phase A 条目为行 4636–4808 范围内的前 14 条"。

### F-06 [MEDIUM] `_WriteCommandContext` 不含 `execution_options`，Phase-specific typed context 缺失

**计划行号**: §11b 行 600–609

**问题描述**: `_WriteCommandContext` 仅有 `args: DayuCliArguments` 和 `paths_config: WorkspaceConfig` 两个字段。但 Phase A 的 3 个 adapter（clear/verify/recover）和 Phase B 的 2 个 adapter 都需要 `execution_options`。

当前设计要求每个需要 `execution_options` 的 adapter 自行调用 `_build_execution_options(ctx.args)`——这导致：
1. 同一 `args` 多次计算 `execution_options`（F-01 的根因）。
2. adapter 签名 `Callable[[_WriteCommandContext], int]` 无法表达"此 adapter 需要 execution_options"的类型约束。

**v3.5 修改要求**: 至少提供两种方案之一的明确决策：
- **方案 A**: `_WriteCommandContext` 添加 `execution_options: ExecutionOptions | None = None`，Phase B 创建 context 时注入。
- **方案 B**: 保持 context 精简，但 adapter 签名分为 `Callable[[_WriteCommandContext], int]`（不需要 execution_options 的 11 个）和带额外参数的变体（需要的 5 个）。
- 在计划中明确选择并更新所有受影响的 §11 代码。
