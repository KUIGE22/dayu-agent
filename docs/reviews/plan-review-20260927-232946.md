### 01-未修复-低-staged diff 检查安排在 stage 之前而失去验收对象

- **位置**: 澄清 V1 §“实施范围与验收”第 39 行。
- **问题类型**: 门序 / 验收证据缺口。
- **当前写法**: “冻结修复后重跑 … 文件覆盖率及 staged diff 检查；非作者代码复审逐条关闭 M1/M2。只有 S31-B 整片 fresh `0/0/0` 且接受报告落盘后才 stage/commit。”
- **反例/失败场景**: 当前 S31-B 六文件均未 stage；实施者严格按这段顺序做 staged diff 检查，会检查到空 index。之后再 stage 时误加入越界路径，先前的空检查仍为绿。
- **为什么有问题**: allowlist 与最终提交物的检查必须针对实际 index；stage 之前的 `git diff --cached` 不能证明后续 staged 集合。代码审查的冻结身份也不能代替最终 staged 内容核对。
- **直接证据**: V1:37 限六个实现/文档路径，V1:39 将 staged 检查置于 stage 之前；本次只读 `git status --short` 显示六文件为 modified/untracked，没有 staged 文件。
- **影响**: staged allowlist 门无法证明最终 commit 内容，破坏本澄清希望保持的冻结与审查边界。
- **建议改法和验证点**: 精确顺序写为：实现/测试通过与最终文件 SHA 冻结 → 非作者代码复审关闭 M1/M2 → Controller 限定接受并落盘 → 仅 stage 明确 allowlist 的目标与接受证据 → 对**实际 index** 执行 staged path/内容/`diff --check` 与冻结 SHA 核对 → 确认仍 fresh `0/0/0`、无 stage 后漂移 → commit。若 staged 检查失败，撤回越界 staging 并在必要时重审，不直接提交。stage 前可另做 unstaged diff 检查，但不得把它称为最终 staged gate。
- **修复风险（低/中/高）**: 低，文档顺序澄清。
