### 001-未修复-高-公开的 startup 注入点在冷启动时循环导入失败

- **入口/函数**: `import dayu.startup.platform`，以及 README 推荐的 `dayu.startup.platform.build_platform_composition()` 注入点。
- **文件(行号)**: `dayu/startup/platform.py:15-18`；`dayu/services/__init__.py:35-39`；`dayu/services/startup_preparation.py:39`。
- **输入场景**: 一个未预先导入 `dayu.services` 的进程，按公开模块路径直接导入平台组合注入点。
- **实际分支**: `platform.py` 导入 `dayu.services.protocols` 时，Python 先执行 `dayu.services.__init__`；其第 35 行导入 `startup_preparation`，后者第 39 行又从尚未完成初始化的 `dayu.startup.platform` 导入 `build_platform_composition`。
- **预期行为**: 文档声明的 startup 注入点必须在冷启动下可导入，且不依赖调用方偶然先导入 Service 包。
- **实际行为**: 直接复现 `python -c 'import dayu.startup.platform'` 失败：`ImportError: cannot import name 'build_platform_composition' from partially initialized module 'dayu.startup.platform'`。
- **直接证据**: 上述真实导入栈为 `platform.py:15 -> services/__init__.py:35 -> startup_preparation.py:39 -> platform.py`。`tests/application/test_service_startup_preparation.py:16` 先导入 `dayu.services.protocols`，因此掩盖了这个冷启动路径，也没有 direct-import regression test。
- **影响**: 公开 platform composition root 在合法调用顺序下不可用；后续 provider 或独立启动装配会在 import 阶段失败，不能进入预期的 fail-fast 设置校验。
- **建议改法和验证点**: 消除 package initializer 与 `dayu.startup.platform` 的双向模块依赖（不能以 lazy import 作为临时 seam）；明确 stable import ownership 后添加 fresh-interpreter/direct-import 测试，并覆盖 CLI、WeChat、Web 三条既有启动入口。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### 002-未修复-中-非法 env-name 的异常会回显被误传的 secret

- **入口/函数**: `PlatformSettings.__post_init__()` → `validate()`。
- **文件(行号)**: `dayu/investment/config.py:108-114`。
- **输入场景**: 调用方误把 DSN 或 auth key 值传给公开构造器的 `postgres_dsn_env` 等 env-name 参数。
- **实际分支**: `_ENV_NAME_PATTERN.fullmatch(env_name) is None`，随后异常 f-string 插入未经 redaction 的 `env_name!r`。
- **预期行为**: Slice 0.2 的“只记录 env name、不回显 secret”契约也应覆盖 `repr` 和异常路径；错误消息只能标识字段/环境变量名，不能回显不可信输入。
- **实际行为**: 复现以 `postgres://review-user:review-secret@db/dayu` 构造禁用 development settings，得到：`postgres_dsn_env 必须是合法环境变量名称，收到 'postgres://review-user:review-secret@db/dayu'`。
- **直接证据**: `config.py:112-114` 直接格式化字段值；`tests/investment/test_platform_config.py:355-377` 只断言成功加载后的 `str(settings)` 不含 secret，未覆盖构造异常。
- **影响**: 配置错误通常会被启动日志记录；一次参数接线错误即可把 DSN 密码或 key 写入日志/错误上报，违背本 slice 的 secret-redaction hard requirement。
- **建议改法和验证点**: 异常只报告字段名和固定规则，不格式化候选值；新增 DSN、auth key、对象存储 URL 三类非法直构输入的异常 redaction 测试。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。

### 003-未修复-中-平台 fail-fast 发生在 Host 副作用和 recovery 之后，失败路径不原子

- **入口/函数**: `prepare_host_runtime_dependencies()`。
- **文件(行号)**: `dayu/services/startup_preparation.py:196-227, 228-232`。
- **输入场景**: `DAYU_PLATFORM_ENABLED=1`、`DAYU_PLATFORM_PROFILE=production`，但任一 required DSN/object/redis/auth key 缺失；或 settings 合法但 provider 缺失/抛错。
- **实际分支**: 函数先创建 `HostStore` 并调用 `initialize_schema()`，构造 Host，执行 `recover_host_startup_state()`；直到第 228 行才加载平台设置、第 229-232 行才可能抛出 `PlatformSettingsError` 或 `PlatformCompositionError`。
- **预期行为**: production 配置和 provider 是 startup admission 条件，应在任何持久化初始化、Host 构造或恢复副作用之前 fail-fast；失败不应留下“已恢复/已初始化但启动失败”的半提交状态。
- **实际行为**: 使用真实函数调用顺序、替换外部依赖的复现中，缺 production 变量抛出 `PlatformSettingsError` 前已经记录 `['host_store.initialize_schema', 'host.construct', 'startup_recovery']`。
- **直接证据**: 调用顺序由 `startup_preparation.py:196-232` 直接确定；`tests/application/test_service_startup_preparation.py:538-562` 只断言最终抛错，未断言上述副作用未发生。
- **影响**: 无效平台配置仍可变更 Host SQLite schema 并执行恢复/清理，使错误启动与可见治理动作交错；重试配置时难以判断上一轮是否已部分处理。
- **建议改法和验证点**: 将 `load_platform_settings()` 与组合构建前置到第一个有副作用的 Host/Fins 操作之前；对缺四类 production 配置、缺 provider、provider 抛错分别断言 `HostStore.initialize_schema`、Host 构造和 recovery 均未被调用。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 中。

### 004-未修复-中-所谓 Service Protocol 边界对任意对象开放

- **入口/函数**: `build_platform_composition()` 与 `PlatformCompositionProviderProtocol.provide_services()`。
- **文件(行号)**: `dayu/services/protocols.py:34-36, 277-300`；`dayu/startup/platform.py:45-54`；`dayu/investment/composition.py:21-35`。
- **输入场景**: provider 返回 `{"platform": "not-a-service"}`，或任意非 Service 对象。
- **实际分支**: `BaseServiceProtocol` 是零成员 runtime-checkable Protocol，因而任意对象均结构性满足它；`build_platform_composition()` 既不校验 provider，也不校验 `provide_services()` 返回映射中的值，直接将其放进组合根。
- **预期行为**: 计划要求 composition provider 只能接收/暴露 Service Protocol；非法对象必须在组合边界被拒绝，而不是作为可用平台 service 发布。
- **实际行为**: fresh process 先导入 `dayu.services.protocols` 以避开 finding 001 后，实际调用 `build_platform_composition()` 加入 `str`，输出为 `True {'platform': 'not-a-service'}`。同一解释器内 `isinstance('not-a-service', BaseServiceProtocol)`、`isinstance(1, BaseServiceProtocol)`、`isinstance({}, BaseServiceProtocol)` 均为 `True`。现有测试还在 `tests/investment/test_platform_config.py:497-553` 直接构造并认可 `PlatformComposition[str]`。
- **直接证据**: `BaseServiceProtocol` 没有成员（`protocols.py:35-36`）；`platform.py:51-53` 无运行时边界检查；测试只覆盖继承空 marker 的 fake，未覆盖非 Service 值。
- **影响**: composition root 不能作为稳定的 UI/Service 边界；未来 provider 的错误返回会延后为消费者属性错误，并允许 repository/adapter/任意对象穿透公开 composition。
- **建议改法和验证点**: 设计一个能表达并验证“可暴露 Service”的非空稳定契约，或在受控 composition root 中以明确 registry/协议做 validation；移除 `PlatformComposition[str]` 的正向测试，新增非 Service provider 返回值 fail-closed 测试。修复应同时保持 `dayu.investment` 不反向依赖上层。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 中。
