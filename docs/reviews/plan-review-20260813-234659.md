### S23-I6-PLAN-01-未修复-[高]-把 mutable retry `available_at` 当作 immutable 原入队种子使 response-loss 与 takeover 合同不可实现
- **状态**: `accepted-candidate`
- **位置**: target §3.4 930–968、§3.5 986–996、§5.1 1404–1429、§6.1/§6.2、§12 slice 6、§13.1 `test_cross_midnight_deadline_never_moves_available_at_seeded_source_query_window`
- **问题类型**: 状态机漏洞 / 数据一致性 / 并发恢复风险 / 不可直接实施 / 测试缺口
- **当前写法**: `JobIdempotencyRecord.available_at` 被称为原请求事实，并用它重建 `JobEnqueueRequest` 后重算 fingerprint；manual 与 scheduled Source snapshot 也都把 locked `job_runs.available_at` 当作原始 query-window seed，且声称 retry/takeover 不移动窗口。
- **反例/失败场景**:
  1. manual enqueue 在 `T0` commit 后 response 丢失；Job 已执行一次并在 `T1` 进入 retry。调用者重试相同 trigger 时，lookup 只能读到 `T1`。用 `T1` 重算的 fingerprint 必然不同于首次用 `T0` 持久化的 fingerprint，同一合法请求被误报 repository failure；
  2. manual/scheduled 第一次 Source acquire 在 `T0` 冻结 operation snapshot，跨 UTC 午夜 retry 把 `available_at` 改到 `T1`。takeover 用 `T1` 重验原 snapshot，会把合法 lineage 判成 `persisted_invariant`；
  3. scheduled Job 在第一次 Source acquire 前失败并跨午夜 retry，第二 attempt 会直接以 `T1` 构造窗口，违反“occurrence fire/available seed 不变”。
- **为什么有问题**: 该字段在当前 generic queue 中有两个互斥语义：首次 enqueue intent 与下一次 claim eligibility。计划没有第二个 durable、immutable 原始 seed，却要求证明原请求与 byte-identical recovery；implementation agent 无法只靠代码技巧补出已经丢失的事实。
- **直接证据**:
  - `0003_durable_jobs.py:180–190` 只有一个 `available_at`；`:678–690` 明确给 app role 该列 UPDATE 权限；`:745–747` 的 immutable guard 刻意不含该列；
  - `postgres_jobs.py:4017–4077` 的 `_mark_attempt_failed_retry` 明确 `SET ... available_at = next_available_at`，且该 helper被 handler fail、lease recovery、host reconciliation 三条 retry 路径复用；
  - `jobs.py:2048–2080` 的 fingerprint 明确包含精确 `request.available_at.isoformat()`；
  - `postgres_sources.py:1589–1594`、`:1660–1669`、`:2058–2063` 直接读取当前 `job_runs.available_at` 重建 manual/scheduled provenance；
  - Item 5 PG test `_retry_claim` 本身先调用真实 `JobStore.fail` 再 takeover；普通 same-day case因 query window只有日期而偶然不暴露跨日错误，不能证明原始 timestamp identity。
- **影响**: response-loss recovery 失效、同一合法请求假冲突、跨日窗口漂移、合法 takeover 被拒、Source operation 永久 ACTIVE、review 无法验收。
- **建议改法和验证点**:
  - 不要从 fingerprint 反推原值，也不要从当前 mutable `available_at` 猜原值；先把计划冻结为“原始 enqueue seed/identity 有独立 immutable durable owner”。
  - 在 accepted `0005` 之后规划新的 `0006` corrective migration；不要原地改写已接受的 `0003` 或 `0005`。最小设计可以是 `job_runs` 上足够重建原请求的 immutable 列，也可以是一个 canonical original-enqueue identity，但计划必须逐字段证明其足以重算现有 fingerprint，并保持当前 `available_at` 只负责 retry eligibility。
  - 明确 migration/backfill admission：对空库直接升级；对已有 row，只允许使用可证明的 durable facts backfill。已经 progression/retry 的 manual row通常无法恢复原 timestamp；one-way SHA-256 不能反演。安全默认是 migration preflight fail closed。若产品确需保留这类 row，应另行定义显式“original identity unavailable”状态及 public `unavailable` 行为，绝不能静默把当前值冒充原值。
  - 当前 raw Job schema没有对应 ORM model 的直接证据；不要为了迁移形式额外制造 ORM abstraction。计划应明确 `models_identity.py` 是否保持 zero diff，并用真实 consumer 证明；仅在存在 ORM owner 时才加 model。
  - 新 `0006` 会使 §11/§11.1/§14 的 exact key/PG owner/CLI head 发生变化。当前同一 migration PG test file“一次执行且一个 process 不组合两个 owner”的 ledger 与 `0005 + 0006` 两个 changed migration owner会冲突；纠错计划必须先选定新的 coverage owner/ledger 规则，不能只在 allowlist 末尾追加文件名。
  - hostile tests 至少覆盖：同秒外 retry、跨 UTC 午夜 retry、response 丢失后 Job 已 progressed、scheduled 首次 acquire 前 retry、manual/scheduled existing operation takeover、legacy row 无可证明 seed 时 upgrade/admission fail closed。

### S23-I6-PLAN-02-未修复-[高]-generic fingerprint 包含 request payload schema identity，但 `job_runs` 未持久化且当前 admission 允许其与 descriptor 不同
- **状态**: `accepted-candidate`
- **位置**: target §3.4 930–968、§5.1 1409–1416、§13.1 Job lookup exact reconstruction tests；`JobEnqueueRequest` 与 `PostgresJobStore.enqueue`
- **问题类型**: 契约缺失 / 数据丢失 / 不可直接实施 / 最佳实践偏离
- **当前写法**: Store 从 locked definition 取得 descriptor，从 `job_runs` 取得 payload bytes/SHA/time，构造 `CanonicalJobDocument` 与 `JobEnqueueRequest`，重算 generic fingerprint并把不一致视为 persisted drift。
- **反例/失败场景**: 当前合法调用可传 `descriptor.payload_schema_name/version = A/1`，同时传 `payload.schema_name/version = B/7`。fingerprint把 A/1 与 B/7 都纳入。`job_runs` 只保存 bytes/SHA；lookup若用 definition 的 A/1 重建 payload identity，得到另一 fingerprint并把一个合法既存 Job误判为 tamper。
- **为什么有问题**: payload schema identity 不在 canonical JSON bytes 的通用外层保证中；SHA只证明 bytes，不证明调用时 `CanonicalJobDocument.schema_name/version`。计划要求的 exact reconstruction 依赖一个从未持久化、也未由 admission equality约束的事实。
- **直接证据**:
  - `jobs.py:402–415` 显示 `CanonicalJobDocument` 的 schema name/version 是 bytes 之外的独立字段；
  - `jobs.py:1025–1060` 的 `JobEnqueueRequest.__post_init__` 不比较 payload schema 与 descriptor schema；
  - `jobs.py:2068–2080` fingerprint同时加入 descriptor schema与 request payload schema；
  - `0003_durable_jobs.py:180–190` 与 `postgres_jobs.py:92–96, 923–945` 的 `job_runs` 只存 payload bytes/SHA，无 request payload schema name/version；
  - 本轮用当前 domain constructor构造 schema mismatch 请求成功，且用 descriptor schema重建后 fingerprint 不相等（`legal_mismatch=True`, `fingerprints_equal=False`）。
- **影响**: Store 无法实现 target 所称的 immutable record；合法 generic Job 被误报 corruption；Source recovery 随内部 reconstruction 假设变化而不稳定；测试只能硬编码错误假设。
- **建议改法和验证点**:
  - 优先在同一个 `0006` corrective schema决策中持久化足够的原始 request payload identity，保留 generic Job 当前能力与现有 fingerprint算法。
  - 如果希望把 generic contract 收窄为“payload schema必须等于 descriptor schema”，必须把它当成独立 public-contract change：先证明所有 producer、schedule occurrence snapshot、历史 row都满足，再在 domain admission、Store、migration preflight和 hostile tests共同强制。不能只在 lookup 时假定相等。
  - 明确拒绝两个表面修复：删除 fingerprint中的 payload schema字段，或把 persisted fingerprint本身当作无需重算的真源。前者削弱同 key intent冲突检测，后者失去 tamper reconstruction证明。
  - backfill不得默认用 definition schema填入历史 rows；当前合同下这种 mismatch是合法的。非空库若无原 schema事实，必须 fail closed或进入明确 unavailable方案。
  - tests分别覆盖 descriptor/payload schema equal、合法 mismatch（若继续支持）、name-only drift、version-only drift、stored schema/hash/bytes各自 drift，以及 upgrade含不可重建历史 row。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### S23-I6-PLAN-03-未修复-[中]-exact descriptor+key lookup 无法区分合法 cross-definition same-key 与被重定向的 definition identity
- **状态**: `accepted-candidate`
- **位置**: target §3.4 950–968、§13.1 `test_postgres_job_idempotency_lookup_exact_missing_cross_tenant_and_persisted_drift`
- **问题类型**: 契约缺失 / open question 未收敛 / 不可直接实施
- **当前写法**: lookup 用 tenant + exact descriptor + key解析 definition-scoped unique row；missing返回 `None`，但 Store 命中 row发现 `definition_id` drift要抛 repository failure，测试还要求 definition drift矩阵。

- **为什么有问题**: `idempotency_key` 的数据库唯一性明确是 definition-scoped，public lookup又没有 job_id或不可变 original definition proof。计划同时要求互斥的分类结果，却没有提供可观察事实。

  - 当前 `PostgresJobStore.enqueue` 也按 resolved definition_id + key查重，说明 cross-definition same-key是现有 generic语义。
- **影响**: writer要么把 tamper当 miss并可能创建第二个 Source Job，要么把合法其它 definition 的同 key误报 corruption；验收矩阵没有唯一正确实现。
- **建议改法和验证点**:
  - 计划必须选择可观察的合同：最小方案是把 exact lookup能证明的 drift限定为“已解析 exact definition row/record内部的 descriptor、payload、hash、time drift”，并明确 relocated definition identity按该接口不可判别、等价 missing；

  - hostile tests必须同时放入 legitimate B/K 与 corrupted exact-row case，证明不会把合法 cross-definition存在性当 tamper。
- **修复风险（低/中/高）**: 中

### S23-I6-PLAN-05-未修复-[中]-schedule “任一 immutable drift” 未区分 schema-valid caller drift 与 malformed persisted row
- **状态**: `accepted-candidate`
- **位置**: target §5.2 1450–1467、1474–1479、§13.1 `test_schedule_ensure_registered_rejects_same_key_with_any_immutable_drift`
- **问题类型**: 契约缺失 / 测试缺口 / failure handling
- **当前写法**: row无法构造时是 `ScheduleRepositoryError -> unavailable`；但 ensure重读后“任一 immutable drift”又一律 `ScheduleVersionConflictError`，named test用 any覆盖 descriptor、payload、cron、timezone、misfire等字段。
- **反例/失败场景**: 当前 `misfire_policy` 只有 `coalesce_one` 一个schema-valid值。要制造 stored misfire policy drift，只能写入 unknown/malformed值；`ScheduleDefinition` reconstruction会先失败并产生 repository error，不可能进入两个合法 DTO的 immutable compare。若测试期待 version conflict，它会迫使 Store跳过 strict reconstruction或把 corruption误报 caller conflict。
- **为什么有问题**: caller intent conflict与 persisted corruption有不同 ownership和public action。模糊的“any”把两者合并，使前文禁止 message/shape guessing的目标在测试层反向破坏。
- **直接证据**:
  - `schedules.py:74–77` 的 enum只有 `COALESCE_ONE`；
  - `0004_durable_schedules.py:165–166` 的 CHECK也只允许 `coalesce_one`；
  - `postgres_schedules.py:540–576` 在 compare前将 row strict reconstruct为 `ScheduleDefinition`，unknown enum进入 `ScheduleRepositoryError`；
  - target §5.2 同时规定 malformed row为 unavailable 与 any immutable drift为 version conflict，未给测试分界。
- **影响**: corruption被误分类为用户冲突，或验收测试无法构造 schema-valid反例；writer可能放宽 reconstruction以迎合test。
- **建议改法和验证点**:
  - 先 strict reconstruct persisted definition；任何 enum/cron/timezone/canonical/hash/shape非法统一 repository unavailable。只有 persisted与request都是schema-valid complete DTO时，逐字段不同才是 `ScheduleVersionConflictError`。
  - 将 named test矩阵拆成参数分类而非增加模糊 public类型：schema-valid alternate fields走 conflict；single-valued misfire tamper、unknown enum、invalid canonical/hash走 repository unavailable且零mutation。
  - 对未来 enum新增值只测试当时真实schema允许的两种合法值，不为当前不存在的扩展预造兼容逻辑。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## 4. Special review lenses

- **Architecture boundary review**：Source facade拥有 Source caller-intent compare；generic Job owner应拥有完整原enqueue identity；ScheduleService拥有 croniter语义。当前计划在 durable Job owner缺事实，又把 cron语义写给Source facade，两个边界都未闭合。
- **Best-practice review**：重试队列应分离 immutable request identity与mutable scheduling state；hash只能校验已持久化输入，不能替代缺失输入。schema migration必须有可证明backfill/admission，不得从当前projection猜历史。
- **Optimal-solution review**：新的 `0006` 是当前要求下最小可信方向，因为计划已经要求 exact recovery与跨日稳定；移除 fingerprint字段、复用mutable time、把 stored hash当真源都更不安全。`0006` 不等于必须加新表或ORM；应选择最少、可证明足够的列/文档。
- **Overengineering review**：不建议新增 Source-specific Job shadow table、第二 Job repository、兼容 facade或 ORM只读镜像。若 `job_runs` 上少量immutable字段足够，就不应造新aggregate。现有raw SQL Job owner没有ORM consumer证据。
- **Overcoupling review**：不应为了检测一个不可观察的 cross-definition tamper，把generic idempotency key改成tenant-global unique；也不应让Source层依赖croniter/private Schedule helper。修复应保持 Job identity、Schedule semantics、Source intent三个owner单向协作。

## 5. Migration revision policy and minimum safe alternatives

1. **推荐候选（需 Controller裁决）**：新增 `0006` 后继迁移，冻结完整原enqueue seed/identity；`0003`和`0005`保持byte-identical。同步更新 migration head、workspace migration plugin、allowlist、coverage owner matrix、isolated PG ledger、upgrade/downgrade/catalog/security测试。
2. **可能但需额外证据的收窄方案**：让 generic `JobEnqueueRequest` 强制 payload schema identity等于 descriptor，并只持久化独立 immutable original available seed。该方案改变generic public contract，必须先证明所有producer与历史row，不可作为writer临场捷径。
3. **拒绝方案**：从 request fingerprint移除time/schema字段；把mutable `available_at` 称为original；用definition schema猜payload schema；把fingerprint当无需重算的可信事实；原地修改已接受 `0003/0005`；或为无法backfill的row静默写当前值。

数据 admission必须在plan fix时先定：

- clean/empty数据库：正常创建完整immutable事实；
- 有row但可由独立durable事实逐字段证明：允许确定性backfill并验证重算 fingerprint exact；
- 已progress/retry且缺原 timestamp或原payload schema identity：默认upgrade fail closed。若业务要求不拒绝upgrade，必须单独设计显式 unavailable状态、可观测性和调用行为；这属于新增兼容需求，不能由当前Item 6隐含决定。

## 6. Open questions
