## 2. 新攻击面逐一审查

### 攻击 1: claim 与 reserve 是两个公开事务——"claim A→同一 PG transaction reserve"是否可实施；crash-between 两阶段如何安全收敛

**Plan 实际写法分析:**

Plan §4.2.2 描述 claim 为单 PG transaction（SET LOCAL tenant → SKIP LOCKED → 创建 attempt/lease → commit → 返回 raw token）。Plan §4.3 描述 future handler 的固定顺序是 "claim A → 同一 PG transaction reserve/读取 immutable identity → commit → 同步 reconcile → 仅当 START_REQUIRED 时调 Host"。

**关键区分:** §4.3 的 "同一 PG transaction" 指的是 **claim + reserve 在同一个 PG 事务内**——即 claim 出来的 raw lease token 在同一事务中被用于 reserve correlation。这不是两个分离事务，而是一个事务的两个逻辑步骤。

**Crash 场景分析:**

| Crash 时机 | 已提交状态 | 收敛路径 | 安全性 |
|-----------|-----------|---------|-------|
| claim commit 前 | 无 | 可重试 claim（幂等 key + SKIP LOCKED） | ✅ safe |
| claim commit 后、reserve 前 | job=leased, attempt=leased, 无 correlation | recover 发现 lease 过期 → abandon attempt → retry/fail | ✅ safe — old attempt 被 abandon，新 attempt 全新 fence/token |
| reserve commit 后、Host entry 前 | job=leased, correlation=reserved, 无 Host row | recover → abandon attempt; 或 reconcile 观测到 "Host missing + correlation=reserved" → START_REQUIRED → 重用同一 reserved_host_run_id 重入 ensure | ✅ safe — reserved ID 由 attempt UUID 确定性生成，旧 attempt abandon 不影响新 attempt 的 reserved ID |
| Host entry commit 后、模型前 | correlation=reserved, Host row=CREATED | reconcile → WAIT；后续 recover 或重试清理 | ✅ safe |
| 模型执行中 | Host running | fence+token 保护；reconcile → WAIT | ✅ safe |

**判定:** claim 与 reserve 是同一事务的两个逻辑步骤（不是分离事务），crash-between 的每种场景都有明确的收敛路径。Plan §3.1 的 "attempt UUID 生成 run_{attempt_id.hex}" 保证每次 attempt 有确定性、唯一的 reserved ID，不会跨 attempt 冲突。✅ 无 blocker。

### 攻击 2: worker crash 后 raw lease token 已丢——Host SUCCEEDED/FAILED/CANCELLED 的 reconciliation 如何在不绕过 current attempt/fence、不覆盖已重试 attempt 的前提下补 receipt/状态；deadline/cancel/lease-expiry/recover race 谁优先

**Plan 实际写法分析:**

Plan §4.2.7 (recover) 明确所有 stale complete/fail/heartbeat 均因 fence+token+expiry predicate 失败，不能覆盖新 attempt。Plan §4.3 (reconcile) 描述 Host terminal 后的 receipt backfill 仅通过 correlation observation 原子更新。

**Fence 保护机制验证:**

代码证据: `host_store.py:341-392` 的 `write_transaction` 使用 `BEGIN IMMEDIATE`。Plan §4.2 的每个 terminal 操作（complete/fail/heartbeat）都检查 `fence+token+expiry predicate`。Worker crash 后 raw token 丢失，但：

1. **Stale complete/fail/heartbeat**: 因缺少 raw token（只有 hash 存储）和 expired lease，fence predicate 拒绝。✅
2. **Recovery creates new attempt**: 新 attempt 有全新 fence（递增）、全新 token hash、新 expiry。✅
3. **Receipt backfill via reconcile**: `reconcile_agent_run_correlation` 读 Host.get_run → 原子更新 correlation + attempt receipt → 不需要 raw lease token（它操作的是 correlation 层，不操作 lease 层）。✅

**Race 优先级分析:**

| 事件对 | Plan 优先级 | 机制 |
|--------|-----------|------|
| deadline vs cancel | cancel intent 优先 | §4.2.4: "cancel intent 或 deadline 优先：不记录 success，attempt/job 收敛 cancelled 或 failed" |
| lease-expiry vs cancel | cancel intent 优先 | §4.2.6: cancel 转 cancel_requested；§4.2.7: recover 发现 cancel intent 时 "cancel_requested→cancelled，绝不 retry" |
| recover vs stale write | recover 优先 | §4.2.7: "所有 stale complete/fail/heartbeat 均因 fence+token+expiry predicate 失败，不能覆盖新 attempt" |
| deadline vs retry | deadline 优先 | §4.2.7: "非取消 job 走与 fail 相同 retry algorithm；deadline 优先于 retry" |

**残余风险:** Plan §9 将 "外部 provider/tool exactly-once" 归为未来 slice；本 slice 的 fence 保护已覆盖 Host 层面。但 **receipt backfill 的触发时机** 未在当前 `recover()` 方法中显式调用 reconcile——plan §4.3 描述的 "future worker recovery 枚举其已提交 reserved correlation 后" 是 future caller 的职责，本 slice `recover()` 本身不调用 reconcile。

这是一个 **已知设计决策**（plan §7 slice D 测试用 fake future caller 覆盖），不是 plan gap。但需注意：如果 worker crash 后 recovery 只调 `recover()` 而不调 reconcile，receipt backfill 将延迟到 future worker 下次 reconcile 调用时。这在当前 plan 的 non-goal 范围内（本 slice 不注册 handler/worker），但 slice 2.2 的 worker 必须确保 recover 后调用 reconcile。

**判定:** ✅ 无 blocker。Fence 保护完整；race 优先级闭合；receipt backfill 的触发归属 future caller 是合理的架构决策。唯一建议：§4.2.7 recover 描述中补充一句 "recover 本身不触发 reconcile；reconciliation 由 future worker recovery 路径负责"。

### 攻击 3: START_REQUIRED 到 future async caller 的调用点是否既无本 slice 生产 caller 又能完成 test seam

**Test seam 可行性:**

## 4. Open Questions

1. **Recover → Reconcile 的生产调用时机**: Plan §4.2.7 recover 本身不调用 reconcile；§4.3 说 "future worker recovery 枚举其已提交 reserved correlation 后" 调 reconcile。Slice 2.2 的 worker recovery 是否需要在 `recover()` 返回后额外调用 reconcile？如果是，plan 是否应在 §7 slice E 或 §8 中增加相关测试要求？（当前 plan 的 non-goal 范围内——本 slice 不注册 worker——但 slice 2.2 需要此信息。）

2. **CanonicalJobDocument 检查时机**: Plan §3.2 描述了 canonical 格式约束（UTF-8、无 BOM、无重复 key、对象 key 字典序等），但未明确检查是在 `enqueue` 时还是在 DTO 构造时。建议在 DTO 构造期检查（§7 slice B 的 `test_canonical_document_rejects_each_known_sensitive_key` 暗示构造期检查），enqueue 只验证 hash。

3. **Host entry 消失后的 recover 路径**: Plan §4.3 说 "Host row 反向消失…fail closed 为 INVARIANT_FAILURE"。但 recover 发现 lease 过期时，如果 Host row 已不存在（例如 Host SQLite 被删除），recover 应该标记 attempt abandoned 并 retry/fail，还是应该先调 reconcile 检查 correlation？当前 plan 的 recover 不调 reconcile，这意味着 recover 只处理 lease expiry，不处理 Host row 消失。这是否是预期行为？
