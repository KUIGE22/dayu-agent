## 5. Findings

### M1 (Medium): `_challenger_requested` 双 owner 语义裂痕

**描述**：`_challenger_requested` 在 `_write_params_validation.py` 中定义并在 `write.py` 中 re-import。`_validate_research_materialization_args`（定义在 `_write_params_validation.py`）内部通过模块 globals 调用 `_challenger_requested`，解析为 `_write_params_validation._challenger_requested`。而 `run_write_command`（定义在 `write.py`）中的三个 call site 解析为 `write._challenger_requested`（即 re-imported binding）。

这意味着 **monkeypatch `write._challenger_requested` 不会影响 `_validate_research_materialization_args` 内部的 `_challenger_requested` 调用**。两个同名函数在同一个调用链中解析到不同模块绑定。

**证据**：
- `_write_params_validation.py:998`：`challenger_requested = _challenger_requested(args)`（local module global）
- `write.py:21`：`from dayu.cli.commands._write_params_validation import _challenger_requested`（re-import）
- `write.py:2758,3008,3120`：三处 call site 通过 `write` module global 解析

**严重度**：Medium。计划明确要求并测试了此双 owner 行为，但它是非直觉的语义裂痕，未来维护者若只 patch `write._challenger_requested` 可能遗漏 validator 内部路径。

**建议**：在 `_write_params_validation.py` 模块 docstring 中添加注释说明 `_challenger_requested` 的双 owner 语义和 monkeypatch 注意事项。或在 Slice 6-8 中将 `_validate_research_materialization_args` 内部的 `_challenger_requested` 调用改为显式接收参数而非依赖模块 global。

### L1 (Low): `_resolve_write_company_name` 静默吞异常

**描述**：`_write_config_helpers.py:49-52` 使用 `except Exception: return ""` 吞掉所有 `Exception` 子类。这是 pre-existing 行为，迁移未改变。新 docstring 准确描述了此行为（"本函数会吞掉公司名称解析依赖抛出的异常并返回空字符串"）。但旧 docstring 写 Raises: 无 曾是不准确的。

**严重度**：Low。Pre-existing，非本 Slice 引入。

### L2 (Low): Docstring 变更与 plan 的 "exact" 措辞不一致

**描述**：Plan 写 "exact 迁移 4 个函数" 和 "8 个迁移函数保持 exact 签名、控制流、返回值、异常与日志语义，并补齐完整中文 Args/Returns/Raises docstring"。前半句 "exact" 可能被误解为包括 docstring 不变，但后半句明确要求补齐 docstring。实际实施正确（body/signature/control-flow exact，docstring 改进），但 plan 措辞可更精确。

**严重度**：Low。实施正确，不影响行为。
