## Findings

### M-01-open-[MEDIUM]-PIP_NO_INDEX application scope unclear in utility code

- **位置**: `utils/smoke_test_offline_bundle.py` `_run_install_script` (L124-135), plan § S22-CTRL-012 L196
- **问题类型**: Codegen readiness gap
- **当前写法**: Plan L196 requires `PIP_NO_INDEX=1` in the parent process that launches the utility. `_run_install_script` passes `dict(os.environ)` to the subprocess (L124). If the parent env has `PIP_NO_INDEX=1`, it flows through. However, the install script (not in this codebase) may override or ignore it.
- **反例/失败场景**: If the install script sets its own `PIP_NO_INDEX` or if it uses `pip install --index-url` directly (bypassing env), the parent env var may not take effect. The plan does not specify whether the utility itself should also set `PIP_NO_INDEX` in the subprocess env.
- **为什么有问题**: The "sanitized no-index smoke" contract is the acceptance gate. If the env var flow is ambiguous, the implementation agent may produce a utility that passes locally but fails under different install script versions.
- **直接证据**: Plan L196: "设置`PIP_NO_INDEX=1`，清空index/extra-index及大小写proxy变量并指向fresh empty pip cache的父进程中运行官方utility"。Utility L124: `env = dict(os.environ)`.
- **影响**: Implementation agent may add `PIP_NO_INDEX` to the utility's env dict, or may rely solely on parent propagation. Either path works if the install script respects env, but the contract is under-specified.
- **建议改法和验证点**: Plan should clarify: (a) the parent env sets `PIP_NO_INDEX=1` and the utility passes `os.environ` through (current behavior is sufficient), OR (b) the utility should explicitly set `env["PIP_NO_INDEX"] = "1"` in `_run_install_script`. The sanitized smoke test gate must verify the install script actually used `--no-index --find-links` and did not contact PyPI.
- **修复风险**: Low — both interpretations are implementable; the plan just needs one explicit choice.
- **严重程度**: M

### M-02-open-[MEDIUM]-Windows test branch may need OS guard or platform skip

- **位置**: `tests/test_smoke_test_offline_bundle.py`, plan § S22-CTRL-012 L195
- **问题类型**: Test contract completeness
- **当前写法**: Plan L195: "POSIX分支必须断言`True`，Windows分支必须断言`False`，两条闭合分支都不得创建真实venv、依赖本机平台或放宽为truthy断言。"
- **反例/失败场景**: If the test runs on macOS/Linux, the Windows branch (`symlinks=False`) can only be verified via code inspection or mock — it cannot be runtime-asserted without mocking `os.name`. If the test runs on Windows, the POSIX branch (`symlinks=True`) cannot be runtime-asserted. The plan does not specify whether the test should use `monkeypatch.setattr(os, "name", ...)` to cover both branches, or whether it should accept platform-limited coverage.
- **为什么有问题**: "不得依赖本机平台" suggests both branches must be testable regardless of host OS. This implies `os.name` must be monkeypatched for the non-native branch. The plan does not explicitly state this.
- **直接证据**: Plan L195. Existing test uses `os.name == "nt"` for path construction (L33 of current test) without monkeypatching.
- **影响**: Implementation agent may write a test that only covers the native branch, failing the "闭合分支" gate.
- **建议改法和验证点**: Plan should explicitly require `monkeypatch.setattr(os, "name", "nt")` for Windows branch and `monkeypatch.setattr(os, "name", "posix")` for POSIX branch (or equivalent), ensuring both `True` and `False` are asserted. Alternatively, the test could import the helper and call it with a `Path` arg while monkeypatching `os.name`, checking the builder kwargs without creating a real venv.
- **修复风险**: Low — standard pytest monkeypatch pattern.
- **严重程度**: M

### M-03-open-[MEDIUM]-POSIX symlink dylib resolution risk not explicitly addressed

- **位置**: Plan § S22-CTRL-012 L194 ("禁止动态探测launcher/rpath/libpython、复制或重写dylib")
- **问题类型**: Risk coverage
- **当前写法**: Plan prohibits dynamic rpath/libpython detection, dylib copying, or DYLD_* injection. The fix is purely `symlinks=True` on POSIX.
- **反例/失败场景**: On some macOS configurations, symlinked venvs may fail if the Python framework layout differs from the expected structure. The plan relies on "python -m venv and repo .venv are both healthy with symlink" (L189) as evidence, but does not require a verification step that the new `_create_clean_venv` actually produces a working venv on the target platform.
- **为什么有问题**: The sanitized smoke test (L196) does prove end-to-end functionality (create venv + install + import dayu + CLI help). If the symlinked venv were broken, ensurepip or install would fail. So the risk is already covered by the acceptance gate. But the plan could be more explicit about this.
- **直接证据**: Plan L189, L196.
- **影响**: Low — the sanitized smoke test is the definitive proof. If it passes, symlinks work.
- **建议改法和验证点**: No change needed. The sanitized smoke test gate (L196) already proves the symlinked venv is functional. This is a residual risk, not a plan gap.
- **修复风险**: N/A — no fix needed.
- **严重程度**: L
