## Terra S14-01..04 与 MiM M1..M5 逐项闭合验证

### Terra S14-01：注入 FileStore 未覆盖 source/blob 实际读写面

**Controller 裁决**: CLOSED-IN-PLAN via S14-CTRL-03 byte-path matrix + FileStore-backed Source + 禁本地 fallback/双写。

**真实 callgraph 证据**: 确认 Terra S14-01 的全部事实成立——`get_source`/`get_primary_source` 无条件 `_local_path_from_uri`+`LocalFileSource`（`_fs_source_document_core.py:633-641`）；`list_entries`/`read_file_bytes`/`_delete_entry_impl` 直接 `iterdir`/`read_bytes`/`unlink`（`_fs_blob_core.py:39-113`）；`_upsert_processed` 直接 `_write_json`（`_fs_processed_core.py:289-320`）；`read_rejected_filing_file_bytes` 直接本地路径（`_fs_maintenance_core.py:302-307`）；`has_filing_xbrl_instance` 本地目录扫描（`_fs_source_document_core.py:496-502`）。`store_file` 和 `store_rejected_filing_file` 是仅有的两个 FileStore 写入点（`_fs_blob_core.py:146`、`_fs_maintenance_core.py:147`）。

**闭合判定**: S14-CTRL-03 byte-path matrix 逐行覆盖了全部 12 个字节 owner 路径（source 写入、source 主文件/附件读取、blob read/list/delete、rejected read/clear/cleanup、processed JSON 写入、source reset、XBRL 探测、process/evidence 读取），新增 FileStore-backed `Source` adapter 为每个路径指定了 corrective 后实现。闭合 **有效**。

### Terra S14-02：FS batch 与 S3 final 无共同 journal/recovery

**Controller 裁决**: CLOSED-IN-PLAN via S14-CTRL-04 remote-operation journal 状态机/commit ordering/幂等恢复。

**真实 callgraph 证据**: 确认当前 `begin_batch`/`commit_batch`/`recover_orphan_batches` 纯粹是本地 FS journal 状态机（`_fs_storage_infra.py:149-257,353-375`），无任何 S3 感知。journal 仅记录 target/staging/backup/journal 路径（`_fs_storage_infra.py:176-185`），`recover_orphan_batches` 只扫描 `.dayu/repo_batches` 和 `.dayu/repo_backups`（`_fs_storage_infra.py:371-372`）。无 remote operation journal 实现。

**闭合判定**: S14-CTRL-04 定义了 per-target `publish_state`（`staged|final_verified`）独立状态机、commit ordering（publish-before-swap 逐 target 原子持久）、各 crash 窗口的幂等恢复方向、FS staging 缺失 fail closed。状态机清晰、恢复方向唯一。闭合 **有效**，但需注意 `_write_json`（`_fs_storage_utils.py`）非原子写入——journal 本身的 temp+replace 语义已在 S14-CTRL-04 中明确要求。

### Terra S14-03：CopyObject 无并发所有权/覆盖语义

**Controller 裁决**: CLOSED-IN-PLAN via S14-CTRL-09 单 writer 拓扑 + 可执行 admission。

**真实 callgraph 证据**: 当前仅有 per-ticker batch lock（`_fs_storage_infra.py:410-492`，`flock` 系统调用），无全局 writer admission。无 writer lease/flock 机制实现。

### Terra S14-04：S3 preflight 顺序允许 provider side effect 先行

## 7-lens adversarial findings

### MR1-未修复-[中]-begin_batch 的 copytree 在 S3 模式下只拷贝本地 metadata 不拷贝 S3 bytes，recovery 的 metadata roll-forward 依赖本地 staging 完整性

- **位置**: S14-CTRL-04（master plan L1157-1217）、`_fs_storage_infra.py:149-199`（`begin_batch` L190 `shutil.copytree`）、S14-CTRL-04 recovery rule 2
- **问题类型**: 状态机漏洞 / 切片过粗
- **当前写法**: S14-CTRL-04 规定 remote journal 覆盖 S3 操作状态，FS batch 继续管理本地 metadata。recovery rule 2 要求"全部 target verified 且 FS batch staging 目录完整"才执行 metadata roll-forward。`begin_batch` 的 `shutil.copytree`（L190）把整个本地 ticker dir（含 meta.json/manifest）拷贝到 staging。
- **反例/失败场景**: S3 模式下，本地 ticker dir 只有 metadata（meta.json/manifest/journal），blob bytes 在 S3。`begin_batch` copytree 拷贝本地 metadata 到 staging，但 S3 bytes 通过 remote journal 独立管理。若进程在 `commit_batch` swap 本地 staging 前 crash，recovery 需要同时恢复 S3 journal（逐 target verified）和本地 metadata staging。若本地 metadata staging 目录被意外删除或损坏（如磁盘错误），即使 S3 journal 显示所有 target verified，recovery 也无法执行 metadata roll-forward——只能 fail closed。这在 plan 中已声明为"FS batch staging 缺失/损坏 => FAIL CLOSED"，但该 fail closed 路径在 S3 模式下比 FS 模式更脆弱：FS 模式下 copytree 是完整的 bytes+metadata snapshot，而 S3 模式下 copytree 只是 metadata snapshot，一旦丢失 metadata 就只能保留 journal + 远端 objects 供人工恢复。
- **为什么有问题**: plan 明确声称 "FS 只持 metadata/manifest/journal" 且 "S3 是 authoritative blob bytes"。但 `begin_batch` 的 copytree 机制仍然是"拷贝整个本地目录"，在 S3 模式下这个目录只有 metadata。plan 没有显式说明 S3 模式下 `begin_batch` 的 copytree 是否需要变更（如只拷贝 metadata 子集或改为 copy metadata 目录），也没有为 metadata staging 损坏定义更精细的恢复策略（如仅通过 S3 journal 重建 metadata）。
- **直接证据**: `_fs_storage_infra.py:190`：`shutil.copytree(target_ticker_dir, staging_ticker_dir)`。S3 模式下 `target_ticker_dir` 只含 meta.json/manifest/journal（blob bytes 在 S3），copytree 拷贝的是不完整的 snapshot。
- **影响**: implementation agent 可能认为 S3 模式下 `begin_batch` 不需要变更（因为 plan 只说"FS batch 继续管理 metadata"），但实际 copytree 在 S3 模式下的语义与 FS 模式不同。若 metadata staging 损坏，fail closed 路径保留 journal + 远端 objects 但无法自动恢复 metadata。
- **建议改法和验证点**: (1) 在 S14-CTRL-04 明确 S3 模式下 `begin_batch` 的 copytree 行为：是继续拷贝完整 metadata 目录，还是改为只拷贝 meta.json/manifest 子集；(2) 或在 recovery 中增加"若 metadata staging 损坏但 S3 journal 完整，可通过 S3 journal + 远端 objects 重建本地 metadata"的路径（但 plan 已声明 fail closed，需决定是否接受此 tradeoff）；(3) integration 测试须覆盖 S3 模式下 metadata staging 损坏后的 fail closed 行为。
- **修复风险（中）**: 需要修改 `begin_batch` 的 copytree 语义或明确 S3 模式下的特殊处理。
- **严重程度（中）**: plan 已声明 fail closed，不是 data loss，但 fail closed 路径在 S3 模式下更频繁触发（metadata 比 bytes+metadata 更容易丢失）。

### MR2-未修复-[低]-_write_json 非原子写入可能损坏 metadata/journal 文件

- **位置**: `_fs_storage_utils.py`（`_write_json` 函数）、`_fs_storage_infra.py:188,228,231,234,251`（journal 写入点）、`_fs_processed_core.py:289-320`（processed metadata 写入点）
- **问题类型**: 并发恢复风险 / 最佳实践偏离
- **当前写法**: S14-CTRL-04 要求 journal 每次改写为 temp+replace 原子写。`_write_json` 当前直接 `path.write_text(json.dumps(...))`，非原子。`_fs_storage_infra.py` 的 journal 写入点（L188,228,231,234,251）使用 `_write_json` 写入 `transaction.json`。
- **反例/失败场景**: 进程在 `_write_json` 写入 journal 文件过程中 crash（如写入一半后 kill），journal 文件可能损坏为半写状态。FS 模式下这已有风险（但 copytree 备份提供了恢复方向）；S3 模式下 journal 损坏意味着 remote operation 状态不可读，recovery 无法判断 target 的 publish_state，可能误判。
- **为什么有问题**: S14-CTRL-04 明确要求 "journal 每次改写均为 temp+replace 原子写"，但 `_write_json` 是 journal 写入的底层实现，当前非原子。plan 没有显式要求修改 `_write_json` 或在 journal 写入点使用不同的写入机制。
- **直接证据**: `_fs_storage_utils.py` 中 `_write_json` 直接 `path.write_text()`；`_fs_storage_infra.py:188` 调用 `_write_batch_journal(token, phase)` -> `_write_json(journal_path, {...})`。
- **影响**: 极低概率但可复现的 journal 损坏导致 recovery fail closed。
- **建议改法和验证点**: (1) 在 S14-CTRL-04 明确 `_write_json` 在 journal 写入点必须替换为 temp+replace 原子写（或新增 `_write_json_atomic` helper）；(2) 或在 `remote_op_journal.py` 中直接实现 temp+replace，不依赖 `_write_json`。
- **修复风险（低）**: 只需修改 journal 写入路径，不影响其他 `_write_json` 调用者。
- **严重程度（低）**: 极低概率，且 plan 已声明 fail closed。

### MR3-不需要修复-[信息]-staged capability 的 isinstance 检查是类型安全的

- **位置**: S14-CTRL-06（`_StagedFileStore` capability protocol）、`_fs_storage_infra.py:827-842`（`_build_file_store`）
- **问题类型**: 严格类型可实施性（验证结论）
- **当前写法**: S14-CTRL-06 定义私有 capability protocol `_StagedFileStore`（staging put/commit/delete），只由 `S3FileStore` 实现。`_fs_storage_infra` 以该 capability 判断是否启用 journal。
- **验证结论**: `_build_file_store` 返回 `FileStore`（L827-842），判断 `_file_store is not None` 分发。S3 模式下 `self._file_store` 是 `S3FileStore` 实例（实现 `_StagedFileStore`），FS 模式下是 `LocalFileStore` 实例（不实现 `_StagedFileStore`）。`isinstance(self._file_store, _StagedFileStore)` 检查是类型安全的，不需要 `hasattr`/`getattr`。允许使用 `isinstance`（Python 内置类型检查），不违反 AGENTS.md 的 `hasattr`/`getattr` 限制。
- **影响**: 无需修复。类型安全且符合项目约束。

## 显式审查 lenses

### Architecture boundary
S3 settings/parser 放在 `dayu.fins.storage`（`s3_settings.py`/`s3_file_store.py`）、startup 只做选择、platform provider 不接 bucket/key 的方向正确。FS metadata + S3 bytes 分离符合 Fins storage 唯一存取边界。S14-CTRL-03 byte-path matrix 正确识别了所有实际绕过 FileStore 的路径。**但 `begin_batch` 的 copytree 在 S3 模式下的语义差异需要显式声明**。

### Best practice
strict JSON 仅持 env-name、显式 credential、禁止 ETag 充当 hash、verified stat read、typed boto3 stubs、pinned digest/owner-label cleanup 都是合理约束。journal 的 temp+replace 原子写要求正确。**但 `_write_json` 的非原子性需要在 journal 路径上被覆盖**。

### Optimal solution
FS metadata + S3 bytes 是避免复制整套 workspace JSON 到 bucket 的最小方向。remote journal 复用现有 FS batch owner 而非新建第二 metadata repository 是正确的。single-writer flock 是当前 production topology 的最实际约束。**不建议引入 multipart/CAS/second metadata repo**。

### Overengineering
未发现。S14-CTRL-01..10 的每个约束都有明确的 failure mode 支撑。`_StagedFileStore` capability protocol 是最小扩展而非泛化。

### Overcoupling
S14-CTRL-03 byte-path matrix 要求修改 12 个字节 owner 路径，这看起来改动量大但实际是对现有调用点的逐个适配，不是跨层耦合。每个路径的 corrective 后实现自包含在 Fins storage 层内。**唯一风险是 `_fs_processed_core.py` 的 `_upsert_processed` 直接 `_write_json`——S14-CTRL-03 要求它走 FileStore，但 plan 的 Allowed 列表包含 `_fs_processed_core.py` 且 byte-path matrix 明确指定了 corrective 路径，implementation agent 有足够信息实施**。

## Final plan review conclusion

**pass-with-risks**

S14-CTRL-01..10 的核心 corrective contract 对 implementation agent 足够确定性：

1. **Terra S14-01..04 全部 CLOSED-IN-PLAN**——byte-path matrix 全覆盖、remote journal 状态机/commit ordering/recovery 唯一、single writer flock 可执行、startup ordering 固定唯一。
2. **MiM M1..M5 全部 CLOSED-IN-PLAN**——staging orphan recovery 由 journal 覆盖、stat HEAD-only + get verified BinaryIO、startup S3 preflight 固定在 provider 前、list 全量/排序/staging exclusion、MinIO TERM->KILL->rm-f。
3. **S3 authoritative bytes 全路径覆盖且无 local fallback/双写**——12 个字节 owner 路径逐行确认，FileStore-backed Source adapter 新增。
4. **per-target remote journal 可实现**——publish_state 独立、commit ordering 原子、各 crash 窗口恢复方向唯一、FS staging 缺失 fail closed。
5. **单 writer flock admission 可执行**——非阻塞 exclusive flock + 生命周期管理 + 拒绝第二 writer + 多 host 归后续。
6. **staged capability 严格类型可实施**——`_StagedFileStore` protocol + `isinstance` 检查，无 `hasattr`/`getattr`。
7. **allowlist 精确展开到文件级**——5 个新增文件、9 个修改文件、7 个测试文件、3 个文档/依赖文件，明确冻结边界。

**Open 0 H / 1 M / 1 L**：

- **M1**: `begin_batch` copytree 在 S3 模式下的 metadata staging 脆弱性——plan 已声明 fail closed，但需要 implementation agent 显式声明 S3 模式 copytree 语义。建议在 implementation plan 中明确。
- **L1**: `_write_json` 非原子性在 journal 路径上——plan 已要求 temp+replace，但底层实现非原子，implementation agent 需要在 journal 写入点覆盖。

**结论：plan 可以进入 implementation gate**。MR1/MR2 不是 blocker，而是 implementation 阶段需要显式处理的已知约束。Controller 可在接受这两个 risk 的前提下批准 implementation。不建议因这两个 finding 阻塞 implementation gate——它们的影响都在 fail closed 范围内，不会导致 data loss。
