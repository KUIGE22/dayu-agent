## Findings

### M-01-未修复-中-NewType direct construction 绕过 make_\* 校验，强标识运行时无强制

- **入口/函数**: 所有五个 NewType 标识（`TenantId` / `CompanyId` / `SecurityId` / `PortfolioId` / `AccountId`）
- **文件(行号)**: `dayu/investment/domain/identifiers.py:21-34`
- **输入场景**: 调用方直接使用 `TenantId("  bad  ")` 而非 `make_tenant_id("  bad  ")`
- **实际分支**: `NewType("TenantId", str)` 在运行时是 identity function（`lambda x: x`），不经过 `_validate_identifier`
- **预期行为**: 按 plan §8.0 Slice 0.1 描述"五个强类型标识均由 NewType 包装字符串，构造时拒绝空值、仅空白或首尾空白"
- **实际行为**: `TenantId("  bad  ")` 返回 `"  bad  "`，空值和首尾空白均通过；`make_tenant_id("  bad  ")` 正确拒绝
- **直接证据**:
  ```python
  # 复现
  from dayu.investment.domain.identifiers import TenantId
  bad = TenantId("  bad  ")  # 不报错，返回 "  bad  "
  ```
  运行时验证：`TenantId("  bad  ")` 返回含首尾空白的字符串，`Principal.__post_init__` 能拦截（因 `Principal` 是 dataclass），但任何直接接受 `TenantId` 参数的函数不受保护。
- **影响**: 下游 slice（仓储协议、Service 层）若直接以 `TenantId(...)` 构造标识并传入仓储方法，空/空白标识将绕过校验进入业务逻辑。当前 `Principal`/`TenantScope` 的 `__post_init__` 兜底拦截了这两条路径，但仓储方法的参数类型是 `TenantId`，调用方可能绕过 `Principal` 直接传入。
- **建议改法和验证点**: 方案 A（推荐）：在 `make_*` 工厂函数 docstring 和 `dayu/investment/README.md` 中明确声明 `make_*` 是唯一 public constructor，NewType 直接调用是 internal/unsupported path；在后续 slice 的仓储协议中要求所有 `TenantId` 参数必须来自 `make_*` 或 `Principal`。方案 B（更强）：将 NewType 替换为 frozen dataclass + `__new__` 校验，但会改变类型签名（`NewType` 是 `str` 的 subtype，dataclass 不是）。验证点：后续 slice 的代码 review 中检查是否有 `TenantId(...)` 直接调用。
- **修复风险（低）**: 方案 A 只改文档，无代码变更风险；方案 B 需要改类型签名，风险中等。
- **严重程度（中）**: 当前 `Principal`/`TenantScope` 的 `__post_init__` 兜底拦截了主要路径，实际风险受控；但强标识的"强"在运行时不成立，后续 slice 若不遵守 `make_*` 约定则校验链断裂。
