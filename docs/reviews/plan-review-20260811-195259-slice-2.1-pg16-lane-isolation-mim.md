## 3. Findings

### F-001 — 未修复-[无]-三独立进程是最小正确契约

**位置**：plan-fix §2 "PG16 completion gate 改为三个独立进程"；target plan §8 "完成前依次运行"

**审查结论**：**三独立 pytest 进程是最小正确契约，不存在更小的正确等价方案。**

分析：
1. `platform_cluster` 的 session scope 意味着同一 invocation 的所有 test files 共享同一个 PostgreSQL container。这是一个正确的设计选择——integration tests 需要 container 在整个 session 生命周期中存活。
2. group role（`dayu_platform_app`、`dayu_platform_audit`）是 cluster-global 对象。`DROP DATABASE` 只删除 database-level objects，不能移除 cluster-level roles。因此 database cleanup（`lifecycle_database` fixture 的 `DROP DATABASE IF EXISTS ... WITH (FORCE)`）无法回收前一文件创建的 roles。
3. 三个文件分别对应三个不同的测试职责：migration schema（`test_platform_migrations_postgres.py`）、identity repository（`test_identity_repositories_postgres.py`）、durable jobs（`test_postgres_jobs.py`）。它们的 migration admission 假设各自的 upgrade 是首次运行，这在独立进程中成立，在合并 invocation 中不成立。
4. 更少的进程（如 2 个）仍会导致角色污染；更多的进程（如按 class 拆分）不必要且会增加 setup/teardown 开销。
5. 该模式与 Phase 1 已有 validation precedent 一致（`tests/README.md:100-101` 显示独立命令）。

**影响**：无风险。这是 validation orchestration gap 的最小正确修复。

### F-002 — 未修复-[无]-进程隔离不削弱 PG16 覆盖

**位置**：plan-fix §2

**审查结论**：**进程隔离不削弱 PG16 覆盖，反而巩固它。**

分析：
1. 三文件在合并 invocation 下的真实退出码是 63/35（migration 文件 35 个测试全部因 role pre-existence 失败）。这不是"通过"——这是 validation gap 被掩盖。
2. 拆成三个独立进程后，每个文件都在干净的 migration admission 前提下运行，测试断言才能反映真实行为。
3. 每个独立进程仍使用 session-scoped `platform_cluster`，不改变 container 级隔离语义。
4. plan-fix 明确禁止 `-k`、skip 或 masked pipeline exit——这确保覆盖不被选择性削弱。

**影响**：PG16 覆盖从"表面 63/35 且 migration 全 fail"恢复为"三条独立 PASS"。
