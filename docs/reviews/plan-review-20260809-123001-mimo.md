## Findings

### H-1-未修复-[高]-`--quiet` 不能保证 stdout 纯净，exact fail-closed parser 在真实 live 下会误停机

- **位置**：plan §4.2 line 111、§5.2 line 144、§13 line 724；`docs/reviews/plan-fix-20260809-121500-codex.md:15`
- **问题类型**：契约缺失 / 动机假设不成立 / 不可直接实施
- **当前写法**：
  - plan-fix:15：“默认 INFO 会进入 stdout，但公共 logging 参数支持固定 `--quiet`。”
  - plan §5.2:144：“三个 download planned argv 都固定且仅含一次 `--quiet`，以隔离默认写入 stdout 的 INFO 日志……runner 对完整 stdout 做 exact owner-formatter grammar 解析。”
  - plan §4.2:111 / §13:724：未知、缺失、重复、**噪声**、歧义或格式漂移全部 fail closed，并明确定性为“安全停机”。
- **反例/失败场景**：live lane 执行 `download AAPL --forms 10K --quiet`。SEC 侧触发一次 rate limit，`edgar` / `httpx` 打出 WARNING。这些 WARNING 落在 **stdout**，排在 `下载结果` 之前。exact parser 命中“噪声行”，按 §13 强制安全停机——而 download 子进程本身已经成功、文件已落盘、（Slice 5 下）配额已消耗。停机与否取决于当次网络抖动，验收结果不可复现。
- **为什么有问题**：`--quiet` 只设置 root level，**并不静音被显式钉住的第三方 logger**。`dayu/log.py:176-181`：
  ```python
  for name in _ALWAYS_WARNING_LOGGERS:            # 含 "httpx"
      logging.getLogger(name).setLevel(logging.WARNING)
  verbose_level = logging.INFO if min_level.value <= LogLevel.DEBUG.value else logging.WARNING
  for name in _DEBUG_MODE_INFO_LOGGERS:           # 含 "edgar"、"docling"
      logging.getLogger(name).setLevel(verbose_level)
  ```
  这些 child logger 有自己的 level，不受 root ERROR 约束；而 `dayu/log.py:37-38,151` 的 stdout handler 上界是 `_STDOUT_MAX_LEVEL = ERROR - 1`，即 **WARNING 一律走 stdout**。`edgartools` 是直接依赖，`edgar` logger 在真实 SEC 下载路径上必然活跃。
- **直接证据**（本轮实测，等价 subprocess 语义，shell 级重定向）：
  ```
  set_level_from_flags(..., quiet=True)
  logging.getLogger("edgar").warning("Rate limited, retrying")
  logging.getLogger("httpx").warning("HTTP Request: GET https://sec.gov ...")
  print("下载结果")
  ```
  ```
  === STDOUT ===
  [2026-08-09 12:33:17] [WARNING] [edgar] Rate limited, retrying
  [2026-08-09 12:33:17] [WARNING] [httpx] HTTP Request: GET https://sec.gov ...
  下载结果
  === STDERR ===
  （空）
  ```
  次生污染源：plan §5.1:122 明确“不要求用户先 `init`”，因此 `dayu/cli/commands/init.py:428` 的 `_THIRD_PARTY_OUTPUT_QUIET_ENV`（`TQDM_DISABLE` / `HF_HUB_DISABLE_PROGRESS_BARS` / `TRANSFORMERS_VERBOSITY`）不保证生效，`process` 阶段的 docling/OCR 进度输出同样可能进入 stdout。
- **影响**：计划核心机制不可实施；实施 Agent 会被迫要么私自放宽 parser（违反 §4.2 明令禁止的宽松 regex / 忽略未知行），要么交付一个在 live lane 概率性失败的验收器。plan §14:755 的 residual 只预期了“formatter 文案变更”，完全没有覆盖本失败模式。
- **建议改法和验证点**（最小修正，不改 `dayu/`）：
  1. 把 ingress 从“整段 stdout 必须恰好等于 formatter 文本”改为**锚定切片**：以 formatter 的固定标题行（`下载结果` / `上传材料结果` / `全量处理结果`）为唯一起点锚，锚前内容一律丢弃且**不参与 fail-closed 判定**；锚必须恰好出现一次，出现 0 次或 ≥2 次 fail closed。锚之后仍执行原 exact 文法。
  2. 明确规定：被丢弃的锚前前缀必须整体计入 `stdout_prefix_sha256` 与有界脱敏摘要，写入 `CommandRecord`，使停机可诊断（配合 M-3）。
  3. planned argv 在 `--quiet` 之外，additionally 由 acceptance runner 在 subprocess env 固定注入 `TQDM_DISABLE=1` / `HF_HUB_DISABLE_PROGRESS_BARS=1` / `TRANSFORMERS_VERBOSITY=error`，并把该 env 集合纳入 plan fingerprint。这是 runner 侧行为，不修改 `dayu/`。
  4. 验证点：新增 deterministic 测试，向 stdout 预置 `[WARNING] [edgar] ...` 与 `[WARNING] [httpx] ...` 前缀行 + 真实 `format_fins_cli_result` 输出，断言解析成功、evidence 与无前缀情形逐字段一致，且前缀 digest/摘要已入 receipt；再断言两次标题锚 fail closed。
- **修复风险（低/中/高）**：低。修改仅落在 plan 文本与 `utils/` ingress 规格。
- **严重程度**：**高**

### H-2-未修复-download/process 明细行不是稳定可 exact 解析的文法，`|` 与换行可由 owner 自由文本注入

- **位置**：plan §4.2 line 111、§5.2 line 144-150；`dayu/fins/cli_formatters.py:406-430`、`:452-478`、`:504-523`、`:990-1019`
- **问题类型**：契约缺失 / 不可直接实施 / 状态机漏洞（歧义判定）
- **当前写法**：计划要求对 owner 明细行做 exact grammar 解析，并从中收窄 `document_id / form / filing_date / status` 等 discovery 字段；“歧义”一律 fail closed。计划未定义分隔符转义规则、空值语义、空集合占位语义。
- **反例/失败场景**：某个 filing 失败，owner 的 `reason_message` 含 `|`（例如 `HTTP 429 | retry after 600s`）或含换行（多行异常说明）。渲染出的行变成
  ```
    - fil_0000320193-24-000123 | form=10-K | ... | reason=... | message=HTTP 429 | retry after 600s
  ```
  按 `|` 切分的 exact parser 得到超出预期的字段数 → 判为歧义 → fail closed；含换行时更糟：后半段成为一个“未知行”，同样 fail closed。这与 H-1 同源，都是把 owner 的成功输出误判为格式漂移。
- **为什么有问题**：download 明细行直接内插原始文本，**没有做单行归一**：
  ```python
  # cli_formatters.py:420-428
  f"failed_files={failed_count} | reason={reason or '-'} | message={message or '-'}"
  ```
  `reason`/`message` 来自 `_resolve_download_reason_fields` → `_first_non_empty_text`（`:517-523`）只做 `.strip()`，**不折叠内部空白、不转义 `|`**。对照 `_format_value_inline`（`:1106-1123`）确实做了 `" ".join(rendered.split())` 折叠，但它只服务 `_append_optional_field_lines`（upload_material 路径），download/process 明细行完全不经过它。
  另外两个欠规格点，同样会让 exact parser 在正常输入上判错：
  - 空集合占位是中文全角字面量 `"  - （无）"`（`:413`、`:1000`、`:1058`），计划未把它写进文法。
  - `document_id` 与 `form_type` 均可为空串：`document_id=str(item.get("document_id","")).strip()`；`form={item.form_type or ''}`。计划要求 document_id 必须严格闭合 `fil_<accession>`，但没有规定“空 document_id 属于 owner 事实还是解析失败”。
  - **form 名归一未定义**：plan §10 live argv 写 `--forms 8K DEF14A`（无空格），而 discovery 对齐与 evaluator `required_forms` 侧使用 `DEF 14A`（有空格）。计划从未钉死 owner `form=` 实际输出拼写，也没给归一规则。
- **直接证据**：`cli_formatters.py:406-430`（download 明细行拼装，无转义/无折叠）、`:452-478` + `:504-523`（reason/message 仅 strip）、`:990-1019`（process 明细行同构，`_collect_optional_parts` 同样内插原文）、`:413/:1000/:1058`（`（无）` 占位）、plan §10 argv `DEF14A` 与 §5.2 required forms `DEF 14A` 拼写不一致。
- **影响**：exact parser 在**合法**输入上误报歧义 → 与 H-1 叠加，安全停机概率显著上升；或实施 Agent 自行发明宽松切分规则，破坏计划的 fail-closed 承诺，并可能把 message 片段错认成字段值，污染 discovery evidence。
- **建议改法和验证点**：
  1. 计划显式规定明细行文法为**限定字段数的左向解析**：按已知字段名 `form= / filing_date= / report_date= / status= / downloaded_files= / skipped_files= / failed_files= / reason= / message=` 顺序锚定，`message=` 为**行尾贪婪吸收**（其内容不参与结构判定，只做有界脱敏摘要）；`document_id` 取首个 ` | ` 之前的 token。多行 message 造成的后续行，若不匹配任何已知节标题且不匹配明细行前缀 `  - `，归入前一条 message 的续行而非未知行。
  2. 计划显式登记 `"  - （无）"` 为空集合唯一合法占位，写死为具名常量。
  3. 计划显式规定：`document_id` 为空 → fail closed（无法闭合 `fil_<accession>` identity）；`form=` 为空 → 该行不进入 required-form 对齐，但仍作为 discovery row 记录。
  4. 计划钉死 form 归一唯一真源：单一 normalize 函数（去空格、大写、`DEF14A`↔`DEF 14A` 归一），argv 拼写、owner `form=` 拼写、evaluator `required_forms` 三处**必须**经它比较，禁止任一侧硬编码字面量。
  5. 验证点：deterministic 测试用真实 `format_fins_cli_result` 构造 `message` 含 `|`、含换行、`reason`/`message` 全空（渲染 `-`）、空集合、空 `document_id`、空 `form_type` 六类输入，断言前四类解析成功且字段精确，后两类按上述规则分别 fail closed / 降级；并断言 `DEF14A` 与 `DEF 14A` 经归一后判定一致。
- **修复风险（低/中/高）**：低。
- **严重程度**：**高**

### M-1-未修复-[中]-discovery 外部真源未规定必须并入 skipped/failed 分节，缓存命中会假性触发 DEF 14A 门

- **位置**：plan §5.2 line 149-150；`dayu/fins/cli_formatters.py:380-402`
- **问题类型**：契约缺失 / 状态机漏洞
- **当前写法**：计划要求 10-K/10-Q/DEF 14A 必须与 download command-record 的 discovery rows 对齐，并禁止 inventory-derived fallback（正确方向，正确关闭了 DeepSeek H-1 的恒真比较）。但计划未显式规定 discovery rows 的**取值范围**是哪几个分节。
- **反例/失败场景**：第二次执行验收（或任意重跑），全部 filing 已在本地，owner 把它们放进 `跳过的 filings:` 分节，`成功下载的 filings:` 为 `  - （无）`。若实施 Agent 只解析“成功下载”分节，discovery 为空，DEF 14A required-form 门直接 FAIL——但外部事实上 DEF 14A 确实存在且已发现。
- **为什么有问题**：`_format_download_result:380-402` 把 `result.filings` 按 status 分为 downloaded/skipped/failed 三节输出；**外部发现事实分布在三节里**，`skipped` 恰恰代表“SEC 侧已发现 + 本地已有”。只取一节即丢失外部真源。
- **直接证据**：`cli_formatters.py:380-382`（三路 status 分流）、`:397-401`（三节顺序输出）、plan §5.2:149-150 只说“与 download command-record discovery rows 对齐”，未限定分节。
- **影响**：验收在正常缓存路径上假性 FAIL；或实施 Agent 自行取舍，两个 lane 行为分叉。
- **建议改法和验证点**：计划明确 `DownloadCommandEvidence.discovery_rows` = 三节并集，逐行携带 `section_status ∈ {downloaded, skipped, failed}`，以 `document_id` 唯一键去重（重复 document_id 跨节出现 → fail closed）；required-form 对齐只看并集，不看分节。验证点：deterministic 测试构造“全部 skipped”的 download 输出，断言 DEF 14A 门通过且 discovery rows 数量正确。
- **修复风险**：低。
- **严重程度**：**中**

### M-2-未修复-[中]-`CommandRecord` 把通用进程生命周期事实与 fins 专用 evidence 绑在同一 frozen 结构，扩展面会外溢

- **位置**：plan §5.1 line 130-134；`docs/reviews/plan-fix-20260809-121500-codex.md:69-72`
- **问题类型**：过度耦合
- **当前写法**：`CommandRecord` 同时承载 17 个通用执行事实（index / safe_argv / argv_digest / status / start / end / duration / exit_code / stop_reason / termination_action / partial_by_timeout / stdout_sha256 / stderr_sha256 / stderr_summary）与一个 fins 专用 discriminated union `evidence: DownloadCommandEvidence | MaterialImportCommandEvidence | ProcessCommandEvidence | None`。
- **反例/失败场景**：后续要验收第四个 fins 子命令（或非 fins 命令，如 terminal verify 想携带结构化事实），必须同时改动 `CommandRecord` 的 union 与全部 v3 round-trip / reject 测试。union 是闭集这点本身正确，但它挂在通用结构上，使“加一个命令”变成“改 receipt schema”。
- **为什么有问题**：违反计划自身的分层意图——执行层事实（谁跑了、跑多久、怎么结束）与领域层事实（SEC 发现了什么、材料指纹是什么）演进节奏不同。当前设计尚未到 God schema（字段都是扁平单值，union 是闭集且判别明确，没有 bag/`Any`/`extra payload`），因此不判 H；但耦合缺口真实。
- **直接证据**：plan-fix:69-72 的字段清单；plan §5.1:130-134 的机械闭合规则（prepare 精确 0 record / passed 精确全量 / failed 仅 executed prefix / terminal 精确 1 record）——这些规则全部只依赖通用字段，与 `evidence` 无关，说明两组事实本可正交。
- **影响**：后续 slice 每加一个被验收命令都要动 receipt schema 与 schema 版本，返工成本后移。
- **建议改法和验证点**：保留当前 v3 形状（不推翻，避免为假想需求重构），但计划显式写死两条约束：(a) `evidence` union 是闭集，新增成员**必须**同步 bump `_PHASE_SCHEMA_VERSION`，不得静默扩；(b) 通用字段的机械闭合规则与 `evidence` 的语义 gate 由两组独立测试覆盖，禁止把 evidence 断言混进 round-trip 测试。验证点：v3 round-trip 测试不包含任何 evidence 语义断言。
- **修复风险**：低（纯计划文本约束）。
- **严重程度**：**中**

### M-3-未修复-[中]-禁止落盘 raw stdout 但只留 SHA-256，fail-closed 停机不可诊断

- **位置**：plan §4.2 line 111（“禁止……复制 raw stdout 到 receipt”）、plan-fix:69（stdout/stderr SHA-256 + 有界静态脱敏 stderr summary）
- **问题类型**：可观测性缺口
- **当前写法**：`CommandRecord` 只存 `stdout_sha256`；有界脱敏摘要**只给 stderr**，stdout 没有对应摘要。
- **反例/失败场景**：live lane 因 H-1/H-2 触发 fail closed。operator 拿到的全部信息是一个 stdout SHA-256 与一句“命中未知行”。原始 stdout 已随子进程消失，无法判断到底是 rate-limit WARNING、进度条、还是真的 formatter 改版。恢复只能靠盲猜重跑——而重跑在 Slice 5 是付费的。
- **为什么有问题**：计划把 fail-closed 定性为“安全停机”（§13:724），安全停机的前提是可诊断。stderr 有摘要而 stdout 没有，恰好把唯一会触发停机的那条通道设成了黑盒。
- **直接证据**：plan §4.2:111 禁止 raw stdout 入 receipt；plan-fix:69 摘要字段只列 stderr；plan §14:755 residual 只预期 formatter 文案变更。
- **建议改法和验证点**：计划新增 `stdout_reject_summary: str | None`——**仅在 ingress 判定失败时**填充，内容为触发判定的行号 + 该行经同一套静态脱敏与有界截断（复用 `_STDERR_SUMMARY_MAX_BYTES=512`）后的片段 + 判定类别（unknown/noise/missing/duplicate/ambiguous）。成功路径恒为 `None`，因此不构成 raw stdout 落盘。验证点：断言成功路径该字段为 `None`；失败路径含行号与类别，且不含绝对路径 / home / token。
- **修复风险**：低。
- **严重程度**：**中**
