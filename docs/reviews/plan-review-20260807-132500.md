### F-01 — C2 被排除但未说明理由

**位置**: Plan §3 Non-Goals

**声称**: `research_template.py`（4145 行）God file 拆分"属 MiMo C2，不在当前 scope"。

**事实**: `research_template.py` 确为 4145 行，与声称一致。但 plan 仅用"属 MiMo C2"一笔带过，未解释为何排除。C2 与 C1 同为 God file，且 C2 的 100+ 函数涵盖模板/monitoring/bundle/portfolio 等完全不同功能域，拆分复杂度与 C1 相当。

**问题**: 排除 C2 的理由不充分。如果 C1 的 5262 行值得拆分，C2 的 4145 行同样值得。plan 应明确给出排除的技术理由（如"C2 的函数间耦合度低于 C1，拆分收益不匹配风险"），而非仅引用 finding ID。

**严重度**: Low — scope 决策可辩护，但理由缺失降低 plan 可信度。

### F-02 — Characterization RED/GREEN 测试设计缺陷

**位置**: Plan §5 Slice 0

**声称**: 11 个 characterization tests，包括 `test_canonical_json_str_variant_output_is_stable` 和 `test_canonical_json_bytes_variant_output_is_stable`。

**问题**:

1. **RED 测试缺少输入多样性**: `_canonical_json` 的 str 变体接受 `value: object`，bytes 变体接受 `payload: Mapping[str, Any]`。plan 未指定测试输入应覆盖哪些边界类型（`None`、空 dict、嵌套 dict、含 Unicode 的字符串、含 bytes 的值）。仅"锁定当前输出"不足以捕获 Slice 2 迁移中的回归。

2. **GREEN 条件未定义**: plan 说"锁定当前行为"，但未定义"当前行为"的精确语义。例如，`_canonical_json` 的 str 变体对 `None` 输入返回 `"null"` 还是抛异常？bytes 变体对空 dict 返回 `b"{}"` 还是 `b'{}'`？这些细节未在 characterization test 清单中体现。

3. **`test_print_report_side_effect_ordering` 实现可行性存疑**: plan 说"通过 mock 验证副作用顺序"，但 `print_report` 的 7 个子流程共享同一个 `output_dir` 参数，mock 需要拦截每个子流程的 import 路径。如果子流程在 Slice 8 中被提取到 `_write_report.py`，Slice 0 的 mock 路径会在 Slice 8 后失效——characterization tests 自身在后续 slice 中需要修改，违反"安全网"定位。

**严重度**: Medium — characterization tests 的稳定性存疑。

### F-04 — C4 先校验导致 `print_write_report` 副作用顺序改变

**位置**: Plan §5 Slice 8，重构后的 `print_report` 编排函数

**声称**: "副作用顺序锁定：`print_report` 按现状顺序调用子流程函数"

**事实**: Plan 的编排函数代码（§5 Slice 8）显示：

```python
gate_exit = _validate_print_report_gate_conditions(...)
if gate_exit is not None:
    return gate_exit

comparison_exit, health_trend = _print_run_comparison_and_health(...)
if comparison_exit == 2:
    return comparison_exit
```

即**门禁校验在运行比较之前执行**。但 plan §1.3 声称的副作用顺序为：

```
1. print_write_report → 2. 运行比较 → 3. promotion proposal → ...
```

门禁校验（互斥检查）在现状代码中是嵌入在运行比较打印逻辑**内部**的（`write_service.py:460-565`），而非在运行比较之前独立执行。

**问题**: 提取 `_validate_print_report_gate_conditions` 为独立前置步骤，改变了执行顺序：现状是"先开始打印运行比较，遇到互斥条件时中途退出"；重构后是"先校验所有门禁条件，全部通过后再开始打印"。如果门禁校验涉及文件 I/O（如检查 `routing_proposal_input` 是否存在），重构后这些 I/O 会提前发生。

**严重度**: High — 行为重排。即使最终结果等价（门禁失败时两种顺序都返回非零退出码），中间状态不同。characterization test `test_print_report_side_effect_ordering` 需要覆盖此差异。

### F-05 — W12 `_snapshot_builder` 仍保留嵌套函数 + 反向 import

**位置**: Plan §5 Slice 5

**声称**: 提取 `_snapshot_builder` 为 `_write_snapshot_builder.py` 中的 `build_snapshot_builder` factory。

**事实**: Plan 的代码（§5 Slice 5）显示：

```python
# _write_snapshot_builder.py
def build_snapshot_builder(...):
    from dayu.cli.commands.write import _build_fresh_application_routing_snapshot

    def _builder() -> Mapping[str, Any]:
        return _build_fresh_application_routing_snapshot(...)
    return _builder
```

**两个问题**:

1. **嵌套函数未消除**: `_builder` 仍然是嵌套函数。plan §4.2 声称"禁止新增嵌套函数"，§8 声称"Slice 5 — W15/W16/W12 提取为模块级函数"。但 `_write_snapshot_builder.py` 中的 `_builder` 是嵌套在 `build_snapshot_builder` 内部的闭包。虽然这比原来的 5 处重复好，但 plan 的 invariant 声称与实际实现矛盾。

2. **反向 import**: `_write_snapshot_builder.py` → `write.py`（通过 lazy import）。plan 依赖方向图（§2.2）显示 `write.py → _write_snapshot_builder.py`，但实际存在反向依赖。plan 声称"Slice 6 完成后改为顶层 import"，但 Slice 5 和 Slice 6 之间存在一个中间状态：`_write_snapshot_builder.py` 依赖 `write.py` 的私有函数，违反"私有模块不反向依赖主模块"的隐含约束。

**严重度**: High — 硬约束冲突（嵌套函数 + 反向 import）。

### F-06 — Slice 5 新增 `Any`、Slice 7 新增 `getattr` 违反类型不变量

**位置**: Plan §4.3、§5 Slice 5、§5 Slice 7

**声称**:
- §4.3: "禁止新增 `Any`/`object`/无类型签名"、"禁止新增 `getattr`/`hasattr` 动态访问"
- §8: 声称合规

**事实**:

1. **Slice 5**: `_write_snapshot_builder.py` 的 `build_snapshot_builder` 签名为 `execution_options: Any`。plan 在 §10 残余风险中承认此问题但将其归为"C8 不在 scope"。然而 §4.3 的不变量是**无条件**的——没有"C8 治理前豁免"的例外条款。

2. **Slice 7**: `_dispatch_subcommand` 使用 `getattr(args, entry.flag, None)`。plan §8 声称"dispatch table 使用 `getattr(args, flag, None)` 作为 argparse.Namespace 的唯一合法访问边界"，但 §4.3 的不变量是"禁止新增 `getattr`/`hasattr` 动态访问"——没有"argparse.Namespace 例外"的条款。

**问题**: Plan 的不变量声明（§4.3）与实际措施（§8 合规检查）之间存在矛盾。§8 单方面添加了 §4.3 未授权的例外。如果这些例外是合理的，应修改 §4.3 明确列出例外条件；如果不合理，应修改 Slice 5/7 的实现。

**严重度**: High — 硬约束冲突。不变量被违反且例外未在不变量定义中声明。

### F-07 — Pyright ratchet/min-compat 与 Slice/Commit 计数矛盾

**位置**: Plan §9 门禁验证清单、§11 Ready-for-Review 完成定义

**声称**:
- §9: "Pyright（零新增/扩散报错）"——暗示零错误策略
- §11: "所有 9 个 Slice 独立 commit"——10 个 slice（0-9）但说"9 个"

**事实**:

1. **Pyright 策略**: 直接核验确认 `utils/ci_pr_pyright.py` 存在，实现 ratchet 策略（仅阻塞 PR 新增错误，允许基线错误通过）。但 plan §9 的验证命令是裸 `pyright`（零错误策略），与 CI 的 ratchet 行为不一致。如果基线存在已知 pyright 错误，plan 的"零新增/扩散报错"标准可能无法通过（因为裸 `pyright` 会报告所有错误，包括基线）。

2. **Slice 计数矛盾**: Plan §5 列出 Slice 0-9（共 10 个），但 §11 说"所有 9 个 Slice 独立 commit"。10 ≠ 9。

3. **min-compat 未覆盖**: Plan §9 提到"Python 3.13：全量测试（CI `pr-required min-compat` lane）"，但实际 CI 的 `pr-required-min-compat` job 使用 Python 3.11（`constraints/min-py311.txt`），不是 3.13。Python 3.13 的测试在 `ci-mainline.yml` 的 `full-platform-validation-*` jobs 中，不在 min-compat lane。

**严重度**: Medium — 事实错误，影响验证策略的正确性。
