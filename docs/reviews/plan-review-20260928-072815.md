### M2-未修复-中-合法形状的无效片段 locator 被当作依赖故障而丢失拒绝 receipt

- **位置**：V1 §4:41；§5:52,56,58；§9:110,113；主计划 Slice 3.2 的 no evidence→rejected candidate+audit。
- **问题类型**：契约缺失 / 错误分类 / 测试缺口。
- **当前写法**：列出 source/processed identity、version/hash 等 Fins 业务码；一切 unknown Fins code 固定 dependency unavailable，零 candidate/receipt。V1 同时允许五种 locator payload，要求 malformed/no evidence 的有效 context 输入产生拒绝审计。

- **为什么有问题**：这两种正常 owner 数据上的失败是所请求片段不存在；它们不代表 PG/Fins I/O 不可用。V1 把当前已知的确定性无证据输入落入“unknown”，不满足主计划失败链和 A 的 rejected+receipt 目标。
- **直接证据**：`dayu/fins/service_runtime.py:483-492` 在 records rows 已返回后检查行/列并抛上述固定码。本人无 I/O 执行 `EvidenceLocatorSnapshot.from_dict`→public `parse_evidence_locator_projection`，两者均接受 missing-column 的合法 table_cell；再执行未修改的 `_build_table_cell_fragment`，正常一行 records 数据分别得到 `table_column_missing`、`table_row_out_of_range`。现有其它片段分支还含 `table_not_records` (`:476-481`)、`page_not_supported` (`:612-615`)、`xbrl_fact_not_unique` (`:549-552`)、`xbrl_facts_unavailable` (`:534-539`)；这些也需要明确分类，不能只审外层 identity 路径。

### M3-未修复-中-同 operation 并发的唯一键恢复遗漏 candidate ID 键

- **位置**：V1 §6:69-70；§9:116-117；现有 candidate 表 `models_evidence.py:285-313` 与 0007 candidate DDL。
- **问题类型**：并发恢复风险 / 不可直接实施。
- **当前写法**：非 operation 幂等命名唯一键错误一律 conflict；只在 candidate-operation 或 receipt-PK 的 23505 后回滚 SAVEPOINT 并读取已提交 receipt。又要求同 operation/同请求两连接都返回同 receipt，并禁止把 candidate ID 碰撞盲认作相同 operation。
- **反例/失败场景**：两个连接使用完全相同 context/raw；因此 candidate_id、tenant/company、operation_id 都相同。竞争 INSERT 不仅重复 operation unique，也重复 `pk_research_candidates(id)` 和 `uq_research_candidates_tenant_company_id(tenant_id,company_id,id)`。合法 23505 若报告后两者，按 :69 被直接归 conflict，无法执行 :70 的 receipt 回读。相同请求的第二方不能保证返回胜者 receipt。
- **为什么有问题**：PostgreSQL 没有按“业务语义上希望的 operation unique”选择错误名的契约；同一 INSERT 同时触及候选 ID 的独立唯一键。单独处理 operation unique 与 receipt PK不足以实现 §9 的并发承诺。本文不声称本轮运行了 PG 或所有执行一定先报哪一个键；计划缺的是合法 candidate-ID 键冲突的安全核验路径。
- **直接证据**：既有 candidate 的 id primary key、tenant/company/id unique、tenant/operation unique 是三个独立物理键。V1 要先在 SAVEPOINT 插 candidate 再 receipt；完全相同 context 必然也重复前两个键，当前命名分类明确将其排除。
- **影响**：同请求并发可能一方成功、一方得到稳定 conflict；首提交结果策略和响应恢复强断言不成立，作者需要重新设计允许的 23505 分类。
- **建议改法和验证点**：把上述精确 candidate-ID 命名键纳入“允许核验”的 SAVEPOINT 回滚路径。新 READ COMMITTED SELECT 仍只能按 tenant+本次 operation 查 receipt，完整 fingerprint/不可变请求字段一致才返回；找不到、不同 operation/不同 candidate/context 或异常历史闭合仍 fail closed。这样同 candidateID 异 operation 仍是 conflict，不是盲认 ID 碰撞幂等。真实 PG 强制同 candidate_id/operation 两连接竞争、同 ID 异 operation、同 operation 异 ID 和跨 tenant 全球 id 碰撞，核两方结果及零重复/零 partial。
- **修复风险（低/中/高）**：中；恢复必须精确区分合法竞争、不同 operation 与缺失 receipt。
- **严重程度（低/中/高/严重）**：中。
