## 4. Adversarial Validation

### 4.1 Root Capability（S15-CTRL-15 §2）

**验证方法**：对比 plan §2 与当前代码 `_open_regular_no_follow()` 的差异，判断 plan 是否 code-generation-ready。

**当前代码事实**（`_research_template_bundle.py:522-579`）：
- `:548` 以 `os.open(resolved_source_root, os.O_RDONLY | os.O_DIRECTORY)` 打开 root，**不含 `O_NOFOLLOW`**
- `:553-563` 的中间组件和 leaf 使用 `O_NOFOLLOW`
- 每个 member 按 root pathname 重新打开 root（无 capability binding）
- 无 `fstat` identity 验证

**Plan §2 现规定**：
- 从 filesystem root FD 开始，对 `resolved_source_root` 的每个 component 逐段以 `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` + `dir_fd` 打开
- 最终 root FD 立即 `fstat` 并与 preflight `lstat` 的 `(st_dev, st_ino, mode)` exact
- 作为本次 inspection 唯一 capability 保持打开，禁止对每个 member 重新按 source-root pathname 打开
- root rename、root→symlink/root→另一目录替换、member directory/leaf 替换均不得改变本次 capability
- 任一 open/identity 失败即 fail closed
- 所有 FD 以 `ExitStack`/等价结构在 success/exception/`BaseException` 路径 exact close

**结论**：Plan §2 现已完整规定 root FD acquisition、identity binding、capability semantics 和 test requirements。implementation agent 可以从 plan 直接推导出 exact code：从 `/` FD 逐段 O_NOFOLLOW 打开到 source root，fstat 绑定 identity，后续所有 member 操作只相对此 root FD 的 dir_fd 进行。**无 open finding。**

### 4.2 Canonical Path Grammar / Reader Exact Lookup（S15-CTRL-15 §3）

**验证方法**：对比 plan §3 与当前代码路径处理逻辑，判断 plan 是否 code-generation-ready。

**结论**：Plan §3 现已完整规定 path grammar（absolute, no NUL, no mixed separators, no lexical `.`/`..`）、canonicalization owner（bundle owner 唯一）、lookup mechanism（exact string map, zero filesystem I/O）和 test requirements。implementation agent 可以从 plan 直接推导出 canonical 验证逻辑和 reader lookup 逻辑。**无 open finding。**
