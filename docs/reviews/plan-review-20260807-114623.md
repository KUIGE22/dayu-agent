### NF-1 | 未修复 | 严重度: MEDIUM | Event.set() 立即唤醒 Event.wait() 的表述误导

**位置**: 修订版 §2.3

**问题类型**: 技术表述不精确

**当前写法**:
> daemon 线程在 `_stop_event.set()` 后一个 `poll_interval`（0.5s）内退出 while 循环

**反例**:
```python
# cancellation_bridge.py:150
self._stop_event.wait(timeout=self._poll_interval)

# 当 _stop_event.set() 被调用时：
# - 如果线程在 wait() 中 → 立即唤醒，不是等 poll_interval
# - 如果线程在 get_run() 中 → 等 get_run() 返回后检查 is_set()
```

**直接证据**:
- `cancellation_bridge.py:113`: `while not self._stop_event.is_set()` — 循环顶部检查
- `cancellation_bridge.py:150`: `self._stop_event.wait(timeout=self._poll_interval)` — 底部等待
- Python 文档: `Event.set()` wakes all waiting threads

**影响**:
- 误导读者认为 `stop()` 后线程固定延迟 poll_interval 退出
- 实际延迟取决于线程在 `get_run()` 还是 `wait()` 中
- `thread.join(timeout=poll_interval*2)` 的 timeout 设置依据被误解

**建议改法**:
```
daemon 线程在 `_stop_event.set()` 后：
- 若在 `wait()` 中 → 立即唤醒，循环检查 `is_set()` 后退出
- 若在 `get_run()` 中 → 等查询返回后，`wait()` 立即返回，循环退出
- 最坏情况：线程卡在 I/O 阻塞的 `get_run()` 中，需等查询超时
```

**验证点**: 代码路径分析确认

**修复风险**: N/A — 仅影响文档表述

**严重度**: MEDIUM — 技术文档误导

**标签**: `accepted-candidate`

### NF-3 | 未修复 | 严重度: MEDIUM | 测试仍使用 `time.sleep(0.2)` wall-clock 依赖

**位置**: 修订版 §9.1, §9.3

**问题类型**: 测试设计 flaky 风险

**当前写法**:
```python
# 用 wall-clock sleep 等待 0.2s 作为"推进窗口"
# 这不是断言阈值——断言的是 counter 不变，sleep 只是给时间
import time
time.sleep(0.2)
count_after_wait = heartbeat_counter
```

**反例**:
- 在 CI 慢机或高负载下，0.2s 可能不足以让事件循环推进
- 如果系统调度延迟 > 0.2s，即使事件循环未阻塞，counter 也可能不变
- `threading.Event.wait(timeout=5.0)` 的 timeout 也是 wall-clock

**直接证据**:
- 修订版 §9.4 声称"核心断言（counter 比较）与 wall-clock 无关"
- 但 `time.sleep(0.2)` 的作用是给事件循环推进时间，如果时间不够，断言会假阳性

**影响**:
- CI 环境中可能 flaky
- 无法确定性证明事件循环被阻塞 vs 系统调度延迟

**建议改法**: 使用 `loop.call_soon_threadsafe` + `threading.Event` 做事件顺序断言:
```python
# 在外部线程中：
loop.call_soon_threadsafe(event.set)  # 请求事件循环设置 event
event.wait(timeout=5.0)  # 等待事件循环执行
# 此时确定事件循环已推进一次
```

**验证点**: 在 CI 环境中运行 100 次无 flaky

**修复风险**: LOW — 测试基础设施改进

**严重度**: MEDIUM — CI 稳定性风险

**标签**: `accepted-candidate`

### NF-4 | 未修复 | 严重度: HIGH | `asyncio.to_thread` 在 finally 块中的 cancellation 语义错误

**位置**: 修订版 §10.1, §11

**问题类型**: Python 语义理解错误

**当前写法**:
> Python 3.11+ finally 块中 cancellation 被推迟，`to_thread` 会完整执行

**反例**:
```python
async def example():
    try:
        await something()
    finally:
        # 如果 task 在进入 finally 前已被 cancel：
        await asyncio.to_thread(sync_func)  # 可能抛 CancelledError
```

**直接证据**:
- Python 3.11+ 的 "cancellation suppression in finally" 只保证 finally 块**开始执行**
- 但 finally 块中的 `await` 仍然是 cancellation point
- 如果 task 在进入 finally 前已被 cancel，`await asyncio.to_thread(...)` 会抛 `CancelledError`
- 只有 `asyncio.shield()` 或 `uncancel()` 能防止这种情况

**影响**:
- 资源可能泄漏：如果 `to_thread` 被 cancel，`_release_resources` 不会执行
- `bridge.stop()` 不会调用，线程引用丢失
- 虽然 daemon 线程不阻止进程退出，但 permit 可能泄漏

**建议改法**:
1. 使用 `asyncio.shield(asyncio.to_thread(...))` 保护关键清理
2. 或在 finally 块开头调用 `task.uncancel()` (Python 3.11+)
3. 或明确文档说明"如果 task 已被 cancel，资源清理可能不完整"

**验证点**:
```python
async def test_cancel_during_cleanup():
    task = asyncio.current_task()
    task.cancel()
    try:
        await asyncio.to_thread(lambda: None)
    except asyncio.CancelledError:
        print("to_thread raised CancelledError")  # 预期输出
```

**修复风险**: LOW — 使用 `asyncio.shield()` 即可

**严重度**: HIGH — 资源泄漏风险

**标签**: `accepted-candidate`

### NF-5 | 未修复 | 严重度: LOW | `to_thread` 提交失败场景不完整

**位置**: 修订版 §10.2

**问题类型**: 边界场景遗漏

**当前写法**:
> 若默认 `ThreadPoolExecutor` 已 shutdown（仅在事件循环关闭时），`asyncio.to_thread` 会抛 `RuntimeError`

**反例**:
- `asyncio.to_thread` 也可能因线程池耗尽（所有线程都在忙）而阻塞
- OS 线程创建失败时也会抛异常
- 这些场景不限于"事件循环关闭"

**直接证据**:
- `asyncio.to_thread` 内部调用 `loop.run_in_executor(None, func, *args)`
- `run_in_executor` 使用默认 `ThreadPoolExecutor`
- 如果线程池已满，新任务会排队等待，不会立即失败

**影响**:
- 极端情况下 `_finish_run_async` 可能长时间阻塞在 `to_thread` 提交
- 但不会导致资源泄漏（atomic-pop 已完成）

**建议改法**:
1. 文档补充"线程池耗尽时 `to_thread` 会排队等待，不会立即失败"
2. 或考虑设置线程池大小上限

**验证点**: 压力测试

**修复风险**: N/A — 仅影响文档

**严重度**: LOW — 极端场景

**标签**: `defer-candidate`
