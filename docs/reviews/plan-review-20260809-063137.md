## 2. Findings

### P1-已修复-[严重]-download 不产出 processed 快照，live 阶段序列缺少 `process`，硬门禁 §5.2 在 live lane 必然失败

- **位置**：plan §5.2「源清单逐文档记录 … processed snapshot SHA-256/状态」「缺 primary/processed … 均为硬失败」；§10 runner argv（只有 `download` → `write --preflight-only` → `write --materialize-research` → validators）；§4.2「源文档盘点使用 … `ProcessedDocumentRepositoryProtocol`」
- **问题类型**：不可直接实施 / 契约缺失 / 动机与代码事实不同源
- **当前写法**：plan 把 `processed` 状态当作 `download` 的产物，并把它写成 live 硬门禁，但 §10 的 allowlisted argv 序列中没有任何 `process` 阶段，§5.4 的 `phase-receipts/` 也只有 `download / write-preflight / write / validations` 四个 receipt。
- **反例/失败场景**：live Slice 5 执行 `download --ticker AAPL`，SEC lane 只写源文档（`sec_download_source_upsert.py:209` 写 `ingest_complete=True`），processed 快照由独立的 `process` 命令经 `sec_process_workflow.py:224 register_processed_snapshot_document` → `_processed_repository` 写入 `workspace/portfolio/{ticker}/processed`（README.md:1727 明确）。download 路径只做 `_mark_processed_reprocess_required`（`sec_download_source_upsert.py:136-143`），即“标记需重处理”，不生成快照。于是 `verify` 阶段每一份 filing 的 processed 字段都是缺失/需重处理 → 按 §5.2「缺 processed = 硬失败」，整次 live run 在花完 DeepSeek+MiMo 全部预算之后必然 FAIL。
- **为什么有问题**：这是把付费阶段排在必然失败的门禁之前，违反 plan 自身 §4.1「不自动进入后续付费阶段」的意图，也违反 CLAUDE.md「root cause 必须逻辑/数据同源」——门禁写的是 `process` 的产物，序列跑的是 `download`。
- **直接证据**：
  - `dayu/fins/pipelines/sec_download_source_upsert.py:136-143, 266-291`（download 只 mark reprocess required）
  - `dayu/fins/pipelines/sec_process_workflow.py:19, 224-271, 328`（processed 快照由 process workflow 写入）
  - `dayu/cli/command_names.py:9-18`（`download` 与 `process` 是两个独立 FINS 命令）
  - `README.md:1695-1728`（`process` 快照写入 `processed/`，是独立命令）
  - 注：`dayu/fins/tools/service.py:120-128` 声明工具链「不依赖 `processed/*.json`」，因此 `write` 本身不会替 plan 补上这一步。
- **影响**：live run 花费真实 Token/费用后在最后一道门禁 FAIL；或者 implementation agent 为了让门禁通过而擅自放宽 §5.2（掩盖 freshness 契约），两种结果都污染首个 baseline。同时 deterministic Slice 0/1 的 fixture 会按错误的“download 即有 processed”结构固化，Slice 5 才暴露。
- **建议改法和验证点**：二选一，并在 plan 中写死：
  1. 在 §10 argv 序列的 `download` 之后、`write --preflight-only` 之前插入 `python -m dayu.cli process --ticker AAPL --base <run-root>/data-workspace`，§5.4 增加 `phase-receipts/process.json`，§8.1 增加 process 阶段恢复语义；或
  2. 把 §5.2 的 processed 硬门禁降级为「source-level `ingest_complete=true` + `primary_document` 指向 `_docling.json`」硬门禁，processed 快照状态改为 warning-only residual。
  验证点：Slice 1 的 evaluator 测试必须有一个「source 完整但 processed 缺失」用例，且其期望结果与所选方案一致；Slice 2 的 fake command runner 断言必须锁定包含（或明确不包含）`process` 阶段的精确 argv 序列。
- **修复风险（低/中/高）**：低（纯 plan 文本 + 一个阶段/一条门禁的定义调整）
- **严重程度（低/中/高/严重）**：严重

### P2-已修复-[高]-run root 不是 self-contained：`--base <run-root>/data-workspace` 需预先存在且需 workspace init 产物，plan 无前置步骤

- **位置**：plan §4.1「live 产物只写入 … `<run-id>/`」；§5.1「live run 开始前工作区目标路径必须不存在」；§5.4 产物 inventory；§10 全部 argv 的 `--base <run-root>/data-workspace`
- **问题类型**：不可直接实施 / 前置条件缺失
- **当前写法**：plan 同时要求「run root 目标路径必须不存在」和「所有命令用 `--base <run-root>/data-workspace`」，但没有任何创建/初始化该 workspace 的前置阶段，也没有说明 `--config` 如何解析。
- **反例/失败场景**：`resolve_workspace_config` 在 `dayu/cli/dependency_setup.py:332-338` 对 `--base` 做 `if not workspace_dir.exists(): Log.error(...); raise SystemExit(1)`。因此第一条 `download` argv 会在任何网络动作之前直接 exit 1。若 implementation agent 为绕过它而先 `mkdir -p`，则 `--config` 未显式传入时按 `dayu/startup/paths.py:42-49` 回落到 `<run-root>/data-workspace/config`，该目录为空，`ConfigFileResolver`（`config_file_resolver.py:66-78`）会回落到包内 `dayu/config`——于是 §5.1 要求绑定的 "package config SHA-256" 与实际生效配置的关系变得含糊，且与用户日常 `workspace/config` 覆盖完全脱钩。
- **为什么有问题**：plan 声称 Slices 0–4 结束即 handoff-ready，但 live 序列的第一条命令在当前代码下 100% 失败；这属于 plan 未达到 "code-generation-ready"。同时 §5.1 的 config 指纹绑定语义未定义清楚（是包内默认还是用户 workspace 覆盖），会让 receipt 的可复现声明失真。
- **直接证据**：`dayu/cli/dependency_setup.py:332-338, 340-341`；`dayu/startup/paths.py:21-49`；`dayu/startup/config_file_resolver.py:66-80`；`README.md:165-189`（`init` 负责复制 config/assets）
- **影响**：live 阶段 0 秒即失败，或 implementer 自行发明前置逻辑（越权、绕过 §9 白名单）；receipt 的 config 指纹语义不可验证。
- **建议改法和验证点**：在 §10 明确 run root 准备契约：runner 显式创建 `<run-root>/data-workspace`（这不违反 §5.1，§5.1 应改写为「run root 在 `prepare` 前不存在，由 `prepare` 一次性创建并写入 plan」），并对所有 `dayu.cli` argv 显式传 `--config <明确路径>`（推荐 `workspace/config`，若不存在则 fail closed 并提示先 `dayu-cli init`）。§5.1 的 config 指纹必须指明对哪个已解析目录取指纹。验证点：Slice 2 的 fake runner 测试断言每条 argv 都带显式 `--config`，且 run root 预创建后 `--base` 存在性检查通过。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：高

### P3-已修复-[高]-`--research-base` 不能真正把 research 产物隔离到 run root，与 §5.4 目录树和 §5.1 containment 冲突

- **位置**：plan §5.4 产物 inventory `research/assets/research_templates/…`；§10 write argv `--research-base <run-root>/research`；§5.1「输入或输出真实路径必须位于精确 run root」
- **问题类型**：架构边界 / 契约缺失
- **当前写法**：plan 假定 `--research-base <run-root>/research` 能让全部 13 个 research 产物落在 run root 内。
- **反例/失败场景**：`dayu/cli/commands/write.py:522-528` 确实把 `research_base` 传给 `resolve_research_template_selection(workspace_root=research_base)`，而 `dayu/cli/research_template_assets.py:126-130` 把 composed 模板写到 `workspace_root / "assets" / research_templates / …`。也就是说产物落点是 `<run-root>/research/assets/research_templates/`，而 plan §5.4 画的树正是这个形状——这一半是对的。但 `resolve_research_template_selection` 的行为是：若目标文件已存在且内容与包内 composition 不一致，直接 `raise ValueError`；若不存在则创建。plan §5.1 同时要求「run root 目标路径必须不存在」，因此首跑必然走「创建」分支，这没问题；真正的缺口是 plan 从未说明 `common-plus-technology.md` 的**源**是包内 `dayu/assets/research_templates/`（`resolve_package_assets_path()`），而 §5.1 要求 receipt 绑定 "technology/common 模板 SHA-256"——如果 implementer 误以为模板来自 `<run-root>` 或 `workspace/assets`，指纹将取自错误来源，且 `--research-base` 隔离下 `workspace/assets` 的用户自定义模板**不会**生效，plan 也没有声明这一点。
- **为什么有问题**：§5.1 的模板指纹是 receipt 可复现性的一部分；来源模糊会让「配置指纹完整」这一评分项（§6.2 可复现与恢复 4 分）不可验证。且 plan 没有告诉 implementer「本次验收刻意绕开了 workspace 自定义模板覆盖」，这是一个应显式记录的 residual。
- **直接证据**：`dayu/cli/commands/write.py:522-528`；`dayu/cli/research_template_assets.py:45, 69, 100-150`；`dayu/startup/config_file_resolver.py:37`
- **影响**：模板指纹取错来源 → receipt 声称的可复现性不成立；用户自定义模板静默失效且未进入 residuals。
- **建议改法和验证点**：§5.1 明确写「模板 SHA-256 取自 `resolve_package_assets_path()/research_templates/{common,technology}.md`」，并在 §14 残余风险中加一条「`--research-base` 隔离下 workspace 自定义模板不参与本次验收」。验证点：Slice 1 增加断言——receipt 中模板指纹等于包内文件指纹。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：高

### P4-已修复-[中]-§5.3 的 evidence 契约表述比实现更强，evaluator 会与生产 builder 产生判定分歧

- **位置**：plan §3.1 表格「evidence line 至少四段，来源清单按前三段去重并保留定位字段」；§5.3「四段均非空」「定位不得只写‘见财报/官网’」
- **问题类型**：非最优方案 / 契约表述偏差
- **当前写法**：plan 把「四段非空」当作与生产实现同源的契约。
- **反例/失败场景**：`source_list_builder.py:104-113 looks_like_evidence_item` 只在**缺 `- ` bullet** 的兜底路径上要求 `len(parts) >= 4 and all(parts[:4])`；而 `extract_evidence_items:76-82` 对带 `- ` 前缀的行**无条件收录**，不做四段校验。`_extract_dedup_key:238-258` 在 `len(parts) < 3` 时退化为整行去重。因此生产链路允许「`- ` 开头但只有两段」的 evidence 进入来源清单；plan 的 evaluator 若按「四段非空」硬失败，会在真实报告上判 FAIL，而生产 validator 判 PASS。
- **为什么有问题**：两套规则不同源，评分结果不可解释；且 plan §4.2 明确禁止反向修改 `dayu/` 迁就验收器，implementer 会陷入死角（改不了生产、又满足不了 plan）。
- **直接证据**：`dayu/services/internal/write_pipeline/source_list_builder.py:59-83, 88-113, 238-258`
- **影响**：Slice 1 的 fixture 与真实 live 报告判定标准不一致；首个 baseline 的 rubric 分数不可复现到 live。
- **建议改法和验证点**：§5.3 改为显式两层：(a) 与生产同源的**结构层**——复用 `looks_like_evidence_item` 的同一判定语义；(b) 验收器**额外加严层**——四段非空 + 定位非模板化，且明确标注「这是验收器高于生产 builder 的附加门禁，其失败归类为质量 finding 而非产物损坏」。验证点：Slice 1 增加「带 `- ` 的三段 evidence」用例，断言归类为验收器加严失败而非 builder 契约破坏。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### P5-已修复-[中]-price snapshot 声明「不联网」，但 write scene 自带 `web` 工具，plan 未封住模型侧联网取价

- **位置**：plan §5.2「验收器不得新增联网或 live web 抓价能力」；§15.4「验收器只校验/指纹化该文件，不自行联网抓价」
- **问题类型**：范围漂移 / 隔离边界不完整
- **当前写法**：约束只覆盖「验收器」，未覆盖被验收的 `write` 运行本身。
- **反例/失败场景**：`dayu/config/prompts/manifests/write.json` 的 `tool_selection.mode=select, tool_tags_any=["fins","web"]`——DeepSeek 主写在 live run 中可自行调用 web 工具抓取当日股价。于是报告里的价格可能来自模型自取的 web 结果，而 receipt 里指纹化的却是用户提供的 price snapshot 文件，两者可能不一致；§6.1 hard gate 8 只校验 snapshot 文件本身合法，检测不到这种分歧。
- **为什么有问题**：plan 的核心承诺是「重要判断可追溯到来源」；估值价格是最典型的重大数字主张，却存在一条未被 receipt 覆盖的取值通道。这是 observability gap，不是风格问题。
- **直接证据**：`dayu/config/prompts/manifests/write.json`（`tool_selection.tool_tags_any: ["fins","web"]`）；plan §5.2/§15.4 的约束主语仅为「验收器」
- **影响**：估值章节价格与已授权 snapshot 不一致却仍判 PASS；live run 产生未预算的 web 请求。
- **建议改法和验证点**：§5.3 增加确定性门禁「报告估值章节中出现的价格/市值数值必须与 price snapshot 的 `price` 一致（或显式标注为 snapshot 派生），否则 FAIL」；§14 增加 residual「write scene 含 web 工具，模型可能自取外部价格，本次靠交叉校验而非工具禁用来兜底」。验证点：Slice 1 增加「报告价格 ≠ snapshot 价格」fixture，断言 fail closed。
- **修复风险（低/中/高）**：低
- **严重程度（低/中/高/严重）**：中

### P6-已修复-[中]-wall-clock hard timeout 的取消语义未定义，Slice 2「逐阶段剩余 wall-clock timeout」缺少可实施的终止/清理契约

- **位置**：plan §7「runner 把 `max_wall_seconds` 作为整个 run 的 hard timeout」；§9 Slice 2「逐阶段剩余 wall-clock timeout」；§9 Slice 2 预期断言；§8.1 恢复
- **问题类型**：状态机漏洞 / 并发恢复风险 / 测试缺口
- **当前写法**：只说「hard timeout」「逐阶段剩余时间」，没有定义超时命中时对子进程做什么、部分写入的产物如何标记、phase receipt 如何记录。
- **反例/失败场景**：`write` 阶段在 `max_wall_seconds` 剩余 0 时被 timeout。若 runner 只 `kill` 而不处理，子进程可能在 SIGKILL 后留下半写的 manifest / 部分章节，`data-workspace` 仓储 journal 处于中间态。plan §8.1 只覆盖了「download 失败」「write 中断」「materialize 失败」，但没有覆盖「wall-clock 超时导致的强制中断」这一独立分支：它同时具备「已花费真实费用」+「产物半成品」+「不允许自动 resume」三个属性。Slice 2 的预期断言里也没有 timeout/signal 后的产物状态断言，只写了「runner 在 timeout、signal 后停止」。
- **为什么有问题**：这是最贵的失败路径（钱已花、状态不明），却是 plan 中定义最薄的一处。implementation agent 会自行发明终止策略（SIGKILL vs SIGTERM+grace、是否 `kill` 进程组），不同选择对 SQLite/journal 的后果差异很大。
- **直接证据**：plan §7、§9 Slice 2、§8.1 三处均无超时终止/清理语义；§8.1 的恢复清单不含 timeout 分支
- **影响**：live 超时后 run root 状态不可判定；恢复决策依赖人工猜测；Slice 2 的测试无法证明超时路径安全。
- **建议改法和验证点**：§9 Slice 2 明确：超时先 SIGTERM 并给固定 grace，再 SIGKILL；终止后必须写 `phase-receipts/<phase>.json` 且 `status=timeout`、记录已用时与剩余时；§8.1 增加「wall-clock timeout」独立恢复条目，规定「一律 FAIL、不自动 resume、产物原样保留并在 residuals 标记 `partial_by_timeout`」。验证点：Slice 2 增加 fake runner 用例——阶段超时后断言（a）后续阶段未执行、（b）timeout receipt 已写、（c）产物目录未被删除或重命名。
- **修复风险（低/中/高）**：中
- **严重程度（低/中/高/严重）**：中

### P7-已修复-[中]-§6.1 hard gate 10 与 §6.2「人工给分」把主观复核塞进自动判定，rubric 边界不可交付

- **位置**：§6.1 hard gate 10「人工质量复核没有未解决的 unsupported material claim；High/Medium finding 必须为 0」；§6.2「需要判断语义的项必须由复核者明确给分并列出引用位置」；§5.4 `quality-review.json`
- **问题类型**：切片过粗 / 不可直接实施
