### M-2 — security：`main()` 异常脱敏不完整

**严重度：Medium** ｜ 类别：security

**直接代码证据**：

```
CLI:1795  except (ContractError, OSError) as exc:
CLI:1796      message = _redact_cli_text(str(exc))
CLI:1797      sys.stderr.write(f"investment-agent-acceptance: {message}\n")
```

只有这两类异常走脱敏。任何其它异常（`ValueError`、`KeyError`、第三方库异常、`json` 解析异常等）会以完整 traceback 直接落到 stderr，**不经过 `_redact_cli_text`**。traceback 中可能包含局部变量 repr、路径、以及 provider 抛出的携带 key 片段的错误消息。

**最小修复**：在 CLI:1795 之后追加兜底分支，保持退出码语义不变：

```python
except Exception as exc:  # 兜底：任何未预期异常同样脱敏，绝不裸露 traceback
    sys.stderr.write(f"investment-agent-acceptance: {_redact_cli_text(repr(exc))}\n")
```

### M-3 — correctness/recovery：`SubprocessFactory.start` 未固定 `cwd`、未关闭 `stdin`

**严重度：Medium** ｜ 类别：correctness / recovery

**直接代码证据**：

```
CLI:1146-1152  process = subprocess.Popen(
                   argv,
                   shell=False,
                   stdout=subprocess.PIPE,
                   stderr=subprocess.PIPE,
                   text=True,
               )
```

无 `cwd`、无 `env`、无 `stdin`。

**风险一（cwd，已实证）**：terminal verify argv 是

```
CLI:1397-1405  (python_path, "-m", "utils.investment_agent_acceptance", "verify", "--plan", ..., "--json")
```

而 `utils` 包**不在安装分发内**：`pyproject.toml:105` 为 `include = ["dayu*"]`。已实测 `cd / && python -c "import utils"` → `ModuleNotFoundError: No module named 'utils'`。因此 `-m utils.investment_agent_acceptance` 能否解析**完全依赖调用者进程的 cwd**。对一个以「fingerprint 化、可复现」为核心卖点的验收工具，把关键子进程的可解析性挂在继承来的 cwd 上是真实缺陷：同一份 plan、同一个 fingerprint，从不同目录发起 run 会得到不同结果（其中一种是 `process_start_failed` 或 exit≠0）。

对比：`GitRepositoryStateProvider.read` 在两次 `subprocess.run` 中都显式传了 `cwd=repository_root`（CLI:960、968）。同一模块内两处子进程创建的严谨度不一致，说明这是遗漏而非有意设计。

**风险二（stdin）**：付费 `write` 阶段继承调用者 tty stdin。若被调用的 `dayu.cli` 在任何路径上读 stdin（确认提示、getpass），子进程会静默阻塞直到 whole-run wall clock 耗尽——耗掉全部预算窗口，且 receipt 只会记 `whole_run_wall_clock_timeout`，不指向真实原因。

**最小修复**：

```python
process = subprocess.Popen(
    argv,
    shell=False,
    cwd=repository_root,          # 由 RuntimeIdentity 显式注入，不继承调用者 cwd
    stdin=subprocess.DEVNULL,     # 子进程不得读取 stdin
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
    text=True,
)
```

`SubprocessFactory` 需接受 `repository_root` 构造参数（由 `main` 从 `default_runtime_identity()` 传入），`ProcessFactory` 协议签名不变。

### M-4 — recovery：失败诊断信息被完全丢弃

**严重度：Medium** ｜ 类别：recovery

**直接代码证据**：

```
CLI:2828  return "command_failed_with_stderr" if stderr else "command_failed"
```

stderr 原文在此处被完全丢弃，且 `_execute_command`（CLI:2287）只把这个二值分类写入 receipt 的 `stop_reason`。run root 内**不留任何诊断痕迹**。

不脱敏回显的判断是对的（见攻击面 9 PASS），但「不回显」被实现成了「不保留」，二者被过度合并。后果：付费 `write` 阶段失败后，operator 拿到的全部信息是 `command_failed_with_stderr` + exit code，无法判断是配额、鉴权、网络还是数据问题，只能重跑——而重跑要再付一次模型费用。这与 accepted plan 的 recovery 目标相悖。

**最小修复**：保留脱敏后的 stderr 尾部到 run root 内的独立文件，不进入 fingerprinted receipt（避免影响 receipt 字节稳定性与 digest 闭合）：

```python
# 在 _execute_phase / _execute_terminal_verify 中，失败时：
diagnostics = run_root / "phase-receipts" / f"{phase_name}.stderr.txt"
_atomic_write_bytes(diagnostics, _redact_cli_text(stderr[-4096:]).encode("utf-8"))
```

同时须把该文件名加入 `_validate_receipt_root`（CLI:2578）的 `allowed_files`，否则后续 live verify 会因「未知或非普通 phase receipt」拒绝。

### M-5 — test gap：whole-run wall-clock 耗尽路径从未被执行

**严重度：Medium** ｜ 类别：test coverage / correctness

**直接代码证据**：

```

                   monotonic_value: float = 100.0     # 常量，monotonic() 永不前进
```

因 `monotonic()` 恒为 100.0，`remaining = plan.max_wall_seconds - (monotonic() - run_started)` 恒等于 `max_wall_seconds`，以下两条分支**永不进入**，覆盖率 miss 列表证实：

```

CLI:2181       stop_reason="whole_run_wall_clock_exhausted_before_terminal_verify"  # miss
```

**次生问题**：`_load_planned_receipt_prefix`（CLI:2634）的 `receipt.remaining_wall_seconds > previous_remaining` 单调性检查，在测试中因所有 receipt 的 `remaining_wall_seconds` 完全相等而被**平凡满足**——该断言的实际有效性从未被验证。若比较符号写反（`<` 写成 `>`），当前测试套件不会发现。

**最小修复**：给 `_FixedClock` 增加可注入的 monotonic 序列：

```python

    monotonic_values: tuple[float, ...] = (100.0,)
    _index: int = 0
    def monotonic(self) -> float:
        value = self.monotonic_values[min(self._index, len(self.monotonic_values) - 1)]
        self._index += 1
        return value
```

补三条用例：(a) 首条命令前预算已耗尽 → `whole_run_wall_clock_exhausted_before_start`；(b) planned 全通过但 terminal 前耗尽 → `..._before_terminal_verify`；(c) 严格递减的 `remaining_wall_seconds` 序列 + 一条被人为构造成递增的 receipt，断言 live verify 拒绝。

### M-6 — test gap：`termination_unconfirmed` 两条 OSError 分支未测

**严重度：Medium** ｜ 类别：test coverage

**直接代码证据**（两处均在覆盖率 miss 列表中）：

**最小修复**：`_FakeProcess` 增加 `raise_on_terminate: bool` / `raise_on_kill: bool` 字段，补两条用例，分别断言 `termination_action == "termination_unconfirmed"`、`status == "timeout"`、`partial_by_timeout is True`。

### M-7 — availability：fixture 固定 temp root 的 stale lock 与 cleanup 掩盖

**严重度：Medium** ｜ 类别：recovery / availability

**直接代码证据**：

```
CLI:2857-2861  try:
                   lock.mkdir()
               except FileExistsError as exc:
                   raise ContractError("fixture verify 已有并发实例") from exc
...
CLI:2890-2892  finally:
                   if workspace.is_dir() and not workspace.is_symlink():
                       shutil.rmtree(workspace)
                   lock.rmdir()
```

**问题一（stale lock 永久阻塞）**：lock 路径固定为 `{tempdir}/dayu-investment-agent-aapl-fixture-verify.lock`。进程被 SIGKILL / OOM kill / 断电后，`finally` 不执行，lock 目录永久残留，此后**所有** fixture verify 都会以「已有并发实例」失败。implementer 在 artifact 第 88 行自述「stale lock/root 需要 operator 明确检查后处理」——但 lock 目录内没有任何信息（无 pid、无时间戳）能让 operator 判断它是活锁还是死锁，只能靠猜。「fail closed」是对的，但「fail closed 且无法诊断」不是。

**问题二（cleanup 掩盖主异常）**：`finally` 中的 `lock.rmdir()` 若自身抛 `OSError`（例如 rmtree 部分失败导致 lock 目录非空、或权限变更），会**替换掉** try 块中正在传播的真实异常。operator 看到的是 `OSError: Directory not empty`，真正的评估失败原因丢失。

**最小修复**：

1. lock 目录内写一个 `owner.json`（pid + ISO8601 UTC 启动时间），使 stale 可诊断；
2. `finally` 改为：

```python
finally:
    with contextlib.suppress(OSError):
        if workspace.is_dir() and not workspace.is_symlink():
            shutil.rmtree(workspace)
    with contextlib.suppress(OSError):
        lock.rmdir()
```

清理失败不得掩盖主异常；清理确实失败时由下一次运行的 stale 检查（CLI:2864）报出。

### L-1 — hardening：absolute path sanitizer 不覆盖 `--flag=/abs` 形式

**严重度：Low（当前不可利用）** ｜ 类别：security hardening

**直接代码证据**：

```

contracts:2931-2945  return (PurePosixPath(token).is_absolute() or token.startswith("~")
                             or re.match(r"^[A-Za-z]:[\\/]", token) is not None)
```

两处判定**只检查 token 起始字符**。形如 `--config=/Users/alice/...` 的 token 因首字符是 `-` 而被判为非绝对路径，直接原样进入 receipt 的 `safe_argv`，泄漏宿主用户名与目录结构。

**当前不可利用**：`build_phase_specs` 只产生分离式 `--config /path`，且 `_validate_cli_command_shape`（CLI:3511）用 `command.count("--config") != 1` 计数——`--config=/x` 形式会因计数为 0 而被拒。因此这是纵深防御缺口，不是活跃漏洞。

**最小修复**：在两处判定前先做 `token.partition("=")[2]` 拆分，对右半段同样应用绝对路径判定。

### L-2 — latent：contracts 解析层归一化会接受被篡改输入

**严重度：Low（被上层堵死）** ｜ 类别：security hardening

**直接代码证据**：

## 五、值得肯定的设计

以下几点在返修中**不应被改动**，它们是本 slice 的正确核心：

1. **canonical-bytes 逐字节相等作为最终防线**（CLI:2488、2711）——比任何字段级校验都强，且让解析层的实现细节无法成为攻击面。
2. **terminal verify 的双向自引用断言**（CLI:1529-1532）——正反两个方向同时断言，而非只断言期望方向。
3. **有意不复用 `dayu.redaction` 的动态 redactor 与 `RedactingArgumentParser`**——复用现成组件反而会引入枚举环境变量值的路径；自建 `_PresenceSafeArgumentParser` 是正确取舍，不是重复造轮子。
4. **`build_phase_specs` 保持单一 188 行 pure builder**——它的「唯一性」是 `run_acceptance` canonical equality 检查能成立的前提，拆分会削弱安全性。
5. **`termination_unconfirmed` 作为一等状态**——诚实承认「不知道进程是否已死」，而非谎报 `kill`。（正因如此，M-6 的测试缺口才必须补。）
