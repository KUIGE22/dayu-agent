## 2. 根因分析

### 2.1 FunctionDef 40→41：**陈旧 plan 条目，非漏实施**

§1.5 声明 "entry 1 + runners 39，FunctionDef exact 40"。但 Slice 10 在 `research_template.py` 中新增了 `_resolve_research_template_action`（S10-CTRL-04 的 selector 函数），使终态为 entry 1 + runners 39 + selector 1 = **41**。

§11 item 15 写 "主模块 FunctionDef exact40" — 此为 v5.1 (S9-CTRL-01) 时的计数，未随 v5.2 (S10-CTRL-04) 同步更新。

**结论**：plan erratum，FunctionDef 应为 **41**。selector 是 Slice 10 的显式交付物（S10-CTRL-04），不是遗漏。

### 2.2 LOC gate 冲突：**陈旧估算，非漏实施**

所有 15 个 Slice（0–13）的结构交付物均已在 HEAD `2a4bafb` 验证存在：
- write.py: 16 adapter + Phase A dispatch loop + Phase C–H 完整
- research_template.py: entry + selector + 39 runners
- 5 个子模块: 83 迁移函数正确分布
- _write_dispatch.py: 4 class
- arguments.py: 3 class (Protocol × 2 + Dayu)

**没有代码缺失。** LOC 超标的原因是 plan 低估了两处：

1. **adapter 模板开销**：每个 adapter 含 docstring + 类型注解 + context 构造 + runner 调用，plan 估算 ~11 行/adapter，实际 ~17 行。16 个 adapter 合计多出 ~96 行。
2. **runner 模板开销**：39 个 `_run_*` 函数平均 27 行（含 docstring + try/except + 参数解析 + 错误处理），plan 隐含 ~15 行/runner。39 个 runner 合计多出 ~468 行。

## 3. Findings

### H-01: research_template.py LOC gate 严重超标（HIGH）

**事实**：§11 item 2 要求 `research_template.py` ≤ 800 行，实际 1369 行，超出 71.1%。

**影响**：§11 是 plan 的完成定义（definition of done）。该 gate 在所有 15 个 Slice 实施后仍未满足，意味着 plan 的 LOC 预算模型存在系统性低估。虽然这不是功能缺陷（所有结构交付物均存在），但作为"可验证的完成标准"已实质失效。

**裁决**：plan gate 需要修正。两个选项见 §4。

### M-01: FunctionDef 40→41 计数未同步（MEDIUM）

**事实**：§1.5 和 §11 item 15 声明 FunctionDef exact40，实际 41。差异来源为 `_resolve_research_template_action`（Slice 10 S10-CTRL-04 交付物）。

**影响**：任何依赖 exact40 的 AST 断言测试会失败。当前未发现此类测试（Slice 10 的测试验证 mapping 39-key 而非 FunctionDef 计数），但未来维护者可能被误导。

**裁决**：plan erratum，改为 exact41。

### L-01: write.py LOC gate 轻微超标（LOW）

**事实**：§11 item 2 要求 `write.py` ≤ 850 行，实际 1014 行，超出 19.3%。

**影响**：1014 行仍在可维护范围内。adapter 平均 17 行/个是 docstring + 类型安全的合理开销。Phase C–H 482 行包含 6 个阶段的完整逻辑，进一步压缩会损害可读性。

**裁决**：gate 放宽至 ≤1050 即可覆盖。

## 4. 裁决：Gate 修正 vs 新增 Slice 14

### 方案 A：修正 plan gate（RECOMMENDED）

**操作**：发布 v5.6 plan erratum：
1. §11 item 2: `write.py` ≤ 850 → ≤ 1050；`research_template.py` ≤ 800 → ≤ 1400
2. §1.5 / §11 item 15: FunctionDef exact40 → exact41
3. §1.5: 原 123 函数 → 124（83 + 41 = 124）

**理由**：
- 低风险：零代码变更，零回归可能
- LOC 低估的根因是 docstring/类型注解/错误处理的模板开销，这些是 AGENTS 硬约束（中文 docstring、零 Any、零无类型签名）的必然成本
- 进一步压缩 LOC 需要削减 docstring 或合并 adapter，违反编码硬约束

**残余风险**：research_template.py 1369 行仍然偏大，未来可独立治理（非本 plan scope）。

### 方案 B：新增 Slice 14 瘦身（NOT RECOMMENDED）

**操作**：新增 Slice 14 提取 runner 公共模式（try/except 模板、参数解析）为辅助函数。

**风险**：
- 39 个 runner 各有不同的参数组合、异常类型、错误消息，强行提取模板会引入 `**kwargs` 或 `Any`
- 改动 39 个函数 + 测试迁移 = 高回归风险
- 违反 "默认按全新设计处理" 原则——当前实现已通过全部测试

**结论**：方案 A 风险/收益比显著优于方案 B。
