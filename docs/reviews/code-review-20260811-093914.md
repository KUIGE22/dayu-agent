# Code Review

## Findings

### 1-未修复-高-import 专用参数可绕过显式模式并触发普通 init 写入旧 workspace
- **入口/函数**: `dayu-cli init --base <legacy-root> --import-manifest <path> --target-tenant-id <uuid>`，`run_init_command()`。
- **文件(行号)**: `dayu/cli/arg_parsing.py:1460-1471`，`dayu/cli/commands/init.py:1823-1879`。
- **输入场景**: 操作员提供 import manifest 与 target tenant，但遗漏 `--import-existing-workspace`；或把这些 import 专用参数误用于普通 `init`。
- **实际分支**: argparse 把两个专用参数正常写入 Namespace；`run_init_command()` 仅以 `import_existing_workspace` 判断，值为 `False` 时直接进入普通 init 分支。
- **预期行为**: S15-CTRL-04 要求 import 语义参数 unknown/missing/repeated 时 fail closed，且 explicit-import 与普通 init 隔离；带有 import 专用语义但缺少唯一模式开关不得执行普通初始化。
- **实际行为**: `import_manifest` 与 `target_tenant_id` 被静默忽略；随后普通分支在同一个 `--base` 上执行 `mkdir`、workspace lock、复制 config/assets 和 `apply_all_workspace_migrations()`。因此一个本意为导入旧 workspace 的命令行拼写错误可改写该 source tree，恰好触发 S15 明令隔离的副作用。
- **直接证据**: 两个参数以普通 `store` 参数注册且没有互斥/依赖校验（`arg_parsing.py:1460-1471`）；唯一分流条件是 `init.py:1823`；false 分支从 `1826` 开始，明确创建目录（`1846`）、复制文件（`1870-1875`）并执行 legacy migration（`1877-1879`）。现有 parser 测试只覆盖完整 import 参数与完全无 import 参数的普通 init（`tests/cli/test_workspace_migrations.py:1435-1477`），未覆盖该混合输入。
- **影响**: 高风险数据完整性问题。失败命令不会停在安全错误，而可能修改旧 workspace 的 config/assets/Host SQLite，违背 Slice 1.5 的 read-only import 边界与 normal-init 隔离。
- **建议改法和验证点**: 在 parser 或进入 `run_init_command()` 的唯一语义 gate 中，要求三项 import 参数只能与主开关一起出现；反向要求主开关存在时两项均恰好一次，并拒绝所有重复语义参数。先于路径 resolve、目录创建和任何普通-init 调用返回 `workspace_import_usage`。补充 CLI 行为测试，断言该输入返回 1、普通 init 的全部副作用调用数为 0、source tree manifest 不变。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### 2-未修复-高-bundle closure 在 containment/non-symlink 校验前读取不受信任路径
- **入口/函数**: `stage_workspace_import()` -> `_inspect_bundle_closure()` -> `inspect_research_template_bundle_closure()`。
- **文件(行号)**: `dayu/cli/workspace_migrations/platform_import.py:751-759,877-880`，`dayu/cli/commands/_research_template_bundle.py:516-525,536-579,629-645`。
- **输入场景**: manifest 指向 source root 内的 bundle descriptor symlink；或 descriptor 的 `monitoring_rules`、`source_map`、`research_workbook`、`research_checklist` 或 `source_write_manifest.path` 指向 source root 外的常规文件/符号链接。
- **实际分支**: staging 只作 locator 字符串形态检查，随即调用 closure owner；owner 在对 descriptor 及 artifact 做 `lstat`、regular、contained 检查前调用 `_load_json_object(bundle_path)` 和 `validate_research_template_bundle_descriptor(payload)`。
- **预期行为**: S15-CTRL-07 要求 manifest 和每个 closure 引用路径均先以 `lstat` 证明 non-symlink/regular，再 resolve 并证明 contained 于 source root；staging 不得读取 source-root 外的内容或未列的 raw bytes。
- **实际行为**: `_load_json_object(bundle_path)` 在 `:518` 先跟随 descriptor symlink 读取 JSON；后续 full validator 在 `:523` 会使用 descriptor 中的原始绝对路径。其监控校验直接 `_load_json_object(rules_path/source_map_path)`（`_research_template_bundle.py:147-153`），检查单校验直接 `read_text()`（`:208-215`），随后才在 `:536` 起逐条调用 `_build_closure_file_entry()` 做 containment/symlink 拒绝。最终会报错，但敏感路径内容已被读取。
- **直接证据**: `platform_import.py:877-880` 未在 owner 调用前执行文件安全检查；owner 的安全检查位于 `_build_closure_file_entry()` 的 `:629-645`，晚于 descriptor parse/validator。现有 escape/symlink 测试仅断言最终抛出 `ResearchBundleClosureError`（`tests/cli/test_research_template_command.py:5482-5518`），没有 read/hash spy，因而未证明“拒绝前零外部读取”。
- **影响**: 高风险 trust-boundary 失效。恶意或并发变更的旧 workspace 可诱导 import 进程在 fail-closed 前读取 source root 外的本地内容，违反本 slice 的 raw-byte/read-only 约束；错误收敛不能撤销已经发生的读取。
- **建议改法和验证点**: 将 descriptor 与所有引用路径的 descriptor-only 安全预检置于任何解析、validator、hash 或内容读取之前；应通过已验证的 non-symlink file descriptor/等价无跟随打开方式完成读取，以消除检查后替换的 TOCTOU 窗口。只有所有 closure 路径已证明 contained/regular 后，才复用现有 descriptor validator。为 descriptor symlink、外部 `source_map`/`research_workbook`/checklist/source-manifest 与检查后替换场景增加 read/hash spy，断言外部文件打开次数为 0。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 高。

### 3-未修复-中-strict manifest 未拒绝跨 company 的重复 security，错误延后为 repository drift
- **入口/函数**: `stage_workspace_import()` 的 manifest 解析与 verified company 构造。
- **文件(行号)**: `dayu/cli/workspace_migrations/platform_import.py:337-369,708-790`。
- **输入场景**: 两个不同 `legacy_company_id` 均通过 inventory exact-set，且各自声明相同 `(exchange_mic, ticker)` security（例如两个不同 portfolio 目录的元数据都声明 canonical `AAPL`）。
- **实际分支**: `_parse_manifest_payload()` 只维护 `seen_company_ids`；bundle parser 只维护单一 company 内的 `seen_templates`，没有跨 company 的 security key 集合。staging 会为两个公司派生同一个 `SecurityId`，并返回 request。
- **预期行为**: S15-CTRL-05 要求 strict manifest 拒绝 duplicate company/security/bundle；冲突应在无数据库连接的 strict staging 中归类为 manifest/identity 输入失败。
- **实际行为**: 首次 company/security reconcile 可插入；第二个 company 的同一 `SecurityId` 在 repository `_reconcile_security()` 中才因 `company_id` 不一致触发 drift（`postgres_workspace_import.py:625-643`）。事务虽会回滚，但错误类别和失败层次已错误：无效 operator manifest 被作为数据库 drift 处理并要求连接 PostgreSQL。
- **直接证据**: `platform_import.py:339-349` 的唯一 company 去重集合与 `:423-439` 的单公司 template 去重集合之外，没有 `(exchange_mic, ticker)` 或 bundle 全局 identity 去重；现有测试只覆盖重复 legacy company id（`tests/cli/test_workspace_migrations.py:1127-1167`），未覆盖重复 security。
- **影响**: 中等。违反 strict operator-input 与 stage-before-connect 的失效分层，运维会收到误导性的 drift 类别；在 schema/DB 不可用时还可能掩盖本应确定的 manifest 错误。
- **建议改法和验证点**: 在 manifest 收窄阶段以已验证 canonical `(exchange_mic, ticker)` 建立全局 security key 集合，并以定义的 bundle identity 建立全局去重；重复直接抛对应稳定 staging 错误。新增双目录/双 company 的重复 security fixture，断言 staging 失败且 dependency/DB connect 计数为 0。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
