## Assumptions tested

1. FS metadata + S3 blob 分离是 safe 的最小 backend 边界，不会在 transaction window 内产生不可恢复的不一致。
2. single-PUT staging + CopyObject + finally cleanup 足以保证 S3 对象的原子性和 cleanup。
3. `stat_object` 的远端 metadata + exact bytes 实算 hash 验证是闭合 hash drift 的正确设计。
4. startup 选择 S3/FS 的唯一路径无旁路，且 fail-fast 顺序早于所有 workspace side effect。
5. pinned digest MinIO fixture 的 cleanup 能覆盖所有 failure mode（包括进程 hang）。
6. S3 staging objects 的 orphan recovery 由现有 FS batch recovery 覆盖或不需要额外处理。
7. `_build_store_key` 产生的相对 key 在 S3FileStore 中被正确拼接为 full S3 object key。

## Findings

### M1-未修复-[中]-FS metadata + S3 blob 双层 transaction window 产生不可恢复的 orphan S3 staging objects

- **位置**: S14-CTRL-03/04、Slice 1.4 completion、`_fs_blob_core.py:115-151`（`store_file`）、`_fs_storage_infra.py`（`begin_batch`/`recover_orphan_batches`）
- **问题类型**: 并发恢复风险 / 测试缺口
- **当前写法**: S14-CTRL-03 规定 FS 继续拥有 company/source/processed meta、manifest、batch/recovery JSON，S3 只实现 `FileStore` blob bytes。S14-CTRL-04 规定 staging key `.dayu-staging/{operation_uuid}/{sha256}` 在 `finally` 中 bounded 重试删除，integration 必须证明失败后无 staging object 且旧 final 可读。`_fs_storage_infra.py` 的 `begin_batch` 使用 `shutil.copytree` 做 FS 级备份，`recover_orphan_batches` 按 `.dayu/batch_locks/` 和 `transaction.json` journal 恢复本地 FS 状态。
- **反例/失败场景**: 进程在 S3 `put_object(staging_key)` 成功后、FS meta commit 前 crash。此时：(a) S3 上残留 staging object 无法被 `recover_orphan_batches` 发现或清理（FS recovery 只看本地 `.dayu/` journal 和 lock files）；(b) 旧 final 对象完好但新 staging object 成为永久 orphan，占用 bucket 空间并违背 "staging 不可列出" 契约的 spirit（虽不被 `list_objects` 暴露，但实际存在于 bucket 中）。若 MinIO 被替换为 production S3，长时间运行后 orphan 积累不可控。
- **为什么有问题**: 现有 `FsStorageCore` 的 batch recovery 机制 (`recover_orphan_batches`) 完全基于本地 FS journal + lock files 工作。当 blob 被 S3 实现时，crash 留下的 S3 staging objects 超出了该 recovery 机制的观测范围。S14-CTRL-04 的 `finally` cleanup 只覆盖 process-lifetime 内的清理，不覆盖 crash 后的 orphan recovery。Plan 没有为 S3 staging orphan 定义 startup-time 或 background-time cleanup 路径。
- **直接证据**: `_fs_storage_infra.py:128-145`（`ensure_batch_recovery`）只调用 `recover_orphan_batches`，后者解析本地 `.dayu/batch_locks/` 和 `transaction.json`。S14-CTRL-04 的 `finally` cleanup 无法在 crash 后执行。`_fs_storage_infra.py:149-199`（`begin_batch`）的 `shutil.copytree` 只复制本地 FS，不触及 S3。
- **影响**: long-running production deployment 中 orphan staging objects 累积，bucket 膨胀，且无自动清理路径；对 MinIO integration test 影响较小（测试后清理 bucket），但对 production S3 是真实运维风险。
- **建议改法和验证点**: (1) 在 S14-CTRL-04 增加 startup-time staging cleanup：process 启动时按 `.dayu-staging/` 前缀 list 并删除所有 orphan staging objects（bounded time/count）；(2) 或在 `recover_orphan_batches` 中增加 S3 staging prefix 的 list+delete 路径（需注入 S3 client）；(3) integration 测试须覆盖：在 S3 put 成功后 kill 进程，重启后证明 staging orphan 被清理；(4) 若选择 background cleanup 而非 startup cleanup，须在 S14-CTRL-07 中增加对应 integration 场景。
- **修复风险（中）**: 需要修改 startup 或 recovery 流程，但范围可控——只增加一次 S3 list+delete。
- **严重程度（中）**: production S3 部署下 orphan 积累是真实运维风险；MinIO 测试可暂不覆盖但 plan 应显式声明。

### M2-未修复-[中]-`stat_object` 强制下载完整对象计算 hash 违背 stat 语义

- **位置**: S14-CTRL-04
- **问题类型**: 最佳实践偏离 / 非最优方案
- **当前写法**: "`stat_object` 必须要求远端 `dayu-sha256` metadata 存在且合法，并以流式读回实算 hash 复核，任一 mismatch `OSError` fail closed。"
- **反例/失败场景**: 对于大文件（如 100 MB+ 的 SEC filing PDF），每次 `stat_object` 调用都下载完整对象计算 SHA-256。`stat` 在 S3 语义中是 HEAD request（~1 KB response），不应该是 GET（完整 object download）。在高并发场景下（如多个 Agent 同时读取不同 locator 的 citation），`stat` 的全量 download 会成为网络带宽和延迟瓶颈。现有 FS `LocalFileStore.stat_object` 只读 metadata 不读内容，S3 实现却要下载全部内容，行为不一致。
- **为什么有问题**: `stat_object` 在 `FileStore` protocol 中定位为轻量元数据查询。强制 full download 把一个 O(1) metadata 操作变成了 O(n) IO 操作（n = object size）。这不只是性能问题——在证据链 resolve/validate/read 路径中，每个 locator 的 postflight 都会触发 `stat_object`（S13-CTRL-03），对同一 document 的多 locator 场景，同一文件被反复下载。
- **直接证据**: `file_store.py:53-66`（`stat_object` protocol 定义为返回 `FileObjectMeta`，无 bytes 返回）。S14-CTRL-04："stat_object 必须要求远端 dayu-sha256 metadata 存在且合法，并以流式读回实算 hash 复核"。S13-CTRL-03 要求 validate/read "重新读取当前 owner 状态并重算 primary/locator SHA"。
- **影响**: S3 实现的 stat 操作比 FS 实现慢 100-1000x（取决于 object size）；在高频读取路径上成为性能热点。
- **建议改法和验证点**: (1) `stat_object` 只做 HEAD request，验证 `dayu-sha256` metadata 存在且格式合法（lower-64-hex），不 download 内容；(2) 原子性保证由 `put_object` 的 staging + copy + head 验证承担（S14-CTRL-04 已覆盖写入时验证）；(3) 如需 read-time hash re-verification，可在 `get_object` 返回时做（data already in memory），而不是 `stat_object`；(4) S14-CTRL-07 integration 须证明 put → stat 的 metadata 一致性（不需要 full download）。
- **修复风险（低）**: 只改 S3FileStore.stat_object 实现，不改 protocol。
- **严重程度（中）**: 性能退化在高频读取路径上可感知；若当前设计意图是 defense-in-depth（防止 S3 端数据腐蚀），应改为 `get_object` 内验证而非 `stat_object`。

### M3-未修复-[中]-startup S3 preflight 在 provider composition 之后执行，provider 失败时 S3 资源泄漏

- **位置**: S14-CTRL-05、`startup_preparation.py:503-561`（`prepare_host_runtime_dependencies`）
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: S14-CTRL-05："startup 在 `load_platform_settings(os.environ)` 后、任何 Host/Fins side effect 前解析配置与 credential presence；production enabled 构建唯一 S3FileStore 并注入 runtime，其他路径传 `None`。选择 S3 时必须在 Host/Fins 初始化前执行 bounded `head_bucket`，不存在/无权限/不可达即 fail-fast。" 同时："endpoint 连通性 preflight 允许在 provider composition 后、但必须早于 Host/Fins workspace side effects。"
- **反例/失败场景**: 当前 `prepare_host_runtime_dependencies` 的实际执行顺序是：(1) `load_platform_settings` → (2) `_default_provider_or_fail` (创建 PostgreSQL provider) → (3) `build_platform_composition` → (4) `DefaultFinsRuntime.create()` → (5) `Host(...)` → (6) `recover_host_startup_state()`。若 S3 preflight 放在 (2) 和 (3) 之间，且 PostgreSQL provider 已 auto-created 但 S3 preflight 失败，except 块会 dispose engine，但 S3 client 资源（如果有已构造的部分）不受控制。更关键的是，Plan 允许 "endpoint 连通性 preflight 允许在 provider composition 后"——这意味着 provider 的 auto-created engine 已经存活，S3 preflight 失败需要同时 dispose engine + 清理 S3 状态，而 cleanup 路径只显式覆盖了 engine dispose。
- **为什么有问题**: Plan 的 startup 顺序描述和代码实际顺序存在 gap。"任何 Host/Fins side effect 前" 的表述与代码中 provider composition 先于 Fins runtime 创建矛盾（provider 是 Side effect）。S14-CTRL-05 需要明确 S3 preflight 的 exact position in `prepare_host_runtime_dependencies`，否则 implementation agent 可能把它放在错误位置。
- **直接证据**: `startup_preparation.py:503-561` 的实际顺序：`load_platform_settings` → `_default_provider_or_fail` → `build_platform_composition` → ... → `DefaultFinsRuntime.create()`。S14-CTRL-05 说 "任何 Host/Fins side effect 前" 但 provider 是 Host 前的 side effect。
- **影响**: implementation agent 可能把 S3 preflight 放在错误位置（过早或过晚），导致：(a) 过早——S3 client 在 Fins runtime 之前创建但 Fins runtime 创建失败时 S3 资源泄漏；(b) 过晚——provider engine 已创建但 S3 不可用，cleanup 路径不清理 S3 部分。
- **建议改法和验证点**: (1) 在 S14-CTRL-05 明确 exact insertion point：`load_platform_settings` 之后、`_default_provider_or_fail` 之前；或 (2) 把 S3 preflight 紧跟在 `DefaultFinsRuntime.create()` 调用前（此时 provider 已就绪但 Fins 尚未初始化）；(3) 无论哪种位置，startup 失败的 except 块必须同时 dispose engine + 清理 S3 client（如果有）；(4) integration black-box test 必须覆盖 S3 preflight 失败时 provider engine 被 dispose 且无 S3 resource leak。
- **修复风险（中）**: 需要修改 `prepare_host_runtime_dependencies` 的异常处理路径。
- **严重程度（中）**: startup failure path 的资源泄漏在 production 重启时可能累积。

### M4-未修复-[低]-`list_objects` 协议未明确 stipulate 排序和 pagination 的 contract boundary

- **位置**: S14-CTRL-06、`file_store.py:99-112`（`list_objects` protocol）
- **问题类型**: 契约缺失
- **当前写法**: S14-CTRL-06："`list_objects(prefix)` 只接受 canonical prefix、分页穷尽、按 key 排序且排除 staging；不得依赖 S3 返回顺序。" `file_store.py:99-112`：`list_objects(self, prefix: str) -> list[FileObjectMeta]`
- **反例/失败场景**: `FileStore` protocol 的 `list_objects` 返回 `list[FileObjectMeta]`（一次性全量列表），但 S3 `list_objects_v2` 是分页 API（max 1000 keys/page）。S3FileStore 实现必须内部 pagination 并合并结果。若 implementation agent 把 S3 分页的中间结果直接暴露给 caller（如返回 iterator），会违反 protocol 的 `list[FileObjectMeta]` 返回类型。此外，protocol 未明确 "排序" 是 caller requirement 还是 implementation guarantee——`LocalFileStore` 按 `name` 排序，S3 应按 key 排序。
- **为什么有问题**: protocol 签名是 `list[FileObjectMeta]`，暗示全量结果。S3 的分页是 implementation detail，但 plan 的 "分页穷尽" 描述可能让 implementation agent 在 protocol 层暴露 pagination。需确认 `FileStore.list_objects` contract 是否要求 (a) 全量、(b) 排序、(c) exclusion。
- **直接证据**: `file_store.py:99-112` protocol 签名。S14-CTRL-06 要求 "分页穷尽、按 key 排序且排除 staging"。`LocalFileStore` 的实现在 `local_file_store.py` 中。
- **影响**: implementation agent 可能产生与 `LocalFileStore` 行为不一致的 S3 实现（如不排序或不全量），导致上层 caller（如 `list_files`）行为异常。
- **建议改法和验证点**: (1) 在 `FileStore.list_objects` 的 docstring 中明确 contract：返回全量、按 key 升序排列的 `list[FileObjectMeta]`；(2) S14-CTRL-08 unit test 须证明 S3 实现的排序和全量与 FS 实现一致。
- **修复风险（低）**: 只需在 protocol docstring 中明确 contract。
- **严重程度（低）**: 当前 protocol 签名已暗示全量返回，implementation agent 通常会遵循；但显式 contract 减少歧义。

### M5-未修复-[低]-MinIO fixture 缺少 process hang 的 force-kill cleanup 路径

- **位置**: S14-CTRL-07
- **问题类型**: 测试缺口 / 最佳实践偏离
- **当前写法**: S14-CTRL-07："HTTP health endpoint bounded 30 秒；超时保存有界、脱敏后的 container log 摘要并清理。" "删除前重新 inspect name+label；cleanup 只能删除 exact owned container/bucket，禁止 prune/glob。"
- **反例/失败场景**: MinIO 进程 hang（非 crash）时，`docker stop` 发 SIGTERM 后等 10 秒默认超时，然后 fixture 可能只做 `docker rm` 而不先 SIGKILL。若 MinIO 进程持有 bucket lock（如正在进行 multipart upload cleanup），`docker rm` 可能 hang 或 fail，导致 fixture cleanup 超时且容器泄漏。Plan 要求 "删除前重新 inspect name+label" 但未规定 inspect 失败（进程 hang 导致 Docker daemon 无响应）的 fallback。
- **为什么有问题**: 在 CI 环境中，容器泄漏会阻塞后续测试运行（端口冲突、资源耗尽）。现有 PG16 fixture（S11-CTRL-06）的 cleanup 同样面临此风险，但 MinIO 的 health check 路径（HTTP endpoint）比 PG 的 `pg_isready` 更容易 hang（HTTP 连接未关闭）。
- **直接证据**: S14-CTRL-07 要求 "bounded 30 秒" health check 和 "删除前重新 inspect"，但未规定 inspect timeout 或 force-kill 路径。
- **影响**: CI 中 MinIO 容器泄漏导致后续测试端口冲突或资源耗尽，阻塞 pipeline。
- **建议改法和验证点**: (1) 在 S14-CTRL-07 增加 cleanup 的 force-kill 路径：`docker stop -t 1` + bounded timeout 后 `docker rm -f`；(2) 或在 cleanup 中增加 `docker kill` 作为最后手段；(3) fixture 的 `finally` 块须有 bounded total timeout（如 60 秒），超时后打印 diagnostic 并 exit。
- **修复风险（低）**: 只影响测试 fixture，不改 production code。
- **严重程度（低）**: 只在 CI 环境中触发，且 MinIO hang 是低概率事件。

## Open questions

1. **S3 staging orphan startup cleanup 的 ownership**: 若决定增加 startup-time S3 staging cleanup，owner 应在 `dayu.fins.storage`（作为 `_FsStorageInfra.recover_orphan_batches` 的扩展）还是在 `dayu.services.startup_preparation`（作为 startup sequence 的一步）？前者更内聚但需要注入 S3 client 到 recovery 路径；后者更简单但把 S3 概念泄漏到 startup layer。

2. **`stat_object` hash 验证的 defense-in-depth 边界**: Plan 的 "流式读回实算 hash" 是 defense-in-depth（防止 S3 端数据腐蚀）还是 atomicity verification（确认 copy 完成）？若是前者，应在 `get_object` 返回时验证；若是后者，已在 `put_object` 的 staging → head → copy 路径中覆盖。

3. **FS metadata 的 `create_directories=True` 在 S3 模式下的语义**: `FsStorageCore.__init__` 无条件执行 `self.portfolio_root.mkdir(parents=True, exist_ok=True)` 和 `self._ensure_batch_storage_dirs()`（创建 `.dayu/` 目录结构）。当使用 S3 blob backend 时，这些本地目录仍被创建（用于 metadata/manifest）。Plan 应确认这是有意设计（FS metadata + S3 blob = 两层存储）还是遗漏。

## Residual risks

- **FS+S3 双层存储的运维复杂度**: FS metadata 仍在本地磁盘，S3 blob 在远端。部署时需要保证本地 FS 可靠性（备份、快照），且 FS 和 S3 的 backup 策略需分别维护。这是 FS metadata + S3 blob 设计的固有 tradeoff，不属于 plan defect，但应在 `dayu/fins/README.md` 的运维前置条件中显式声明。
- **`_build_store_key` 的 key 格式变更风险**: S14-CTRL-03 规定 key 逐字复用 `_build_store_key`，但该函数位于 `_fs_storage_infra.py`（FS infra layer）。若未来 Fins owner 修改 key 格式，S3 对象的 key 会同时变更，导致新旧 key 不兼容。这是所有 backend 共享的 risk（FS 同样受影响），不是 S3 特有的。

## Final plan review conclusion

**pass-with-risks**

S14-CTRL-01..08 的核心契约（boto3 依赖窗、strict JSON settings、FS metadata + S3 blob 分离、single-PUT staging + atomic copy、`DefaultFinsRuntime.create(file_store=...)` 注入、production-only startup selection、pinned MinIO integration）是 solid 的，对 implementation agent 足够确定性。五个 findings 中 M1（S3 staging orphan recovery）是真实的恢复 gap，建议在 S14-CTRL-04 增加 startup-time cleanup 路径；M2（stat_object full download）是可优化的设计选择，建议改为 HEAD-only + get 时验证；M3（startup ordering）需要 plan 明确 S3 preflight 的 exact insertion point。M4/M5 是低风险的契约明确性和测试健壮性改进。

所有 findings 均为 accepted-candidate，无 blocker。Plan 可以进入 dual re-review，但建议 Controller 在 re-review 前决定是否接受 M1 和 M3 的 fix（两者影响 plan 的 startup sequence 和 recovery flow 描述）。
