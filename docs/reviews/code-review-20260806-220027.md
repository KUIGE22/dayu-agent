## Open Questions

1. **SECRET_KEY_PATTERN 是否应匹配大写 `SK-` 前缀**：当前正则 `(?<![A-Za-z0-9_])sk-[A-Za-z0-9_-]{20,}` 仅匹配小写 `sk-`。若未来使用的 API key 或 secret 格式包含大写 `SK-` 前缀，当前模式不会匹配。当前所有测试和文档均使用小写 `sk-`，属于设计范围内的有意限制。建议在相关文档中明确说明仅匹配小写 `sk-` 前缀的 secret shape。

2. **`_validate_secret_shape_fields` 不短路的意图**：当 spec 字段检测到 secret shape 后，`validate_spec()` 仍继续执行后续所有校验（包括 `_validate_ready_inbox(_render_task_unchecked(spec))`）。`_render_task_unchecked` 会将含 secret shape 的值渲染为 Markdown 文本，然后被 `_validate_ready_inbox` 解析。虽然最终在 `validate_spec()` 返回前统一脱敏，但 secret-shaped 值在内存中短暂存在于渲染后的 Markdown 文本内。当前实现中不存在将中间渲染文本输出到外部（stdout/stderr/文件）的路径，风险极低，但若未来有人在 redaction 前添加中间输出版本，可能构成泄露路径。

## Residual Risk

1. **测试覆盖 gap — `--help` + secret-shaped 参数组合**：`RedactingArgumentParser` 仅覆盖 `error()` 方法。当用户使用 `-h/--help` 时，argparse 在解析参数前先处理 help 请求，不会触发 `error()`。help 输出全部来自 `add_argument(help=...)` 定义，不包含用户输入值，因此无泄露风险——但缺少显式回归测试确认此行为不会因 argparse 版本变化而改变。

2. **测试覆盖 gap — 非标准 secret 形状**：所有测试均使用 `"sk-" + ("A" * 20)` 作为 secret 值。对于 `sk-` 后恰好 20 字符的边界（最小匹配长度）、包含大量连续 `-` 或 `_` 的极端值、Unicode 全角字符混入等边缘情况，直接验证了正则行为正确，但缺少端到端 CLI 测试覆盖这些边缘 secret 形状。

3. **未覆盖的 CLI 参数位置**：`--root` 参数接受 `Path` 类型，若用户传入包含 secret shape 的目录路径（如 `/tmp/sk-AAAA...`），错误路径中的 `--root` 值仅在 task generator 的 "wrote" 通知中被脱敏。其他三个 CLI（handoff validator、Codex review、aggregate pipeline）的 `--root` 出现在错误消息中的路径（如 "missing required file"）没有被显式测试覆盖。这些路径来自 `validate_handoff_docs()` 内部的文件路径拼接，不直接回显 `--root` 的原始值，但缺少回归测试。

4. **架构耦合**：`RedactingArgumentParser` 定义在 `utils/validate_handoff_docs.py` 中，但它是一个通用 CLI 基础设施组件，与 handoff 文档校验业务无关。所有四个 CLI 模块本就依赖 `validate_handoff_docs`（因为共享 `SECRET_KEY_PATTERN`、`redact_secret_shapes` 等），当前不引入新依赖，但若未来需要将 redacting parser 复用于非 handoff 场景，需要考虑将其抽取到独立的 CLI 基础设施模块。
