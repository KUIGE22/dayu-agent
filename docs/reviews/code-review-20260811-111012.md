## Findings

### 1-中-import 主开关的重复出现被静默折叠，未按 fail-closed 合同拒绝

- **入口/函数**：`dayu-cli init --import-existing-workspace --import-existing-workspace ...` → `parse_arguments()` → `run_init_command()`。
- **文件(行号)**：[dayu/cli/arg_parsing.py](/Users/wsk/workspace/dayu-agent/dayu/cli/arg_parsing.py:1519)、[dayu/cli/commands/init.py](/Users/wsk/workspace/dayu-agent/dayu/cli/commands/init.py:1788)、[dayu/cli/commands/init.py](/Users/wsk/workspace/dayu-agent/dayu/cli/commands/init.py:1860)。
- **触发输入与实际分支**：主开关使用 `action="store_true"`，argparse 对其重复出现只保留 `import_existing_workspace=True`，没有 `*_seen` 或 `*_repeated` 状态。`run_init_command()` 因而直接进入 `_run_import_existing_workspace()`；后者只检查 manifest/tenant 的重复标志，不检查主开关重复。
- **预期行为**：S15-CTRL-04 明确要求 import 语义参数的 unknown/missing/repeated 全部 fail closed；本轮 implementation/fix artifact 还把“重复主开关”列为已在任何副作用前拒绝的 A 闭合项。因此该命令必须输出 `workspace_import_usage` 并返回 1，不能进入 staging、建 DB 依赖或发布。
- **实际行为**：只要 manifest 与 tenant 合法，该重复开关命令会继续执行 read-only staging，随后装配数据库依赖并可能完成一次 import；它不是预期的 usage rejection。现有测试仅覆盖 `--import-manifest`、`--target-tenant-id` 的重复（[tests/cli/test_workspace_migrations.py](/Users/wsk/workspace/dayu-agent/tests/cli/test_workspace_migrations.py:1671)），没有覆盖主开关重复。
- **直接证据**：`_ImportSemanticStore` 仅被注册给两个带值参数；主开关仍为默认 `store_true`。两个调用分支也均不读取主开关出现次数。这是同一条 CLI 解析→分支→副作用路径上的直接行为，不依赖推测。
- **影响**：显式 import mode 的 fail-closed 命令契约未闭合；操作员提供被合同判为非法的重复语义输入时，仍可触发 PostgreSQL 写入。它不重现 Terra 1 的普通-init source-tree 改写路径，但阻断本轮 A 的最终验收。
- **修复方向与验证点**：为主开关采用同类的计数 action（或统一的 typed import-semantic action），在解析期保留出现次数，并在 `_run_import_existing_workspace()` 的任何 `Path.resolve()`、staging 或依赖装配前要求次数精确为 1。补充端到端 parser + `run_init_command()` 测试：重复主开关、其余两项合法时返回 1，`stage_workspace_import` 与 `prepare_workspace_import_dependencies` 调用次数均为 0；同时保留普通 init 的零副作用 gate。
- **修复风险（低/中/高）**：低。
- **严重程度（低/中/高/严重）**：中。
