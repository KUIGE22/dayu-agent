### 2.3 为何保留这两个 re-import —— 调用者分析

这两个 re-import 仅服务以下**非生产**用途：

**(a) 旧测试直接导入** — `tests/engine/test_cli_running_config.py:24-29`

    _needs_auto_research_bootstrap,
    _validate_live_smoke_plan_args,       # ← 从这里导入

    run_write_command,

该测试文件在 line 2436/2444 直接调用 `_validate_live_smoke_plan_args`。

**(b) Identity binding 断言** — `tests/application/test_write_cli_dispatch.py:608-615`
```python
assert (
    write_command_module._validate_challenger_run_plan_args
    is write_params_validation._validate_challenger_run_plan_args

assert (
    write_command_module._validate_live_smoke_plan_args
    is write_params_validation._validate_live_smoke_plan_args
)
```

### 2.4 违反项目约束判定

> CLAUDE.md 编码硬约束: "禁止兼容性代码：兼容性 re-export：仅为保持旧导入路径而转发符号。"

`_validate_challenger_run_plan_args` 和 `_validate_live_smoke_plan_args` 在 `write.py` 中的 re-import **仅**为保持旧测试导入路径（`test_cli_running_config.py` 从 `write.py` 导入）而存在，不加任何有效语义。这**精确命中**"兼容性 re-export"定义。

> CLAUDE.md 测试约束: "测试必须跟着实现边界迁移，不得为了保住旧测试而在生产代码里堆兼容逻辑。"

当前现状也违反此条：为了保住 `test_cli_running_config.py` 的旧导入路径，在 `write.py` 中保留了兼容 re-import。

## 4. 替代方案评估与驳回

### 4.1 `__all__` 显式导出列表

**主张**: 在 `write.py` 添加 `__all__` 显式列出公开符号，lint 工具可能对 `__all__` 中的符号放宽 F401 检查。

**驳回**:
- `__all__` 控制 `from module import *` 行为，不能抑制 F401（ruff/flake8 均不以此豁免未使用导入）
- 即使某工具豁免，根本问题仍在：re-export 本身违反项目禁止兼容代码的硬约束
- `__all__` 增加维护负担却未解决实际问题

### 4.2 `# noqa: F401` 行级抑制

**主张**: 去掉 alias，改为普通 import + `# noqa: F401`。

**驳回**:
- CLAUDE.md 思考纪律 3: "不走捷径，不做表面修复" —— lint 抑制是典型的表面修复
- 保留 dead import 违反模块间依赖最小化原则
- 违反 "禁止兼容性 re-export" 硬约束的本质未变

### 4.3 构造 dummy 调用来"使用"导入

**主张**: 在 `write.py` 中某处写 `_ = _validate_challenger_run_plan_args` 以抑制 F401。

**驳回**:
- 制造 dead code 比 dead import 更恶劣 —— 增加混淆而无任何语义价值
- 违反 "不做表面修复" 纪律
- 未来维护者需额外认知负担来理解为何存在无用赋值

### 4.4 保留现状（ref retention）

**主张**: 接受 PLC0414 作为已知 lint，不修改。

**驳回**:
- 违反 CLAUDE.md "禁止新增、扩散、掩盖或绕过类型错误" —— PLC0414 是 Slice5 实施直接引入的
- 违反 "禁止兼容性代码" —— 这两个 import 存在的唯一理由就是保持旧测试路径
- 违反 "测试必须跟着实现边界迁移" —— 测试应当从真正的 owner 模块导入
- 延迟修复会让问题固化，后续修改者可能依赖此 re-export 路径而进一步扩散
