## 指定攻击向量分析

### 攻击向量 1: claim 与 reserve 是两个公开事务——同一 PG transaction 是否可实施，crash-between 如何收敛

**分析**:

`JobService.claim` 和 `JobService.reserve_agent_run_correlation` 是两个独立的公开方法，各自接收 `TenantScope`。Plan §4.3 声称："claim A → 同一 PG transaction reserve/读取 immutable identity → commit"。但这在当前架构下不可实施：

- `claim` 内部执行 `SELECT ... FOR UPDATE SKIP LOCKED` + 创建 attempt/lease/event + UPDATE job state = leased，在一个 PG transaction 内 commit。
- `reserve_agent_run_correlation` 是另一个公开方法，有自己的 PG transaction。
- 两者之间没有共享事务上下文的机制。`JobService` 不暴露事务句柄；caller 无法将两个调用绑定到同一个 PG transaction。

**这意味着 crash window 真实存在**：worker 调用 `claim` 成功（attempt committed, job = leased）→ crash → 未调用 `reserve` → 无 correlation row。

**Plan 对此的覆盖**:

Plan §4.3 说："fresh schema 的 Agent attempt 在任何 Host 调用前必须已有 correlation；发现缺失代表数据库 invariant 破坏，记 safe event、终止该 attempt，并禁止创建 Host run。"

`reconcile_agent_run_correlation` 对 `correlation_missing` 返回 `INVARIANT_FAILURE`。

**问题**: Plan 将 crash-between claim-reserve 导致的 `correlation_missing` 称为"数据库 invariant 破坏"，但实际上这是预期的 crash recovery 场景——不是 invariant violation，而是 incomplete operation。术语不准确可能导致 implementation agent 过度反应（如触发 alert 或 skip retry）。

**收敛路径**:
1. Worker crashes after claim, before reserve → attempt = leased, no correlation
2. Lease expires → `recover` marks attempt abandoned, job may retry
3. Or: future recovery enumerates committed attempts without correlation → detects gap → calls reconcile → `INVARIANT_FAILURE` → fail attempt → retry if budget

**闭合判定**: 路径闭合（lease expiry → recover 使 job 回到 ready），但 plan 术语需要修正，且缺少专门的 crash-between-claim-and-reserve 测试。§7 slice D 的测试 `test_crash_after_correlation_before_future_host_call_reuses_same_reserved_id` 覆盖的是 crash after reserve，不是 before reserve。

### 攻击向量 2: Worker crash → raw lease token 丢失 → Host terminal reconciliation

**分析**:

**complete/fail/heartbeat 的 token 保护**: 这三个操作都要求 `JobLeaseHandle`（包含 raw token）。Store 内部用 `lease_token_sha256` + `fence` + `lease_expires_at` 做 predicate UPDATE。Worker crash 后丢失 raw token → 无法调用这些操作。这是正确的设计。

**recover 的 lease-expiry 保护**: `recover` 锁定 `lease_expires_at < now` 的 attempt → 标记 abandoned → job 走 retry 或 terminal。不依赖 raw token。正确。

**reconcile 的 BACKFILL_SUCCESS gap**: Plan §4.3 说 `reconcile` 在 Host `SUCCEEDED` 时"原子补 PG receipt"后返回 `BACKFILL_SUCCESS`。这里存在两个问题：

1. **reconcile 是否真的写 receipt？** Plan 说 reconcile 是 "observation/decision-only"，但又说 "原子补 PG receipt"。如果 reconcile 真的写 receipt，它需要：
   - 锁定 job/attempt row
   - 检查 attempt 仍然是 `leased` 状态
   - 检查 fence 未被递增（即无新 attempt）
   - 检查 lease 是否过期（如果过期，recover 可能已经 abandoned）
   - 写入 receipt + event + 转 attempt/job 为 succeeded

   但 reconcile 的签名是 `reconcile_agent_run_correlation(scope, correlation_id)`，不接收 lease handle 或 fence。它无法做 token-based fencing。

2. **reconcile 与 recover 的 race**: 如果 Host 成功但 worker crash，lease 过期后 `recover` 会 abandon attempt。此时 `reconcile` 观察到 Host SUCCEEDED，但 attempt 已经 abandoned。reconcile 应该：
   - 检查 attempt 状态 → 如果已 abandoned → 不写 receipt → 返回 `RETRY_OR_FAIL`（因为 attempt 已被回收，新 attempt 需要重新执行）
   - 但 plan 没有指定这个分支。

**关键发现**: Plan 对 `BACKFILL_SUCCESS` 的防护机制未明确。如果 reconcile 可以在无 token、无 fence 检查的情况下写 receipt，则存在以下 race：

| 时间 | recover | reconcile |
|------|---------|-----------|
| T1 | | 观察 Host = SUCCEEDED |
| T2 | lease expired → abandon attempt | |
| T3 | | 写 receipt + attempt succeeded ← **覆盖 abandoned** |

这是 data corruption：attempt 从 abandoned 回到 succeeded，但 lease 已释放、fence 可能已被新 attempt 使用。

**建议**: 如果 `BACKFILL_SUCCESS` 要求 reconcile 写 receipt，必须明确：
- reconcile 在写 receipt 前检查 attempt 状态 = leased（否则返回 `RETRY_OR_FAIL`）
- reconcile 检查 `lease_expires_at > now`（否则返回 `RETRY_OR_FAIL`，让 recover 处理）
- 或者：`BACKFILL_SUCCESS` 只是 decision，不写 receipt；caller 自行用 lease handle 调 `complete`

## Findings

### 001-未修复-高-BACKFILL_SUCCESS 缺少 fencing 机制，reconcile 与 recover 存在 race

- **位置**: §4.3 Agent correlation query-before-retry；§4.2 recover；§4.2 complete
- **问题类型**: 并发恢复风险 / 状态机漏洞
- **当前写法**: "SUCCEEDED 原子补 PG receipt 后返回 BACKFILL_SUCCESS"；reconcile 签名为 `(scope, correlation_id)`，无 lease handle/fence 参数
- **反例/失败场景**: Worker 执行 Host Agent 成功（Host = SUCCEEDED），但 crash 丢失 raw lease token。Lease 过期 → `recover` abandon attempt → reconcile 观察 Host SUCCEEDED → 写 receipt + attempt succeeded。attempt 从 abandoned 回到 succeeded，但 fence/token 已被新 attempt 使用。如果新 attempt 已 claim 并正在执行，旧 attempt 的 succeeded receipt 会覆盖新 attempt 的状态。
- **为什么有问题**: `complete` 和 `fail` 都要求 raw lease token + fence predicate，但 `reconcile` 的 `BACKFILL_SUCCESS` 路径绕过了这些保护。这是 token-based fencing 的缺口。
- **直接证据**: Plan §4.3 "SUCCEEDED 原子补 PG receipt 后返回 BACKFILL_SUCCESS"；§4.2 complete "相同 fence predicate 锁定 job/attempt"；reconcile 签名无 lease handle
- **影响**: 数据损坏——attempt 状态从 abandoned 回到 succeeded；新 attempt 的 fence 被旧 attempt 的 receipt 覆盖
- **建议改法和验证点**:
  1. 明确 `BACKFILL_SUCCESS` 的写入必须检查：attempt state = leased AND `lease_expires_at > now` AND fence 未变。任一条件不满足 → 返回 `RETRY_OR_FAIL`。
  2. 或者：`BACKFILL_SUCCESS` 只是 decision signal，不写 receipt；caller 自行用 lease handle 调 `complete`（需要 caller 在 crash 前持久化 lease token）。
  3. 添加测试：`test_reconcile_backfill_after_recover_abandoned_does_not_overwrite`
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 002-未修复-中-claim 与 reserve 的 crash window 缺少专门测试

- **位置**: §4.3；§7 slice D tests
- **问题类型**: 测试缺口 / 并发恢复风险
- **当前写法**: §7 slice D 测试覆盖 "crash after correlation before future host call" 和 "crash after host reserved insert before model"，但不覆盖 "crash after claim before reserve"
- **反例/失败场景**: Worker 调 `claim` 成功（attempt committed, job = leased）→ crash → 未调 `reserve` → 无 correlation row。`recover` 最终 abandon attempt 并可能 retry，但 §7 没有测试验证这条路径。
- **为什么有问题**: claim 和 reserve 是两个独立公开方法（不可绑定到同一 PG transaction），crash window 真实存在。没有测试 = implementation agent 可能不处理此场景。
- **直接证据**: `JobService.claim` 和 `JobService.reserve_agent_run_correlation` 是两个独立签名；§7 slice D 无 "crash between claim and reserve" 测试名
- **影响**: Implementation agent 可能假设 correlation always exists after claim，导致 reconcile 逻辑不完整
- **建议改法和验证点**:
  1. 添加测试：`test_crash_after_claim_before_reserve_correlation_missing_recovers`
  2. 验证：attempt committed + no correlation → lease expires → recover abandon → job ready for retry → new attempt gets new correlation
  3. 验证：reconcile 对 correlation_missing 返回 INVARIANT_FAILURE 但不阻止 job retry
- **修复风险（低）**: 只需添加测试
- **严重程度（低/中/高/严重）**: 中

### 003-未修复-中-correlation_missing 称为"invariant 破坏"术语不准确

- **位置**: §4.3 "发现缺失代表数据库 invariant 破坏"
- **问题类型**: 契约缺失
- **当前写法**: "fresh schema 的 Agent attempt 在任何 Host 调用前必须已有 correlation；发现缺失代表数据库 invariant 破坏"
- **反例/失败场景**: claim 成功后 crash（未 reserve）→ 无 correlation → 这是预期的 crash recovery 场景，不是 invariant violation。如果 implementation agent 将 INVARIANT_FAILURE 视为不可恢复的错误（如触发 alert、skip retry），job 会永远卡在 leased 状态直到 lease expiry → recover。
- **为什么有问题**: 术语不准确导致 implementation agent 可能对 correlation_missing 过度反应。正确的分类是：(a) 从未 reserve 的 attempt → 预期 crash recovery → recover 处理；(b) 已 reserve 但 correlation row 被外部删除 → 真正的 invariant violation。
- **直接证据**: Plan §4.3 的 invariant 语句；§4.1 "correlation_missing 不是重建分支"
- **影响**: Implementation agent 可能将预期的 crash recovery 场景误判为 invariant violation
- **建议改法和验证点**: 将 "invariant 破坏" 改为 "correlation 未创建（可能由 claim 后 crash 导致）"；保留 INVARIANT_FAILURE 返回值但文档说明其包含两种场景；在 recover 中明确：过期 attempt 无 correlation → abandon → retry
- **修复风险（低）**: 纯文档修正
- **严重程度（低/中/高/严重）**: 中

### 004-未修复-中-fault matrix 条目与 named tests 未完全映射

- **位置**: §7 implementation slices + §8 fault matrix
- **问题类型**: 测试缺口
- **当前写法**: §8 列出 20+ fault 场景（lost token、wrong fence、dead owner、Host row missing after observation、RLS setting leak、immutable app-role mutation 等），但 §7 named tests 没有覆盖所有场景
- **反例/失败场景**: Implementation agent 只实现 named tests，遗漏 fault matrix 中未映射的场景（如 "Host row missing after observation"、"RLS setting leak"）
- **为什么有问题**: §8 fault matrix 是 completion gate 的一部分，但没有明确哪些场景已有 named test、哪些需要额外 integration test。Implementation agent 可能只做 named tests 就认为完成。
- **直接证据**: §8 fault matrix 条目 vs §7 named test 列表
- **影响**: 测试覆盖不完整，某些 fault 场景可能未被验证
- **建议改法和验证点**: 在 §8 中为每个 fault matrix 条目标注对应的 named test 或 integration test；无对应 test 的条目标注为 "integration test only"
- **修复风险（低）**: 纯 plan 补充
- **严重程度（低/中/高/严重）**: 中

## Final Plan Review Conclusion

**PASS-WITH-RISKS**

Plan 在 PG schema、状态机、cross-store consistency（PG-first ordering）、idempotency、lease fencing、grants/RLS、DTO 严格性、composition lifecycle 和 A–L closure 上均达到 code-generation-ready 标准。fix artifact 的 11 个 accepted + 3 个 rejected-with-reason 全部闭合。

**2 个 Material Risks**:

1. **高 — BACKFILL_SUCCESS 缺少 fencing**（Finding 001）: reconcile 可以在无 token、无 fence 检查的情况下写 receipt，与 recover 存在 race。必须在实施前明确 fencing 机制或改为 decision-only。

2. **中 — claim-reserve crash window 无测试**（Finding 002）: 两个独立公开方法之间的 crash window 真实存在，但无 named test 覆盖。

**2 个 Clarification Risks**:

3. **中 — correlation_missing 术语不准确**（Finding 003）: 将预期 crash recovery 称为 "invariant 破坏" 可能导致 implementation agent 过度反应。

4. **中 — fault matrix 与 named tests 未完全映射**（Finding 004）: Implementation agent 可能遗漏未映射的 fault 场景。

**结论**: Finding 001 是唯一的 blocker——BACKFILL_SUCCESS 的 race condition 是数据损坏风险。建议在实施前将 reconcile 的 BACKFILL_SUCCESS 路径明确为以下两者之一：
- (a) 写 receipt 前检查 attempt state = leased + `lease_expires_at > now` + fence 未变，否则返回 `RETRY_OR_FAIL`
- (b) BACKFILL_SUCCESS 只是 decision signal，caller 自行用 lease handle 调 `complete`

其余 finding 可在实施阶段通过补充测试和文档修正解决。
