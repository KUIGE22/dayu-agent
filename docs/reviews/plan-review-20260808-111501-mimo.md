## 3. 挑战项深度分析

### 3.1 Callable 逆变

`Callable[[DayuCliArguments], int]` 的参数是逆变的：只有当 `DayuCliArguments` 是目标的**超类型**时才可赋值。当前 dispatch mapping（`write.py`）声明 `Callable[[DayuCliArguments], int]`，如果 runner 签名改为 `Callable[[Namespace], int]`，则 `Namespace` 作为超类型**可以**赋给逆变参数。但反之不行 — `DayuCliArguments` 不能赋给 `Callable[[Namespace], int]` 的参数位置。

**方案 B 影响**: snapshot 链的回调类型为 `Callable[[], Mapping[...]]`（零参数），不涉及 `args` 逆变。方案 B 无逆变风险。

### 3.2 Helper 实际字段访问

`_build_fresh_application_routing_snapshot` 对 `args` 的唯一使用:

```python
write_cli_config = setup_write_config(args, paths_config, running_config)
```

`setup_write_config` 内部使用 `getattr` 访问通用 argparse 字段（`output`、`template`、`research_template`、`write_max_retries` 等），**零处**访问 `research_template_action`。

**结论**: snapshot 链对 `DayuCliArguments` 的类型依赖是虚幻的 — 它实际只需要 `argparse.Namespace`。

### 3.3 Callback 签名

`build_snapshot_builder` 返回 `Callable[[], Mapping[str, ModelConfigJsonValue]]`。这是一个零参数回调，`args` 已通过 `functools.partial` 捕获。回调签名本身不暴露 `args` 类型，下游消费者（`apply_write_model_configuration_preapplication_plan` 等）只关心回调的返回类型。

**方案 B 影响**: 回调内部捕获 `Namespace` 而非 `DayuCliArguments`，但回调签名不变，下游零冲击。

### 3.4 Future Slice 11 Contexts

Slice 11 向 `DayuCliArguments` 追加 20 个 write 字段（`WriteDispatchArguments(Protocol)` 的字段）。snapshot 链的 3 个函数**不使用**这些字段。

- **方案 A/C**: snapshot 链持有 `DayuCliArguments`，Slice 11 追加字段后 snapshot 链「名义上」可以看到这些字段，但实际不使用 — 类型签名虚增。
- **方案 B**: snapshot 链保持 `Namespace`，Slice 11 追加字段对 snapshot 链零冲击 — 类型签名精确。

**结论**: 方案 B 在 Slice 11 演进中更稳定。

### 3.5 Test Fixtures

当前测试中构造 `DayuCliArguments()` 作为 args fixture。方案 B 允许 snapshot 相关测试使用更简单的 `argparse.Namespace()` fixture，减少不必要的类型构造。

### 3.6 Coverage

方案 B 修改 3 个函数签名（`_build_fresh_application_routing_snapshot`、`_build_snapshot_for_args`、`build_snapshot_builder`），均为签名级变更，不改变运行时行为，不影响覆盖率。

### 3.7 终态一致性/分层

| 层级 | 方案 B 终态 |
|------|------------|
| CLI 入口 (`write.py`) | `DayuCliArguments` ✓ |
| Config application CLI runner | `DayuCliArguments` ✓ |
| Snapshot builder 基础设施 | `argparse.Namespace` ✓（与 `setup_write_config` 对齐） |
| Rollback/Recovery CLI runners | `argparse.Namespace` ✓（不接触 write dispatch 字段） |
| Service layer | 不关心 CLI 类型 |

分层清晰：**CLI dispatch 层**使用 `DayuCliArguments` 提供运行时身份；**CLI 内部基础设施**使用 `argparse.Namespace` 保持最小契约。

## 6. 结论

**方案 B 是最优解**。理由:

1. **类型签名精确对齐实际语义**: snapshot 链不使用 `DayuCliArguments` 专有字段，接受 `Namespace` 是正确契约。
2. **与终态消费者一致**: `setup_write_config` 已接受 `Namespace`，snapshot 链与其对齐消除虚幻的类型收紧。
3. **最小修改面**: 3 个签名变更 vs 方案 A 的 4 个或方案 C 的 15 个。
4. **Slice 11 演进最稳定**: snapshot 链保持宽类型，write 字段追加对它零冲击。
5. **分层清晰**: CLI dispatch 层用 `DayuCliArguments`；CLI 内部基础设施用 `argparse.Namespace`。

**需 v5.3 plan erratum**: 45 → 42，snapshot_builder 的 2 个 slot 移出 Dayu 传播目标。
