- **独立复证**：110 个 root/SEC owner focused tests 与 reviewer controlled-stream 红队均通过；generic
  body 后两次 cleanup cancel 保留第一份 cleanup cancel，body 首 cancel 后第二/第三 cancel 保留 body 原对象，
  close 恰好一次、completed、result reaped 且无同名 pending orphan。真实 FS batching rollback 后
  active/staging/publish 为空且同 ticker 可重入；commit response-loss 仍零补偿 rollback。
- 下列内容保留为本 finding 在旧 frozen SHA 上的历史触发证据，不代表最新代码仍走该分支。

- **入口/函数**：`DefaultFinsWorkerSourceSyncRuntime.sync_worker_source`
- **文件(行号)**：`dayu/fins/source_sync_runtime.py:711-745`
- **输入场景**：
  1. stream body 已产生 generic provider `RuntimeError`，root 正等待一个尚未完成的
     `inner.aclose()`，调用方此时真实调用 `task.cancel()`；
  2. 第一次 `task.cancel()` 已使 body 产生 primary `asyncio.CancelledError`，root 进入同一个
     blocking `inner.aclose()` 后，调用方再次 `task.cancel()`。
- **实际分支**：root 在 722-723 行保存 body primary，随后直接在当前 task 内
  `await inner.aclose()`。close await 收到 `asyncio.CancelledError` 后，如果已有 primary，729-735 行只
  把 close cancellation 写成 note；generic primary 最终在 742-743 行映射 `UNAVAILABLE`。若已有第一份
  asyncio primary，第二次取消同样中断 close；736-737 行虽重抛第一份 cancellation，但不会继续驱动或
  reap 已中断的 close。
- **预期行为**：accepted plan §4.3 的全局优先级是 asyncio cancellation > domain cancellation >
  proven invariant > generic exception；它也不能只以 `aclose_calls == 1` 证明 owner 收敛。任何在 body
  或 cleanup wait 期间观察到的真实 task cancellation 都必须按该优先级传播；direct inner close 必须在
  repeated cancellation 下实际结束，且不能遗留后台 cleanup task。
- **实际行为**：独立可控 `AsyncGenerator` 复现得到：

  ```text
  generic_then_real_cleanup_cancel returned unavailable
  A close_calls 1 cancelled True completed False
  repeated_cancel raised CancelledError CancelledError('first cancel')
  B close_calls 1 cancelled True completed False
  B after release completed False
  ```

  分支 A 吞掉了真实 task cancellation；分支 B 保留第一份 cancellation identity，却在传播前让 direct
  inner cleanup 永久停在未完成态。释放原 gate 后 `completed` 仍为 false，证明不是延迟收敛。
- **直接证据**：当前组合测试只覆盖 body primary + 立即抛出的 close exception，以及 clean body +
  立即抛出的 close `CancelledError`；`tests/fins/test_fins_source_sync_runtime.py:1128-1201` 没有在 close
  await 正在进行时发出真实 cancellation，也没有第二次 cancel 或 `close_completed` 断言。仓库既有
  `dayu/host/worker.py:1737-1758::_await_cleanup_task` 已说明所需机制：独立 cleanup task + shield 循环 +
  真实 reap；Fins 层不能反向 import Host，但可在自己的 owner 内实现同一局部所有权模式。
- **影响**：调用方会把已取消的同步误判为 retryable provider outage；重复取消还能让 nested stream 的
  direct cleanup 半途退出。下层 token owner 对单次 `GeneratorExit`/cancel 的 rollback 已修复，但上层
  “调用过一次 close”仍不等于最深 inner 已关闭，可能遗留 provider/stream 资源并破坏 exactly-once
  owner contract。
- **建议改法和验证点**：在 Fins root 内创建唯一 owned close task，使用 `asyncio.shield` 循环抵抗当前
  owner 的重复取消，并在返回/raise 前等待该 task terminal 且读取其结果；禁止只
  `await shield(inner.aclose())` 一次后遗留 orphan。记录 cleanup wait 期间收到的第一份真实
  `asyncio.CancelledError`，将“body 与 cleanup 阶段观察到的异常”按全局优先级统一仲裁；已有 body
  asyncio cancel 时保留原对象。至少新增：generic body + real cancel during close、first body cancel +
  second cancel during close、clean + intrinsic close cancellation、domain/invariant + generic close 四组
  测试；每组断言 `aclose_calls == 1`、`close_completed is True`（或 cleanup task terminal/reaped）、无
  pending task，且最终分别为 asyncio re-raise / 原 cancellation / 既定优先级结果。
- **修复风险（中）**：必须区分外层 repeated cancellation 与 close task 自身异常；shield 必须配合
  显式 task owner 和循环 reap，不能产生 detached cleanup。`KeyboardInterrupt`/`SystemExit` 仍需原样传播。
- **严重程度（中）**：Medium

  `_consume_event` 在 ordinary started 入站时拒绝已存在的同 form candidate；started 在 ordinary terminal 后

- 下列内容保留为本 finding 在旧 frozen SHA 上的历史触发证据，不代表最新代码仍走该分支。

- **入口/函数**：`DefaultFinsWorkerSourceSyncRuntime._consume_event` / `_correlate_terminal`
- **文件(行号)**：`dayu/fins/source_sync_runtime.py:510-527,839-846`
- **输入场景**：CN/HK 同一 request form（复现为 CN `FY`）同时出现合法 synthetic
  `candidate_not_found` 和一组合法 ordinary `FILING_STARTED` + ordinary terminal；分别交换两组事实的事件
  顺序，并构造与 terminal 顺序、summary 精确一致的 `PIPELINE_COMPLETED(status=ok)`。
- **实际分支**：candidate 分支只以 `state.candidate_forms` 防同类重复，ordinary started 分支只以
  document id 防重复；两边都没有检查另一种同-form 事实。因而 candidate 先到时，后续 ordinary started
  仍写入 `state.started`；ordinary 先到时，后续 candidate 仍写入 `state.candidate_forms`。
- **预期行为**：accepted plan §4.3（1187-1194 行）规定普通 terminal 与 started 一一对应，并把
  `candidate_not_found` 定义为 CN/HK 唯一无-started synthetic terminal、每 request form 最多一个。
  “该 form 无 candidate”与“该 form 已有 ordinary candidate”是互斥事实；任一顺序都必须映射
  `INVARIANT_FAILED`，不能由事件顺序决定是否接纳。
- **实际行为**：两条独立 public runtime 复现都接受矛盾 wire，而不是 invariant：

  ```text
  candidate_then_ordinary unavailable discovered 2 downloaded 0 reused 0 ignored 1 failed 1 documents 0 aclose 1
  ordinary_then_candidate unavailable discovered 2 downloaded 0 reused 0 ignored 1 failed 1 documents 0 aclose 1
  ```

  这里 ordinary terminal 为合法 `failed`，所以矛盾事实进一步污染 discovered/ignored/failed，并把结果映射
  为 `UNAVAILABLE`；换成成功 ordinary terminal 同样会接纳矛盾，只是 outcome/counts 不同。
- **直接证据**：`_correlate_terminal` 的 candidate guard（510-526 行）不查看 `state.started`；
  `_consume_event` 的 started guard（839-845 行）不查看 `state.candidate_forms`。当前
  `test_cn_candidate_not_found_remains_the_only_terminal_identity_exception` 只覆盖 candidate 单独存在，现有
  identity 参数化测试也只覆盖 ordinary terminal 自身字段 missing/mismatch，没有任一交叉顺序。
- **影响**：runtime 是 DownloadEvent 的 fail-closed correlation owner；接纳自相矛盾的 provider wire 会产生
  不可信 counts/outcome，并可能把 provider 协议漂移误报为可重试 outage 或成功，破坏上层对同步结果的
  retry/health 判断。该缺陷同时位于 CN/HK 共用的 non-US 分支。
- **建议改法和验证点**：最小双向互斥为：(1) 接受 candidate 前，若 `state.started.values()` 已有同
  `form_type` 即 invariant（started 会保留到 terminal 后，覆盖 ordinary 先到的两种阶段）；(2) 接受
  ordinary `FILING_STARTED` 前，若其 form 已在 `state.candidate_forms` 即 invariant。至少对 CN/HK 参数化
  锁定 candidate→started/terminal、started→candidate、terminal→candidate 三种同-form 顺序均
  `INVARIANT_FAILED`，并保留不同 request form 可各自合法、candidate 每 form 仍最多一个；同时断言 final
  result mirror 不能洗掉先前矛盾。
- **修复风险（低）**：状态已有两侧所需事实，无需扩大 wire 或 public DTO；注意不能按 document id 比较
  synthetic candidate，因为它按合同没有 document id。
- **严重程度（中）**：Medium
