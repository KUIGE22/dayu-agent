## 2. Findings

### H-001-已修复：source-sync 提前关闭或任务取消会绕过 SEC/CN per-filing batch rollback，留下活跃事务和 ticker 锁

- **严重性**：High
- **入口 / 函数**：
  `DefaultFinsWorkerSourceSyncRuntime.sync_worker_source` -> market stream ->
  `run_download_stream_impl` / `run_cn_download_single_filing_stream`
- **文件（行号）**：
  `dayu/fins/source_sync_runtime.py:446-466`；
  `dayu/fins/pipelines/sec_download_workflow.py:503-562`；
  `dayu/fins/pipelines/cn_download_filing_workflow.py:599-707`
- **输入场景**：启用真实 `FsBatchingRepository`，单 filing 已 `begin_batch` 且至少发出一个
  `FILE_DOWNLOADED`，随后 source-sync 因外部取消、event/document cap、协议不变量或调用方主动
  `aclose()` 提前关闭整个嵌套流；任务级 `asyncio.CancelledError` 也可触发同一窗口。
- **实际分支**：source-sync 在 `finally` 中直接 `await inner.aclose()`。SEC owner 在 batch 开启后
  于 `yield event` 暂停，外层 `aclose()` 注入 `GeneratorExit`；CN owner同样在 663-674 行的
  `FILE_DOWNLOADED` yield 暂停。两处事务 owner 都只写了 `except Exception` rollback，因
  `GeneratorExit` 与 `asyncio.CancelledError` 属于 `BaseException`，会绕过 rollback；正常循环后的
  commit/rollback 也不会执行。
- **直接证据**：使用现有 `tests/fins/test_per_filing_terminal_state.py` 的 real FS core、
  `_RecordingBatching` 与现有 SEC/CN harness，在首个 `FILE_DOWNLOADED` 后调用 outer `aclose()`：

  ```text
  SEC seen=['pipeline_started','company_resolved','filing_started','file_downloaded']
  begin=['AAPL'] commit=[] rollback=[] active_batch_keys=['AAPL']

  CN seen=['file_downloaded']
  begin=['600519'] commit=[] rollback=[] active_batch_keys=['600519'] published=[]
  ```

  现有 `test_sec_cancelled_error_rolls_back_same_token` 只让 inner 在首个 yield 前抛 domain
  `CancelledError`；18 层 close 测试只断言 inner `aclose` 次数。两者都没有在 batch 已开启且 owner
  正暂停于 yield 时检查 rollback/active batch。
- **预期行为**：直接拥有 batch token 的层必须在 commit point-of-no-return 前，对正常失败、
  domain/asyncio cancel、`GeneratorExit`/outer `aclose` 全部 rollback 同一 token 恰好一次；关闭最深
  inner 后不得残留 active batch、staging 或 publish。
- **影响**：`FsBatchingRepository` 的 `_active_batches` 与 per-ticker lock 留在进程内，后续同 ticker
  `begin_batch` 会因已有活跃 batch 失败；staging/事务状态也不会按 owner 契约收敛。source-sync
  可以先返回 typed cancellation/invariant，而真正的 storage owner 仍处于活动事务，直接破坏后续
  同 ticker 同步的可用性与隔离性。
- **建议改法与验证点**：在 SEC/CN 的 token owner 内把 rollback 清理覆盖到
  `GeneratorExit`、`asyncio.CancelledError` 与其它 pre-commit `BaseException`，保留原始异常/取消且
  rollback 失败不得遮蔽它；明确 commit-start 后仍由 journal/recovery 收敛。新增 batching-enabled
  SEC/CN outer-`aclose` 与 task-cancel 测试，逐项断言 begin=1、rollback=1、commit=0、inner close=1、
  active batch/staging/publish 均为空，并证明随后同 ticker 可再次 `begin_batch`。
- **修复风险**：高。异常优先级、rollback failure、commit point-of-no-return 和嵌套 async-generator
  cleanup 必须一起锁定，不能仅把 `Exception` 机械改成 `BaseException` 后吞掉取消。

### M-001-已修复：ordinary terminal 身份关联 fail-open，CN `source_id` 被采集后从未验证

- **严重性**：Medium
- **入口 / 函数**：`_parse_started`、`_parse_terminal`、`_correlate_terminal`、
  CN `_build_filing_result`
- **文件（行号）**：`dayu/fins/source_sync_runtime.py:116-125,226-252,255-340`；
  `dayu/fins/pipelines/cn_download_filing_workflow.py:1385-1414`
- **输入场景**：ordinary SEC terminal 缺失 `report_date` 和 accession mirror，或 CN/HK terminal
  缺失 `fiscal_year`、`fiscal_period`、`source_id`；其 document/form/filing_date 与 source meta 仍合法。
- **实际分支**：`_parse_started` 对 SEC 强制读取 accession、对 CN/HK 强制读取 fiscal/source identity，
  但 `_correlate_terminal` 对 terminal 的 report/accession/fiscal 字段只在字段非 `None` 时比较，缺失即
  通过。`_StartedFiling.source_id` 在构造后没有任何读取点；真实 CN `_build_filing_result` 也根本不
  输出 `source_id`。因此 real CN 主链无法证明 terminal 仍属于 started 的同一 provider candidate。
- **直接证据**：源码全文检索显示 `source_sync_runtime.py` 中 `source_id` 仅出现于 dataclass 声明、
  `_parse_started` 局部赋值和构造，没有消费点；CN terminal builder 1397-1411 行的 payload 不含该键。
  另用现有 runtime test fixture 删除 SEC terminal nested/flat/result 中的 `internal_document_id` 与
  `report_date` 后执行完整 source sync，结果仍为 `complete`，documents/discovered 均为 1。
- **预期行为**：accepted plan §4.3 明确 SEC started identity 包含 report/accession，CN/HK 包含
  fiscal-year/period/source-id，并要求每个 ordinary terminal 与恰好一个 started 匹配。terminal producer
  应输出市场所需的完整身份，consumer 应要求字段存在且逐字段精确相等；缺失与 mismatch 都应
  `invariant_failed`。
- **影响**：malformed、裁剪或串接错误的 terminal 可被当成另一个 started filing 的成功证据；CN/HK
  中两个 provider records 即使远端 `source_id` 不同，也无法在终态关联处区分。当前 document id
  与日期检查降低了误配概率，但没有实现计划冻结的 exact candidate identity。
- **建议改法与验证点**：冻结每个 market 的 required terminal identity shape；CN producer在 nested
  result 与 flat mirror 输出 `source_id`，SEC producer输出冻结的 report/accession 字段；consumer 对
  缺失或不相等均 fail closed。补齐每个字段独立 missing/mismatch 测试，并加入真实 SEC/CN producer
  event -> source-sync consumer 的相关性测试，避免只用手写 event fixture 自证。
- **修复风险**：中。需同步所有 ordinary terminal producer 与聚合 `result.filings` canonical mirror，
  candidate_not_found synthetic terminal 必须保持独立例外。

### M-002-部分修复：`inner.aclose()` 异常覆盖 primary cancel/invariant，三种高优先级结果都被降级为 `unavailable`

- **严重性**：Medium
- **入口 / 函数**：`DefaultFinsWorkerSourceSyncRuntime.sync_worker_source`
- **文件（行号）**：`dayu/fins/source_sync_runtime.py:446-466`
- **输入场景**：event cap / correlation 先抛 `_InvariantError`，或 stream 的 `__anext__` 先抛
  domain `CancelledError` / `asyncio.CancelledError`，同时 direct-owned stream 的 `aclose()` 抛
  `RuntimeError("close failed")`。
- **实际分支**：`await inner.aclose()` 位于裸 `finally`。Python 在 cleanup 再抛异常时用 close 的
  `RuntimeError` 替换正在传播的 primary exception；随后 465-466 行的 generic `except Exception`
  捕获它并返回全空 `UNAVAILABLE`。这会同时吞掉必须原样 re-raise 的 task cancellation、把 domain
  cancellation 改成 provider outage、把已证实 invariant 改成 provider outage。`aclose()` 调用次数
  仍为 1，但 exactly-once close 本身没有保住 outcome priority。
- **直接证据**：基于现有 `_TrackedStream` / `_runtime` fixture，只覆盖 `aclose()` 为计数后抛
  `RuntimeError`，分别运行 event-cap invariant、domain cancel、asyncio cancel，得到：

  ```text
  invariant_plus_close unavailable aclose_calls 1
  domain_plus_close unavailable aclose_calls 1
  asyncio_plus_close_returned unavailable aclose_calls 1
  ```

  最后一行证明 coroutine 正常返回，调用方未收到 `asyncio.CancelledError`。
- **预期行为**：accepted plan §4.3 固定优先级为 asyncio cancellation > external/domain cancellation
  > proven invariant > generic exception。close 必须恰好一次，但 cleanup failure 不得覆盖已确定的
  primary outcome；只有没有 primary exception 的正常退出路径，close failure 才可按其自身类别处理。
- **影响**：Host/task cancellation 治理失真，调用方会把已取消任务当成 retryable provider outage；
  event cap、duplicate、correlation drift 等 fail-closed 证据也被错误降级，破坏可诊断性与重试决策。
  H-001 修复若让 inner close 执行 rollback，rollback/close failure 会使这个组合窗口更现实。
- **建议改法与验证点**：让 stream owner 显式保留 primary `BaseException`/typed outcome，执行 direct
  inner close 恰好一次后优先重抛/映射 primary；单独记录或附注 cleanup failure，不能遮蔽 primary。
  新增组合测试矩阵：asyncio+close、domain+close、invariant+close，分别断言 re-raise/CANCELLED/
  INVARIANT_FAILED 且 `aclose_calls == 1`；另测 clean exhaustion+close 与 generic provider+close，锁定
  无 primary 或同优先级情况下的规则。
- **修复风险**：中。捕获范围必须覆盖 `BaseException` 才能保留 task cancellation，但不得把
  `KeyboardInterrupt`/`SystemExit` 等误转成业务 result，也不得造成 close 重入。
