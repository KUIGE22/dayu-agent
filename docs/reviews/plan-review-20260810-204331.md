## 结论

**FAIL**。Open H/M/L：**3 / 1 / 0**。

候选已把 client、严格配置、单 PUT staging、checksum、MinIO digest 和多数 gate 写得比原计划具体；其动机成立，S3 可替换 blob bytes 也不是过度设计。但现有 Fins 的真实读写面仍是 local-path owner，且 FS batch 与 S3 没有共同恢复状态机。因而“仅注入一个 `FileStore`”不足以交付 S3 blob repository；直接实施会留下本地读路径、不可恢复的远端孤儿/metadata 悬挂，以及多进程最后写覆盖。以下 High finding 未收敛前，不应进入 implementation。

## 已测试的关键假设

1. `FsStorageCore` 的现有 `FileStore` 注入足以令 source、processed、blob 的实际 bytes 均进入并从 S3 读取。
2. 先完成 S3 final copy、再由 FS 承担 metadata/manifest/batch 的方案，对失败、重试、崩溃与 cleanup 有可恢复的一致性语义。
3. single-PUT staging + `CopyObject` 已定义 production 并发 overwrite 的线性化/ownership 边界，而不仅是单调用的 old-or-new 可见性。
4. strict JSON/env-name、显式 credential、path-style、禁用 ambient chain 的秘密边界可由当前 `PlatformSettings` 与 startup 唯一落实。
5. `stat_object` 的 metadata + 流式 bytes hash、boto3/stubs exact pins、pinned-digest MinIO 与 owner cleanup 都可由 unit/integration gate 可实施地证明。
6. startup 可在不让 bucket/key 泄漏到 platform provider 的前提下，按可验证顺序完成 S3 配置、preflight、provider、Host/Fins 装配。

## Findings

### S14-01-未修复-[高]-注入 FileStore 没有覆盖现有 Fins 的 source/blob 实际读写面
- **位置**: master plan S14-CTRL-03（第 1070–1083 行）、S14-CTRL-05（第 1107–1109 行）；controller fix 的 “FS metadata + S3 blob bytes” 与 “`create(file_store=None)`” 决定。
- **问题类型**: 架构边界 / 不可直接实施 / 过度耦合
- **当前写法**: 计划要求仅把同一 `FileStore` 注入现有 `_FsRepositorySet`，保持 Fins domain/protocol 不变；FS 继续拥有 metadata，S3 承担 blob bytes。
- **反例/失败场景**: production runtime 注入 `S3FileStore` 后，调用已有 source primary read、blob read/list/delete 或任一 processor 读取源文件。写入可能把对象放入 S3，但随后 source 构造仍把 `s3://...` URI 当作本地 `portfolio/` 路径；blob 读、枚举、删除则完全绕过 `FileStore`。结果为读不到刚写入的文件，或在 workspace 缺少本地副本时把 S3-backed document 判为不存在。
- **为什么有问题**: 这不是实现偏好，而是已有 public repository 行为与候选 backend 边界不相容。仅给 factory 增加注入参数，会制造“metadata 指向 S3、所有读取仍只认识 local path”的半替换。若为绕过它保留本地完整副本，又与本 slice 所声称的 S3 blob owner、checksum 和 remote drift 验证不一致，并把双写一致性进一步推迟。
- **直接证据**: `FsStorageCore._build_file_store()` 只在有注入时返回该 store（`dayu/fins/storage/_fs_storage_infra.py:89-126`）；但 `_FsBlobMixin.list_entries()`、`read_file_bytes()` 与 `_delete_entry_impl()` 分别直接 `iterdir()`、`read_bytes()`、`unlink()` 本地路径（`dayu/fins/storage/_fs_blob_core.py:26-113`）。`_FsSourceDocumentMixin.get_source()` 无条件调用 `_local_path_from_uri()` 并返回 `LocalFileSource`（`dayu/fins/storage/_fs_source_document_core.py:615-641`），`get_primary_source()` 正是证据定位器规定的读取真源（第 643–662 行；Slice 1.3 第 407–410 行）。既有测试也先用 `LocalFileStore(root=repository.portfolio_root)` 写入，再把其 local URI 写入 source metadata（例如 `tests/fins/test_sec_pipeline_process_filing_source.py:62-64`）。
- **影响**: 实施 Agent 会在不改 protocol 的限制下误交付只写不读的 S3 backend；Fins tool、processor 与 Slice 1.3 exact-bytes evidence 读取会失败或退回本地双副本，导致 production 行为、数据真源和验收断裂。
- **建议改法和验证点**: 在计划中先锁定完整 adapter 方案及允许文件：保持现有 `DocumentBlobRepositoryProtocol`/domain 不变，但让 FS repository 的 `get_source`、primary source、blob read/list/delete 和 source/processed ingestion 的实际 bytes 全部经 injected `FileStore`；新增一个满足现有 `Source.open() -> BinaryIO` 的 S3-backed source adapter，明确 StreamingBody 的关闭 owner。或明确本 slice 仅做“write-through archive”并不得声称 S3 是 blob owner（这与当前目标不符）。增加 FS/S3 同一套 source、processed、rejected artifact 的 create/read/process/delete/evidence-locator round-trip，且断言 workspace 没有可作为 bytes fallback 的副本。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### S14-02-未修复-[高]-FS batch 与 S3 final object 缺少共同 journal、恢复和补偿状态机
- **位置**: S14-CTRL-03（第 1070–1073 行）、S14-CTRL-04（第 1087–1103 行）、S14-CTRL-07（第 1146–1150 行）；controller fix S14-CTRL-03/04。
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 契约缺失
- **当前写法**: S3 在 staging head 校验后 copy 到 final key，`finally` 有 bounded staging cleanup；FS 继续原子管理 metadata、manifest、batch/recovery JSON，失败时 old final 不变。
- **反例/失败场景**: (a) final `CopyObject` 成功，随后 FS metadata/manifest 写入、FS commit 或进程崩溃失败；S3 留下没有 metadata 引用的 final object。(b) metadata 已指向新 S3 URI 后，本地 batch commit/journal 处于 backup/swap 失败路径，或 S3 cleanup 失败而 `put_object` 按要求报错；调用方得到失败但 final 已公开。(c) rollback/recovery 只恢复本地目录，永远不知道该删除、保留还是重新验证哪一个 S3 staging/final key。重试会把这些未知对象与新的最终状态混合。
- **为什么有问题**: S3 与 FS 不能享有单一原子事务，计划必须定义可恢复的顺序和持久意图，而不是只规定单对象 copy 的原子可见性。现有 `FsStorageCore` 的 crash recovery 是 FS journal 状态机；它没有 S3 操作记录，故不可能凭现有 recovery 补偿 remote side effect。只测试“失败后无本 operation staging object”不能覆盖进程在 finally 前死亡、final 已 copy 但 FS 未提交、或 cleanup 永久失败这三种真实窗口。
- **直接证据**: 现有 batch journal 仅记录 target/staging/backup/journal/lock 的本地路径（`dayu/fins/storage/_fs_storage_infra.py:528-556`），`recover_orphan_batches()` 仅扫描 `.dayu/repo_batches` 与 `.dayu/repo_backups` 并移动/删除目录（第 353–375、594–694 行）。`_FsBlobMixin.store_file()` 则在没有 `_execute_with_auto_batch()` 的情况下直接 `file_store.put_object()`（`dayu/fins/storage/_fs_blob_core.py:115-151`）。候选计划同时要求 remote final copy（第 1090–1097 行）和 FS batch/recovery 继续为 metadata owner（第 1070–1073 行），但未给任何 remote-operation journal、commit ordering、crash recovery 或 orphan final policy。
- **影响**: 状态不一致、不可证明的 orphan S3 bytes、metadata 悬挂、重试误覆盖以及证据读取的不可恢复失败；实现后无法仅靠当前 FS recovery 修复。
- **建议改法和验证点**: 将一个**最小的 remote-operation journal** 加入现有 FS batch journal（不是第二 metadata repository）：逐对象持久 `operation_id`、canonical key、digest/size、预期旧状态、staging/final phase 与 cleanup intent；明确状态机，例如 `remote_staged -> remote_final_verified -> fs_metadata_committed -> remote_cleanup_done`，并规定各 crash phase 的幂等恢复方向和只按 operation-owned key 删除。对 auto-batch、显式 batch、overwrite、metadata commit 前失败、commit 后 cleanup 失败、进程在每个 phase 后终止分别做 fault-injection/restart tests；验收必须在恢复后证明“metadata 恰指向一个 verified final，且仅本 operation 的 staging/orphan 被清理”。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### S14-03-未修复-[高]-CopyObject 只保证单对象可见性，未定义跨进程写入的并发所有权与覆盖语义
- **位置**: S14-CTRL-04（第 1090–1097 行）、S14-CTRL-07（第 1146–1149 行）。
- **问题类型**: 并发恢复风险 / 契约缺失 / 最佳实践偏离
- **当前写法**: 每次写入使用随机 staging key，验证后以单次 `CopyObject` 发布 final；copy 异常后按 final 的 digest/size 判定本次幂等成功，并要求 integration 覆盖 “overwrite old-or-new atomicity”。
- **反例/失败场景**: 两个 API/worker 进程或两个 workspace 对相同 logical key 并发写入不同 bytes。二者可各自成功 staging/head/copy；后到 copy 覆盖先到 copy，两个调用都可返回成功，先到调用返回的 `FileObjectMeta` 又立即失真。若某个 copy 响应超时，它 `head_object` 时可能读到另一个 writer 的 final，因 digest 不同而 fail closed，但其 own final 已可能短暂发布；若 bytes 相同又无法区分 own completion 与他人写入。当前 workspace ticker file lock 不跨机器/工作区，也没有进入 S3 conditional write。
- **为什么有问题**: “old-or-new” 仅说明一个读者不会得到半对象，不等于写入序列可线性化或与 FS metadata 绑定。候选把 S3 作为 production blob owner，却没有声明 single-writer/shared-workspace 前提、remote generation/version/CAS 方案或冲突错误。此缺口会直接放大 S14-02 的 FS/S3 不一致窗口。
- **直接证据**: 现有互斥是 workspace `.dayu/batch_locks/{ticker}.lock` 的本地文本文件锁（`dayu/fins/storage/_fs_storage_infra.py:410-492`），不是 S3 或跨 workspace lock。计划规定 final key 固定复用 `{TICKER}/.../{filename}`（第 1074–1079 行），但只规定 staging `operation_uuid` 与 copy 后的 digest/size head（第 1090–1094 行），没有 version、destination precondition、single writer deployment constraint 或 conflict contract。S14-CTRL-07 也只要求 old-or-new atomicity，没有 two-writer interleaving 验收（第 1146–1149 行）。
- **影响**: 静默 last-writer-wins、metadata 与 blob 指向不同版本、ambiguous completion 误判、以及无法重放/审计写入所有权。
- **建议改法和验证点**: 在进入实现前二选一并写成稳定契约：(1) 明确 Slice 1.4 只支持单个 writer 和同一共享 workspace，startup/Compose 必须拒绝第二 writer；或 (2) 定义可实现的 cross-process publish coordinator（例如 FS journal 持有的 logical-key generation/lease 配合 S3 version id/conditional request，冲突稳定映射为 `OSError`，不把未知覆盖视为成功）。无论选择哪一条，都增加两个独立 core/进程对同 key 不同 digest、copy response ambiguous、重启 recovery 的 integration test；断言唯一 winner、loser 的稳定错误和最终 FS metadata/blob digest 一致。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### S14-04-未修复-[中]-startup 的 S3 preflight 顺序允许已创建 production provider side effect 后才发现 endpoint 不可用
- **位置**: S14-CTRL-05（第 1110–1118 行）、S14-CTRL-08（第 1154–1157 行）。
- **问题类型**: 状态机漏洞 / 可直接实施性 / 最佳实践偏离
- **当前写法**: strict settings/credential 缺失必须早于 provider side effect；但 endpoint `head_bucket` “允许在 provider composition 后”执行，只要求早于 Host/Fins workspace side effect。
- **反例/失败场景**: production settings 和 credential 形式均合法，但 S3 endpoint 不可达或 bucket 无权限。实现按候选允许的次序先调用 existing `_default_provider_or_fail()`；它创建 PostgreSQL engine 并执行 admission probe，随后才 `head_bucket` 失败。测试若只哨兵 Host/Fins，则会漏掉已发生的 provider 连接/engine resource 生命周期；不同实现可得到不同顺序，无法据计划裁决。
- **为什么有问题**: 这不要求 provider 接触 bucket/key，也不需要新增跨层依赖。S3 store builder 属于 Fins storage，而 startup 是 composition root；应先完成所有无 Host/DB 的 configuration + S3 availability admission，再构造 platform provider。候选自身把 fail-fast 和唯一选择路径列为目标，却在唯一有外部 endpoint 的步骤留下了两个不等价顺序。
- **直接证据**: 现有 `prepare_host_runtime_dependencies()` 在 `load_platform_settings()` 后立即调用 `_default_provider_or_fail()`（`dayu/services/startup_preparation.py:503-507`）；该 provider path 会 `create_platform_engine(dsn)` 与 `_probe_production_engine(engine)`（第 250–280 行），后者真实 `engine.connect()`/`SELECT 1`（第 206–239 行）。候选第 1117 行显式允许 endpoint preflight 在这之后。现有测试虽有 side-effect sentinels，但计划未锁定 S3 preflight 相对 `_default_provider_or_fail` 的断言。
- **影响**: startup 的 failure hygiene 不可验收，S3 配置/权限故障可制造不必要的 DB 连接和资源创建；implementation agent 可能按不同顺序实现且都声称符合计划。
- **建议改法和验证点**: 将顺序固定为：`load_platform_settings` -> 仅在 production+enabled 时 parse strict JSON/read explicit credentials/build typed S3 store/`head_bucket` -> `_default_provider_or_fail`/`build_platform_composition` -> path/config/Host/Fins。规定任一 S3 parser、credential、client、head failure 时 provider builder、engine probe、workspace resolver、HostStore、runtime 都未被调用；成功时同一 S3FileStore 实例只经 `DefaultFinsRuntime.create(file_store=...)` 注入。用顺序记录 fake 与真实 MinIO startup black-box 分别证明。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## 显式审查 lenses

- **Architecture boundary**：S3 settings/parser 放在 `dayu.fins.storage`、startup 只做选择、platform provider 不接 bucket/key 的方向正确；但现有 repository 的 local source/blob API 证明当前边界并非仅六方法 FileStore 可替换，S14-01 必须先收敛。
- **Best practice**：strict JSON 仅持 env-name、显式 credential、禁止 ETag 充当 hash、verified stat read、typed boto3 stubs、pinned digest/owner-label cleanup 都是合理约束。缺的是跨资源失败可恢复性与写入并发契约（S14-02/03），它们比增加 multipart 更优先；在既定 <=5 GiB 上限下，single PUT 没有被证据推翻。
- **Optimal solution**：FS metadata + S3 bytes 是避免复制整套 workspace JSON 到 bucket 的最小方向，不建议引入第二 S3 metadata repository。但最优实现不是“一个注入参数”，而是复用既有 FS batch journal 记录最小 remote operation intent，并补齐真实 FileStore 读路径。
- **Overengineering**：未发现当前候选的 strict JSON、stat read 或 MinIO digest/owner cleanup 是无需求泛化；相反，新增多 provider/builder 或 multipart 都没有当前收益。建议的 journal 仅为已选择的双存储 owner 提供恢复，不扩公共协议。
- **Overcoupling**：候选避免让 investment/provider 接触 bucket/key 的初衷正确。若以 Service/Agent 重建 key 或以本地 fallback 迁就现有读路径，会形成跨层耦合；修复应封装在 Fins storage core/adapter 与其 batch owner 内。

## Open Questions

1. 目标 production topology 是否明确为单 writer + 单个共享 workspace？若是，必须作为 deployment/startup admission 契约和测试前提写入；若否，S14-03 的跨进程 publish coordinator 是 blocker。
2. S3 是唯一 authoritative bytes，还是保留一个受控 local cache？若保留，cache 的完整性、清理、read preference 与 metadata ownership 必须先定义；不能由各 pipeline 自行双写。
3. remote-operation journal 的恢复入口应由现有 `ensure_batch_recovery()` 调用，还是由显式 Fins maintenance job 调用？无论选择，必须在 startup/first write 发生远端 side effect 前可重放，且 cleanup 只作用于 journal-own 的 key。

## Residual Risks 与建议跟踪位置

- 在上述 H finding 修复并验证后，仍保留 S3 读回 hash 对 5 GiB 对象的时间/费用放大风险；这是当前 fail-closed integrity contract 的可接受代价，建议在 Slice 1.4 implementation artifact 记录测得上限与 timeout，不要以 ETag 或抽样校验退化。
- boto3/boto3-stubs 的 minimum/current exact lock 组合及 MinIO digest 的本地多架构可用性尚未执行 resolver/Docker 验证，按 S14-CTRL-01/07 的既定 clean-install 和 image-inspect gates 跟踪；本次因审查边界未运行。
- MinIO fixture 可沿用现有 investment integration lane 的“随机资源 + inspect label + bounded/redacted diagnostics”模式；需在 implementation plan 中把 bucket owner marker/验证、copy-ambiguous wrapper 与 crash/restart fault injection 写为具体 helper，不允许以 fake-only 覆盖代替。

## 最终计划审查结论

`fail`。在 S14-01、S14-02、S14-03 关闭且 S14-04 固定 ordering 前，Slice 1.4 不具备 code-generation-ready 条件；不得解除依赖安装、镜像拉取或实现编辑 gate。
