### S15-未修复-[中]-M03-research bundle locator owner 边界

- **Plan位置**: §S15-CTRL-07（Read-only staging 第 4 步）
- **问题类型**: 架构边界
- **当前写法**: "每个显式 bundle locator 必须 contained 且 owner `inspect_research_template_bundle()` 返回 `validation.ok is True`；descriptor 的 template/research_target ticker/company 必须与 manifest/CompanyMeta 精确一致；其 artifacts 与可选 source write-manifest 都必须 contained regular non-symlink；staging 只记录 bundle 自身及 owner 已验证 closure 中每个文件的 POSIX relative locator、size、SHA-256，并计算 sorted canonical artifact-manifest SHA-256"
- **反例/失败场景**: `inspect_research_template_bundle()` 返回 `validation.ok is True` 但 `research_target` 中的 ticker 与 manifest 不一致时，plan 要求 "descriptor 的 template/research_target ticker/company 必须与 manifest/CompanyMeta 精确一致"，但 `inspect_research_template_bundle()` 本身不校验与外部 manifest 的一致性——这个校验需要 staging adapter 自行实现。plan 未明确这个额外校验的 owner 和具体实现位置。
- **为什么有问题**: `inspect_research_template_bundle()` 只验证 bundle descriptor 自身的结构完整性，不验证与外部 manifest 的一致性。staging adapter 需要额外读取 descriptor 的 `research_target` 字段并与 manifest 比较，但 plan 未明确这个额外校验的实现 owner 是 staging adapter 还是 domain。
- **直接证据**: `_research_template_bundle.py:386-425`：`inspect_research_template_bundle()` 返回 `{"validation": {..., "ok": ...}, ...}`，但 `research_target` 字段只是 raw dict，不与外部 manifest 比较
- **影响**: implementation agent 可能遗漏 cross-validation，导致 manifest 与 bundle descriptor 不一致时静默通过
- **建议改法和验证点**: 在 S15-CTRL-07 step 4 明确：staging adapter 读取 `inspect_research_template_bundle()` 返回的 `research_target.ticker` 与 `research_target.company_id`，与 manifest 对应条目比较；不一致时 fail closed。要求测试覆盖 mismatch 场景
- **修复风险**: 低
- **严重程度**: 中

### S15-未修复-[中]-M04-UUIDv5 namespace 选择可验证性

- **Plan位置**: §S15-CTRL-06（Pure contracts）
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: "ID 唯一算法固定为 UUIDv5：namespace 使用标准库 `NAMESPACE_URL`，name 精确前缀分别为 `dayu:workspace-import:v1:company:{legacy_company_id}`、`dayu:workspace-import:v1:security:{exchange_mic}:{ticker}`、`dayu:workspace-import:v1:source:{source_key}`、`dayu:workspace-import:v1:marker:{tenant_id}:{migration_id}`、`dayu:workspace-import:v1:bundle:{tenant_id}:{exchange_mic}:{ticker}:{template_name}`"
- **反例/失败场景**: `NAMESPACE_URL` 是 UUIDv5 的预定义 namespace（值为 `6ba7b810-9dad-11d1-80b4-00c04fd430c8`），但 plan 未明确说明这个 namespace 是否适合 investment domain。更关键的是，plan 未定义 `legacy_company_id` 的 canonical form——`CompanyMeta.company_id` 是 raw string（如 `"AAPL_US"`），但 plan 未说明是否需要 normalize 后再拼入 UUIDv5 name。
- **为什么有问题**: `legacy_company_id` 的 canonical form 未定义。如果 manifest 中 `"legacy_company_id": "aapl_us"` 与 inventory 中 `company_meta.company_id: "AAPL_US"` 不一致，UUIDv5 会产生不同 ID，导致 no-op 判断失败。
- **直接证据**: `document_models.py:151`：`CompanyMeta.company_id` 是 `str` 类型，无 normalize；plan §S15-CTRL-06 UUIDv5 name 包含 `{legacy_company_id}`
- **影响**: 如果 `legacy_company_id` 有大小写/格式不一致，同一公司会产生不同 ID，破坏 idempotent no-op
- **建议改法和验证点**: 在 S15-CTRL-06 明确 `legacy_company_id` 使用 inventory 中的 raw `company_meta.company_id`（不经 normalize），并要求 staging 阶段做 exact string match；或者明确 normalize 规则（如 uppercase）并要求测试覆盖
- **修复风险**: 低
- **严重程度**: 中

### S15-未修复-[高]-M05-single transaction repository 与现有 identity/source repository 的关系

- **Plan位置**: §S15-CTRL-09（Single transaction repository）
- **问题类型**: 架构边界 / 过度耦合
- **当前写法**: "`WorkspaceImportRepositoryProtocol.publish_import(scope, request) -> receipt` 是唯一 DB transaction owner；`PostgresWorkspaceImportRepository` 每次调用只建一个 session，`SET LOCAL app.tenant_id` 后在同一 transaction 完成 marker lock、public reference reconcile、source definition reconcile、locator inserts、completed marker。禁止通过现有 identity/source repository 的多方法拼出跨 transaction 流程，也禁止 Service/CLI 持 session 或做 SQL。"
- **反例/失败场景**: plan 要求 `publish_import` 在同一 transaction 内做 "public reference reconcile"（company/security insert or reuse）和 "source definition reconcile"。但 `IdentityRepositoryProtocol.register_company_security()` 是 atomic company+security registration，每个方法自己拥有一个 `Session.begin()` 事务（见 S12-CTRL-01）。`PostgresWorkspaceImportRepository` 不能复用 `IdentityRepositoryProtocol` 的方法（因为它们自己开事务），只能直接用 SQL/ORM 操作同一 session。这意味着 workspace import 仓库需要直接操作 identity 表，绕过 `IdentityRepositoryProtocol` 的事务隔离。plan 未明确这个绕过是否被允许，以及 `IdentityRepositoryProtocol` 的测试是否需要覆盖 "workspace import 绕过" 场景。
- **为什么有问题**: 这是一个架构边界问题：`PostgresWorkspaceImportRepository` 需要直接操作 `companies`/`securities`/`source_definitions` 表，但这些表的 owner 是 `IdentityRepositoryProtocol`。plan 明确说 "禁止通过现有 identity/source repository 的多方法拼出跨 transaction 流程"，但没有明确 `PostgresWorkspaceImportRepository` 可以直接操作这些表。
- **直接证据**: plan §S12-CTRL-01 "`postgres_identity.py` 可由一个 transaction-scoped implementation 同时实现两项 protocol；每个方法自己拥有一个 `Session.begin()` 事务"；plan §S15-CTRL-09 "禁止通过现有 identity/source repository 的多方法拼出跨 transaction 流程"
- **影响**: implementation agent 可能不确定是否可以绕过 `IdentityRepositoryProtocol` 直接操作 identity 表，导致实现犹豫或错误
- **建议改法和验证点**: 在 S15-CTRL-09 明确：`PostgresWorkspaceImportRepository` 在同一 session 内直接操作 `companies`/`securities`/`source_definitions` 表（通过 ORM model 或 SQL），不经过 `IdentityRepositoryProtocol` 的方法（因为那些方法自己开事务）；这是 workspace import 的特殊 transaction owner 权限，不扩展到其他 slice。要求测试证明 workspace import 的 company/security insert 与 `IdentityRepositoryProtocol` 的独立 insert 不冲突
- **修复风险**: 中
- **严重程度**: 高

### S15-未修复-[高]-M06-no-op 判断的 row drift 检测不完整

- **Plan位置**: §S15-CTRL-09（Single transaction repository）
- **问题类型**: 状态机漏洞
- **当前写法**: "已有 marker 的 schema/root/payload/counts 全相同且 intended company/security/source/locator rows 仍 exact 时返回 `status=no_op`，数据库字节/版本/时间不变；marker 任一字段不同，或 marker exact 但 row missing/drift，抛稳定 drift error"
- **反例/失败场景**: plan 要求 "intended company/security/source/locator rows 仍 exact"，但未定义 "exact" 的比较粒度。对于 `companies` 表，是比较 `id` 还是比较所有字段（`legal_name`、`lei`、`country_code`）？对于 `source_definitions`，是只比较 `source_key` 还是比较所有字段？如果 manifest 中 `legal_name` 与 DB 中已有值不同，是 no-op 还是 drift？
- **为什么有问题**: no-op 判断的 "exact" 语义未定义，implementation agent 可能只比较主键（导致数据不一致被静默忽略），或比较所有字段（导致正常 no-op 被误判为 drift）。
- **直接证据**: plan §S15-CTRL-09 "intended company/security/source/locator rows 仍 exact"
- **影响**: no-op 判断可能不正确，导致 either 数据不一致被忽略 or 正常 rerun 被误判为 drift
- **建议改法和验证点**: 在 S15-CTRL-09 明确 no-op 判断的比较粒度：对于 public reference 行（companies/securities/source_definitions），只比较主键 ID 和业务键（ticker/MIC/source_key），不比较 display 字段（legal_name 等）；对于 locator 行，比较所有字段（因为 locator 是 immutable append-only）；对于 marker 行，比较所有字段。要求测试覆盖 "marker exact 但 company legal_name 不同" 场景
- **修复风险**: 中
- **严重程度**: 高

### S15-未修复-[低]-M09-locator 表 `repository_key` CHECK 约束过宽

- **建议改法和验证点**: 确认这是刻意设计（当前 slice 只支持 legacy-workspace，未来扩展通过新 migration 修改 CHECK 约束）。如果确认，无需修改；如果需要更灵活，改为 `CHECK (length(repository_key) > 0)`
- **修复风险**: 低
- **严重程度**: 低

### S15-未修复-[中]-M11-downgrade 闭合性验证

- **Plan位置**: §S15-CTRL-08（Exact schema 0002）
- **问题类型**: 测试缺口
- **当前写法**: "downgrade 先拒绝外部依赖，再仅删除 0002 policy/grants/tables，保留 0001 的 13 表/roles/schema/default org；禁止 CASCADE"
- **反例/失败场景**: plan 要求 `0001 -> 0002 -> 0001 -> 0002` 可重复，但未明确 downgrade 时是否检查 `research_bundle_locators` 行是否存在对 `companies`/`securities` 的 FK 依赖。如果有 locator 行引用了 company/security，downgrade 0002 时 FK 会阻止删除 locator 表，除非先删除 locator 行或使用 CASCADE（但 plan 禁止 CASCADE）。

- **建议改法和验证点**: 在 S15-CTRL-08 明确：downgrade 0002 先检查 locator 表是否有行引用 0001 的表，有则拒绝 downgrade（fail/rollback），无则正常删除。要求测试证明有 locator 行时 downgrade 拒绝，无 locator 行时 downgrade 成功
