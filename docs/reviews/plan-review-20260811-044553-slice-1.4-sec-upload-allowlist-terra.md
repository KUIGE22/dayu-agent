## 审查范围与动机判断

本次勘误的动机成立且严重性判断准确：基线 `HEAD` 中
`run_upload_filing_stream` 与 `run_upload_material_stream` 都在调用
`DoclingUploadService.execute_upload` 前调用
`reset_upload_target_for_overwrite`；而已接受的 S14-CTRL-12 明确要求 reset 只能位于
`execute_upload` 的同一 per-document 显式 batch 内。若不允许修改
`dayu/fins/pipelines/sec_upload_workflow.py`，该行为契约无法落实，且 batch 外 destructive
reset 的失败无法靠 rollback 恢复。

本复审没有对实现 WIP 作代码验收；下列代码事实仅用于验证计划可实施性与测试边界。

## 已压测的关键假设与结果

1. **遗漏的 production owner 是否真实且唯一**：成立。基线
   `sec_upload_workflow.py` 的 filing/material 两条路径分别在 `execute_upload` 前调用该
   helper；当前 WIP diff 仅删除这两处调用及 import 整理。对当前 Python 源码搜索
   `reset_upload_target_for_overwrite`，已无其它生产调用点。因此不需要新增其它 production
   workflow owner。
2. **删除两处 pre-reset 是否是必要最小改动**：成立。当前
   `DoclingUploadService._execute_upload_with_batch` 先 `begin_batch`，再在
   `overwrite and previous_meta is not None` 时 `reset_source_document`，随后写 blob/source
   meta，异常 rollback、成功 commit。保留 workflow pre-reset 会形成第二个、位于 batch 外的
   destructive owner；删除它不会引入 second batch 或 wrapper。
3. **public/action/upsert/event contract 是否漂移**：未发现。WIP 的功能性 diff 只有两段
   helper 调用删除；`run_upload_*_stream` 的函数签名、`resolve_upload_action`、company upsert、
   `execute_upload` 实参和所有 yield 的相对顺序均未改变。`reset` 自身不产生 workflow event。
4. **过度扩 scope/恢复风险**：未发现。将唯一生产文件加入 Allowed 是窄且可维护的修正；恢复
   pre-reset、业务 wrapper、嵌套/第二 batch 都会违反既有 single transaction owner，不能作为
   替代方案。
5. **验证假设**：不成立，见以下 Medium finding。`test_upload_overwrite_batch.py` 锁定 service
   owner 的事务语义，但没有锁定 SEC workflow 在进入该 owner 前不再 reset；完整
   `tests/fins/` 只会重复执行未能区分新旧 workflow 排序的断言。

## Findings

### TERRA-S14-UPLOAD-ALLOWLIST-01-未修复-[中]-真实 workflow 的前置 reset 删除没有回归测试
- **位置**: 勘误 artifact §2 第四项、§4 第一项及 master plan Slice 1.4 测试修改清单
  `tests/fins/test_sec_pipeline_upload_filing_stream.py` /
  `tests/fins/test_sec_pipeline_upload_material_stream.py`（约 1661-1669）；finding closure
  表的 MiM upload-overwrite 行（约 2403）。
- **问题类型**: 测试缺口。
- **当前写法**: 勘误声称既有 `tests/fins/test_upload_overwrite_batch.py` 负责 filing/material、
  create/update/overwrite、失败 rollback 与旧 bytes 可读，并以它和完整 `tests/fins/` 作为本次
  删除的全部验证；同时冻结测试 WIP，不增加测试文件。
- **反例/失败场景**: 后续实现或整理时，在 filing 或 material workflow 任一路径重新插入
  `reset_upload_target_for_overwrite`。`DoclingUploadService.execute_upload` 的直接单测仍会看到
  自己的 begin → reset → write → commit，照样通过；现有 pipeline 测试仍只看最终文件名、action
  和结果状态，旧的 batch 外 reset 与修正后的 batch 内 reset 产生相同 happy-path 最终状态，亦可
  通过。完整 `tests/fins/` 因而不能证明 destructive reset 没有发生在 service batch 之前。
- **为什么有问题**: 本次勘误唯一的行为价值就是把 reset 的事务 owner 从真实 workflow 收敛到
  `execute_upload`。不在调用路径上作负向/顺序断言，会让 S14-CTRL-12 的核心 recovery invariant
  退化为没有回归保护的实现细节；这与计划已为 SEC filing/material workflow 指定测试 owner 的
  设计不一致。
- **直接证据**:
  - `tests/fins/test_upload_overwrite_batch.py` 全部直接调用
    `DoclingUploadService.execute_upload`，其中 overwrite batch 覆盖使用
    `SourceKind.FILING`；文件没有调用 `run_upload_filing_stream` 或
    `run_upload_material_stream`，也没有 material workflow 路径。
  - `tests/fins/test_sec_pipeline_upload_filing_stream.py:82-166` 与
    `tests/fins/test_sec_pipeline_upload_material_stream.py:83-135` 确实执行两条真实 workflow，
    但只断言 action/status/document id/final file list，未观测 reset 与 active batch 的先后；它们
    在当前 WIP 中没有 diff。
  - master plan 已把这两个测试文件列为 S14-CTRL-12 upload 测试 owner，并明确要求它们验证
    overwrite reset 位于 `execute_upload` per-document batch、零第二 batch/auto-begin、失败后
    旧 source/bytes 可读；无需新建测试抽象或扩张 production scope。
- **影响**: 实现可以在不触发现有 hard gate 的情况下重新引入 batch 外 destructive reset；S3
  store/publish 或随后的 source-meta 写失败时，旧 source/bytes 可能在 rollback 前已被破坏，导致
  recovery 与 S14-CTRL-12 的唯一事务 owner 不可验收。
- **建议改法和验证点**: Controller 应将此 finding 裁决后，要求在已允许的
  `test_sec_pipeline_upload_filing_stream.py` 与
  `test_sec_pipeline_upload_material_stream.py` 增加/改造 overwrite 场景：对真实 workflow 路径证明
  workflow 在 `execute_upload` 前没有调用 reset，并证明每条路径只由 service 的同-core
  per-document batch 执行 reset → blob/source-meta 写 → commit；至少覆盖 pre-commit 失败 rollback
  后旧 source/bytes 可读。保留 `test_upload_overwrite_batch.py` 作为 service-owner 单测，不能替代
  调用链测试；完整 `tests/fins/` 仅在这些针对性断言存在后才是有效 gate。
- **修复风险（低/中/高）**: 低（测试 owner 已在既有 Slice 1.4 Allowed 清单内；无需更改 public
  contract 或新增 production abstraction）。
- **严重程度（低/中/高/严重）**: 中。
