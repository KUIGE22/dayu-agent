### 2-未修复-高-to_utc_iso 将语义上 naive 的时间静默按本机时区换算
- **入口/函数**: `to_utc_iso()`。
- **文件(行号)**: `dayu/investment/domain/money.py:275-290`；`tests/investment/test_architecture_boundaries.py:542-554`。
- **输入场景**: 调用方传入 `datetime(2026, 8, 10, 7, 46, 2, tzinfo=custom_tzinfo)`，其中 `custom_tzinfo.utcoffset(moment)` 返回 `None`。Python 将此 datetime 定义为 naive，尽管 `tzinfo is not None`。
- **实际分支**: 288 行只检查 `value.tzinfo is None`，因此该输入进入 290 行的 `astimezone(timezone.utc)`；运行在当前 `+08:00` 主机时最小复现输出 `2026-08-09T23:46:02+00:00`，没有抛出异常。
- **预期行为**: Slice artifact、`dayu/investment/README.md:56-59` 与函数 docstring 都规定 naive 输入一律拒绝；金融事实与事件时间必须是可确定的 UTC 时刻。
- **实际行为**: 没有 UTC offset 的墙上时间被解释成执行进程本机时区，得到依赖部署地点的错误时刻并跨日序列化。
- **直接证据**: `datetime` 的 aware 判定要求 `tzinfo` 与 `utcoffset()` 均非 `None`；实现只检查前者（288-290 行）。现有负例仅通过 `.replace(tzinfo=None)` 生成 naive 时间（552-554 行），所以 99 个通过测试和 100% statement coverage 都未执行这个语义分支。
- **影响**: 后续入库的 `effective_at`、`published_at`、`available_at` 或审计时间可能被静默错移，破坏计划冻结的 UTC / point-in-time 不变量；在不同部署时区会产生不同事实与回测输入。
- **建议改法和验证点**: 以 `value.tzinfo is None or value.utcoffset() is None` 拒绝 naive 输入；为 `parse_utc()` 与 `to_utc_iso()` 补充 custom `tzinfo` 返回 `None` 的反例，并断言不会调用本机时区转换。
- **修复风险（低/中/高）**: 低（局部校验与回归测试）。
- **严重程度（低/中/高/严重）**: 高。
