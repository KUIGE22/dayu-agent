## 2. Findings

### F01-未修复-严重-_validate_research_materialization_args 迁移导致 params→write→params 循环依赖

- **位置**: Plan §5 Slice 5:786；源码 `write.py:3595`、`write.py:2137`
- **问题类型**: 架构边界 / 切片过粗
- **当前写法**: Plan Slice 5 列出 `_write_params_validation.py` 包含 `_validate_challenger_run_plan_args`、`_validate_live_smoke_plan_args`、`_validate_research_materialization_args` 共 3 个函数。Plan 未提及 `_validate_research_materialization_args` 内部调用了 `_challenger_requested`。`_challenger_requested` 在 §1.2 被归入 "Challenger 实验 14 函数"（行 2137–2730），计划在 Slice 8 迁移至 `_write_challenger.py`。
- **反例/失败场景**:
  1. **Slice 5 独立提交时**: `_write_params_validation.py` 内的 `_validate_research_materialization_args`（行 3595）调用 `_challenger_requested(args)`。此时 `_challenger_requested` 仍在 `write.py` 中定义。`_write_params_validation.py` 必须 `from dayu.cli.commands.write import _challenger_requested` 才能工作，但 `write.py` 同时 `from dayu.cli.commands._write_params_validation import _validate_research_materialization_args`——形成直接循环 import，Python 模块加载失败。
  2. **Slice 5 交付 → Slice 8 之间**: 上述循环持续存在于 `codex/dual-model-research-mvp` 分支的多个 commit 之间，违反 plan §2.2 声明的 "write.py → _write_params_validation" 单向依赖方向。
  3. **若 Slice 5 临时保留 copy**: `_write_params_validation.py` 内保留 `_challenger_requested` 的私有副本 → 产生重复定义，Slce 8 迁移时必须删除其中之一，容易漏删或删错，违反 C5 "零重复" 目标。
- **为什么有问题**: `_validate_research_materialization_args` 与 `_challenger_requested` 之间存在编译期强耦合（函数调用），但 plan 将它们分配到两个不同 slice 的两个不同目标模块，且未声明这一依赖。按当前 plan 执行，Slice 5 无法独立通过 pyright + pytest。
- **直接证据**:
  - `write.py:3595`: `challenger_requested = _challenger_requested(args)` — 位于 `_validate_research_materialization_args` 函数体内
  - `write.py:2137-2143`: `def _challenger_requested(args: argparse.Namespace) -> bool` — 仅 7 行的简单布尔检查
  - Plan §1.2: "Challenger 实验 14 函数" 覆盖行 2137–2730，包含 `_challenger_requested`
  - Plan §5 Slice 5:786 未提及 `_challenger_requested`
  - Plan §2.2 依赖方向: `write.py → _write_params_validation`（单向），但 `_challenger_requested` 的调用链打破了这一方向
- **影响**: Slice 5 commit 无法独立编译/测试；若强行临时 workaround 则产生后续 Slice 8 的重复定义删除风险；`_challenger_requested` 的归属（validation vs challenger）在 plan 中被错误分类
- **建议改法和验证点**:
  - **推荐方案**: 将 `_challenger_requested` 作为 Slice 5 的第 8 个函数迁入 `_write_params_validation.py`（与 `_validate_research_materialization_args` 同模块，无需跨模块 import）
  - Slice 8 的 Challenger 函数计数从 **14 改为 13**（`_challenger_requested` 不再计入 Challenger 组）
  - 验证点:
    1. `write.py` 改为 `from dayu.cli.commands._write_params_validation import _challenger_requested, _validate_research_materialization_args, ...`
    2. `run_write_command` 内 3 处 `_challenger_requested(args)` 调用（行 4829/5079/5191）通过 import 可用
    3. `_write_params_validation.py` 内模块级 `_challenger_requested` 被 `_validate_research_materialization_args` 直接调用，无循环
    4. `pyright dayu/cli/commands/write.py dayu/cli/commands/_write_params_validation.py` 零 errors
    5. `pytest tests/engine/test_cli_running_config.py tests/application/test_write_cli_dispatch.py -v -k "write"` 全绿
- **修复风险**: 低 — `_challenger_requested` 是一个纯函数（零外部依赖、零副作用、7 行），移动它只改变 import 路径，不改变行为
- **严重程度**: **严重** — 按当前 plan 执行 Slice 5 会直接编译失败；属于 implementation-blocking 缺陷

### F02-未修复-高-setup_model_name monkeypatch 目标迁移未在 plan 中声明

- **位置**: Plan §1.8:333（monkeypatch 契约仅锁定 `WriteService.print_report`）、§5 Slice 0:497（monkeypatch 路径契约仅覆盖 `test_write_service_top_level_import_in_write_py_is_stable`）；测试 `tests/engine/test_cli_running_config.py:2226`
- **问题类型**: 契约缺失 / 测试缺口
- **当前写法**: Plan §1.8 声明了 monkeypatch 契约 `monkeypatch.setattr("dayu.cli.commands.write.WriteService.print_report", ...)` 并标记为不受 Slice 8 影响。但 plan 未覆盖 `setup_model_name` monkeypatch。测试在 `test_cli_running_config.py:2226` 使用 `monkeypatch.setattr("dayu.cli.commands.write.setup_model_name", partial(_return_value, ModelName(model_name="deepseek-v4-pro")))`。
- **反例/失败场景**:
  1. Slice 5 将 `_resolve_write_model_override_name` 移到 `_write_config_helpers.py`。该函数内部调用 `setup_model_name(args).model_name`。`setup_model_name` 是从 `dayu.cli.dependency_setup` 顶层 import 到 `_write_config_helpers.py` 的。
  2. 测试 patch 路径 `"dayu.cli.commands.write.setup_model_name"` 只影响 `write.py` 模块命名空间中的 `setup_model_name` 绑定。`_write_config_helpers.py` 中的 `setup_model_name` 绑定不受此 patch 影响。
  3. 测试将静默失败：`_resolve_write_model_override_name` 调用的是未被打补丁的真实 `setup_model_name`，可能因缺少配置文件而抛出异常，而非返回测试预期的 `ModelName(model_name="deepseek-v4-pro")`。
- **为什么有问题**: Plan 明确声明了 "monkeypatch 契约"（§1.8）但仅覆盖了 `WriteService.print_report` 一条路径。`setup_model_name` 的 monkeypatch 路径变更是一个确定性会发生的 breaking change，不在 plan 的 scope 中属于遗漏。
- **直接证据**:
  - 测试文件 `tests/engine/test_cli_running_config.py:2225-2228`:
    ```python
    monkeypatch.setattr(
        "dayu.cli.commands.write.setup_model_name",
        partial(_return_value, ModelName(model_name="deepseek-v4-pro")),
    )
    ```
  - 源码 `write.py:25`: `from dayu.cli.dependency_setup import ... setup_model_name ...`
  - 源码 `write.py:190-203`: `_resolve_write_model_override_name` 调用 `setup_model_name(args).model_name`
  - Plan §5 Slice 5:786: `_resolve_write_model_override_name` 迁至 `_write_config_helpers.py`
  - Plan §1.8:333: monkeypatch 契约仅锁定 `WriteService.print_report`
- **影响**: Slice 5 后 `test_cli_running_config.py` 中依赖 `setup_model_name` monkeypatch 的测试（至少 `test_run_write_command_preflight_only` 等）会失败，因为 patch 目标的模块绑定已迁移到 `_write_config_helpers.py`
- **建议改法和验证点**:
  - **必须做**: 将测试中的 monkeypatch 目标从 `"dayu.cli.commands.write.setup_model_name"` 改为 `"dayu.cli.commands._write_config_helpers.setup_model_name"`
  - **禁止做**: 在 `write.py` 中新增 `setup_model_name` 的 re-export（`from dayu.cli.commands._write_config_helpers import setup_model_name` 或等效的 `from dayu.cli.dependency_setup import setup_model_name` 仅为了保持旧测试路径）——这违反 AGENTS.md "禁止兼容性 re-export"
  - **禁止做**: 在 `write.py` 中新增 wrapper/seam（如 `setup_model_name = _write_config_helpers.setup_model_name`）——违反 AGENTS.md "禁止胶水 seam" 和 "禁止兼容性 wrapper/facade"
  - `_write_config_helpers.py` 内 `setup_model_name` 是正常的功能 import（从 `dayu.cli.dependency_setup`），不是 re-export
  - 同时排查 `tests/application/test_write_cli_dispatch.py` 中是否也有类似的 monkeypatch 需要更新
  - 验证点: `pytest tests/engine/test_cli_running_config.py -v -k "preflight_only"` 全绿
- **修复风险**: 低 — 纯测试路径字符串更新，无生产代码变更
- **严重程度**: **高** — plan 对 monkeypatch 契约的覆盖不完整，Slice 5 实施后会导致相关集成测试静默失败或误报；虽不影响生产代码正确性，但破坏 CI 门禁

### F03-未修复-高-MODULE 常量真源位置与 Slice 8 终态声明冲突

- **位置**: Plan §5 Slice 5:786, §5 Slice 8:814; 源码 `write.py:186`, `write.py:2106-2134`
- **问题类型**: 架构边界 / 契约缺失
- **当前写法**: `MODULE = "APP.WRITE"` 在 `write.py:186` 定义。Plan Slice 5 将 `_log_write_preflight_result` 迁至 `_write_config_helpers.py`，该函数体内 13 处使用 `MODULE`（行 2110/2115/2121 等 Log.info/Log.warn/Log.error 调用）。Plan Slice 8 声明 `write.py` 最终保留 "MODULE 常量"。但 plan 未说明 `_write_config_helpers.py`（以及后续 `_write_execution.py`、`_write_challenger.py`、`_write_config_application.py` 等使用 MODULE 的模块）如何获取 MODULE。
- **反例/失败场景**:
  1. **MODULE 留在 `write.py`**: `_write_config_helpers.py` 内的 `_log_write_preflight_result` 需要 MODULE。若从 `write.py` import → `write.py` 同时从 `_write_config_helpers` import → 循环 import。即使技术上可行（顶层 import 在 `_log_write_preflight_result` 调用前完成），也违反 plan §2.2 声明的单向依赖方向 `write.py → _write_config_helpers`。
  2. **MODULE 复制到 `_write_config_helpers.py`**: `write.py` 和 `_write_config_helpers.py` 各自定义 `MODULE = "APP.WRITE"` → 违反 C5 "零重复" 目标和 AGENTS "重复逻辑必须抽取"。
  3. **MODULE 移到 `_write_config_helpers.py` 但 plan 未更新**: 与 Slice 8 声明 "write.py 最终保留 MODULE 常量" 矛盾，implementation agent 可能按 plan 文字保留 MODULE 在 write.py 而引入上述任一问题。
- **为什么有问题**: MODULE 是真源常量，被至少 4 个目标模块（`_write_config_helpers`、`_write_execution`、`_write_config_application`、`write`）使用。Plan 未指定其最终归属模块，也未声明跨模块 import 策略。这迫使 implementation agent 在 Slice 5 现场做架构决策，违反 plan 应 "code-generation-ready" 的标准。
- **直接证据**:
  - `write.py:186`: `MODULE = "APP.WRITE"`
  - `write.py:2106-2134`: `_log_write_preflight_result` 函数体内 13 处 `module=MODULE`
  - Plan §2.1: `_write_config_helpers.py` 包含 `_log_write_preflight_result`
  - Plan §5 Slice 8:814: "write.py 降至 ~660 行（仅 `run_write_command` + `_materialize_research_after_write` + MODULE 常量）"
  - Plan §2.2 依赖方向: `write.py → _write_config_helpers`（单向），但若 MODULE 留在 write.py 则 `_write_config_helpers → write.py`，形成反向依赖
  - `_run_write_stage` (行 273)、`_run_write_preflight` (行 318)、`_build_fresh_application_routing_snapshot` (行 557)、`_run_write_model_configuration_application` (行 610)、`_run_write_model_configuration_rollback` (行 696) 等均使用 `MODULE`——这些函数分别迁移到 `_write_execution.py` (Slice 7)、`_write_config_application.py` (Slice 6) 等模块
- **影响**: implementation agent 在 Slice 5 面临未解决的架构决策；若选错方案（如 MODULE 留在 write.py），会导致后续 Slice 6/7/8 每一级都产生反向 import 或复制常量
- **建议改法和验证点**:
  - **推荐方案**: MODULE 定义移至 `_write_config_helpers.py`（该模块是 Slice 5 首批创建的叶子模块，被其他所有使用 MODULE 的模块 import）。`write.py` 改为 `from dayu.cli.commands._write_config_helpers import MODULE`（这是正常的功能 import，非 re-export）
  - Slice 8 文案修正: `write.py` 最终状态从 "`run_write_command` + `_materialize_research_after_write` + MODULE 常量" 改为 "`run_write_command` + `_materialize_research_after_write`"（MODULE 不再在 write.py 中定义）
  - 未来抽取 `_write_execution.py` (Slice 7) 和 `_write_config_application.py` (Slice 6) 时，它们分别 `from dayu.cli.commands._write_config_helpers import MODULE`——这是合法的单向依赖（`_write_execution → _write_config_helpers`）
  - 验证点:
    1. `grep -rn "MODULE" dayu/cli/commands/` 确认仅 `_write_config_helpers.py` 有 `MODULE = "APP.WRITE"` 定义，其余文件均为 import
    2. 无 `write.py` → `_write_config_helpers` 以外的反向 import
    3. `pyright dayu/cli/commands/` 零 errors
- **修复风险**: 低 — MODULE 是简单的字符串常量，移动不影响行为
- **严重程度**: **高** — plan 存在明确的内部矛盾（Slice 8 声明 MODULE 留在 write.py vs Slice 5 `_log_write_preflight_result` 迁移需要 MODULE），不做裁决会导致实施时架构决策随意化
