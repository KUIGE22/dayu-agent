## 1. Problem Statement

The v4.8 plan extracts the 5 W12 `_snapshot_builder` closures into two modules:

- **`_write_snapshot_builder.py`**: owns `build_snapshot_builder` factory (functools.partial) → wraps `_build_snapshot_for_args` → delegates to `_build_fresh_application_routing_snapshot`
- **`_write_config_application.py`**: owns `_build_fresh_application_routing_snapshot` (raw function) + `_run_write_model_configuration_application` (the application runner)

The documented dependency is **one-way**: `_write_snapshot_builder` imports from `_write_config_application`. The plan's §2.2 proof states "无反向路径".

**The gap**: Of the 5 original closures in `write.py`, one is produced inside the code block that becomes `_run_write_model_configuration_application` (the application runner). After extraction, if that runner needs a zero-arg snapshot-builder callable (e.g., to pass to `execute_write_model` or similar downstream), it must obtain one. Two options exist:

| Option | Mechanism | Cycle? |
|--------|-----------|--------|
| Import `build_snapshot_builder` from `_write_snapshot_builder` | `_write_config_application` → `_write_snapshot_builder` | **YES** — reverse of existing `_write_snapshot_builder` → `_write_config_application` |
| Use `functools.partial(_build_fresh_application_routing_snapshot, ...)` directly | No import of `_write_snapshot_builder` | **NO** |

The v4.8 plan does not explicitly specify which option the application runner must use. This is the cycle gap.

## 2. Adversarial Evaluation: Three Approaches

### Approach A: Direct `functools.partial` in application runner (RECOMMENDED)

**Description**: The application runner creates its own zero-arg callable via:
```python
snapshot_builder = functools.partial(
    _build_fresh_application_routing_snapshot,
    args=args,
    paths_config=paths_config,
    execution_options=execution_options,
    run_label="configuration-application",
)
```

The remaining 4 closures in `write.py` use `build_snapshot_builder` from `_write_snapshot_builder.py` as the plan specifies.

**Gates**:

| Gate | Status | Rationale |
|------|--------|-----------|
| No nested def | ✅ PASS | `functools.partial` is a library call, not a nested function definition |
| Identical callable behavior | ✅ PASS | `partial` returns a zero-arg `Callable[[], Mapping]` with identical defaults bound; runtime behavior is indistinguishable from a closure |
| Identical run_label | ✅ PASS | `run_label="configuration-application"` bound at partial-creation time, same default as plan |
| Typed `Mapping[str, ModelConfigJsonValue]` | ✅ PASS | Return type of `_build_fresh_application_routing_snapshot` is already `Mapping[str, ModelConfigJsonValue]`; `partial` preserves it |
| Typed `ExecutionOptions` | ✅ PASS | `execution_options: ExecutionOptions` parameter is bound at partial-creation time; type is explicit at call site |
| Zero cycle / zero reverse import | ✅ PASS | `_write_config_application.py` imports only `_write_config_helpers` and `dayu.execution.options`; no import of `_write_snapshot_builder` |
| Same-module scope | ✅ PASS | `partial` call is inside `_write_config_application.py`, same module as `_build_fresh_application_routing_snapshot` |

**Trade-off**: The application runner's callable is constructed inline rather than via the shared factory. This is acceptable because:
1. The factory's value is deduplication; 1 inline `partial` + 4 factory calls = zero duplication of the wrapping logic.
2. The alternative (importing the factory) creates a hard cycle.
3. `functools.partial` is stdlib, zero-dependency, and the project already uses it per the plan's factory design.

### Approach B: Ownership inversion (factory moves into `_write_config_application.py`)

**Description**: Move `build_snapshot_builder` into `_write_config_application.py` so the application module owns both the raw function and the factory. `_write_snapshot_builder.py` becomes a thin re-export or is deleted.

**Gates**:

| Gate | Status | Rationale |
|------|--------|-----------|
| No nested def | ✅ PASS | Factory is module-level |
| Zero cycle | ✅ PASS | No reverse import needed |
| Identical callable behavior | ✅ PASS | Same functools.partial mechanism |

**Rejection reason**: Violates architectural layering. `_write_config_application.py` is the **application runner** module — its responsibility is executing configuration application. Snapshot-building is a **separate concern** (creating lazy callable snapshots for deferred execution). Putting the factory in the application module merges two distinct responsibilities and makes the application module importable by callers who only need snapshots (pulling in application-runner transitive dependencies unnecessarily). The current plan's separation is correct.

### Approach C: DI / glue seam

**Description**: Inject the snapshot-builder callable into the application runner via a parameter (e.g., `snapshot_factory: Callable[[], Mapping[str, ModelConfigJsonValue]]`).

**Gates**:

| Gate | Status | Rationale |
|------|--------|-----------|
| No nested def | ✅ PASS | Factory is external |
| Zero cycle | ✅ PASS | Runner doesn't import builder |
| Identical callable behavior | ⚠️ DEGRADED | Caller must construct and pass the callable; shifts burden upward |

**Rejection reason**: Violates CLAUDE.md encoding constraint "禁止胶水 seam". The application runner already has direct access to `_build_fresh_application_routing_snapshot` in the same module. Adding a DI parameter for a function that is already in scope is unnecessary indirection — it exists solely to avoid a cycle that shouldn't exist in the first place. Approach A achieves the same cycle-avoidance without the seam.

## 4. Findings

### F-01 [MEDIUM] v4.8 Slice 6 does not explicitly specify application-runner callable construction

- **Location**: Plan Slice 6 (lines 961-974), §2.2 dependency proof (lines 430-468)
- **Description**: The plan documents `_write_snapshot_builder.py → _write_config_application.py` as one-way and states "无反向路径". However, it does not explicitly state how `_run_write_model_configuration_application` obtains its snapshot-builder callable. If the implementation naively imports `build_snapshot_builder` from `_write_snapshot_builder`, the cycle materializes. The plan must be explicit.
- **Severity**: MEDIUM — the cycle is structural and will be discovered during implementation, but explicit specification prevents wasted implementation effort and review cycles.
- **Resolution**: v4.9 erratum (see §5 below).
