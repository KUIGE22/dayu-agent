## 二、逐点复核证据

### 1. 闭包是否覆盖真实 materialization 输入

plan 第 113 行把 package research asset 指纹定义为两部分：(1) `resolve_package_assets_path()/research_templates/` 的 canonical tree，按包相对 POSIX 路径排序、对每个 regular `.md`/`.definition.json` 记录路径 + 字节 SHA-256；(2) 根级 `定性分析模板.md` 的独立 SHA-256。逐条对照代码实际读取点：

| 真实读取点 | 代码事实 | 是否在闭包内 |
|---|---|---|
| composed `common-plus-technology.md` | `research_template_assets.py:59-72` 读 `common.md` + `technology.md` + 根级 `定性分析模板.md` | 是（前两者在 tree，后者独立 SHA） |
| `technology.checklist.md` | `_research_template_core.py:178` → `load_research_template_definition("technology")` → `research_template_definitions.py:27/115-117` 读 `technology.definition.json` | 是（tree 含 `.definition.json`） |
| bundle checklist 完整性重算 | `_research_template_bundle.py:203-210` 用同一 definition 重算并比对 | 是 |
| `research-template.manifest.json` | `_research_template_core.py:782-817` 遍历 `list_research_templates()`（`:53-60`，`glob("*.md")` 排除 README），对每个模板调 `build_monitoring_rules_payload`（`:280-317`，再读该模板 `.md` 提取监控变量） | 是（tree 覆盖全部五个 `.md`） |

实测 `build_research_template_package_manifest()` 输出模板集为 `["common","consumer","cyclical","financial","technology"]`——确认 manifest 产物内容确实依赖 `consumer.md`/`cyclical.md`/`financial.md`，而这三者**不在**旧的两文件指纹内。这正是 PRR-001 指出的缺口，corrective fix 通过全目录 tree 覆盖，覆盖面正确且不多不少：目录内除 `README.md` 外的所有文件均为 `.md`/`.definition.json`，tree 定义与实际目录内容一一对应，未遗漏、未引入不存在的文件类别。

`README.md` 被纳入 tree（它是 regular `.md`）而不被 `list_research_templates()` 消费，属于**保守多覆盖**：会在 README 变更时产生一次不必要的新 plan，但不会漏检。fix artifact 第 6 节已把这类保守性显式记为 residual，判断一致，不构成 finding。

symlink / 非 regular file / 重复 canonical locator 三种情况 plan 第 113 行与第 587 行均定义为 fail closed，堵住了「用 symlink 指向仓外文件绕过指纹」的路径，与第 116 行对外部 price JSON 的同类约束同源，边界一致。

### 2. config tree 与 asset tree 的边界

- 第 112 行：config 指纹为 `resolve_package_config_path()` 下**全部 regular-file canonical tree**，`prompts/manifests/write.json`、`audit.json`、`llm_models.json` 在同一闭包内；单列关键文件「只是诊断分解，不是替代 tree 的不完全 allowlist」（第 103 行同口径）。这一表述纠正了旧版「单列关键文件」可能被读成 allowlist 的歧义。
- 两棵树语义分离且不重叠：config tree 根为 `dayu/config`，asset 闭包根为 `dayu/assets`（tree 部分限定在 `research_templates/` 子目录，根级 base template 单列）。`dayu/assets/` 根下实际只有 `research_templates/` 与 `定性分析模板.md` 两项，闭包与目录现状完全对齐。
- 第 114、250、586、624、642、644 行的 receipt 绑定、运行身份、stop condition、completion report 与 live-auth 展示项已全部改为同一三元组（config canonical tree + research-template canonical tree + 根级 base template SHA），未残留旧的「common/technology 两文件」表述。**一致性无遗漏**。
- 脱敏口径保持：第 114 行仍要求 receipt 用包相对 locator、不泄漏 home 绝对路径。这一点与代码事实有关联风险，见 PRR-002。

### 3. drift 测试契约

plan 第 308 行（Slice 1）要求：「分别修改 base template、`technology.definition.json`、`common.md`、`technology.md` 或任一其它会被 package manifest 枚举/消费的 research asset（例如 `consumer.md`）都必须改变闭包指纹并在 subprocess 前触发 drift fail」。五类扰动逐一对应第 1 节表格中的真实读取点，测试断言与闭包定义同源，不是「测已实现的行为」而是「测契约」。第 329 行（Slice 2）把同一闭包写入 subprocess 前的 drift 判据，slice 间口径一致。

未发现为贴合实现而削弱断言的迹象；也未发现把 drift 检测下沉成大集成链路才能证明的耦合——扰动 → 指纹变化 → fail 是纯本地可测的。

### 4. `verify` fixture 与 plan+fingerprint 互斥（OQ-B）

第 323 行定义两种互斥模式：fixture 模式只接受 `--fixture <dir>`；live/run 模式必须同时提供 `--plan <file> --fingerprint <sha256>`；同传、或 live 模式缺任一参数，均**在读取产物前** fail closed。第 332 行给出对应 CLI 参数测试：两个 happy path + 三个 fail-closed 用例（同传、单独 `--plan`、单独 `--fingerprint`）。第 501 行 live 收尾与第 568 行 deterministic 验证分别使用两种形状，与定义一致，无残留歧义。OQ-B 关闭。

「读取产物前 fail closed」这一时序限定是关键——它排除了「先读 fixture 再发现参数冲突」导致的部分副作用，属于正确的最佳实践收口。

### PRR-002-已修复-[低]-`research-template.manifest.json` 产物内嵌 package 绝对路径，与 receipt/baseline 的「不泄漏 home 绝对路径」约束存在潜在冲突

> **状态更新（2026-08-09）**：Controller adjudication `ACCEPTED`，corrective fix `docs/reviews/plan-fix-20260809-072322-codex.md` 已落地，final corrective re-review `docs/reviews/plan-review-20260809-072913.md` 判定**已修复**。plan 第 116、202、310、389、599、630 行已把泄漏 gate 作用域闭合枚举为 acceptance harness-owned 四类输出，生产 validator artifacts 双向锁定（不因内嵌 package 绝对路径单独 FAIL、不改写原字节），引用形状收敛为 package-relative locator + SHA-256 且禁止摘录内容，Slice 1 sanitizer 测试契约有界。以下为原始 finding 记录。

- **位置**：plan 第 114 行（「receipt 中 config/assets 路径用包相对 locator，不泄漏 home 绝对路径」）、第 200 行 hard gate 第 9 项（「无 …… 任意外部绝对 home 路径泄漏到提交用 baseline 或 completion report」）、第 5.4 节第 165-176 行 13 产物清单中的 `research-template.manifest.json`、第 386 行脱敏 baseline 规则
- **问题类型**：契约缺失 / 测试缺口
- **当前写法**：plan 把「不泄漏 home 绝对路径」写成 hard gate（第 200 行第 9 项），适用对象表述为「提交用 baseline 或 completion report」；同时第 5.4 节把 `research-template.manifest.json` 列为必须存在并通过 validator 的 13 产物之一，第 196 行要求「13 个 research 产物全部存在并通过各自当前 validator」。plan 未说明该产物自身内容是否受第 9 项 hard gate 约束。
- **反例/失败场景**：`build_research_template_package_manifest()`（`_research_template_core.py:803-812`）为每个模板写入 `"template_file": str(template.path)`，`template.path` 来自 `resolve_package_assets_path()` 解析后的**绝对路径**。实测输出为 `/Users/<user>/workspace/dayu-agent/dayu/assets/research_templates/common.md`。同理 `build_monitoring_rules_payload`（`:302`）写入 `"source_template_file": str(template)`，也是绝对路径，而 `technology.monitoring-rules.json` 同样是 13 产物之一。若实施 Agent 把「13 产物」整体或摘要纳入脱敏 baseline / completion report（第 386 行允许保留「artifact 相对路径/指纹」，但未禁止摘录产物内容），第 200 行第 9 项会在验收自身的输出上被触发；反之若实施 Agent 为了通过该 gate 而去改写产物内容，就变成了「修改生产 validator 的输入/输出」，与第 4.2 节「禁止反向修改 `dayu/` 生产代码来迁就验收器」冲突。
- **为什么有问题**：这是一处 gate 作用域未定义，而两种自然解法各自撞上不同约束。它不是生产缺陷——生产产物写绝对路径是既有行为，验收器无权也不应改动；问题在于 plan 没有明确「生产产物内的 package 绝对路径属于既有行为、不计入第 9 项泄漏 gate；第 9 项只约束验收器自己生成的 receipt/baseline/report」。缺这一句，实施 Agent 在 Slice 1 写脱敏断言时无法自行安全裁决。注意这与 PRR-001 独立：即使闭包完全正确，该歧义依旧存在。
- **直接证据**：
  - `dayu/cli/commands/_research_template_core.py:807`（`"template_file": str(template.path)`）
  - `dayu/cli/commands/_research_template_core.py:302`（`"source_template_file": str(template)`）
  - `dayu/cli/commands/_research_template_core.py:53`、`research_template_assets.py` 中路径经 `resolve_package_assets_path()` 解析为绝对路径
  - 实测 `build_research_template_package_manifest()` 输出 `template_file` 为绝对路径
  - plan 第 114、196、200（第 9 项）、第 5.4 节、第 386 行
- **影响**：脱敏断言口径不定 / 实施 Agent 可能误判为生产缺陷并越界修改 `dayu/` / 或误把验收自身输出判为 FAIL / Slice 1 脱敏测试可能写出与 gate 不一致的断言
- **建议改法和验证点**：在第 6.1 第 9 项或第 5.1 节补一句作用域限定——第 9 项只约束**验收器自己生成**的 phase receipt、`acceptance-receipt.json`、脱敏 baseline 与 completion report；生产 validator 产物（如 `research-template.manifest.json`、`technology.monitoring-rules.json`）内既有的 package 绝对路径属于生产既有行为，验收器只做存在性/指纹校验，不改写、不因此判 FAIL，若需引用则只引用其 SHA-256 与包相对 locator。验证点：Slice 1 增加一条断言——脱敏检查只作用于验收器自产 JSON，且对含绝对路径的生产产物只记录指纹不摘录内容。
- **修复风险（低）**：单句 plan 作用域澄清，不改代码、不改闭包定义。
- **严重程度（低）**
