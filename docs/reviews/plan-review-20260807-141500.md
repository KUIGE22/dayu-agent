### R2-03 — `_validated_fingerprint` 异常文本统一破坏行为保持

**位置**: §1.5.3 (行 163–166)

**plan 声称**:
> 因异常文本不同，共享函数需接受 `error_label: str` 参数或使用统一文本。本计划选择统一为 `"must be a sha256 fingerprint"`（str 系的文本更精确）。

**事实**: 两个异常文本族:
- `"must be a sha256 fingerprint"` — str 系 11 个文件
- `"must use sha256"` — bytes 系 6 个文件

将 bytes 系的 6 个文件统一为 `"must be a sha256 fingerprint"` 改变了异常消息文本。这违反 §4.2 不变量 (行 405):
> 错误消息文本不变 — grep diff

以及 §4.2 (行 406):
> 文件格式不变...指纹格式...canonical JSON 输出字节级不变

**失败路径**: Slice 2 迁移 bytes 系 6 个文件时，异常消息从 `"must use sha256"` 变为 `"must be a sha256 fingerprint"`。现有测试若断言具体异常消息文本，会失败。这违反行为保持不变量。

**v3 修订要求**:
1. 要么接受 `error_label: str` 参数（plan 已提到此方案但未选择）
2. 要么在 Slice 0 characterization tests 中明确锁定两个异常文本族，并在 Slice 2 迁移时逐文件更新测试
3. 要么将此统一延迟到 characterization tests 建立之后

### R2-04 — `normalize_now`/`parse_utc`/`persist_immutable` 非严格等价，强行统一破坏行为保持

**位置**: §1.5.7 Group A/B (行 195–206)

**(a) `_normalize_now` 三个变体** (行 195):

| 变体 | 实现 | 文件数 |
|------|------|--------|
| (a) | `value.astimezone(UTC).replace(tzinfo=None)` | 7 |
| (b) | `value.replace(microsecond=0)` | 3 |
| (c) | `value.astimezone(UTC).replace(microsecond=0, tzinfo=None)` | 1 |

plan 声称 (行 195):
> 语义意图相同（规范化到 UTC 并去除微秒），差异仅在微秒处理。抽取为统一版本 `normalize_utc_now` 去除微秒（最严格版本 c）。

**事实**: 变体 (a) **不去除微秒**——它只做 `replace(tzinfo=None)`。将 7 个使用变体 (a) 的文件统一为版本 (c)（去除微秒）是**行为变更**，不是 "语义意图相同" 的等价替换。微秒精度丢失可能导致:
- 指纹计算差异（如果 datetime 值被序列化到 JSON）
- 日志/审计时间戳精度变化
- `_format_utc` 调用结果不变（因为 `%Y-%m-%dT%H:%M:%SZ` 不含微秒），但中间值不同

**(b) `_parse_utc` 两个变体** (行 197):

| 变体 | 实现 | 文件数 |
|------|------|--------|
| (a) | `datetime.fromisoformat(text.replace("Z", "+00:00"))` + UTC 转换 | 6 |
| (b) | `datetime.fromisoformat(text)` + `replace(tzinfo=UTC)` | 2 |

plan 声称 "行为等价（均解析 ISO-8601 并转为 UTC）"。这是正确的——两个变体对标准 ISO-8601 输入产生相同结果。但变体 (b) 对含时区偏移的输入（如 `2024-01-01T00:00:00+08:00`）的行为不同：变体 (a) 会正确转换到 UTC，变体 (b) 会覆盖为 UTC 但不调整时间值。

**(c) `_persist_immutable` 三个变体** (行 206):

plan 声称 "可抽取核心 `_persist_immutable_atomic`，接受 `overwrite: bool` 参数"。这是合理的——三个变体的差异仅在存在性检查策略。

**失败路径**: `_normalize_now` 统一为版本 (c) 导致 7 个文件的 datetime 微秒被去除。若这些文件的下游逻辑依赖微秒精度，行为改变。

**v3 修订要求**:
1. `_normalize_now`: 要么保留三个变体（不统一），要么在 Slice 0 characterization tests 中显式测试微秒保留/去除行为，确认无下游影响后再统一
2. `_parse_utc`: 统一是安全的，但需在 characterization tests 中覆盖含时区偏移的输入
3. `_persist_immutable`: 统一方案合理，保持不变

### R2-06 — min-compat 命令错误，必须复刻 CI 的 pip install -e extras -c

**位置**: §9 (行 1492–1493)

**plan 声称**:
```bash
# 门禁 2: min-compat 全量测试（Python 3.11 + 最小依赖约束）
pip install -r constraints/min-py311.txt
python -m pytest tests/ -v --timeout=120
```

**问题**: 这不是 CI 的实际命令。CI 的 min-compat lane 使用 `pip install -e '.[dev]' -c constraints/min-py311.txt`（editable install with extras constrained by min-py311）。直接 `pip install -r constraints/min-py311.txt` 可能:
1. 不安装项目本身（`-r` 只安装依赖，不安装项目包）
2. 不安装 dev extras（测试依赖如 pytest、pyright 可能缺失）
3. 不使用 editable 模式（测试可能无法正确导入项目模块）

**v3 修订要求**: 使用 CI 的 exact command:
```bash
pip install -e '.[dev]' -c constraints/min-py311.txt
python -m pytest tests/ -v --timeout=120
```

### R2-08 — C3 方案仍动态 getattr 且所谓 "编译期可校验" 不成立；备选恢复线性 if 与 C3 dispatch table 目标冲突

**位置**: §5 Slice 9 (行 1156–1231), §12 未锁定问题 #5 (行 1555)

**plan 声称** (行 1227–1231):
> - `_WriteSubcommandEntry.flag: str` 是编译期常量字符串，对应 `argparse.Namespace` 上的已知属性名
> - 每个 `getattr(args, entry.flag, None/default)` 的 flag 名来自 `_add_write_args` 的 `parser.add_argument("--xxx", ...)` 注册——argparse 自动将 `--xxx-yyy` 转为 `xxx_yyy` 属性名
> - 不使用 `getattr` 遍历未知属性列表——所有 flag 名均在 `_WRITE_SUBCOMMAND_ENTRIES` 中显式列出
> - pyright 无法校验 `getattr(args, literal_string)` 的属性存在性（这是 argparse 的固有限制），但所有 flag 名从 `_add_write_args` 的注册中 1:1 提取，argparse 保证它们存在于 Namespace

**问题**:

1. **"编译期可校验" 自相矛盾**: plan 承认 "pyright 无法校验 `getattr(args, literal_string)` 的属性存在性"。这意味着 "编译期可校验" 的声明不成立——`getattr` 是运行时动态访问，pyright 无法静态验证属性存在。

2. **getattr 是设计选择，不是临时措施**: Slice 9 的 `getattr` 不像 Slice 5 的 `Any` 那样有明确的修复时间点（Slice 5.5）。它是 C3 dispatch 的核心机制。§4.3 不变量 "零 getattr" 要么适用于此（违反），要么需要明确声明 argparse 例外。

3. **备选方案与 C3 目标冲突** (行 1555):
   > 备选方案是为每个 flag 写显式 `if args.xxx:` 分支（恢复线性 if/elif，仅将 runner 委托改为 dispatch table 调用，不改变属性访问方式）

   这意味着如果要满足 "零 getattr"，C3 dispatch table 就退化为线性 if/elif——这正是 C3 要消除的。C3 的目标是 "将 30+ `if bool(getattr(...))` 分支替换为 dispatch table"，备选方案恢复了 if/elif，与 C3 目标矛盾。

**同理，C2 (Slice 8) 也有 `getattr`** (行 1115):
```python
action = str(getattr(args, "research_template_action", "") or "").strip().lower()
```

**失败路径**: C3 的 getattr 是结构性的，不是可修复的 bug。plan 的 "编译期可校验" 声称被自身 "pyright 无法校验" 的承认推翻。备选方案（恢复线性 if）与 C3 目标矛盾。

**v3 修订要求**:
1. 修改 §4.3 不变量，明确声明 `getattr(args, literal_flag)` 用于 argparse.Namespace 的例外条件
2. 或者修改 C3 方案，使用 `vars(args).get(flag)` 替代 `getattr`（语义等价但更明确）
3. 或者接受 C2/C3 的 getattr 使用并在 §8 合规检查中明确列出
4. 删除 "编译期可校验" 的虚假声称，改为 "运行时保证（argparse 注册）+ 手动审查（flag 名从 add_argument 1:1 提取）"
