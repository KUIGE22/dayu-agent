## Findings

### 1-未修复-[中]-`JobCompletion` 的嵌套 document 只做外形重建，非 canonical bytes 与伪 hash 可被持久化为成功

- **入口/函数**: `JobService.execute_claim` 对动态 handler 返回的 `JobCompletion` 做防御校验。
- **文件(行号)**: `dayu/investment/domain/jobs.py:402-434,1320-1344`；`dayu/services/job_service.py:795-805`；下游证据为 `dayu/host/worker.py:1144-1193`、`dayu/investment/storage/postgres_jobs.py:1435-1518,3306-3369`、`dayu/investment/storage/migrations/versions/0003_durable_jobs.py:460-496`；缺口测试位于 `tests/application/test_job_service.py:2193-2236`。
- **输入场景**: handler 用公开构造器返回 `JobCompletion(CanonicalJobDocument(...))`，其中字段外形合法，但 `canonical_bytes` 是非 JSON、含敏感键、非 canonical JSON，或 `sha256` 与 bytes不相等。例如 `b"not-json" + "a"*64`、`b'{"token":"secret"}'`、带空白/非排序 JSON，或 canonical JSON配错误 digest。
- **实际分支**: `CanonicalJobDocument.__post_init__` 只检查 schema文本、正整数、bytes类型与 64-hex hash形态；不解析/重编码 bytes、不递归拒绝敏感键，也不计算 `sha256(canonical_bytes)`。`JobCompletion` 只检查 result实例类型。gateway所谓“重建嵌套 document”仅再次调用同一浅构造器，随后返回 handler 的原 completion。
- **预期行为**: accepted Slice 2.1 plan把 `CanonicalJobDocument` 定义为 payload/result/receipt 的唯一 canonical JSON表示，要求 bytes自身严格 canonical、递归拒绝 closed敏感键且 SHA-256 等于 bytes；Slice 2.3又要求 handler非法返回统一收窄为 `HANDLER_REJECTED`，不得将畸形 result推进为成功。
- **实际行为**: malformed completion越过 gateway；Worker调用 `complete`，PostgreSQL store用 document的原 schema/bytes/hash构造 receipt引用并原样插入 result列，随后将 job/attempt写成 `SUCCEEDED`。0003表约束只验证 result字段成组存在与 hash为 64-hex，不计算真实 digest，也不验证 canonical JSON，因此数据库接受伪证据。
- **直接证据**:
  - `jobs.py:417-434` 没有 `json.loads`、canonical re-encode、敏感键 validator或 `hashlib.sha256` 比对；真正 strict入口 `parse_canonical_document` 位于 `556-602`，但 gateway没有调用。
  - `job_service.py:799-804` 逐字段浅重建后丢弃新对象；该操作对上述 bytes/hash语义没有新增验证。
  - 独立对抗复现中四类 ordinary public-constructor completion（非 JSON、敏感键 JSON、非 canonical JSON、错误 hash）均由 `execute_claim` 按原对象 identity返回，而非 `HANDLER_REJECTED`。
  - `postgres_jobs.py:1493-1518` 用 `completion.result`构造并持久 receipt；`3335-3367` 把 result schema/bytes/hash逐字段原样作为 SQL参数；migration `493-496` 只检查 hex64形态。
  - 新增 negative test `test_job_service_rejects_constructor_bypassed_malformed_completions_before_store` 只构造空 `schema_name`，因此在浅构造器就失败；它没有覆盖语义外形合法但 bytes/hash畸形的真实反例。
- **影响**: Job和attempt可被持久化为成功，但 result bytes不可 strict解析、可能包含禁止的敏感字段，且持久 hash不是内容真值；receipt中的 result引用也继承伪 hash。这破坏审计、重放、idempotency与后续 source result验证的证据链。
- **建议改法和验证点**:
  1. 在 gateway动态信任边界对 result执行严格 canonical reparse/re-encode，并验证 schema、bytes与 hash逐字段相同；异常统一返回 `_handler_rejected_failure()`。不要只重调浅 DTO构造器。
  2. 返回经严格验证的 immutable document/completion，或确保原对象在验证与返回间不能由 subtype/accessor改变；至少拒绝非 exact owner/subclass漂移，不把浅 `isinstance` 当安全证明。
  3. 增加非 JSON、duplicate/noncanonical/空白 JSON、每个 closed敏感键、hash mismatch、bytes/hash字段缺失的 ordinary constructor与 constructor-bypass tests；断言返回 `HANDLER_REJECTED` 且不进入 complete/fail persistence。保留正常 completion与四类 source failure对象 identity/语义测试。
- **修复风险（低/中/高）**: 中；`CanonicalJobDocument` 还用于数据库读回投影，不能无计划地把全局构造器改成只接受 strict业务 JSON而破坏 receipt引用/已有 owner。修复应优先收敛在 handler gateway，或先清点所有直接构造 owner。
- **严重程度（低/中/高/严重）**: 中。
