### 4-未修复-中-Phase F guard 语义偏差

- **位置**: §11f lines 2172-2178
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**:
  ```python
  # Phase F: Run Approval Verification（直接属性访问，零 getattr）
  if challenger_run_plan is not None and bool(
      (args.routing_challenger_run_approval_input or "").strip()):
  ```
- **反例/失败场景**:
  HEAD 中 `challenger_run_plan is None` 但 `routing_challenger_run_approval_input`
  被设置的情况会触发 `assert challenger_run_plan is not None` → `AssertionError`。
  Plan 版本将 guard 提前到 if-condition（短路求值），在 plan=None 时静默跳过审批验证。
  如果在未来某个 slice 中 Phase E 逻辑被修改导致 plan 可能在 approval_input 设置时
  为 None，此行为差异会被掩盖。

- **为什么有问题**:
  - 虽然 Slice11 的 Phase A/B 重构不改变 Phase E 行为（plan 仅在
    `challenger_run_plan_required` 为 True 时被构建），实际运行中 plan=None +
    approval_input 已设置的情况在当前代码路径上不可能出现。但 guard 语义从 `assert`
    （fail-loud）变为短路 `and`（fail-silent）降低了防御性。
  - 若采用方案 A 修复 Finding 3（Phase E 代码精确复制 HEAD），Phase F 的 guard
    也应精确复制 HEAD 的 `assert` 模式以保持防御性一致。

- **直接证据**:
  - **HEAD `write.py` lines 370-378**:
    ```python
    if bool(str(getattr(args, "routing_challenger_run_approval_input", "") or "").strip()):
        assert challenger_run_plan is not None
    ```
  - **Plan lines 2172-2174**:
    ```python
    if challenger_run_plan is not None and bool(
        (args.routing_challenger_run_approval_input or "").strip()):
    ```

- **影响**: 低概率（当前 HEAD 路径上不可达），但降低了 fail-loud 防御性

- **建议改法**:
  恢复 HEAD 的 assert 模式（同时保持直接属性访问以符合 Protocol 设计）：
  ```python
  # Phase F: Run Approval Verification
  if bool((args.routing_challenger_run_approval_input or "").strip()):
      assert challenger_run_plan is not None
      run_approval_exit = _verify_and_consume_challenger_run_approval_before_host(
          args=args, paths_config=paths_config, execution_plan=challenger_run_plan)
      if run_approval_exit != 0:
          return run_approval_exit
  ```

- **修复风险**: **低** — 恢复与 HEAD 一致的 fail-loud 语义

- **严重程度**: **中** — 行为语义偏差，非阻塞性但降低防御性

### 5-未修复-低-Phase C/D "不变" 标注不精确

- **位置**: §11f lines 2154-2166
- **问题类型**: 契约缺失
- **当前写法**:
  ```python
  # Phase C: Recovery Gate（不变）
  if not args.summary:
      ...
  # Phase D: Challenger Preflight（不变）
  if args.preflight_only and _challenger_requested(args):
      ...
  ```
- **反例/失败场景**: "不变" 标注暗示代码与 HEAD 逐字相同，但实际上 `args.summary` 和
  `args.preflight_only` 使用了直接属性访问（Protocol 风格），而 HEAD 使用
  `getattr(args, "summary", False)` 和 `getattr(args, "preflight_only", False)`。
  若实施 Agent 误解 "不变" 为 "保留 HEAD getattr"，会产生不一致。

- **为什么有问题**:
  - `summary` 和 `preflight_only` 均在 `WriteDispatchArguments` Protocol 中声明
    （§11a lines 1809-1810），因此可以直接属性访问。这是 Slice11 的正确行为。
  - 但 "不变" 标注会误导 reviewer/implementer 以为代码逐字不变，而实际上访问方式
    随 Protocol 引入而变化。语义等价，但标注不精确。

- **直接证据**:
  - Plan §11a line 1809-1810: `summary: bool`, `preflight_only: bool` 在 Protocol 中
  - HEAD: `getattr(args, "summary", False)`, `getattr(args, "preflight_only", False)`

- **影响**: 低 — 语义等价，仅标注措辞问题

- **建议改法**:
  将 Phase C/D 注释改为 "语义不变，访问方式随 Protocol 升级为直接属性访问"

- **修复风险**: **低** — 纯文档措辞

- **严重程度**: **低** — 不影响实施正确性

- **额外成本**: 需要确定 owner module（`_write_challenger.py`? `write.py`? 新文件?）、
  编写单元测试、更新 dispatch identity 测试、传播 import。
- **风险**: 中 — 引入不必要的变更面，可能引入新的时序/异常处理 bug
