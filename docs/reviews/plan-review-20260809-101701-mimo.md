### PRM-001-未修复-[严重]-verify 命令进入 fingerprint 造成自指循环，plan 不可计算

- **位置**: §5.1 新增段「ordered commands 精确覆盖……validators 与 verify」；§10 line 512；Slice 2「变更内容」`run` 序列末尾 `verify`
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: 全部 ordered phase/command argv token 进入 `to_json()` 与唯一 `fingerprint`；而末阶段 argv 为 `verify --plan <run-root>/acceptance-plan.json --fingerprint <exact-fingerprint>`。
- **反例/失败场景**: fingerprint = SHA-256(canonical JSON(含 verify argv))，而 verify argv 内含该 fingerprint 字面量。求值需先知道结果，属不动点，无解。
- **为什么有问题**: plan-fix 第 5 条要求「所有字段进入 `to_json()`、strict parser 与唯一 fingerprint」，与 §10 的 verify argv 形状直接冲突；implementation agent 只能自行发明规避（占位符、二次写回、排除字段），即重新设计。
- **直接证据**: 计划 line 512 `verify --plan <run-root>/acceptance-plan.json --fingerprint <exact-fingerprint>`；plan-fix line 28「所有字段进入 `to_json()`、strict parser 与唯一 fingerprint」。
- **影响**: 实施 Agent 跑偏 / 生成错误代码 / plan 无法生成 / 后续返工。
- **建议改法和验证点**: 明确 verify 不属于 fingerprinted ordered command specs（它是 plan 的消费者，不是 plan 身份的一部分），由 runner 在 plan 落盘后用已计算 fingerprint 组装并写入 `validations.json`/独立 receipt；或规定 plan 内只存不含 fingerprint token 的 verify argv 前缀，runner 追加。验证点：新增测试断言 plan fingerprint 可一次性计算、且 verify argv 由 runner 在 plan 之后派生。
- **修复风险**: 低
- **严重程度**: 严重

### PRM-002-未修复-[高]-raw absolute `--config` argv 必然触发 acceptance-owned sanitizer，hard gate 9 恒 FAIL

- **位置**: §5.1「实际 subprocess argv 保留 resolved config 绝对路径」与新增段「raw `acceptance-plan.json` ……允许保存绝对 run/config argv；phase receipts……只输出 locator、argv digest」；§6.1 hard gate 9
- **问题类型**: 架构边界 / 契约缺失 / 过度耦合
- **当前写法**: plan 只声明 phase receipt「不复制 raw absolute argv」，未说明既有 `PhaseReceipt` schema 必须随之变更，且 `utils/investment_agent_acceptance_evaluator.py` 不在 Slice 2 白名单。
- **反例/失败场景**: 已 accepted 的 Slice 1 中，`PhaseReceipt.argv: tuple[tuple[str, ...], ...]` 是必填原始 argv 且 `to_json()` 原样输出（contracts.py:506、535）；evaluator 把每条 phase receipt `to_json()` 直接喂给 acceptance-owned sanitizer（evaluator.py:892-893），`_HOME_PATH_PATTERNS` 匹配 `/(?:Users|home)/…`（evaluator.py:95-98）。而 `resolve_package_config_path()` 返回绝对路径（`dayu/startup/config_file_resolver.py:34`），本仓位于 `/Users/wsk/...`。因此 Slice 2 runner 一旦按 §5.1 把绝对 `--config` 写进 phase receipt argv，`sanitizer.sensitive_shape` 必然命中，hard gate 9 恒 FAIL。
- **为什么有问题**: 现有测试 `tests/test_investment_agent_acceptance.py:1973-1988` 正是断言「phase argv 含 `/Users/alice/...` → `sanitizer.sensitive_shape`」，即该行为是被锁定的 accepted 契约，不是实现自由度。plan-fix 只扩展了 `AcceptancePlan`，未指出真正的阻塞耦合点在 `PhaseReceipt.argv` 与 sanitizer。
- **直接证据**: contracts.py:506/535；evaluator.py:95-98、892-893；tests:1973-1988；config_file_resolver.py:34。
- **影响**: 状态不一致 / live run 必然假 FAIL / review 不可验收 / 返工到 Slice 1 边界。
- **建议改法和验证点**: 在 plan 中显式规定 `PhaseReceipt` 的对外 argv 表示改为 sanitized 形式（run-relative locator + `argv_sha256` digest + 脱敏 token 序列），并把该 schema 变更纳入 Slice 2 白名单说明；同时明确 evaluator 侧是否需要同步（若需要，必须扩白名单或再次 STOP，不得由 implementer 自裁）。验证点：fake runner 用真实绝对 `--config` 跑完整链，断言 phase receipt 无 home 绝对路径且 `sanitizer.sensitive_shape` 不出现，同时 digest 可与 raw plan argv 闭合。
- **修复风险**: 中
- **严重程度**: 高

### PRM-003-未修复-[中]-plan-fix 关于 `AcceptanceInputs.plan` 的事实陈述不成立

- **位置**: plan-fix line 18「其 `AcceptanceInputs.plan` 继续消费同一扩展 dataclass」
- **问题类型**: 动机不成立 / root cause 非同源
- **当前写法**: 以「evaluator 通过 `AcceptanceInputs.plan` 消费 `AcceptancePlan`」为由，判定 evaluator 无需进入白名单并设置 STOP 触发条件。
- **反例/失败场景**: `AcceptanceInputs` 字段为 contract/inventory/price_snapshot/quality_review/write_manifest/run_summary/report_text/research_artifacts/runtime/acceptance_owned_outputs，**无 `plan` 字段**；evaluator 只从 contracts 导入 `BudgetLimits`、`PhaseReceipt` 等，从不导入 `AcceptancePlan`。
- **为什么有问题**: 该 STOP 条件锚在不存在的耦合上，因而不会触发；真实耦合（PRM-002 的 `PhaseReceipt`+sanitizer）反而没有任何 STOP 保护。错误的风险模型比没有风险模型更危险。
- **直接证据**: evaluator.py:245-268（`AcceptanceInputs` 字段表）；evaluator.py:30（仅导入 `BudgetLimits`）；`grep AcceptancePlan utils/investment_agent_acceptance_evaluator.py` 无结果。
- **影响**: review 不可验收 / 真实耦合失去守卫 / 实施期才暴露。
- **建议改法和验证点**: 更正为「evaluator 不消费 `AcceptancePlan`，扩展该 dataclass 不影响 evaluator；真实跨模块耦合是 `PhaseReceipt.argv` 与 acceptance-owned sanitizer」，并把 STOP 条件改挂到该耦合上。
- **修复风险**: 低
- **严重程度**: 中

### PRM-005-未修复-[中]-run root / env presence 入 fingerprint 使运行身份成为主机绑定，plan 未声明且缺 run_root 校验器规格

- **位置**: §5.1 新增段 (1)(4)；§8.2「复现」；§14 残余风险表
- **问题类型**: 契约缺失 / 非最优方案
- **当前写法**: 「解析后的精确 run root」与「逐项 presence boolean」全部进入唯一 fingerprint，但未规定 run_root 的存储形态（绝对 / 仓库相对）与校验器。
- **反例/失败场景**: 现有 locator 校验器 `_require_safe_locator` 明确拒绝绝对路径、`..`、`~`（contracts.py:3001-3019），无法复用于绝对 run root；implementer 需自造校验器而 plan 无规格。同时同一代码/输入/预算在另一主机或另一 run-id 下 fingerprint 必不同，§8.2 列举的漂移源未包含 run root 与 env presence，§14 残余风险表也未记录。
- **为什么有问题**: fingerprint 的语义从「输入闭包身份」变成「本机本次执行身份」，Controller 在 §15.7 展示 fingerprint 时的含义随之改变，却无文档表述。
- **直接证据**: contracts.py:3001-3019；计划 §8.2 line 258 漂移源列表；§14 残余风险表无对应行。
- **建议改法和验证点**: plan 规定 run_root 以绝对 POSIX 存于 raw plan、使用独立于 `_require_safe_locator` 的严格校验器（must be absolute / 非 symlink / 位于 `workspace/acceptance/investment-agent-aapl/` 下），并在 §8.2 漂移源与 §14 残余风险中补记「fingerprint 为主机与 run-id 绑定」。
- **修复风险**: 低
- **严重程度**: 中
